## Context
- 成果物は「P0 の動く PoC と、外注向けの仕様書」（オーナーの決定）。スタックとクラウドは要件で選ぶ。
- オーナーの指摘：本質は「企業がメールや電話を本人確認に使わない」こと。そうすれば、漏れた連絡先を知っている・受け取れるだけでは、その企業での本人確認を突破できない（フィッシングの宛先などには使われうる。割符の外の第三者での悪用も残る。1-2）。そのうえで、企業はそれらを持たない。住所は企業が持たざるを得ない点が課題。
- 背景：2026年9〜10月には、国内で大規模な個人情報の漏えいの公表が相次いだ（各社の公表による。個別の原因は事案ごとに異なる）。NICT は2026-10-13に **A2B攻撃**（App-to-Backend）と名付けた攻撃について注意を促し、相次ぐ漏えいの原因の一つとした。総務省も同日に注意喚起した。公開アプリを解析して接続先のサーバーを狙い、BOLA（IDOR）・SSRF・RCE・SQL インジェクションなどを突く攻撃である（NICT の CYNEX の資料が、重点的に点検する脆弱性として挙げたもの。ADR 0012 の決定15）。漏えいは防ぎきれない前提で設計する。
- 2026年10月には、JPCERT/CC（10-08 公開、10-09 更新）と国家サイバー統括室（10-09）も、相次ぐ不正アクセスによる漏えいについて注意を促し、対策を求めた。この計画の主張は、漏えいの経路を問わない（1-2）。この計画は、これらの資料を個別の事案に結び付けない（確認状況は standards.md を正とする。どちらも2026-10-22に原文で確認した）。これらを受けて変えたことは ADR 0008 にまとめた。
- v3 と、土台の文書（v4）を、反対側の立場で点検し、その指摘を反映した。

## 1. 本質
### 1-1. 原則
1. **使わせない（第一原則）**：本人確認・回復・承認・識別の根拠にしてよいものを、**肯定リスト**で決める（ADR 0001）。それ以外は、例として挙げているかどうかにかかわらず、一切根拠にしない（否定リストは必ず漏れるため）。
   - (a) **企業（RP）の側**：次だけを根拠にしてよい。
     - 割符が発行した ID トークンの iss・sub・acr・auth_time
     - 操作に結び付いた step-up の結果。用途 `desk` は照会と軽い手続きだけに使い、高リスク操作には対象・内容に結び付く別の承認を使う（ADR 0019）
     - 初回移行専用の、登録・回復経緯を確認できる旧パスキーまたは FIDO2 の資格情報の検証と、同じ申請に結び付く割符の操作別承認（ADR 0020）。旧パスワード・メール・SMS・旧セッションだけは使わない
     - アカウントの付け替えは、割符が署名したイベントだけで行う。
   - (b) **割符の内部**：次だけを根拠にしてよい。
     - UV 付きのパスキーのアサーション
     - 回復コード、回復協力者の承認、待機期間の満了の3つがそろったとき
     - P1 では JPKI も加える
   - (c) 企業の受付番号と回復コードのハンドルは、参照または指名子にすぎず、それだけでは何も許可しない。
   - (d) (a)(b) のどちらにも入らないもの：本物のメールや別名、電話、住所、氏名、生年月日、注文や予約の番号、決済の情報、email クレーム、中継した返信や着信。配送のための照合（relay での別名の解決、送信元ロックの検査）は許すが、その結果を許可の判断に流さない。
   - (a) は、割符のサービス、rp-kit の SDK、demo-rp の参照実装には、例外なく適用する（CLAUDE.md の不変条件1(a)）。demo-rp の「悪い RP」のモードは、適合テストキットが不合格にすることを示すための模擬で、参照実装には含めない（3-3、テスト9）。接続する企業に課す接続要件（3-3）では、移行中の参加（ADR 0010）の企業に限り、入り口の一覧の経路の中だけで、その経路が使う値（パスワード、メールや SMS に届くリンクやコード、予約番号や電話番号など）を根拠にすることを、期限まで認める。別名と email クレームは、この例外に含めない（3-3）。この企業は、1-2 の主張の対象に含めない。
2. **持たせない**：企業は本物の連絡先を持たない。P0 で達成できるのはメールだけで、それも割符に参加した後に企業へ渡すものについてである（紐付けの前から企業が持っているものは、1-2 と 3-3）。電話は未達（7章）。住所は段階的に減らす（5章）。
3. **つなげさせない・届けさせない**：企業ごとの pairwise sub と別名を使う。送信元ロックをかけ、使い終えた値は二度と割り当てない。

### 1-2. 主張できる範囲と、残るリスク
**主張できること**：漏れた連絡先や属性を「知っている」「受け取れる」だけでは、割符と、接続要件を守る企業での本人確認は突破できない。

この主張は、漏えいがどの経路（どの製品、どの脆弱性、どの業種のシステム）で起きたかを問わない。漏えいそのものを防ぐことは主張しない。

「接続要件を守る企業」は、完全な参加の企業を指す。移行中の参加（3-3、ADR 0010）の企業は含めない。この主張は、移行中の企業には及ばない。移行中から完全な参加に移った企業でも、移行中に攻撃者の sub が紐付いたアカウントは残る（下の「移行中の企業に残っている入り口」）。

**残るリスク**（仕様書と脅威モデルには、全項目を省かずに書く）：
- **窓口でのリアルタイム中継**：攻撃者が自分の受付番号を利用者に入力させ、承認を誘導しうる。公式窓口への自発的な連絡と操作の確認を求め、相手発の電話なら承認しない。利用者が偽の説明を信じる危険は残る。窓口用途の承認では高リスク操作を許さず、変更は通知・取消の対象とする。
- **同期パスキーの提供者側の回復**：Apple や Google が SMS などでのアカウント回復を許していると、SIM スワップ → 同期アカウントの奪取 → 同期パスキーの入手、という連鎖が成り立つ。
- **割符の外の第三者**：運送会社の受け取りの認証、カード会社の 3DS の SMS、携帯キャリアでの SIM の再発行は、割符からは変えられない。
- **電話について原則2は未達**（7章、ADR 0004）。
- **企業をまたいだ突き合わせ**：氏名と受け取り場所を企業に渡す限り、防げない。
- **回復の弱点**（ADR 0003）：端末をすべて失うと、待機中の知らせが本人に届かない。身近な人が協力者で、回復コードも手に取れる場合は、1人で2つの要素がそろう。
- **フィッシングや詐欺の宛先にされること**と、**住所による物理的な被害**。
- **割符自身の漏えい報告義務**は残る。
- **別名の導出鍵の漏えい**（ADR 0005）：導出用の鍵が漏れると、鍵と ID の組から全員の別名を計算できる。
- **回復コードのフィッシング**（ADR 0003）：回復コードは、偽の回復ページなどのフィッシングで盗まれうる。盗んだ攻撃者が協力者もだまして承認させると、回復が待機に入る（待機中は、登録済みの端末から取り消せる）。
- **企業の側の漏えいそのもの**：割符は、企業の Web システム、管理用・内部の API、BI ツールなどからの漏えいを防がない。企業が持ち続ける氏名、住所、注文の履歴などは漏れうる。紐付けの前から企業が持っている本物の連絡先は、企業が消さない限り残る（消すことは推奨。必須にするかは M9 で決める。3-3）。割符が減らすのは、漏れた連絡先や属性が、接続要件を守る企業で本人確認に通用すること（上の「主張できること」の範囲）と、企業が持つ本物の連絡先（P0 ではメールだけ）である。
- **移行中の企業に残っている入り口**（ADR 0010）：移行中の参加の企業では、入り口の一覧（3-3）にある経路が、期限まで残る。漏れた連絡先や属性で、その経路から本人確認を突破されうる。この企業独自のパスワードでのログイン（ENT-02）が残る間は、漏れたパスワードでも突破されうる。メールや SMS による再設定（ENT-01）が残る間は、未紐付けの会員の旧アカウントを奪って、攻撃者の sub を紐付ける場面（紐付けの攻撃）も成り立ちうる。移行中に攻撃者の sub が紐付いたアカウントでは、攻撃者が自分の端末で操作ごとの承認を出せるので、高リスクの操作を操作ごとの承認だけに限っても守れない。このアカウントは、完全な参加に移った後も残る。P0 には、付け替えの手段がない（3-3。P1）。割符が確かめて「切り替わったもの」に移した入り口も、確かめた時点の、試験用のアカウントについての結果である。この企業は、主張の対象から外す。高リスクの操作は、移行中でも、操作ごとの承認だけを根拠にさせる。入り口の一覧の各項目が、割符で確かめる方法に切り替わったか、まだ残っているかを、利用者の画面に出す（DESIGN.md の警告文 I）。
- **利用者が自分から企業に伝えた連絡先や属性**：利用者が、問い合わせのメールの本文、企業のチャット、電話、店頭などで、本物の連絡先や属性（電話番号、住所、別のメールアドレス、氏名など）を自分から伝えると、企業はそれを持つ。割符からは止められない。チャット、電話、店頭は relay を通らない。relay の返信の検査が見るのは本物のメールアドレス1つだけで、利用者がうっかり書いたものを止めるためのものである（意図して崩した書き方は対象にしない。ADR 0021）。このとき崩れるのは原則2（持たせない）である。完全な参加の企業では原則1が残り、企業がその値を本人確認の根拠にすることは、接続要件で禁じている。移行中の参加の企業では、入り口の一覧の経路が期限まで残るので、伝えた値がその経路で本人確認に使われうる（上の「移行中の企業に残っている入り口」）。

- **旧資格情報の盗難**（RR-16、ADR 0020）：適格な旧パスキーまたは FIDO2 の資格情報を攻撃者が支配できると、正当な所有者を装って自分の割符へ紐付ける危険が残る。同期パスキーの提供者側の回復も侵入経路になりうる。
- **企業の虚偽の移行証跡**（RR-17、ADR 0020）：企業が登録や回復の履歴について虚偽の結果を出すと、割符の署名や承認だけでは誤りを検出できない。移行プロファイルの審査・監査と企業側の根拠確認が必要である。
- **企業アプリの虚偽表示**（RR-18、ADR 0019）：企業が対象・担当者・操作を誤ってまたは偽って表示しても、割符はその内容を独立に検証できない。固定ラベルと同一申請への結び付け、適合検査・監査は危険を減らすが、虚偽表示を保証して防げない。

**一次資料の裏付け**（2026-10-22 に原文で照合した。確認状況は `docs/standards.md`、照合の結果は ADR 0012）：
- NIST SP 800-63B-4：パスワードを選ぶときに KBA や秘密の質問を促してはならない（KBA は認証器の種類にない）。メールを OOB 認証に使ってはならない（SHALL NOT）。PSTN は制限付き。
- NIST SP 800-63A-4：KBV を身元確認に使ってはならない（SHALL NOT）。
- OIDC Core §5.7：email や phone_number を識別子にしてはならない（MUST NOT）。
- FIDO：弱い回復手段は推奨しない。認証器を失ったら、最初の登録と同じかそれ以上の保証レベルで身元を確認し直す（P0 の回復が満たすとは書かない。ADR 0012）。
- ASVS 5.0：6.4.2〜6.4.4、6.6.1。
- デジタル庁 DS-511／DS-512：当人認証のレベル2以上は多要素で、フィッシング耐性のある手法を提供する。2026年2月時点では、マイナンバーカードかパスキーの採用が実質的に必須と想定する（DS-512）。回復の手段は、当人認証と同等以上の強度にする（P0 の回復が満たすとは書かない。ADR 0012）。
- 金融庁の監督指針（証券 2025-10、銀行 2026-02）と日本証券業協会のガイドライン：フィッシング耐性のある多要素認証を必須にする。
- 犯罪収益移転防止法の施行規則改正（2027-04 施行）：非対面の本人確認を、JPKI と IC チップに原則一本化する。
- 個人情報保護委員会 Q&A Q6-11：連絡先だけの漏えいは、ただちには財産的被害の類型（第2号）に当たらない。割符の報告義務がなくなるという意味ではない（上の「割符自身の漏えい報告義務は残る」）。法的な扱いは弁護士の確認待ち（イシュー #15）。

この原則は、NIST（メールや SMS で回復コードを送ることを条件付きで認めている）より厳しい、この製品の方針として扱う。

## 2. A2B攻撃への備え（割符が最大の標的になる）
- **BOLA を防ぐ**：
  - DB の境界：全テーブルに RLS の ENABLE と FORCE を付ける。アプリ用のロールは NOSUPERUSER と NOBYPASSRLS にする。境界はトランザクションごとに `set_config(…, …, true)` で渡し、`withTenant()` か `withWarifuUser()` 以外から DB に触れない（例外は CLAUDE.md の不変条件8）。
  - 利用者の境界：利用者向けのすべてのルートで、所有者を照合する認可をかける（別名の一覧、協力者、受信箱、窓口の申請 など）。
- **SSRF を防ぐ**：
  - 外向きの通信（HTTP(S)、SMTP、名前解決を含む）は、すべて送信サービス（`packages/sender`）1つに集める。このサービスは KMS の権限を持たず、IMDS にも VPC 内にも届かない。
  - URL は https に限る。名前解決した IP がプライベートなら拒否し、その IP に直接つなぐ（DNS rebinding 対策）。MX の名前解決の結果にも同じ制限をかける。リダイレクトには従わず、サイズと時間に上限を設ける。
  - Web Push の宛先は、既知のプッシュサービスのホストに限る。
  - oidc-provider の動的クライアント登録は無効にし、`jwks_uri`・`sector_identifier_uri` は受け付けない（企業の鍵は登録時に `jwks` で受け取る）。`request_uri` は、割符の PAR の受け口が発行した urn だけを受け付け、外へ取りに行かない（ADR 0025）。ロゴは登録時に取り込んで、割符側で配信する。
- **逆引きをしない**：外から呼べるルートで、本物の連絡先や本人を返さない。ルート一覧をテストで固定する。
- **内部の API**：keysvc、relay の内部配送 API、sender は、割符の内部からだけ呼べるようにし、外から届かないようにする。呼べるのは、それぞれを使うと決めたサービスの資格情報だけにする（例：relay の内部配送 API は idp だけ）。割符の内部の接続も、要るサービスの組だけに限る（本番では、ネットワークの設定でも塞ぐ。設定は P1 の AWS アダプタで決める）。内部の接続の認証は、keysvc はサービスごとの資格情報と Unix ドメインソケットにした（ADR 0013）。relay の内部配送 API も同じ形にし、呼べるのは idp だけにした（ADR 0021）。sender も同じ形にし、呼べるのは relay（配送と名前解決）と company-api（Webhook）だけで、呼び出し元ごとに口を分けた（ADR 0022）。
- **レート制限**：機能ごと（ログイン、回復の開始、受付番号の試行、窓口の操作別承認、宛先確認の送信、協力者への依頼、企業向け API）に上限を決め、キーを「アカウント」「送信元（IP、端末、テナント）」「その組み合わせ」の3つに分けて組み合わせる。具体的な値は、M3（アカウントの作成、ログイン、宛先確認の送信。ADR 0018）、M5（企業向け API。ADR 0022）、M7（受付番号と窓口の承認）、M8（回復の開始、協力者への依頼）で決めて ADR に記録する。SMTP の受信は、1通 10 MiB、同時接続 100、1トランザクション1宛先にした。送信元ごとの上限は、P1 の受信の前段で決める（ADR 0021）。
- **トークンの期限と無効化**：割符が発行するトークンは、用途に要る範囲と期間に限り、漏えいが疑われるときに、発行済みのものを速やかに無効にできるようにする。
  - 受付番号と操作ごとの承認は、3-1 のとおり（承認の有効期間は M7 で決める）。
  - ID トークンは5分、oidc-provider のセッション（SSO の窓）は10分、PWA のセッションは最後の操作から30分（最長8時間）。リフレッシュトークンは出さない。パスキーを削除したら、その利用者のセッションをすべて消す（ADR 0018）。パスキーの一時停止（回復の後）のときの扱いは M8 で決める。
  - テナントの JWT は、ES256 で5分、scope は1つ（M5では別名の入れ替えと検証の SET の依頼）、リフレッシュトークンなし。窓口・初回移行用の限定scopeはM7・M9で新たに設計する。検証のたびに、テナントが登録簿にあり、緊急停止していないことを確かめる（緊急停止にして配備し直すと、発行済みのものも断る。ADR 0022）。
- **ブラウザ側**：PWA には、厳格な CSP（nonce を使う）と Trusted Types を必須にし、テナント由来の文字列はテキストとしてだけ描画する。承認系の画面は別のオリジンに分ける。PWA と承認系の画面の配信物（HTML、JavaScript、Service Worker）は、解析される前提で作る。資格情報、鍵、API キーを含めず、認証と認可の判断はすべてサーバーで行い、配信物の中の検査に頼らない。
- **テナントが侵害されたときの封じ込め**（運用の手順。管理の機能にする場合は、2人承認と実行までの遅延を付ける）：
  - 緊急停止（送信、窓口の承認、API）
  - 別名の再発行は、テナントの資格情報と DKIM 鍵を入れ替えた後に行う
  - クライアント認証は private_key_jwt に限る
  - P0 では管理 API を作らない（4章）ので、緊急停止は運用の手順として行う。静的な設定を直して配備し直す：API と SET は company-api の登録の `suspended`、送信は relay の登録からテナントを外す、ログインは idp の登録簿からクライアントを外す（窓口承認は M7。ADR 0022）。
- **鍵と資格情報の入れ替え**：割符の鍵、サービスの資格情報、テナントの資格情報には、漏えいが疑われるときの失効と入れ替えの手順を持たせる。保存用の鍵、照合用の HMAC 鍵、署名の鍵、サービスの資格情報の手順は、ADR 0013 と ADR 0014 で決めた。定期的に入れ替えるかと、その周期は P1 で決める（それまでは、漏えいが疑われるときだけ入れ替える）。sub の導出に使う鍵（`pairwise_sub`）は入れ替えない（全企業の sub が変わるため。付け替えのイベントと合わせて P1。ADR 0018）。DKIM と ARC の鍵は、新しいセレクタで作り直して DNS を差し替える（ADR 0021。DNS の更新の手順は P1）。テナントの資格情報は、jwks に新しい鍵を足して切り替えた後に古い鍵を外す（ADR 0022）。別名の導出鍵と、`alias_lookup` の鍵の入れ替え（全世代の索引の作り直し）は P1（ADR 0005、ADR 0022）。
- **運用者のアクセス**：割符の運用者が、本番の環境（クラウドの管理画面、DB、鍵）と、リポジトリや CI の管理に入るときは、フィッシング耐性のある多要素認証（パスキーかセキュリティキー）を必須にする。手順は、未定（本番の運用の手順として P1 で決める）。
- **検知と初動**：
  - API の利用と拒否を監視できるようにする。検知の対象（例：レート制限にかかった要求、認証と認可の失敗、鍵サービスの 403、送信サービスが拒否した宛先の種類と件数。宛先そのものは残さない）と、監視の仕組みは、未定（本番の運用の手順として P1 で決める）。監視に使うログにも、不変条件4を適用する。
  - 初動の手順（テナントの緊急停止、鍵と資格情報の入れ替え、利用者への知らせ、漏えい報告の要否の判断）と、その点検の頻度は、未定（本番の運用の手順として P1 で決める）。

## 3. 本人確認に使わせない仕組み
### 3-1. 代わりを渡す
- **ログイン**：OIDC＋パスキーだけにする。企業独自のパスワード、メールのリンク、SMS は使わせない。
- **高リスクの操作は、操作に結び付けた承認で技術的に強制する**：
  - 対象：配送先・返金先・支払い手段の変更、解約、高額の取引、住所の法定開示への同意。
  - 方法：利用者が自分の端末で step-up する（オリジンに結び付いたパスキーと、RFC 9396 RAR）。企業側の API は、割符が発行した操作ごとの短命な承認がなければ動かない。この参照実装を rp-kit に入れる。
  - 承認画面には、操作の種類と内容の要点を出す（DESIGN.md 1章）。
- **窓口（電話・チャット・店頭）**：利用者が企業の認証済み画面で受付番号、対象、操作を確認し、割符で用途 `desk` の操作別 step-up を行う（ADR 0019）。通常ログインや受付番号だけでは許可しない。
  - 受付番号は企業が発行する応対セッションの参照で、割符へ送らず本人確認に使わない。企業画面で入力した番号と窓口・担当者を表示する。申請・対象・版・入力・担当者・主体・期限を固定し、変更時は再承認する。
  - 割符の承認画面に登録済みの企業名、固定の操作ラベル、権限範囲、相手からの電話かの問いと警告文 A-1 を出す。企業の自由文と受付番号を出さない。
  - 通知と24時間取消を維持する。承認後は作成通知前でも受信箱から取消を受け付け、未作成は企業の確定報告で閉じる。通知起点・配送・受付終了の詳細は ADR 0019 に従い、実装前に未決の詳細を確認する。CIBA と割符の窓口コードは P0 で提供しない。
  - 企業アプリを通話中に操作できない利用者は一般案内・申告受付に限り、P0の書き込みを作成と利用者自身の取消に絞る（オーナーの決定（仮））。
- **企業への知らせ**：SET（RFC 8417）を割符の鍵（ES256）で署名して送る。iss、aud（テナントごと）、jti、iat を必須にする。企業どうしで時刻から突き合わされないよう、送信時刻をテナントごとにランダムにずらし、jti もテナントごとの乱数にする。P0 は Webhook、P1 で SSF に完全対応する。

### 3-2. 技術的に使えなくする
- **別名**：
  - 鍵サービスの `derive_alias(tenant_id, user_id, generation)` で導き、DB には置かない（ADR 0005）。
  - 再発行で世代を上げ、古い世代は廃番として残す。照合用の HMAC に一意制約をかけ、二度と割り当てない。
  - SMTP の RCPT への応答は、生きている別名でも、廃番でも、存在しなくても同じにする。
  - email クレームは別名だけにし、`email_verified` は常に false にする。独自のクレーム（`contact_alias`）を使う選択肢も用意する。どちらも nOAuth 型の自動統合を防ぐため。
- **送信元ロック**：
  - d= は登録したドメインと完全に一致させる。DKIM のセレクタと鍵の指紋は、登録時に固定する。
  - l= 付きの署名は拒否する。h= に From、To、Subject、Date、Message-ID を必須にし、重ねて署名すること（oversign）も求める。From、To、Subject が重複していれば拒否する。
  - t= を必須にし、7日より古い署名と、5分より先の時刻の署名は拒否する。x= があれば期限の前であること（ADR 0021）。
  - リプレイは、(d、s、b=、別名) の HMAC を、その署名を受け付ける間（t= から7日と x= の早いほう）保持して判定する。HMAC は HMAC-SHA-256 で作り、別名は平文で置かない（不変条件4・9）。同じ内容の再試行は 2xx で受けて捨てる。
- **中継の衛生**：
  - Disposition-Notification-To と Return-Receipt-To を削除する（開封通知で本物のアドレスが出るため）。
  - List-Unsubscribe の mailto: は、relay 経由のアドレスに書き換える。https: は残し、それ以外は消す。
  - To は別名だけにし、Cc と Bcc は消す（全員に返信したときの漏れを防ぐ。relay 経由のアドレスに書き換える案より強くした。ADR 0021 の O-18）。
  - From は、登録簿の企業名と、relay 経由のアドレス（返信用のアドレス）にする。Reply-To は、企業が署名したものだけを返信の先に使う。
  - これらの書き換えで、企業の元の DKIM 署名は壊れる。その影響は 8章で扱う。
- **返信の中継**：
  - 返信用のアドレスは、やり取りごとの使い捨ての乱数にする。
  - 本物のアドレスのドメインで DMARC が整合して pass した返信だけを中継する。pass しても、本人の承認としては扱わない。
  - 利用者側の DKIM-Signature、Received、X-* を取り除く（残すのは、件名、日付、MIME の項目、In-Reply-To と References だけ。References からは本物のアドレスのドメインの Message-ID を消す）。件名と本文（各部分のヘッダー、転送したメールを含む）に本物のアドレスが含まれていれば、転送せずに利用者へ差し戻す。符号化、文字コード、HTML の文字参照、全角などは戻してから探す。中身を確かめられない部分（添付ファイル、画像、知らない文字コードなど）を含む返信も、P0 では差し戻す（ADR 0021）。
  - DMARC の判定に使う DNS は、注入したリゾルバだけを通す。リゾルバがないときは中継しない。リゾルバは、送信サービスの名前解決の口（TXT、MX、A、AAAA だけ）につなぐ（ADR 0021、ADR 0022）。
  - 機械で読めるヘッダー `X-Warifu-Unauthenticated` を付ける。本文への表示（DESIGN.md の警告文 D）は P1。

### 3-3. 接続要件（契約）と適合テスト
- 識別は (iss, sub) だけで行い、根拠は 1-1(a) の肯定リストに限る。企業の API は、要求ごとに、その利用者が対象（予約、注文、配送先など）に触れてよいかをサーバーで確かめる。要求に含まれる番号だけで対象を引かない（移行中の参加の例外は、下の「移行中の参加」）。
- **既存会員の紐付け**：
  - **初回移行の確認**：登録・追加・回復の経緯を確認できる旧パスキーまたは FIDO2 の資格情報を、UV付きの新しいチャレンジで検証し、同じ申請に結び付けた割符の操作別承認と組み合わせる（ADR 0020）。旧パスワード・メール・SMS・旧セッションだけでは紐付けず、履歴不明や弱い回復で追加された資格情報も自動的に適格としない。
  - 移行証跡は用途・署名・宛先・期限・申請との対応を検証し、旧連絡先・属性・注文内容・認証器の生データを割符へ送らない。待機・通知・再確認と確定処理の詳細はADR 0020に従う。旧資格情報の盗難や企業の虚偽証跡は残るリスクである。
  - 適格な資格情報のない会員は本案では移行できない。旧残高や契約の履行方法を別途定める。移行中の企業で対象会員の旧経路の閉鎖・再開制限を追加する（オーナーの決定（仮））。これは企業の参加自体を制限する条件とは区別する。
  - 紐付けは1回だけ。完了と同時に、旧ログインと、メールや SMS による再設定を廃止する。企業が割符に参加した時点で、未紐付けの会員についても、メールや SMS による再設定を止める（移行中の参加の例外は、下の「移行中の参加」）。
  - 窓口、管理画面、管理用・内部の API で sub を書き換えたり、アカウントを統合したりしてはならない。
  - 付け替えが要る場合は、割符が署名したイベントだけで行う（P1 の JPKI による再確認の後）。
  - 紐付けの前から企業が持っている本物の連絡先の扱いは、未定（M9 で決める。原則2）。保有の必要性を見直して減らすことを推奨する。
- **ゲスト照会の禁止**：予約番号、電話、メール、氏名の組み合わせで、照会・変更・取り消しを受け付ける画面と API を持たない（移行中の参加の例外は、下の「移行中の参加」）。
- **中継されたメールを根拠に、アカウントや取引の状態を変えない**（`X-Warifu-Unauthenticated` の付いたメール）。
- **イベントを受けたとき**：連絡先による再確認に逃がさない。回復の直後は、高リスクの操作を保留する期間を設けることを義務にする。
- **代わりの手順**：本人確認なしでできるのは、一般的な案内と、アカウントの一時停止（安全側の操作）だけ。
- **管理用・内部の経路と委託先**：高リスクの操作に操作ごとの承認を求めること（3-1）は、公開していない管理用・内部の API、管理画面、窓口担当者の画面、バッチの処理にも適用する。従業員や委託先の権限だけで、高リスクの操作をさせない。窓口や管理の運用を委託している場合は、委託先（再委託先を含む）にも接続要件を守らせる。
- **資格情報と判断の置き場所**：企業の資格情報（private_key_jwt の秘密鍵、テナントの JWT、DKIM の秘密鍵）は、企業が管理するサーバー（委託した送信事業者や鍵管理サービスを含む）の中だけに置き、公開アプリ（モバイルアプリ、ブラウザで動くコード）や公開のリポジトリに含めない。ID トークンと操作ごとの承認の検証、高リスクの操作を許すかどうかの判断も、企業のサーバーで行う。企業のモバイルアプリは、企業のサーバーとだけ話し、企業のサーバーが割符の OIDC のクライアントになる。アプリの中では、企業のサーバーが始めた認可を、システムのブラウザ（ASWebAuthenticationSession、Custom Tabs）で開く。アプリそのものは割符のクライアントにしない（不変条件7。ADR 0018）。
- **企業の側のシステムの管理（推奨）**：窓口や管理の画面と API を使う従業員と委託先に、フィッシング耐性のある多要素認証を求める。公開している資産を継続的に点検し、業務上要らない管理の機能を外に出さない。
- **移行中の参加**（ADR 0010）：
  - 参加は「完全な参加」と「移行中の参加」に分ける。完全な参加では、接続要件をすべて守る。1-2 の「接続要件を守る企業」は、完全な参加の企業を指す。
  - 移行中の参加では、次の入り口の一覧にある経路だけを、期限まで残してよい。一覧にない経路は残さない。それ以外の接続要件は、すべてそのまま守る。

    | ID | 入り口 | 緩める接続要件 |
    |---|---|---|
    | ENT-01 | メールや SMS に届くリンクやコードでの、パスワードなどの再設定 | 紐付けの後と、参加の時点での、メールや SMS による再設定の廃止 |
    | ENT-02 | この企業独自のパスワードでのログイン | ログインを割符だけにすること（紐付けの後の旧ログインの廃止を含む）と、この経路のログインでの (iss, sub) による識別 |
    | ENT-03 | 予約番号や電話番号などでの、予約や注文の確認・変更・取り消し | ゲスト照会の禁止と、番号だけで対象を引かないこと（画面と API の中だけ。高リスクの操作は除く） |

  - 利用者の画面に出す入り口の文言は、DESIGN.md 3章の警告文 I を正とする。
  - 入り口の一覧の経路の中に限って、その経路が使う値（パスワード、メールや SMS に届くリンクやコード、予約番号や電話番号など）を根拠にすることも、期限まで認める（1-1(a) を接続要件で課すときの例外。ENT-02 のログインでの識別と、ENT-03 の画面と API の中での番号などによる照合を含む）。住所や生年月日などの属性による照合は、ENT-03 でも認めない。ENT-03 で照合に使ってよいのは、ゲスト照会の禁止に挙げた値（予約番号、電話、メール、氏名。別名は除く）だけにする。経路の外（窓口、高リスクの操作、アカウントの統合、紐付けと sub の扱い）では、1-1(a) の肯定リストをそのまま守る。どの経路でも、別名（email クレームを含む）を、再設定の宛先にも、アカウントを探す値にも使わせない。高リスクの操作は、移行中でも操作ごとの承認だけを根拠にする（3-1）。ENT-01 の再設定の宛先（企業が持つメールや電話番号）の変更も、移行中は高リスクの操作と同じく、操作ごとの承認だけを根拠にし、入り口の一覧の経路（ENT-03 の変更を含む）から変えさせない。
  - 窓口で氏名や生年月日を聞いて本人確認すること（属性による本人確認と、窓口担当者の画面での検索）は、監査でしか確かめられないので、一覧に載せない。移行中でも残してはならない。
  - 一覧に載せるのは、割符が閉じたことを確かめられる経路だけにする。M9 で確かめ方が決まらない項目は、一覧から外す（その経路は、移行中でも残せない）。
  - 移行中の参加には期限を付ける。期限の長さと、期限を過ぎたときの扱いは、未定（M9 で決める）。完全な参加から移行中の参加に戻すことは認める。戻すときは、警告文 I を出し、その企業と接続済みの利用者に知らせる。その条件と手順は、未定（M9 で決める）。
  - rp-kit の SDK と demo-rp の参照実装は、完全な参加だけを実装し、入り口の一覧の経路を作る機能や設定を入れない。入り口の一覧の経路は、demo-rp の「悪い RP」のモード（テスト9）の中にだけ置き、適合テストキットが不合格にすることを示すためだけに使う。検査の分け方は、このモードを移行中の設定にしたうえで、一覧1に移った入り口に対応する検査と、緩めていない検査が不合格になることで示す。このモードは、テストの中でだけ有効にし、既定では無効にする。キットに合格する移行中の企業の設定を、demo-rp の画面や手引きで見本として示さない。適合テストキットは、移行中の参加の検査の分け方を持つ。CLAUDE.md の不変条件は変えない。このモードと、CLAUDE.md の不変条件（「テスト用の補助」にも適用する）との関係は、未定（CLAUDE.md に注記を足すかを、オーナーが M9 の前に決める。ADR 0010）。
  - 移行中の企業については、入り口の一覧の各項目を、「割符で確かめる方法に切り替わったもの」と「まだ残っている入り口」に分けて、接続の同意の画面と、別名の一覧の企業ごとの詳細に出す（DESIGN.md 2章、警告文 I）。項目を「切り替わったもの」に移すのは、割符が閉じたことを確かめたときだけで、企業の自己申告では移さない。確かめた日を出し、確かめ直しの間隔を過ぎた項目は「残っている」に戻す。割符の側から確かめる方法、確かめた結果を記録する経路、確かめ直しの間隔、移行中の参加から完全な参加に移す条件と手順（移行中に紐付けたアカウントの扱いを含む）は、未定（M9 で決める）。確かめるときは、利用者の本物の連絡先も別名も使わず、割符が用意した試験用のアカウントだけを使う。外へつなぐのは、送信サービスだけにする（不変条件2・4・7）。検査で受け取った再設定のリンクやコードも、平文で残さない（不変条件4）。試験用のアカウントで確かめた結果は、確かめた時点の、そのアカウントについてのもので、企業が利用者の一部にだけ入り口を残すことは見抜けない（RR-14）。
  - 接続の契約で、この表示と、割符の側からの確かめ（外からの検査など）に、企業の同意を得る。企業に不利な表示を出すことの契約と法務の面での確認は、イシュー #15 と合わせて行う。
  - 表示を作る M9 までは、移行中の参加の企業を接続しない。
- **適合テストキット（P0）**：
  - rp-kit SDK の単体検査。
  - 模擬 OP で「同じ email で sub の違う2人」を出し、RP 側のテスト用フックで、内部のアカウントが別であることを確かめる。
  - 紐付けの後に旧経路が閉じていること、sub を書き換える管理 API がないこと、ゲスト照会の API がないことを確かめる。
  - 窓口の運用は、自己申告のチェックリストと監査で確かめる。
  - 移行中の参加に合わせて広げる（M9）：緩めるのは、警告文 I の一覧2にある（割符が閉じたことを確かめていない）入り口に対応する検査だけにする。一覧1に移った入り口に対応する検査と、入り口の一覧で緩めていない検査は、移行中でも不合格にする。キットは企業の側で動くので、その結果だけでは、表示の項目を一覧1に移さない。

## 4. 割符自身にも原則を適用する（ADR 0003）
- **本物のメール**：用途は配送先だけ。変更は、step-up と、新しいアドレスの宛先確認だけで行う。旧アドレスには、操作のリンクを含まない知らせだけを送る。知らせのメールには操作のリンクを入れない。登録済みかどうかで応答を変えない。
- **電話番号**：P0 では集めない（入力欄、列、クレームを作らない）。
- **予防**：パスキーを2つ以上登録してもらい、うち1つは端末固定（セキュリティキーなど）を推奨する。BE/BS フラグを記録し、同期パスキーかどうかの変化をリスクの信号として扱う。同期先アカウントの強化（Apple の復旧キーなど）を案内する。パスキーの追加と削除には step-up を求め、全端末に知らせる。
- **回復の流れ**：
  1. 回復コードだけで始める。コードには、アカウントを指す乱数のハンドルと、64ビット以上の秘密を含める。回復の画面に、メール・電話・氏名の入力欄は置かない。協力者への依頼と、登録済み端末への通知は、コードを確かめた後に出す。
  2. 回復協力者が承認する。
     - 指名：対面の QR か、使い捨ての招待コードに限る。連絡先で検索する機能は作らない。確定には step-up を求め、全端末に知らせる。
     - 承認：回復を求めている人の新しい端末に出た QR を、協力者が対面で読み取る。QR が使えない場合だけ、コードを手で入力する。電話やビデオ通話で伝えられたコードは使わない（DESIGN.md の警告文 C）。
     - 直近14日以内に回復した協力者や、パスキーを追加した協力者の承認は無効にする（14日の考え方は ADR 0012）。P0 は協力者1人、P1 で k-of-n にする。
     - 協力者がいない場合、P0 では回復できない（P1 で JPKI による回復）。
  3. 待機期間は、回復コードの確認と協力者の承認がそろった時点から数える。既定は72時間、本番の下限は24時間で、起動時に強制する（一次資料に数値の根拠はない。値の考え方は ADR 0012）。登録済み端末の受信箱と協力者に知らせ、端末のパスキーで取り消せるようにする。
  4. 取り消されたら、使われた回復コードを失効させ、14日間は回復を始められないようにする。回復が成立したら、使われた回復コードを失効させ、新しい回復コードを発行する。回復コードの再発行は、全端末と協力者に知らせる（NIST SP 800-63B-4 の 4.2.1.1。ADR 0012）。
  5. 回復の後7日間は、協力者の変更、他のパスキーの削除、配送先の変更、高リスクの承認を禁止する。古いパスキーは一時停止にする。企業には、独自クレーム `recovered_at` と SET で伝える。
- **基準との関係**：NIST の recovery contacts は、アドレスに発行型のコードを送る方式で、この協力者の方式とは別物である。原文を照合した結果（ADR 0012）、割符の回復は NIST の AAL2 の回復の組み合わせ（4.2.2.2）に当たらず、FIDO と DS-511 の「同等以上の強さ」を満たすとも言えない。独自の方式として記述し、準拠・相当・同等以上とは書かない。
- **通知**：サーバー側の「端末の受信箱」を正とし、PWA はポーリング（30秒ごと）で受け取る（M6。SSE は使わない。ADR 0023）。Web Push は起こすだけのアダプタにする（P1。受信確認を返す方式にして、届いていなければ待機期間を延ばす）。ロック画面には一般的な文言だけを出す（DESIGN.md 1章）。
- **管理者**：P0 では管理 API を作らない。利用者アカウントの凍結と、法令に基づく開示は P1 で、開示の対象・請求者・承認の手順を ADR で決めるまで実装しない。法令に基づく開示は、ルート一覧のテスト（テスト6）の唯一の例外として扱い、2人承認、根拠法令の記録、監査ログへの追記を必須にする。連絡先、認証器、協力者、回復の設定を変える機能は、管理 API に作らない。
- **協力関係**：サーバーには内部 ID の組だけで持ち、名前や連絡先を置かない。協力者が相手を見分ける表示名は、協力者の端末の中だけに保存する。

## 5. 住所
- **第一原則は、すぐに適用する**：住所と生年月日での照合のような本人確認を、接続要件で禁じ、代わりに操作別 step-up を使ってもらう（移行中の参加でも緩めない。3-3）。
- **第1段階**：受け取り場所を指定する配送（営業所止め、コンビニ、PUDO、ヤマトの EC自宅外受け取りAPI）。SDK に「受け取り場所の選択」を入れる（P1）。
- **運送会社と交渉する要件**（イシュー #16）：
  - 受け取りの認証は、割符アプリに出す荷物ごとの使い捨てのコード（QR）だけで行う。
  - 送り状の電話番号には、識別に使えない番号を載せる。
  - 宛先の変更、転送、再配達は、割符を通した確認に限る。
  - 交渉がまとまるまでは「運送会社の側では原則が成り立たない」と明記する。
- **第2段階**：割符がプラットフォームの立場で、匿名の送り状を出す（企業をまたいだ突き合わせを防ぐための必須条件）。
- **使えないもの**：
  - デジタルアドレス：事業者は API で住所を引ける。日本郵便は、複数サービスに横断する住所の名寄せと、転居後の住所の取得を用途に挙げている（企業をまたいだ突き合わせのキーになる。不変条件5、ADR 0012）。送り状にも実住所が要る。
  - 割符が荷物を受け取って転送する形：犯収法の郵便物受取サービス業者に当たる可能性が高い（経済産業省の Q&A 問2。原文で確認済み）ので、採らない。
- **法定開示フロー**（古物商の買取など。P1）：目的を限り、明示の同意と記録を取る。法令上の確認は、JPKI を割符経由で行い、住所に宛てた郵送で確かめる方法は使わせない。開示した住所は記録の目的にだけ使うよう、接続要件で縛る。JPKI だけで要件を満たせるかは、弁護士に確認する（イシュー #15）。
- **配送先の不正照合 API**（割賦販売法のガイドラインへの対応。P1）：入力は業界で共有する不正配送先リストの側に限り、利用者の住所の候補を入力に取らない。返すのはリスクの判定だけにする。

## 6. 決済
- 決済代行会社に渡す連絡先は、別名にする。
- カード会社の 3DS で使われる SMS は、割符の管理外の残るリスクとする。推奨要件として、カード会社の側のパスキー（FIDO に対応した 3DS、Secure Payment Confirmation）を挙げる。
- 3DS のデータ項目でメールや電話を求められた場合の扱いは、決済代行会社に確認する（イシュー #17）。

## 7. 法規制（実装範囲を左右する）
> この章は、実装の範囲を決めるための、このプロジェクトの作業上の前提である。弁護士や所管の官庁の確認は、まだ受けていない（イシュー #13〜#15）。出典の確認状況は `docs/standards.md` を正とする（総務省の電気通信事業参入マニュアルと犯収法のページ、個人情報保護委員会の Q&A は、2026-10-22 に原文で確認した。ほかは検索結果の抜粋で確かめただけ）。法的な助言ではなく、企業やほかの事業者が、自社の判断の根拠にすることは想定していない。

| 法律 | 対象 | いまの前提（未確認） |
|---|---|---|
| 電気通信事業法 | メール中継、電話中継 | 他人の通信の媒介に当たる可能性が高く、**届出が要る前提**で計画する（イシュー #13） |
| 犯罪収益移転防止法 44号 | **電話の中継（番号の種類を問わない）** | **電話転送サービス事業者に当たる可能性が高い**。取引時確認、7年保存、疑わしい取引の届出が要る（イシュー #14）。メール中継は、44号の列挙には見当たらない（抜粋による。照会で確かめる） |
| 携帯電話不正利用防止法 | 050 のアプリ通話 | 050アプリ電話として、本人確認の義務を負う可能性がある |

## 8. 暗号・保存・中継の基本
- **用途ごとに許す暗号方式**（CLAUDE.md の不変条件9）：
  - 保存：AES-256-GCM（IV は96ビットの乱数）
  - MAC と照合用の索引：HMAC-SHA-256
  - JWS（ID トークン、SET、操作ごとの承認、テナントの JWT、企業の client assertion の検証）：ES256 だけ。oidc-provider の設定で固定する
  - WebAuthn：ES256、EdDSA（曲線は Ed25519）、RS256 だけを受け付ける。RS256 は、登録のときに RSA の鍵長を確かめて記録し、2048 ビット未満は拒否する（M3）。CRYPTREC の設定基準で、RSA 2048 ビットのエンティティ認証は2030年までなので、2030年中に3072 ビット未満の RSA を受け付けない設定に移る（手順は P1。ADR 0012）
    - EdDSA（-8）は、WebAuthn Level 3（2026-08-25 勧告）が、幅広い認証器に対応したい RP に含めることを勧めている（SHOULD）ので、2026-10-23 に足した（ADR 0012 の決定10。オーナーが決めた）。登録の選択肢の順は、ES256、EdDSA、RS256 にする。
  - プロトコルで決まる例外（CRYPTREC への掲載を問わない）：Web Push（RFC 8291、VAPID は ES256）、DKIM と ARC の署名（rsa-sha256）、受け取ったメールの DKIM の検証（rsa-sha256 と ed25519-sha256。rsa-sha1 は不合格）
  - テストで固定する範囲は、自前のコードが直接呼ぶ `node:crypto` と、ライブラリに渡すアルゴリズムの設定。
- **ローカルの鍵サービス**（`packages/keysvc`）：別プロセスで立て、サービスごとの資格情報と、操作ごとの ACL を持たせて、KMS の IAM を模す。本番は KMS（HMAC 鍵も外に出せない）。サービスと能力の対応：
  - idp：encrypt（連絡先）、照合用の mac、derive_alias、ID トークンの署名（sign と public_keys。ADR 0014）
  - company-api：照合用の mac、derive_alias、テナントの JWT と SET の署名（sign と public_keys。tenant_jwt と set。ADR 0022）
  - relay：decrypt（唯一）、照合用の mac（別名の照合、リプレイ、返信用のアドレス、Message-ID）、返信用のアドレスの宛先の encrypt（relay_queue）、DKIM と ARC の署名（sign と public_keys。ADR 0021）
  - sender、rp-kit、demo-rp：なし
  - 操作と対象（鍵か用途）の単位の表、MAC の鍵を用途ごとに分けること、暗号文を文脈（利用者 ID など）に結び付けることは、ADR 0013 で決めた。
- **能力の表にまだないもの**：ES256 の ID トークンの署名の鍵は、鍵サービスに置いた（ADR 0014）。SET とテナントの JWT の鍵（ES256）は、company-api の `set` と `tenant_jwt` として足した（ADR 0022）。操作ごとの承認の鍵は M7 で足す。DKIM と ARC の鍵（RSA 2048、rsa-sha256）も鍵サービスに置いた（ADR 0021）。sub の導出は、MAC の用途 `pairwise_sub`（idp だけ）にした（ADR 0018）。
- **サービスの資格情報**（鍵サービスを呼ぶ資格情報、DB のログインロールの資格情報）は、リポジトリ、コンテナのイメージ、設定ファイル、配信物に平文で置かない。ローカルでは、鍵サービスの資格情報は起動のたびに乱数で作って標準入力で渡し（ADR 0013）、DB のログインロールには資格情報を付けない（ADR 0015）。本番の渡し方は、P1 の AWS アダプタで決める。
- **DB とログ**：
  - DB には、本物の連絡先も別名も平文で置かない。oidc-provider の保存物は、id を HMAC（`mac(oidc_storage_id)`）にしてから保存する。P0 では、保存物（セッション、インタラクション、Grant、認可コード、アクセストークン）をプロセスのメモリに置き、永続化は P1 で決める（ADR 0018）。relay は、受け取ったメールを DB に置かず、メモリの中で処理する。返信用のアドレスの宛先（企業の側のアドレス）は暗号化して置く（ADR 0021）。
  - ログは構造化したフィールドで書き、伏せる対象は warifu-core の1か所にまとめる。載せてよいフィールドとメッセージを決める許可リスト方式にする（ADR 0017）。別名を URL に載せない。
  - 配送ログは最小限にする（件名と本文は残さず、Message-ID は HMAC にし、期限で消す）。
  - 保存するものごとに保存期間を決め、過ぎたら消す。いま期限が決まっているのは、配送ログ（30日）、リプレイの判定の記録（署名を受け付ける間と1時間）、返信用のアドレス（30日。どれも ADR 0021）、端末の受信箱（承認待ちは期限の30日後、知らせは90日後。その利用者の受信箱を読み書きするときに消す。ADR 0023）だけ。受付番号は企業側で管理し、割符へ渡さない。監査ログは、P0 では消さない（ADR 0016。本番の期間と消し方は P1）。oidc-provider の保存物と PWA のセッションは、メモリの中で、それぞれの期限（ADR 0018 の表）が過ぎたら読めなくなり、掃除される。ほかの保存物（回復の記録、退会した利用者や接続をやめた企業のデータ）の保存期間と消し方は、未定（その保存物を作るマイルストーンで決めて、ADR に記録する）。別名の照合用の HMAC は、P0 では消さない（再利用しないことを一意制約で保つため。退会の流れで残し方を決める。ADR 0018）。退会の流れ（保存物の消し方、別名の廃番、企業への知らせ）は P1 で扱う（10章の P1 の一覧）。
- **メール中継**：
  - 件名と本文はバイト単位で変えない。relay の DKIM を付け直し、ARC で封印する。企業ごとに relay のサブドメインを分ける。
  - 中継の衛生（3-2）でヘッダーを書き換えるため、企業の元の DKIM は壊れる前提で設計する。企業の DMARC が p=reject でも届くように、From は relay のドメイン（返信用のアドレス）に書き換え、表示名で企業を示す（ADR 0021）。
  - relay から本物のアドレスへの配送は、送信サービス（sender）の内部 API に、署名と封印を付けたメッセージを渡す形にする。送信サービスが MX を引き、内部の IP を指す宛先を拒否して接続する。送信サービスの内部 API（`/v1/mail`）は M5 で作った。実配送は、受け取ったメールの永続化と再試行を作るまで始めない（ADR 0021 の O-19、ADR 0022）。
  - DMARC は RFC 9989（2026-05。RFC 7489 を置き換えた）で判定する。組織ドメインは DNS Tree Walk で決める。`mailauth` 7.3.1 がこれに従うことを確かめた（ADR 0021。ADR 0012 の決定11）。

## 9. スタックと環境
- **スタック**：TypeScript（Node 22、ESM、`module: nodenext`）。
  - `oidc-provider` 9.x：pairwise と CIBA に対応している。Fastify には @fastify/middie で載せ、oidc-provider の経路にはボディ解析を通さない。
  - そのほか：`@simplewebauthn` 14、`smtp-server`、`mailauth` 7、`nodemailer`（送信サービスの SMTP。ADR 0022）、`jose`（company-api のトークンの検証。ES256 だけ。ADR 0022）、Fastify 5、`pg`、Vitest、Biome。
- **Playwright**：`@playwright/test` を **1.56.1 に完全固定**する（この環境の Chromium の revision 1194 に合わせるため）。CDP の仮想認証器を使う。CI では、`npm ci` の後に `npx --no playwright install --with-deps chromium` を実行する。
- **Postgres**：`scripts/pg-up.ts` で起動する。
  - バイナリは `/usr/lib/postgresql/16/bin`（`PG_BIN` で上書きできる）。root で実行されたときだけ `runuser -u postgres` を使い、TMPDIR を見ずに `/tmp` の下に作ったディレクトリを postgres の利用者に chown する。データとソケットは `mktemp -d` 相当で作ったディレクトリに置き、TCP では待ち受けず、空いているポートの番号を使う。テストを速くするため `fsync=off` にする。サーバーのログには FATAL 以上だけを terse で残す（CLAUDE.md「環境の注意」）。
  - Vitest の globalSetup が起動して止める。Playwright の E2E は、各ファイルが自分のワーカーの中で、一時的なクラスタ、鍵サービス、idp を起動する（M3。`test/leak/x-idp-browser.e2e.ts`）。Vitest のワーカーごとに、TEMPLATE から DB を作る。監査ログのチェーンへの追記は `pg_advisory_xact_lock` で直列にする。
- **ローカルの構成**：
  - 各サービスは localhost のポート違いで動かす（`*.localhost` は Node で名前解決できないため）。ポートが違ってもクッキーは共有されるので、クッキー名はアプリごとに一意にし、Cookie と Authorization のヘッダーをログに出さない。WebAuthn の `expectedOrigin` はポート込みで固定する。
  - sub はテナント ID と HMAC から導き、コードフローの `pairwiseIdentifier` を使う。P0ではCIBAを提供しない（ADR 0019）。同じテナントのクライアントでは同じ sub、別のテナントでは別の sub になる。
- **DB の分け方**：DB は1つにし、サービスごとにスキーマとログインロールを分け、列単位の GRANT をかける（ロール、スキーマ、ポリシー、SQL の書き方、マイグレーションは ADR 0015）。relay がテナントを横断して使えるのは、「別名の HMAC → 利用者 ID とテナント ID」を解決する SECURITY DEFINER 関数だけにする（所有者は非ログインの専用ロール、search_path は固定）。BI ツール、分析基盤、SQL を自由に書ける管理ツールは、割符の DB につながない。そのためのログインロールも作らない（不変条件8の例外にない）。運用で集計が要るときの扱いは、未定（P1 の本番の運用の手順で決める）。
- **企業の認証**：private_key_jwt の client_credentials で、テナントに結び付いた JWT を発行する。
- **依存の更新**：
  - 版は完全に固定する（`.npmrc` の `save-exact` と package-lock.json）。`.npmrc` の `ignore-scripts=true` で、インストールスクリプトを動かさない（CI の `npm ci` にも `--ignore-scripts` を付ける）。GitHub のアクションはコミットの SHA で固定する。
  - Dependabot（`.github/dependabot.yml`。M1 で設定した）で、npm とアクションの更新の PR を週に1回出す。`@playwright/test` は 1.56.1 に完全固定するので、対象から外す。
  - 既知の脆弱性の修正は、週ごとの更新を待たずに取り込む。取り込む手順と、公開から取り込むまでの目安は、未定（本番の運用の手順として P1 で決める）。
  - `oidc-provider` と `@simplewebauthn/server` を更新するときは、ADR 0006 と ADR 0007 で頼っている内部の振る舞いと、外向きの通信の呼び出しを点検し、それを守るテストを通す。
  - 本番の実行環境（Node、Postgres、コンテナのイメージ）の更新の手順は、未定（P1 の AWS アダプタで決める）。
- **配置**：CLAUDE.md の「配置」を正とする。
- **クラウド**：AWS 東京（KMS、SES、RDS、ECS）。AWS アダプタは P1。

## 11. 検証（漏えいシナリオのテスト）
- 各マイルストーンの PR で、`npm run lint && npm run typecheck && npm test && npm run e2e` がすべて通ること。
- 各マイルストーンでは、下のうち割り当てたテストが通ること。ゲートでは、それまでに割り当てたテストもすべて通ること。
- テストは `test/leak/` に置き、名前か先頭のコメントに、攻撃者が持っている情報、試す経路、期待する結果を書く（CLAUDE.md の不変条件12）。

1. 別名、sub、氏名、予約番号を持つ攻撃者は、窓口の承認なしに個別情報へアクセスできない。攻撃者の受付番号を被害者に入力させる中継を試し、用途 desk の承認で高リスク操作ができないこと、相手発の電話と答えたとき承認を中止すること、通知と取消を確かめる。
2. 受付番号だけでは認証・認可されず、期限切れ・他社・再利用を拒否する。対象・操作・主体・担当者の差し替え、通常ログインへの縮退、承認後の権限流用を拒否する。
3. 回復：回復の流れのどこにも、メールを入力する箇所がない。回復コードだけでは回復できない。コードと協力者の承認がそろうと待機に入る（ハーネスが DB の `ready_at` を書き換えて時間を進める）。直近14日以内に回復した協力者の承認は無効になる。取り消すとコードが失効し、回復を始められなくなる。回復が成立すると使ったコードが失効し、新しいコードが発行されて、全端末と協力者に知らせが届く。回復後の制限が効き、`recovered_at` が企業に届く。
4. 同じ人の sub と別名は、A社とB社で別々になり、同じテナントのコードフローのクライアント間では sub が同じになる。入れ替え後の旧別名あてのメールは同じ 250 で受けて届けず、割り当て処理は一意制約により旧値を返せない。企業に渡る値を一覧で確認する（ADR 0022）。
5. 送信元ロック：署名なし、d= の不一致、l= 付き、ヘッダーの重複、リプレイは拒否される。返信の中継：From を詐称した返信（DMARC 不一致）は中継されない。中継された返信には `X-Warifu-Unauthenticated` が付き、本物のアドレスが入らない。開封通知、配信停止、全員に返信から、本物のアドレスが漏れない。転送した本文はバイト単位で同じ。DMARC が p=reject の送信元から来たメールについて、受信側の検証（mailauth で模擬）の結果を記録する。
6. A2B：A社のトークンでB社のものに触れない。利用者 U1 は U2 のものに触れない。逆引きのルートが存在しない。連絡先・認証器・回復協力者・回復の設定を変えるルートは、利用者自身が 4章の手順（step-up と、回復の流れ）で行う idp のルートだけにする。管理用のルートにも、企業向けのルート（company-api、窓口の承認で呼べるもの）にも置かない（ルート一覧で固定）。企業のトークンで、参加の状態、移行中の期限、割符が確かめた入り口と確かめた日を変えようとすると拒否される（ADR 0010）。機能ごとのレート制限が働く。窓口の作成通知・利用者取消・状態照会、初回紐付けの証跡・待機・再確認・取消配送・結果報告と内部経路も実装時に一覧で固定し、認証・認可と U1／U2 の分離を検査する（ADR 0019・0020）。
7. 割符の全サービスの DB（pg_dump）とログ、配送ログを、本物のアドレス、別名、トークン、回復コード、窓口コード（P0では作らない）、招待コード、協力者の表示名、申請ID、受付番号、変更ID、取消要求ID、移行証跡で検索して、ヒットが0件（demo-rp の DB とテスト用の受信箱は対象外）。
8. 各サービスが、能力の表（8章）にない鍵の操作をすると 403。監査ログのチェーンが検証できる。暗号の呼び出しとアルゴリズムの設定が、許可リストどおりに固定されている。
9. 適合テストキットが、「email でアカウントをまとめる RP」と「本案で紐付けた会員に旧経路が残る RP」を、移行中も含め不合格にする（ADR 0020）。**紐付けの攻撃**として、漏れたメールで旧アカウントを奪い、攻撃者自身の sub を紐付けようとする場面も、適合している RP では失敗する。**移行中の参加**（ADR 0010）では、適合テストキットが、入り口の一覧で緩めていない検査（email でアカウントをまとめる、sub の書き換え、本案で紐付けた会員の旧経路閉鎖）と、一覧1に移った入り口に対応する検査を、移行中でも不合格にする。警告文 I は、接続の同意の画面と、別名の一覧の企業ごとの詳細にだけ表示される。承認、回復の画面、ロック画面、プッシュ通知と、完全な参加の企業の画面には出ない。項目が一覧1に移るのは、割符が閉じたことを確かめた後だけで、企業の自己申告や適合テストキットの結果では移らない。確かめ直しの間隔を過ぎると、項目は「まだ残っている入り口」に戻る。
10. 登録済みかどうかで、登録時と回復時の応答（本文、ステータス、所要時間の大きな差）が変わらない。SMTP の RCPT への応答も一律。
11. SSRF：IMDS、内部 API、プライベート IP、DNS rebinding、リダイレクト、MX が内部の IP を指すアドレスへの配送は、送信サービスで拒否される。
12. 2社の SET のログから、sub を突き合わせられない（時刻のずらしと、jti の独立）。
