# 割符の仕様書（骨子）

> 状態：M1 時点の骨子。M10 で確定する（plan 10章）。正は [docs/plan.md](../plan.md)。
> この仕様書は、plan、[CLAUDE.md](../../CLAUDE.md) の不変条件、[docs/adr/](../adr/)、[DESIGN.md](../../DESIGN.md)、[docs/standards.md](../standards.md) から、要件を引き出して並べ直したもの。ここで新しい設計判断はしない。

## 目的

割符（Warifu）を作る人と、割符に接続する企業に向けて、守ることを要件の形で示す。

割符の目的は、企業が利用者の本物の連絡先を本人確認に使わず、持たずに済む状態をつくること。この仕様書は、そのために次の4つを定める。

- 何を本人確認・承認・識別の根拠にしてよいか（[01](01-principles.md)）
- 接続する企業が何を守るか（[02](02-rp-requirements.md)）
- 何を、誰から、どう守るか（[03](03-threat-model.md)）
- 割符のどのサービスが、何をできるか（[04](04-capabilities.md)）

## 外注先に求めること

- 外注先（再委託先を含む）にも、CLAUDE.md の不変条件と、この仕様書の要件を適用する（plan 10章。CONTRIBUTING.md が、人の開発者にも不変条件を適用するのと同じ考え方）。
- 開発と試験の値は、乱数で作る。本物らしい連絡先、氏名、番号を書かない（[test/leak/README.md](../../test/leak/README.md) の書き方の決まり）。
- 外注先に渡す権限、再委託の条件、管理状況を確かめる方法と頻度は、未定（P1 で決める。plan 10章）。

## 要件の書き方

| 表現 | 意味 |
|---|---|
| しなければならない | 必須。守らなければ、接続要件や受け入れ基準を満たさない |
| してはならない | 禁止。守らなければ、接続要件や受け入れ基準を満たさない |
| 推奨する | 従うことを求める。従わない場合は、理由と影響を説明できるようにする |
| してよい | 許可。肯定リストでは「これだけを根拠にしてよい」の意味で使う。リストにないものは許可しない |

- 要件には ID を付ける。後の文書、テスト、監査の記録は、この ID で引く。
- ID は再利用しない。要件を消したときは、その ID を「欠番」として残す。
- 各要件には、段階（P0、P1、保留）と出典（plan の節、ADR、不変条件の番号）を書く。
- plan が決めていないことは、設計を作らずに「未定（Mn で決める）」と書く。Mn は plan 10章のマイルストーン。人の作業で決まるものは、イシューの番号を書く。
- 「テスト n」は、plan 11章の漏えいシナリオのテストの番号を指す。
- 「不変条件 n」は、CLAUDE.md の不変条件の番号を指す。

## 用語

用語は [CLAUDE.md](../../CLAUDE.md) の用語表を正とする。この仕様書では、次の言葉も使う。

| 用語 | 意味 |
|---|---|
| 肯定リスト | 根拠にしてよいものの一覧（ADR 0001）。載っていないものは、例に挙げているかどうかにかかわらず、根拠にしない |
| 根拠にする | アカウントを探す、本人と見なす、操作を許可する、のどれかの判断の入力に使うこと |
| 高リスクの操作 | 配送先・返金先・支払い手段の変更、解約、高額の取引、住所の法定開示への同意 |
| step-up | 利用者が自分の端末で、操作に結び付いた承認をすること（オリジンに結び付いたパスキーと、RFC 9396 RAR） |
| 指名子 | 利用者を指すだけで、それだけでは何も許可しない値（受付番号、回復コードのハンドル） |
| 安全側の入力 | 制限を強める方向にだけ使う信号（例：`recovered_at`）。根拠ではない |
| 適合テスト | 企業が接続要件を守っているかを確かめる、rp-kit の検査（plan 3-3、テスト9） |
| 完全な参加 | 接続要件をすべて守る参加の状態。「接続要件を守る企業」は、この状態の企業を指す（[02 の 14章](02-rp-requirements.md#14-移行中の参加)、ADR 0010） |
| 移行中の参加 | 入り口の一覧（ENT-01〜03）にある経路だけを、期限まで残してよい参加の状態。主張の対象に含めない（[02 の 14章](02-rp-requirements.md#14-移行中の参加)、ADR 0010） |

## 主張の書き方

この仕様書と、仕様書から作る文書は、CLAUDE.md の「主張の書き方」に従う。

- 書いてよい：「漏れた連絡先や属性を知っている・受け取れるだけでは、割符と、接続要件を守る企業での本人確認は突破できない」
- 「接続要件を守る企業」は、完全な参加の企業を指す。移行中の参加の企業は含めない（[01 の 3章](01-principles.md#3-主張できる範囲)）。
- 書かない：「漏れても無害」「個人情報保護法の対象外」「安全です」のような断定。
- 残るリスクは plan 1-2 の一覧を正とし、全項目を省かずに書く（[01 の 4章](01-principles.md#4-残るリスク)）。
