## 1. 3つの原則

| ID | 原則 | 内容 | P0 で達成する範囲 |
|---|---|---|---|
| PRN-01 | 使わせない（第一原則） | 本人確認・回復・承認・識別の根拠にしてよいものを、肯定リスト（2章）で決める。それ以外は、例として挙げているかどうかにかかわらず、一切根拠にしない | 企業の側と割符の内部の両方 |
| PRN-02 | 持たせない | 企業は本物の連絡先を持たない。代わりに、企業ごとの別名と企業別ID（sub）を渡す | メールだけ（割符に参加した後に企業へ渡すものについて。紐付けの前から企業が持っているものは RR-13）。電話は未達（RR-04）。住所は段階的に減らす（plan 5章。受け取り場所の SDK は P1） |
| PRN-03 | つなげさせない・届けさせない | 企業ごとの pairwise sub と別名を使う。別名あてのメールには送信元ロックをかける。使い終えた値は二度と割り当てない | 氏名と受け取り場所を渡す限り、企業をまたいだ突き合わせは防げない（RR-05） |

肯定リストの形にするのは、根拠にしてはならないものを列挙する否定リストには、必ず漏れが出るから（ADR 0001）。2-4 の一覧は確認のための例で、網羅ではない。

## 2. 肯定リスト

肯定リストは、立場ごとに2層に分ける（ADR 0001、不変条件1）。

### 2-1. 企業（RP）の側

企業は、次だけを本人確認・承認・識別の根拠にしてよい。接続要件（[02](02-rp-requirements.md)）と適合テストで課す。

| ID | 根拠にしてよいもの | 使ってよい範囲 | 段階 |
|---|---|---|---|
| PRN-10 | 割符が発行した ID トークンの `iss`・`sub`・`acr`・`auth_time`（と、それだけから作った自前のセッション） | 識別は `(iss, sub)` の組で行う | P0 |
| PRN-11 | CIBA の結果 | 照会と軽い手続きだけ。高リスクの操作には使わない | P0 |
| PRN-12 | 操作に結び付いた step-up の結果 | 高リスクの操作は、これだけを根拠にする | P0 |
| PRN-13 | 割符が署名したイベント | アカウントの付け替えだけ。P1 の JPKI による再確認の後に限る（plan 3-3） | P1 |

- 高リスクの操作：配送先・返金先・支払い手段の変更、解約、高額の取引、住所の法定開示への同意。
- 「高額」の基準と「軽い手続き」の範囲は、未定（M7 で決める）。
- PRN-13 は plan 1-1(a)、ADR 0001、CLAUDE.md の不変条件1(a) にある。
- 移行中の参加の企業には、入り口の一覧（ENT-01〜03）の経路の中に限って、期限付きの例外がある（[02 の 14章](02-rp-requirements.md#14-移行中の参加)、ADR 0010）。接続要件の中だけの例外で、割符のサービス、rp-kit の SDK、demo-rp の参照実装には例外を設けない。割符のコードは、移行中の参加の企業についても、連絡先や属性を根拠にしない（CLAUDE.md の不変条件1(a)）。rp-kit の SDK と demo-rp の参照実装は、完全な参加だけを実装し、入り口の一覧の経路を作る機能や設定を入れない。入り口の一覧の経路は、demo-rp の「悪い RP」のモード（テスト9）の中にだけ置く。このモードは、適合テストキットが不合格にすることを示すための模擬で、参照実装には含めず、テストの中でだけ有効にする。別名と email クレームは、この例外に含めない。高リスクの操作は、移行中でも PRN-12 だけを根拠にする。ENT-01 の再設定の宛先の変更も、移行中は同じに扱う（[RP-18](02-rp-requirements.md#14-移行中の参加)）。移行中の参加の企業は、3章の主張の対象に含めない。

### 2-2. 割符の内部

割符は、利用者を認証・回復するとき、次だけを根拠にしてよい。

| ID | 根拠にしてよいもの | 使ってよい範囲 | 段階 |
|---|---|---|---|
| PRN-20 | 登録済みのパスキー（UV 付き）のアサーション | ログイン、step-up、窓口コードの発行、回復の取り消し、協力者の確定など | P0 |
| PRN-21 | 回復コード、回復協力者の承認、待機期間の満了の3つがそろったとき | 回復だけ。どれか1つや2つでは成立しない（ADR 0003） | P0（協力者は1人。k-of-n は P1） |
| PRN-22 | JPKI | 協力者がいない場合の回復など。照合のキーの方式は P1 の ADR で決める | P1 |

協力者がいない場合、P0 では回復できない（plan 4）。

### 2-3. 指名子

| ID | 要件 |
|---|---|
| PRN-30 | 窓口コードと回復コードのハンドルは、利用者を指す指名子にすぎない。それだけでは何も許可してはならない |

- 窓口コード：CIBA を始めるための使い捨ての値。発行先の client_id に結び付き、有効期間は数分で、一度使えば失効する（plan 3-1）。許可の根拠は、その後に利用者が端末で行う承認（PRN-11）にある。
- 回復コードのハンドル：アカウントを指す乱数。回復コードは、ハンドルと64ビット以上の秘密を含む（plan 4）。

### 2-4. 根拠に使わないもの

| ID | 要件 |
|---|---|
| PRN-40 | 次のものを、2-1 と 2-2 の判定の入力に使ってはならない。アカウントを探す、本人と見なす、操作を許可する、のどれにも使わない |

- 本物のメール、電話、住所、氏名、生年月日
- 注文や予約の番号、決済情報
- 別名、ID トークンの email クレーム（`email_verified` は常に false）
- 中継した返信や着信（DMARC が pass しても、本人の承認として扱わない。plan 3-2）

電話番号について：P0 では、割符は利用者の電話番号を集めない（入力欄、列、クレームを作らない。不変条件11）。電話の中継は保留している（ADR 0004）。

### 2-5. 配送のための照合と、安全側の入力

| ID | 要件 |
|---|---|
| PRN-50 | 配送のための照合は、例外として許す。その結果を許可の判断に流してはならない |
| PRN-51 | 制限を強める方向にだけ使う信号は、根拠ではなく、安全側の入力として扱ってよい |

PRN-50 で許す照合（不変条件1(e)）：

- relay で、別名の HMAC から配送先を引くこと
- 送信元ロックと中継の衛生の検査（DKIM、DMARC、本文中の本物のアドレスの検出）
- 一意性の検査

PRN-51 の例：`recovered_at`（企業が回復の直後に高リスクの操作を保留するために使う。[RP-53、RP-54](02-rp-requirements.md#7-イベントsetを受けたとき)）。

- 同期パスキーかどうか（BE/BS フラグ）の変化は、plan 4 でリスクの信号として扱う。BE/BS フラグはパスキーのアサーションの一部で、許可の根拠は PRN-20 にある。M3 では記録だけにした（ADR 0018）。信号の具体的な使い方は、未定（回復の M8 で決める）。

### 2-6. 割符自身への適用

割符も、自分の利用者に対して同じ原則を守る（plan 4章、ADR 0003）。回復の流れの詳しい仕様は、M8 で足す。

| ID | 要件 | 段階 |
|---|---|---|
| PRN-80 | 割符が持つ本物のメールは、配送先としてだけ使わなければならない。認証、回復、アカウントを探すことに使ってはならない | P0 |
| PRN-81 | 本物のメールの変更は、step-up と、新しいアドレスの宛先確認だけで行わなければならない。旧アドレスには、操作のリンクを含まない知らせだけを送る。知らせのメールには操作のリンクを入れてはならない | P0 |
| PRN-82 | 登録、回復、宛先確認、SMTP の RCPT への応答は、登録済みかどうかで、本文・ステータス・所要時間を変えてはならない（不変条件10） | P0 |
| PRN-83 | P0 では、電話番号を集めてはならない（入力欄、列、クレームを作らない。不変条件11） | P0 |
| PRN-84 | パスキーの追加と削除には step-up を求め、全端末に知らせなければならない。パスキーを2つ以上、うち1つは端末固定（セキュリティキーなど）で登録してもらうことを推奨する。BE/BS フラグを記録する。同期先アカウントの強化（Apple の復旧キーなど）を案内する | P0 |
| PRN-85 | 回復は、回復コードだけで始めなければならない。回復の画面に、メール・電話・氏名の入力欄を置いてはならない。協力者への依頼と、登録済み端末への通知は、コードを確かめた後に出す | P0 |
| PRN-86 | 回復協力者の指名は、対面の QR か、使い捨ての招待コードに限る。連絡先で検索する機能を作ってはならない。確定には step-up を求め、全端末に知らせる | P0 |
| PRN-87 | 協力者の承認は、回復を求めている人の新しい端末に出た QR を、協力者が対面で読み取って行う。QR が使えない場合だけ、コードを手で入力する。電話やビデオ通話で伝えられたコードは使わない（警告文 C）。直近14日以内に回復した協力者や、パスキーを追加した協力者の承認は無効にする（14日の考え方は ADR 0012） | P0（協力者は1人。k-of-n は P1） |
| PRN-88 | 待機期間は、回復コードの確認と協力者の承認がそろった時点から数える。既定は72時間、本番の下限は24時間で、起動時に強制する（値の考え方は ADR 0012）。登録済み端末の受信箱と協力者に知らせ、端末のパスキーで取り消せるようにする | P0 |
| PRN-89 | 回復が取り消されたら、使われた回復コードを失効させ、14日間は回復を始められないようにする。回復が成立したら、使われた回復コードを失効させ、新しい回復コードを発行する。回復コードの再発行は、全端末と協力者に知らせる（ADR 0012） | P0 |
| PRN-90 | 回復の後7日間は、協力者の変更、他のパスキーの削除、配送先の変更、高リスクの承認を禁止する。古いパスキーは一時停止にする。企業には、独自クレーム `recovered_at` と SET で知らせる | P0 |
| PRN-91 | 協力関係は、内部 ID の組だけでサーバーに持つ。協力者が相手を見分ける表示名は、協力者の端末の中だけに保存し、サーバーに置いてはならない | P0 |

- 確かめ方：テスト3（回復）、テスト10（列挙）、テスト6（ルート一覧）。

## 3. 主張できる範囲

| ID | 要件 |
|---|---|
| PRN-60 | 効果を述べるときは、次の文言の範囲にとどめなければならない |
| PRN-61 | 下の「書かない」表現を使ってはならない |

- 書いてよい：「漏れた連絡先や属性を知っている・受け取れるだけでは、割符と、接続要件を守る企業での本人確認は突破できない」
- この主張は「接続要件を守る企業」に限る。守らない企業と、割符の外の第三者（RR-03）には及ばない。
- 「接続要件を守る企業」は、完全な参加の企業を指す。移行中の参加の企業（[02 の 14章](02-rp-requirements.md#14-移行中の参加)）は含めない。この主張は、移行中の企業には及ばない（RR-14。plan 1-2、ADR 0010）。移行中から完全な参加に移った企業でも、移行中に攻撃者の sub が紐付いたアカウントは残る（RR-14）。
- この主張は、漏えいがどの経路（どの製品、どの脆弱性、どの業種のシステム）で起きたかを問わない。漏えいそのものを防ぐことは主張しない（RR-13。plan 1-2）。
- 漏れた値は、フィッシングなどの宛先には使われうる（RR-08）。
- 書かない：「漏れても無害」「個人情報保護法の対象外」「安全です」（断定）。

法令との関係（plan 7章。弁護士の確認待ち、イシュー #15）：

- 別名と sub は、企業にとって個人関連情報になる。氏名や住所を結び付けた時点で、個人情報になる。
- 令和8年改正（2026-07-17 公布）の後は、連絡可能個人関連情報として、不適正な利用と不正な取得が禁止される。「規制の対象外」とは書かない。
- 割符が漏えいすれば、割符は報告義務の対象になる（RR-10）。暗号化を理由に、報告が要らないとは主張しない（standards.md の「高度な暗号化等の秘匿化」の行）。

## 4. 残るリスク

plan 1-2 の一覧を正とする。plan 1-2 の12項目を、省かずに14行に分けて書く（回復の弱点と、フィッシングの宛先・住所の項目は、それぞれ2行に分ける）。[03 の脅威モデル](03-threat-model.md)も、この ID で引く。

| RR-04 | 電話について原則2は未達 | 電話の中継を保留しているので、企業は電話番号を持ち続けうる（plan 7章、ADR 0004） | 電話番号を根拠にしないことを、肯定リスト（PRN-40）で担保する。これは完全な参加の企業についてのもの。移行中の参加の企業では、ENT-01 の SMS による再設定と、ENT-03 の電話番号などによる照合が、期限まで残りうる（RR-14。[02 の 14章](02-rp-requirements.md#14-移行中の参加)） |

| RR-12 | 回復コードのフィッシング | 回復コードは、偽の回復ページなどのフィッシングで盗まれうる。盗んだ攻撃者が協力者もだまして承認させると、回復が待機に入る（待機中は、登録済みの端末から取り消せる）（ADR 0003） | コードだけでは回復できない（PRN-21）。協力者の承認は対面の QR が第一（PRN-87、警告文 C）。待機中は登録済みの端末と協力者に知らせ、取り消せる（PRN-88、警告文 F）。回復コードの画面に警告文 G |
| RR-13 | 企業の側の漏えいそのもの | 割符は、企業の Web システム、管理用・内部の API、BI ツールなどからの漏えいを防がない。企業が持ち続ける氏名、住所、注文の履歴などは漏れうる。紐付けの前から企業が持っている本物の連絡先は、企業が消さない限り残る（消すことは推奨。必須にするかは M9 で決める。plan 3-3）。割符が減らすのは、漏れた連絡先や属性が、接続要件を守る企業で本人確認に通用すること（3章の主張の範囲）と、企業が持つ本物の連絡先（P0 ではメールだけ）である | 漏れた連絡先や属性を根拠にさせない（PRN-01、PRN-40）。企業が持つ本物の連絡先を減らす（PRN-02、RP-35）。企業の側のシステムの管理の推奨（[02 の 13章](02-rp-requirements.md#13-企業の側のシステムの管理推奨)） |
| RR-14 | 移行中の企業に残っている入り口 | 移行中の参加の企業では、入り口の一覧（ENT-01〜03）にある経路が、期限まで残る。漏れた連絡先や属性で、その経路から本人確認を突破されうる。この企業独自のパスワードでのログイン（ENT-02）が残る間は、漏れたパスワードでも突破されうる。メールや SMS による再設定（ENT-01）が残る間は、未紐付けの会員の旧アカウントを奪って、攻撃者の sub を紐付ける場面（紐付けの攻撃）も成り立ちうる（ADR 0010。plan 1-2）。移行中に攻撃者の sub が紐付いたアカウントでは、攻撃者が自分の端末で操作ごとの承認を出せるので、RP-10 の守りも働かない。このアカウントは、完全な参加に移った後も残る。P0 には、付け替えの手段がない（RP-34。P1）。割符が確かめて一覧1に移した入り口も、確かめた時点の、試験用のアカウントについての結果である | 主張の対象から外す（3章）。残してよいのは入り口の一覧の経路だけで、期限を付ける（RP-15、RP-16。期限の長さは M9 で決める）。高リスクの操作は、移行中でも操作ごとの承認だけを根拠にする（RP-10）。ENT-01 の再設定の宛先の変更も同じに扱う（RP-18）。入り口の一覧の各項目を、警告文 I の一覧1と一覧2に分けて、接続の同意の画面と、別名の一覧の企業ごとの詳細に出す（M9）。一覧1に移すのは、割符が閉じたことを確かめたときだけ |

## 5. 基準との関係

| ID | 要件 |
|---|---|
| PRN-70 | この原則は、NIST（メールや SMS で回復コードを送ることを条件付きで認めている）より厳しい、この製品の方針として扱う |
| PRN-71 | 割符の回復が「NIST の AAL2 に準拠する・相当する」、または「FIDO と DS-511／DS-512 の『同等以上の強さ』を満たす」と書いてはならない。独自の方式として記述する（原文を照合した結果。ADR 0012） |

- NIST の recovery contacts（指定した人のアドレスに発行型のコードを送る方式）は、割符の協力者の方式とは別物である。割符の回復は、NIST の AAL2 の回復の組み合わせ（4.2.2.2）に当たらない（plan 4、ADR 0003、ADR 0012）。
- P0 の回復は、FIDO と DS-511 の「回復は元の認証と同等以上の強さ」を満たすとは言えない。回復コードはフィッシングで盗まれうる（RR-12。DS-512 も明記している）。協力者の対面の承認は、対面であることを技術で確かめていない（ADR 0012）。
- この仕様書は、下の基準を「方向が一致する基準」として挙げるだけで、準拠や適合は主張しない。

方向が一致する基準（plan 1-2）。確認状況は standards.md を正とする（2026-10-22 に、接続できた資料は原文で確認済み。接続できなかった一部は「抜粋のみ」）。
