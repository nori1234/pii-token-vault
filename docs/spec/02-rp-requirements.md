## 0. この章の読み方

- 対象は、割符に接続する企業（テナント）。企業の側の肯定リストは [01 の 2-1](01-principles.md#2-1-企業rpの側) を参照。
- 「確かめ方」の記号：

| 記号 | 意味 |
|---|---|
| 適合 | rp-kit の適合テストキットで確かめる（plan 3-3、テスト9。M9） |
| SDK | rp-kit の参照実装と、その単体検査で確かめる |
| 割符 | 割符の側で強制する。守らない要求は割符が拒否する（括弧内は plan 11章のテスト） |
| 登録 | テナントの登録時に、割符が検査する |
| 監査 | 自己申告のチェックリストと、監査で確かめる |

- 法令との関係（参考。plan 7章、弁護士の確認待ち、イシュー #15）：割符から企業への提供は、個人情報保護法27条の第三者提供として、割符が同意画面で同意を得て記録する。別名と sub は、企業にとって個人関連情報になる。氏名や住所を結び付けた時点で個人情報になる。令和8年改正の後は、連絡可能個人関連情報として規制される。

| RP-23 | `binding_message` は割符が生成する。企業が送ったものは、利用者に表示されない | P0 | 割符（テスト2） |

| RP-27 | 窓口担当者の画面に、氏名・電話・メール・予約番号での検索や、失敗したときの代わりの本人確認（質問、連絡先、予約番号）を置いてはならない | P0 | 監査（demo-rp が参照実装） |
| RP-28 | 窓口での変更は、割符が利用者の全端末に事後通知し、24時間は取り消せる（値の根拠は未確認）。企業は、取り消された変更を元に戻さなければならない | P0 | 監査 |
| RP-29 | 窓口や管理の運用を委託している場合は、委託先（再委託先を含む）にも、接続要件（この章と RP-13 を含む）を守らせなければならない | P0 | 監査 |

- 窓口コードの試行、CIBA の要求、poll には、テナントごとの上限がある（plan 2章）。値と、poll の間隔は、未定（M7 で決める）。
- 未定（M7 で決める）：公式の連絡先の登録と確認の手順、割符が生成した `binding_message` を担当者に見せる方法、窓口での変更を割符に伝える方法と、取り消しを企業に伝える方法、企業が送った `binding_message` を拒否にするか無視にするか（ADR 0006。どちらでも利用者には表示されない）。

| RP-82 | `h=` に From、To、Subject、Date、Message-ID を必ず含め、重ねて署名（oversign）しなければならない | P0 | 割符（テスト5） |
| RP-83 | From、To、Subject を重複させてはならない（拒否される） | P0 | 割符（テスト5） |
| RP-84 | 新しいメールは、署名し直して送らなければならない。割符は、`(d、s、b= の HMAC、別名の照合用の HMAC)` を `x=` の期限まで保持してリプレイを判定する（HMAC はどちらも HMAC-SHA-256。別名は平文では保存しない。不変条件4・9）。同じ内容の再試行は 2xx で受けて捨てる | P0 | 割符（テスト5） |
| RP-85 | 割符が行う書き換えを前提にしなければならない（下の一覧）。企業の元の DKIM 署名は壊れる | P0 | — |

割符が行う書き換え（plan 3-2、8章）：

- Disposition-Notification-To と Return-Receipt-To を削除する。
- List-Unsubscribe の `mailto:` を、relay 経由のアドレスに書き換える。
- 別名以外の To と Cc を、relay 経由のアドレスに書き換える。
- 件名と本文はバイト単位で変えない。relay の DKIM を付け直し、ARC で封印する。relay のサブドメインは企業ごとに分ける。
- 利用者からの返信は、やり取りごとの使い捨てのアドレスから届く。`X-Warifu-Unauthenticated` が付く。

未定（M4 で決める）：

- 企業の DMARC が p=reject のときの From の扱い（企業のドメインのまま ARC に頼るか、relay のドメインに書き換えて表示名で企業を示すか）。
- `x=` を必須にするか、`x=` がない場合の保持期間。
