## 0. この章の読み方

- 対象は、割符に接続する企業（テナント）。企業の側の肯定リストは [01 の 2-1](01-principles.md#2-1-企業rpの側) を参照。
- 参加には、完全な参加と移行中の参加がある（14章）。移行中の企業には、入り口の一覧（ENT-01〜03）の経路に限って、期限付きの例外がある。主張（[01 の 3章](01-principles.md#3-主張できる範囲)）は、完全な参加の企業にだけ及ぶ。
- 「確かめ方」の記号：

| 記号 | 意味 |
|---|---|
| 適合 | rp-kit の適合テストキットで確かめる（plan 3-3、テスト9。M9） |
| SDK | rp-kit の参照実装と、その単体検査で確かめる |
| 割符 | 割符の側で強制する。守らない要求は割符が拒否する（括弧内は plan 11章のテスト） |
| 登録 | テナントの登録時に、割符が検査する |
| 監査 | 自己申告のチェックリストと、監査で確かめる |

- 法令との関係（参考。plan 7章、弁護士の確認待ち、イシュー #15）：割符から企業への提供は、個人情報保護法27条の第三者提供として、割符が同意画面で同意を得て記録する。別名と sub は、企業にとって個人関連情報になる。氏名や住所を結び付けた時点で個人情報になる。令和8年改正の後は、連絡可能個人関連情報として規制される。

- `acr` の値：ログインと step-up は `urn:warifu:acr:passkey`（UV 付きのパスキー）。ID トークンには、要求しなくても acr と auth_time が入る。step-up は、`max_age`（0 も可）か `prompt=login` で新しい認証を求め、auth_time で確かめる（[ADR 0018](../adr/0018-idp-passkey-oidc.md)）。窓口用途の値は M7 で決める（[ADR 0006](../adr/0006-ciba-spike-findings.md)）。
- ID トークンの有効期間は5分。リフレッシュトークンは出さない。企業は、ID トークンを受け取った後、自前のセッションを作る（RP-02）。
- 紐付けの前から企業が持っている既存会員の本物の連絡先をどう扱うか（消すかどうか）は、未定（M9 で決める。plan 3-3、原則2）。いまは推奨（RP-35）にとどめる。必須にするかも、M9 で決める。

- M5 で決めたこと（[ADR 0022](../adr/0022-company-api-sender.md)）：
  - 企業向け API のトークン：`POST /token` で、`grant_type=client_credentials` と private_key_jwt（RFC 7523）の client assertion を送る。assertion は ES256 で、`iss` と `sub` は client_id、`aud` はトークンのエンドポイントの URL の1つだけ（配列にしない）、`exp`・`iat`・`jti` は必須、`iat` から5分まで、`jti` は1回だけ。
  - テナントの JWT：ES256 で5分、`scope` は `company_api` の1つ（別名の入れ替えと、検証の SET の依頼）、リフレッシュトークンなし。
  - 封じ込め：静的な設定を直して配備し直す（company-api の登録の `suspended` で、トークンを出さず、発行済みのものも断り、SET を送らない。送信は relay、ログインは idp の登録から外す）。管理 API は作らない。
  - テナントの鍵の入れ替え：jwks に新しい鍵を足して（4つまで）切り替えた後、古い鍵を外す。定期的な入れ替えの周期は P1。
- 未定：ロゴの渡し方と、受け付ける形式と検査（スクリプトを含みうる形式の扱いを含む）。P0 ではロゴを受け付けない（承認画面は登録簿の企業名だけ。M6・M7 か P1 で決める。ADR 0022 の O-40）。
- クライアント認証は `private_key_jwt` だけ（RP-70）なので、秘密鍵を秘密のまま持てない公開アプリは、割符のクライアントにならない（不変条件7）。企業のモバイルアプリは、企業のサーバーとだけ話し、企業のサーバーが割符のクライアントになる。アプリの中では、企業のサーバーが始めた認可を、システムのブラウザ（ASWebAuthenticationSession、Custom Tabs）で開く（[ADR 0018](../adr/0018-idp-passkey-oidc.md)）。
- コードフローのクライアントでは、`redirect_uris` のホストを1つにする（ホストが2つ以上あると、oidc-provider が `sector_identifier_uri` を求めるため。[ADR 0006](../adr/0006-ciba-spike-findings.md)）。登録の検査で拒否する（[ADR 0018](../adr/0018-idp-passkey-oidc.md)）。PKCE（S256）は必須。

割符が行う書き換え（plan 3-2、8章）：

- From を、登録簿の企業名と、relay 経由のアドレス（返信用のアドレス）にする。企業の DMARC が p=reject でも、受信側の DMARC は relay の署名で整合する。
- To を別名だけにし、Cc と Bcc を消す（企業が並べたほかの宛先は、利用者に届かない）。
- Disposition-Notification-To、Return-Receipt-To、Reply-To、Sender、Return-Path、企業の DKIM-Signature と ARC の組、Authentication-Results、Received-SPF を削除する。
- List-Unsubscribe の `mailto:` を、relay 経由のアドレスに書き換える。`https:` は残し、それ以外は消す。List-Unsubscribe-Post は、`https:` が残ったときだけ、`List-Unsubscribe=One-Click` の値で残す。
- 件名と本文はバイト単位で変えない。relay の DKIM を付け直し、ARC で封印する。relay のサブドメインは企業ごとに分ける。
- 利用者からの返信は、やり取りごとの使い捨てのアドレス（30日で失効する）から、元の Reply-To（署名したもの）か From に届く。`X-Warifu-Unauthenticated` が付き、Message-ID は relay が作り直す。P0 では、添付ファイルや画像を含む返信は届かない（利用者に差し戻す）。
- 1つの SMTP のトランザクションの宛先は1つだけ（2つ目の RCPT は 452）。1通は 10 MiB まで。

- 表示を作る M9 までは、移行中の参加の企業を接続しない。
- 参加の状態、移行中の期限、割符が確かめた項目と確かめた日は、テナントの登録（配備のときの静的な設定）に持たせた（M5。[04 の 3章](04-capabilities.md#3-db)、ADR 0022）。どのルートからも書き換えられない（テスト6）。M9 までは、完全な参加、期限なし、確かめた項目は空だけを受け付ける。

- 企業に不利な表示を出すことの、契約と法務の面での確認は、イシュー #15 と合わせて行う。
