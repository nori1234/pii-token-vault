# ADR 0019：窓口の操作別承認

- 状態：決定（仮、オーナー確認済み）
- 日付：2026-10-27

## 背景と決定

窓口は企業の認証済み画面で対象と応対を選び、割符の操作別 step-up で限定許可を出す。CIBA と割符の窓口コードは P0 で提供しない。企業の受付番号は応対の参照であり、割符へ渡さず、それだけでは何も許可しない。用途 `desk` の承認は照会と軽い手続きだけに使い、高リスク操作には対象・内容に結び付く別の承認を使う。

申請・主体・対象・版・操作・入力・担当者・期限を固定する。割符の承認画面は固定の企業名・操作ラベル・許可範囲を示し、「かかってきた電話で求められていますか？」と尋ねる。相手発の電話なら承認せず、公式窓口からの連絡を案内する。攻撃者が自分の受付番号を被害者に入力させる中継が残り、警告のみで完全に防げるとは主張しない。

窓口の変更は全端末に通知し、24時間取り消せる。取消の受理時刻は割符を正とし、期限内に受理した取消は企業への配送が遅れても失効させない。企業は適用結果を認証済みcompany-apiへ報告する。Webhookの202は配送受付で、業務上の取消完了を意味しない。

作成の承認時に、割符が変更IDを固定した「承認済み（作成の知らせ待ち）」を受信箱へ永続記録し、知らせの前から本人が取り消せるようにする。企業は作成前の取消予約と作成を同じ状態で原子的に競合させ、作成済みなら取り消す。作成されなかった場合は、実行不能も確定した企業の認証済み報告で閉じ、単なる通知未着や期限切れでは閉じない。詳細と障害・再送の検査は仕様案§2.4・D-42〜44に定める。

申請ID・受付番号・変更ID・取消要求ID・移行証跡は不変条件4に従う。企業・委託先のログ、エラー報告、分析・録画も対象とし、必要な状態はHMAC等で保護する。

企業サーバーが作成を完了した場合の通知経路は、`POST /v1/desk/change-notices`（案）である。企業の永続outboxからテナントJWTと限定scopeを使い、承認済みの申請・主体・変更IDと対応する通知だけを受理する。同じ通知の再送は冪等にし、受信箱の永続記録後に取消期限を返す。権限としての承認期限と通知の配送期限を混同しない。期限後の通知照合を新しい業務許可に使わない。

申請・変更・取消の正本はcompany-apiのテナント境界とし、idpは本人の承認・受信箱を利用者境界で扱う。テナント別RLS・列単位GRANT、用途限定の内部資格情報、用途別MACと署名のACLを使う設計案である。idpとcompany-apiの状態を分散トランザクションとみなさず、再送と冪等な状態遷移で整合させる。新しい鍵・内部API・ACLは能力表と同時に定義し、relay以外の復号とテナント横断のDB例外を追加しない。

**監査の保持**：ADR 0016に従う削除しない監査チェーンには、申請ID・受付番号・変更ID・取消要求ID・トークン・移行証跡の原値、企業自由文や業務本文を入れない。固定事象コードと必要最小限の識別・結果を設計し、活動履歴が分かりうることと保存期間を明示する。受信箱の短期保存と監査を混同しない。

M6（ADR 0023）は端末用の承認と通知の基盤だけで、窓口用の型と確定後の引き渡しはまだ持たない。M7では、窓口画面の必須要素・独立した用途と承認結果の引き渡し状態を追加する。承認確定・知らせ待ち項目・再送用状態はidp側の耐障害性を持つ状態遷移で結び付け、承認結果を返したのに項目だけ失われる状態を防ぐ。M6の承認待ち30日後・知らせ90日後の通常の削除規則を、結果不明や取消未完了の項目に無条件に適用しない。M7の実装前に、未解決の最小処理状態の保持と終端後の削除をADR 0023・plan・能力表と整合させ、受信箱の掃除・障害・再送をテストする。→ ADR 0026 の O-63、O-68、O-69 で決めた（窓口の承認は受信箱の承認待ちを使わず、作成の項目は `idp.desk_items` に置き、終端から7日で消す）。

M5のSET実装（ADR 0022）は検証イベントだけに対応し、6回で配送を諦めて送信待ちを削除し、再送時のiat・jtiを変えない。この仕様を取消にそのまま使うと、完了まで取消意思を保持し、受信時間超過時に新しいiat・jtiで再発行する本案を満たせない。M7で取消専用の永続的な配送・結果確認を設計・実装し、既存の署名鍵とsenderの境界に整合させてテストする。必要なscopeも新たに定める。M5で既に対応済みとは扱わない。→ ADR 0026 の O-65、O-67 で決めた（scope `desk`、取消の SET は諦めずに送り直し、`set_too_old` では新しい `iat`・`jti` で送り直す）。

## 仮置きと未決

M7の実装前に、oidc-provider 9のRARの利用方法と実験的扱いの有無、およびPARと要求オブジェクトなしのPOST認可要求が成立するかを検証する。M3ではRARを試していない。→ 2026-10-29 に確かめた。RARは安定した機能で、POSTの認可要求はSameSite=Noneが要るので使わず、PARで受け取る（ADR 0025）。

提示された数値は根拠のない仮置きとし、利用性と濫用耐性を検証して見直す。取消24時間はADR 0012で承認済みの仮置き。受付番号8桁・5分、申請IDの乱数128ビット以上、窓口承認5分、SET受信のiat経過時間−30〜300秒、初回送信遅延0〜60秒、終端確認後の最小記録7日は別の仮置きである。

**オーナーの決定（仮）**：P0の窓口書き込みは一般問い合わせの作成と利用者自身の取消に絞る。RP-60に連絡先検索の例外は追加しない。企業アプリを通話中に使えない人は一般案内・申告受付に限る制約を受け入れる。通知の永続記録を取消期間の起点とする条件、送信・再送と保存の詳細、鍵の能力は実装前に確認する。→ ADR 0026 に既定の案を書いた（O-62〜O-69。オーナーの確認待ち）。
