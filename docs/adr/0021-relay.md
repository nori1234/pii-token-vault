# ADR 0021：relay（送信元ロック、中継の衛生、返信の中継、内部配送 API）

- 状態：提案（オーナーの確認待ち。下の「オーナーの確認」の既定の案で実装した）
- 日付：2026-10-27

## 状況

M4（イシュー #6）で、relay を作る。plan 10章の範囲は、送信元ロック、中継の衛生、返信の中継、内部配送 API、Mailer の差し替え、テスト5と、テスト10（SMTP の RCPT への応答）。plan、仕様書、ADR には、「M4 で決める」とした項目が残っていた。

- relay から本物のアドレスへの配送経路（plan 8章、CLAUDE.md 不変条件7）
- 企業の DMARC が p=reject のときの From の扱い（plan 8章）
- DKIM と ARC の鍵の置き場所と入れ替え（plan 2章・8章、ADR 0014）
- リプレイの記録の期限（`x=` がない場合。plan 8章）
- SMTP の受信の上限（plan 2章）
- 内部配送 API の認証と、受け付ける入力（plan 2章、イシュー #6）
- 配送キューの形（4KB を超えるときの暗号化。ADR 0013）
- mailauth が RFC 9989 の DNS Tree Walk に従うか（ADR 0012 の決定11）

この ADR の番号は 0021 にした。0019 と 0020 は、PR #30（窓口の step-up と、最初の紐付け）が使う。

## 決定

### 構成

- `packages/relay` に、SMTP の受け口（smtp-server 3.20.2）と、内部配送 API（Unix ドメインソケットの HTTP）を置く。メールの検証、正規化、署名の部品は mailauth 7.3.1 を使う。
- テナント（企業）の登録は、M4 では静的な設定で受け取り、起動の時点で検査する（`config.ts`）。登録の中身は、企業名（登録簿の値）、relay のドメイン（テナントごとに分ける。不変条件5）、送信元ロックの d=、s=、公開鍵（SubjectPublicKeyInfo）。M5 で company-api の登録に移し、そこで鍵の種類と長さを確かめる。
- DB は `createRelayDb` の境界だけを通す。テナントの範囲の表（`relay.replay`、`relay.threads`、`relay.delivery_log`）は withTenant で、本物のアドレスは withWarifuUser で読む。テナントを横断するのは、解決関数（`relay.resolve_alias`）だけ（不変条件8）。マイグレーション 0005 で3つの表を足し、どれも RLS の ENABLE と FORCE、テナントの境界のポリシー、列単位の GRANT にした。UPDATE の権限は与えない。

### SMTP の受け口

- 1つのトランザクションの宛先は1つ。2つ目の RCPT には 452 を返す（宛先ごとに、送信元ロックとリプレイの判定を分けるため）。宛先は smtp-server がトランザクションごとに持つ封筒（`session.envelope.rcptTo`）から読み、自前の状態を持たない。封筒は DATA の後と RSET で空になるので、同じ接続の次のトランザクションは、また1つ受け付ける。
- 宛先のドメインで、テナントを決める。どのテナントの relay のドメインでもなければ 550（オープンリレーにしない）。ローカル部によらず同じ応答にする。
- RCPT の応答は、生きている別名、廃番、存在しない別名、別名の形でないもの、返信用のアドレス（生きているもの、知らないもの）で、すべて同じ 250 にする。RCPT の時点では DB を引かない（不変条件10）。VRFY は smtp-server の既定の 252 で、宛先によらない。
- 名前の逆引きをしない（`disableReverseLookup`。不変条件7）。AUTH と STARTTLS は使わない（本番の受信の TLS は、P1 の受信の前段で決める）。
- 上限：1通 10 MiB、同時接続 100、無通信 60 秒で切る。送信元（IP、ドメイン）ごとのレート制限は、P1 の受信の前段（SES の受信など）で決める。

### 受け取ったメールの扱い

- 受け取ったメールの件名と本文は、DB に置かない。DATA の応答を返した後に、メモリの中で処理する（O-19）。
  - 鍵サービスの encrypt は 4KB まで（ADR 0013）で、メールは収まらない。データ鍵の操作を relay だけに足すと、鍵サービスの能力が増える。
  - DB に置いて後で処理する形にしても、P0 では得るものがない（配送は M4 ではメモリだけ）。
- 別名あて（と、どちらの形でもないもの）は、送信元ロックとリプレイの判定を DATA の応答の前に行い、失敗なら 550 で断る。どちらも、別名が生きているかどうかに関係なく決まる。別名の解決と配送は、応答の後に行う（生きているかどうかで、応答の本文と所要時間を変えないため）。
- 返信用のアドレスあては、どれも 250 で受け、送り主が企業か利用者かの判定から後を、応答の後に行う。

### 送信元ロック（plan 3-2）

- DNS は引かない。mailauth の DKIM の検証に渡すリゾルバは、登録した (d=, s=) の公開鍵だけを返す。
- 方式は rsa-sha256（鍵は 2048 ビット以上）と ed25519-sha256 だけ。rsa-sha1 は不合格（不変条件9）。
- d= と s= は登録と完全に一致させる。From のドメインは、d= と同じか、その下（DMARC の relaxed の整合）。
- l= 付きの署名は数えない。h= に from、to、subject、date、message-id を含み、from、to、subject を、メールの中の数より多く並べる（重ね署名）。From は1つ、To と Subject は1つまで。
- t= を必須にし、7日より古いもの、5分より先の時刻のものは断る。x= があれば、期限の前であること（O-23）。
- 断るときは 550 で、ログには理由の種類（`no_valid_signature`、`header_count`、`from_not_aligned`、`signature_time`）だけを残す。

### リプレイ

- `mac(relay_replay, lp('warifu/relay-replay/v1', d, s, b, 宛先のローカル部))` を `relay.replay` に置き、INSERT … ON CONFLICT で判定する。別名は MAC の入力にだけ使い、平文で置かない（不変条件4）。plan の「b= の HMAC と別名の照合用の HMAC の組」を、1つの MAC にまとめた。
- 再送は 250 で受けて捨てる（送信元の再試行と区別できないため）。
- 記録は、その署名を受け付ける間（t= から7日と x= の早いほう）に1時間を足した時刻まで残す。その後は、送信元ロックが署名の時刻で断るので、記録は要らない（plan 8章の「x= がない場合」。O-20）。

### 企業から利用者へ（中継の衛生）

- From は、登録簿の企業名（RFC 2047）と、返信用のアドレス（relay のドメイン）にする（O-22）。企業の元の DKIM は書き換えで壊れるので、受信側の DMARC は relay の署名で整合させる（plan 8章の p=reject の扱い）。表示名の検査は設定の時点で行う（制御文字、書式の文字、引用符、山括弧、バックスラッシュを拒否する）。
- 返信用のアドレスの先は、元の Reply-To（企業が署名した h= に reply-to があり、アドレスが1つだけのとき）、なければ From。署名の外で足された Reply-To には向けない。
- To は別名だけにする。Cc と Bcc は消す（O-18）。plan 3-2 は「別名以外の To と Cc は、relay 経由のアドレスに書き換える」としていたが、より強い形にした。
  - 利用者あての B2C のメールで、別名以外の宛先は、企業の内部の宛先か、ほかの利用者（企業の送り間違い）にあたる。書き換えても漏れはしないが、この利用者からその宛先へ送れる経路を、利用者が求めていないのに作ることになる。
  - 1通に宛先を多く並べるだけで、返信用のアドレスの行を多く作らせることになる。
- List-Unsubscribe は最初の1つだけを読む。mailto: は返信用のアドレスに替え、https: はそのまま残し、それ以外（http: など）は消す。List-Unsubscribe-Post は、値が `List-Unsubscribe=One-Click` で、https: が残ったときだけ残す（RFC 8058。受信側の事業者が POST するだけで、利用者のアドレスは企業に渡らない。O-25）。
- 開封通知（Disposition-Notification-To、Return-Receipt-To）、Reply-To、Sender、Return-Path、企業の DKIM-Signature と ARC の組、Authentication-Results、Received-SPF を消す。
- 件名と本文は、元のバイト列のまま残す。
- 封筒の MAIL FROM は `bounces@<relay のドメイン>` にする。

### 返信用のアドレスと返信の中継（plan 3-2）

- 返信用のアドレスは `r-<128ビットの乱数の base32（26文字）>@<relay のドメイン>`。企業から利用者へ1通届けるたびに作る（From と、List-Unsubscribe の mailto: ごと）。`relay.threads` には、トークンの `mac(relay_thread, …)`、利用者 ID、テナント、企業の側の宛先（`relay_queue` の鍵で、行の ID の文脈で暗号化したもの）、期限を置く。トークンも宛先も平文で置かない。
- 返信用のアドレスは、作ったテナントのドメインでだけ引ける（withTenant）。期限は30日（O-20）。
- 返信用のアドレスに来たメールは、次の順に判定する。
  1. 送信元ロックを通るもの：企業からのメールとして、リプレイの判定の後に利用者へ届ける（上の衛生を通す）。
  2. それ以外は、利用者からの返信の候補：From が1つで、本物のアドレスと一致し（大文字と小文字を区別しない）、そのドメインで DMARC が整合して pass したものだけを残す。DMARC の判定は mailauth の `authenticate` に注入したリゾルバで行う（不変条件7。BIMI は無効）。
  3. 企業へ送るもの（残すヘッダーと、本文の各部分）を検査する（`inspect.ts`）。本物のアドレスがあれば、企業へ送らず、利用者に固定の文面で差し戻す。中身を確かめられない部分があるときも、同じく差し戻す（O-27）。
     - 見る範囲：件名などの残すヘッダー、本文の各部分のヘッダー（ファイル名など）と中身、multipart の前置きと後置き、転送したメール（message/rfc822）のヘッダーと本文。
     - 戻すもの：転送符号化（base64、quoted-printable）、文字コード（charset。ISO-2022-JP などの TextDecoder が知るもの）、ヘッダーの encoded-word（RFC 2047）とパラメータの %xx（RFC 2231）、HTML の数値の文字参照と、アドレスに使う記号の名前の文字参照（`&commat;` など）、HTML のタグ、URL の %xx。比べる前に NFKC で全角を半角にし、書式の文字（ゼロ幅の空白、ソフトハイフンなど）を除き、大文字と小文字を区別しない。
     - 中身を確かめられない部分：添付ファイル（`Content-Disposition` が attachment のもの、またはファイル名（`filename`、`name`）の付いた部分。文字の形式でも同じ）、text/*、multipart/*、message/rfc822 以外の形式（画像、電子署名など）、知らない文字コードと転送符号化、HTML の属性や CSS の値の data: URI、境界の指定のない multipart、始まりか終わりの境界がない（途中で切れた）multipart、8段より深い入れ子、100 を超える部分。
  4. 企業の側の宛先を復号し、企業へ送る（3 の検査は、企業へ送るヘッダーを作った後に行う）。
- relay に DNS のリゾルバを渡していないときは、利用者からの返信を中継しない（確かめられないものは通さない。O-21）。M5 で、送信サービスの名前解決につなぐ。
- 企業へ送る返信のヘッダー：残すのは、件名、日付、MIME の項目、In-Reply-To と References だけ。From は返信用のアドレス、To は企業の側の宛先、Message-ID は relay で作り直し、`X-Warifu-Unauthenticated: 1` を付ける。Received、利用者の DKIM-Signature、X-* などは消える。
  - In-Reply-To と References からは、本物のアドレスのドメイン（とその下）の Message-ID を消す。利用者が自分の送ったメールに返信したとき、独自ドメインや事業者の名前が企業へ渡らないようにするため。
  - ARC の Authentication-Results は `dmarc=pass` だけにし、利用者のドメインを書かない。
- 中継した返信は、DMARC が pass していても本人の承認ではない（RP-45。不変条件1(d)(e)）。From と本物のアドレスの照合は、配送のための照合（不変条件1(e)）で、許可の判断には流さない。

### DKIM と ARC（plan 8章、ADR 0014）

- relay の DKIM と ARC の署名の鍵は、鍵サービスの `dkim`（RSA 2048、rsa-sha256）に置く。relay は `sign('dkim')` と `public_keys('dkim')` だけを持ち、秘密鍵は鍵サービスの外に出ない（CAP-04）。能力の表に、relay の `sign`・`public_keys`（dkim）と、MAC の用途 `relay_replay`、`relay_thread`、`message_id` を足した（ADR 0013 の見込みの `dkim_replay`、`reply_address` を、この名前にした）。
- 署名は relaxed/relaxed。正規化と本文の HASH は mailauth の内部の部品（`lib/tools.js`、`lib/dkim/header`、`lib/dkim/body`）を使い、署名だけを鍵サービスに頼む。mailauth の版を上げるときは、`packages/relay/test/dkim.test.ts` と `test/leak/t05-*` で、受信側の検証が通ることを確かめ直す。
- 企業から利用者へ、と、利用者から企業へのメールには、relay の DKIM（d= は relay のドメイン）を付け、ARC で封印する（i=1、cv=none）。割符からの知らせ（下）には DKIM だけを付ける。
- 鍵の入れ替え：ローカルでは、鍵サービスの起動ごとに作る。漏えいが疑われるときは、新しいセレクタで鍵を作り、DNS の公開鍵を差し替え、古いセレクタの記録を消す。定期の入れ替えと、DNS の更新の手順は P1（AWS アダプタ）。

### 外への配送（plan 8章、不変条件7）

- relay は外へつながない。配送は `Outbound`（封筒と、署名と封印を付けたメッセージ）に渡す。
- 本番の経路は、送信サービス（`packages/sender`）の内部 API に渡し、送信サービスが MX を引き、内部の IP を指す宛先を拒否して、接続する形にする。M4 ではメモリの実装（`MemoryOutbound`）だけを使い、送信サービスの内部 API は M5 で作る。
- 返信の DMARC の判定に使う DNS も、M5 で送信サービスの名前解決につなぐ。

### 内部配送 API（plan 2章、不変条件3、CAP-38）

- Unix ドメインソケットの HTTP で、`POST /v1/deliver` だけ。ほかのパスとメソッドは 404。ソケットの親のディレクトリは、このプロセスの利用者だけが開ける。
- 資格情報は `Authorization: Bearer idp.<32バイトの base64url>`。呼べるのは idp だけ。形が違う、知らない呼び出し元、長さが違うときも、ダミーと定数時間で比べてから 401 にする（鍵サービスと同じ。ADR 0013）。資格情報の渡し方は鍵サービスと同じで、起動の側が乱数で作って両方に渡す。本番は P1。
- 受け付ける入力は、種類と利用者 ID と、宛先確認のときだけ8桁のコード。種類は `email_verification`（`contacts.email_pending` に送る）と `email_changed_notice`（`contacts.email_previous` に送る）だけ。宛先、件名、本文を呼び出し側から受け取らない。本文は 1KB まで。余計な項目があれば 400。
- 応答は 202 か、固定の本文のエラーだけ。利用者がいるか、アドレスがあるかで変えない。送るところまでを同期で行い、送れなければ 503。
- idp は `RelayMailer`（warifu-core の `createRelayDeliveryClient`）で呼ぶ。UDS のクライアントの名前の一覧に `relay.sock` を足した（ADR 0013 の決定6）。

### 割符からの知らせ

- 宛先確認、旧アドレスへの知らせ、返信の差し戻し（アドレスが含まれていたときと、確かめられない部分があったときの2種類）は、relay の固定の文面（`templates.ts`）で送る。差し込むのは確認コードだけ（4桁ずつに区切る）。旧アドレスへの知らせと差し戻しには、操作のリンクもコードも入れない（plan 4章）。企業名、アドレス、利用者の情報を差し込まない。
- From は `割符 <notices@<知らせのドメイン>>` で、知らせのドメインの DKIM を付ける。

### 配送ログと保存期間

- `relay.delivery_log` には、Message-ID の `mac(message_id, …)`、向き（to_user、to_company）、結果（delivered、failed）、時刻、期限だけを置く。件名、本文、宛先は置かない（不変条件4）。
- 保存期間（O-20）：配送ログは30日、返信用のアドレスは30日、リプレイの記録は上の「リプレイ」のとおり。起動のときと1時間ごとに、テナントごとに期限の過ぎた行を消す。

### DMARC（ADR 0012 の決定11）

- mailauth 7.3.1 は、RFC 9989 の組織ドメインの決め方（DNS Tree Walk）に従っている（`lib/dmarc/get-dmarc-record.js`。8ラベル以上は7ラベルに縮めてから歩く、など）。Tree Walk の問い合わせも、注入したリゾルバを通る。

### 依存

- `mailauth` 7.3.1 と `smtp-server` 3.20.2 を relay の依存に足した。mailauth 7.3.1 が固定する `nodemailer` 10.1.0 と `undici` 8.11.2 には既知の脆弱性があるので、ルートの overrides で `nodemailer` 10.1.7 と `undici` 8.12.3 にした（`npm audit` は0件）。テストの送信側は、nodemailer を使わず、生の SMTP の会話（`test/setup/relay.ts`）にした（RCPT の応答と所要時間をそのまま見るため）。plan 9章の「nodemailer（テストの送信側）」は、送信サービス（M5）の依存に回す。

## 採らなかった案

- **受け取ったメールを暗号化して DB のキューに置く**：上の「受け取ったメールの扱い」。
- **From を企業のドメインのまま残し、ARC に頼る**：受信側が relay の ARC を信頼するとは限らず、企業の DMARC が p=reject なら落ちる。
- **別名以外の To と Cc を、返信用のアドレスに書き換える（plan 3-2 の元の案）**：上の「企業から利用者へ」。
- **RCPT の時点で別名を引き、生きていなければ 550 にする**：不変条件10に反する。
- **返信の DMARC の判定を、ライブラリの既定の DNS で行う**：不変条件7に反する。
- **nodemailer の addressparser で宛先を読む**：sender の外では import できない。読み切れない形を落とす、保守的な自前の読み取り（`singleAddress`）にした。
- **relay に derive_alias を持たせ、返信の From を別名にする**：relay の能力を広げる（ADR 0013 の表の性質「relay は derive_alias を持たない」）。返信用のアドレスで足りる。
- **確かめられない部分（添付ファイルや画像）を外し、文字の部分だけを企業へ届ける**（O-27）：差し戻しより使いやすいが、本文を書き換えることになる（plan 8章の「本文はバイト単位で変えない」、plan 3-2 の「本文の書き換えは P1」）。添付ファイルの扱いと合わせて P1 で決める。
- **確かめられない部分も、そのまま企業へ届ける**（O-27）：画像やファイルの中にある本物のアドレスを確かめられず、企業に渡りうる（原則2が弱まる）。

## 残るリスク

- **応答の後に落ちたとき、後の処理や配送が失敗したとき**：250 を返した後に relay が落ちると、そのメールは失われる。後の処理（別名の解決、署名）や配送が失敗しても、送信元は再送できず、配送済みとは限らない（配送ログに failed が残るだけ）。この形は、実配送のない M4〜M5 の開発とテストのための暫定とする（O-19）。実配送を始める前に、受け取ったメールの永続化と、後の処理と配送の再試行を決めて実装する（plan 10章 P1）。
- **返信は本人の承認ではない**：利用者のメールのアカウントを奪った者は、DMARC が pass する返信を中継させられる。企業は中継したメールを根拠にしない（RP-45）。
- **本文はそのまま**：引用や署名に、本物のアドレス以外の個人の情報（氏名、電話番号）があれば、企業へ届く。本物のアドレスの検査は、利用者がうっかり書いてしまうものを止めるためのもので、利用者が意図して崩した書き方（「at」と書く、空白で区切る、上の一覧にない名前の文字参照で書く）は対象にしない。本文への表示（警告文 D）は P1。
- **添付ファイルと画像を含む返信は中継しない**（O-27）：P0 では、添付ファイル（文字の形式のものを含む）、埋め込んだ画像、電子署名（S/MIME など）を含む返信は、差し戻しになる。利用者は文字だけで返信し直す。中身を確かめる方法と、通してよい形式は P1 で決める。メールソフトが自動で付けるもの（署名のロゴ画像、S/MIME の電子署名など）がある利用者は、返信のたびに差し戻される。オーナーは、P0 ではこの制約を受け入れると決めた（2026-10-28）。
- **利用者のメールソフトが付けた値**：MIME の境界の文字列、Date のタイムゾーン、件名の書き方などは残る。
- **返信用のアドレスを知る者**：30日の間、企業を名乗って送ろうとできる（送信元ロックで止まる）。利用者を名乗って送ろうとできる（DMARC で止まる）。
- **送信元ごとのレート制限がない**：同時接続、大きさ、宛先の数の上限だけ。
- **1024 ビットの DKIM の鍵の事業者**：返信の DMARC の判定でも、2048 ビット未満の RSA の署名は数えない（不変条件9、CRYPTREC）。利用者のメール事業者が 1024 ビットの鍵で署名していると、SPF で整合しない限り、返信は中継されない（差し戻しの知らせも出ない）。
- **登録の鍵の検査**：M4 では設定の時点で長さだけを見る（検証の時点で、mailauth が 2048 ビット未満を断る）。鍵の種類と長さの確認は M5 の登録で行う。
- **返信用のアドレスの先は固定**：やり取りの途中で企業が宛先を変えても追わない。

## 結果

- テスト（`test/leak/`）：
  - `t05-relay-sender-lock`：送信元ロックの条件を1つずつ外したもの（署名なし、d= の不一致、登録していない鍵、l=、重ね署名の欠け、h= の欠け、From・To・Subject の重複、From と d= の不整合、別の企業の鍵、古い・未来の t=）の拒否と理由、リプレイ、知らない別名、受信側での DKIM・ARC・DMARC の pass。
  - `t05-relay-hygiene`：開封通知、Cc、Bcc、Sender、Return-Path、企業の署名を消し、To を別名だけにすること。List-Unsubscribe の書き換えと one-click。本文のバイト列。ログに値が出ないこと。
  - `t05-relay-reply`：返信の中継（正規の返信、From の詐称、DMARC の不整合、本物のアドレスでない送り主、件名と本文の本物のアドレスの差し戻し（HTML の文字参照、タグ、%xx、全角、ゼロ幅の文字、ISO-2022-JP、encoded-word、転送したメール、ファイル名）、確かめられない部分の差し戻し（添付ファイル（文字の形式を含む）、画像、data: URI、知らない文字コードと転送符号化、境界のない multipart、終わりの境界がない multipart）、文字だけの multipart は通ること、署名の外の Reply-To、References、別のテナント、期限、企業からのメール、リゾルバがないとき）。
  - `t10-relay-rcpt`：RCPT、VRFY、2つ目の RCPT、DATA、relay のドメインでない宛先の応答が、宛先の状態によらず同じ。同じ接続の次のトランザクションと RSET の後も、1宛先の制限を保って受け付けること。
  - `x-relay-internal-api`：資格情報、パスとメソッド、形の違う要求、知らない利用者、ソケットの権限、idp から relay を経た宛先確認と旧アドレスへの知らせ。
- `packages/relay/test`：DKIM と ARC の署名（`dkim.test.ts`）、送信元ロックの方式と設定の検査（`sender-lock.test.ts`）、返信の検査の境目（`inspect.test.ts`）。
- 鍵サービス：`dkim` の鍵（RSA 2048）、relay の `sign`・`public_keys`（dkim）と MAC の用途 `relay_replay`、`relay_thread`、`message_id`。t08-keysvc-acl、t08-key-client-surface、t08-crypto-allowlist の期待の表を直した。
- マイグレーション 0005：`relay.replay`、`relay.threads`、`relay.delivery_log`。x-rls-fixed の一覧を直した。
- idp：`RelayMailer` を足した。`MemoryOutbox` は、relay を立てない開発とテストのために残す。
- 接続要件：RP-84 を直し、RP-86（`t=`）、RP-87（方式と From の整合）、RP-88（署名した Reply-To）を足した。適合テストの実装（rp-kit）は M9。
- CLAUDE.md の不変条件7の「relay から本物のアドレスへの配送経路」を、この ADR の決定に合わせて直した。
