# ADR 0022：company-api と送信サービス（テナント、別名の入れ替え、SET、外向きの通信）

- 状態：決定（仮）。2026-10-28 に、オーナーが「オーナーの確認」の O-28〜O-40 を、すべて既定の案のまま受け入れた（とりあえずの決定）
- 日付：2026-10-28

## 状況

M5（plan 10章）で、company-api と送信サービス（sender）を作る。範囲は、テナント、別名の入れ替え、SET、送信サービスと、テスト4の後半、6、11。plan、仕様書、ADR には、「M5 で決める」とした項目が残っていた。

- テナントの登録の形と、参加の状態の保存の形（ADR 0010、spec 04 の 3章）
- company-api が sub を扱う方法（spec 04 の 2章）
- テナントの JWT の有効期間と呼べる API の範囲、緊急停止のときに発行済みの JWT を無効にする方法（plan 2章、CAP-39）
- 緊急停止の実行の方法と、テナントの資格情報の入れ替えの手順（plan 2章、RP-74）
- P0 で送る SET のイベントの種類（spec 02 の 7章）
- 送信サービスの内部の接続の認証、ロールとスキーマ（plan 2章、ADR 0015）
- 企業向け API のレート制限の値（CAP-34）
- relay の配送と、返信の DMARC の判定の名前解決を、送信サービスにつなぐこと（ADR 0021）
- 企業の DKIM の公開鍵の種類の確認（ADR 0021 の残るリスク）
- ロゴの渡し方（RP-72）、`alias_lookup` の鍵の入れ替えの手順（ADR 0013）

## 決定

### 構成

- `packages/company-api`：Fastify 5 の企業向け API。トークンの検証に `jose` 6.2.12 を使う（oidc-provider と同じ版。新しい依存は増えない）。DB は `withTenant` だけ。
- `packages/sender`：外向きの通信の唯一の出口。内部 API は Unix ドメインソケットの HTTP で、TCP では待ち受けない。SMTP の送信に `nodemailer` 10.1.7 の SMTPConnection を使う（ルートの overrides と同じ版）。鍵サービスの資格情報と DB を持たない（CAP-21）。
- `packages/warifu-core`：sender の内部 API の約束（`sender/protocol.ts`）と、呼び出し元ごとのクライアント（`sender/client.ts`）。レート制限の窓（`rate-limit.ts`。idp と company-api が使う）。UDS のクライアントの名前の一覧に `sender.sock` を足した（ADR 0013 の決定6）。

### テナントの登録（O-28）

- テナントの登録は、DB に置かず、配備のときの静的な設定にする（`packages/company-api/src/config.ts`）。起動の時点で検査し、1つでも違えば起動しない。どのルートからも書き換えられない。P0 では管理 API を作らないので、登録を DB に置くと、書き込む経路（管理 API か、不変条件8の新しい例外）が要る。静的な設定なら、どちらも作らずに済む。
- 登録の中身：テナント ID、relay のドメイン（別名の右側。テナントごとに分ける）、参加の状態、移行中の期限、割符が確かめた入り口（と確かめた日）、緊急停止、API のクライアント（client_id と jwks。1〜4個）、SET の受け口（任意）。
- 参加の状態（ADR 0010）：参加の状態（`participation`）、移行中の期限（`migrationDeadline`）、割符が確かめた入り口（`verifiedEntries`）を、登録の形に持たせた。M9 で利用者の画面に出せるようになるまでは、`full`（完全な参加）、期限なし（`null`）、確かめた入り口は空（すべて「まだ残っている入り口」）だけを受け付け、それ以外なら起動しない。登録は静的な設定なので、企業向けのルートからも、ほかのどのルートからも書き換えられない（DB にこれらの列はない）。
- 企業の鍵は `jwks` で受け取り、EC の P-256 の公開鍵だけにする（`d`、`x5u`、`jwks_uri` は受け付けない。不変条件7・9）。client_id と relay のドメインは、テナントをまたいで重複させない。
- idp の登録簿（企業名、OIDC のクライアント）と relay の登録（企業名、送信元ロックの鍵）は、それぞれのサービスの静的な設定のまま残す。1つの登録簿にまとめるかは、M9 で警告文 I を出すときに決める。
- 企業の DKIM の公開鍵（relay の登録）は、起動の時点で、長さに加えて種類（SubjectPublicKeyInfo の AlgorithmIdentifier が rsaEncryption か Ed25519）を確かめる。RSA-PSS、EC、Ed448 などは起動しない（ADR 0021 の残るリスクを閉じた）。

### sub の扱い（O-29）

- 企業は sub で利用者を指す。company-api が sub から利用者を引けるように、idp が接続の同意のときに、sub の索引（`aliases.subject`：テナント ID、利用者 ID、sub）を置く。sub の導出（`pairwise_sub`）は、これまでどおり idp だけ（ADR 0018）。company-api に `pairwise_sub` の MAC を与えない。
- sub は秘密ではない（CLAUDE.md の用語）ので、平文で置く。企業に渡す値なので、テナントの中でだけ引ける（RLS）。idp は置けるが読めない（列単位の GRANT）。company-api は読むだけ。

### 別名の入れ替え（plan 3-2、O-37）

- `POST /v1/aliases/rotate { sub }`：テナントの JWT のテナントの中で sub から利用者を引き、次の世代の別名を鍵サービスで導いて、照合用の MAC だけを置く。返すのは新しい別名だけ。
- 照合用の MAC は一意なので、前の世代の別名は二度と割り当てられない。最新でない世代は、relay の解決関数が返さない（廃番）。前の別名あてのメールは、同じ 250 で受けて届けない（不変条件10。ADR 0021）。
- 同じ利用者の入れ替えが同時に来たら、世代の主キーで片方が失敗するので、読み直して3回まで試す。
- 入れ替えは1件ずつ。一括の入れ替えは作らない（一括の操作には、テナントの側の2人承認と実行までの遅延が要る。plan 2章）。企業が自分で頼むので、入れ替えの SET は送らない。監査ログに世代の番号だけを残す（sub と別名は入れない）。

### テナントの JWT（RP-73、CAP-39、O-30・31）

- トークンの発行（`POST /token`）：`grant_type=client_credentials` と、`private_key_jwt`（RFC 7523）の client assertion だけ。
  - assertion は ES256 で、登録した jwks の鍵で検証する。`iss` と `sub` は client_id、`aud` はトークンのエンドポイントの URL だけ（1つの文字列。ほかの宛先と並べた配列は、URL を含んでいても断る。idp と同じ。ADR 0006）、`exp`・`iat`・`jti` は必須、`iat` から5分まで、`exp` は5分先まで（時刻の許容は30秒）。
  - `jti` は期限まで覚えて、2回目を断る。覚えきれないとき（10万件）は、断る側に倒す。
  - 失敗は、理由によらず同じ 401 `invalid_client`。知らない項目、`client_secret`、同じ項目の2回は 400 `invalid_request`。
- アクセストークン：鍵サービスの `tenant_jwt` の鍵で ES256 の署名をした JWT（`typ` は `at+jwt`。RFC 9068 の形）。
  - クレームは `iss` と `aud`（company-api）、`sub` と `client_id`（クライアント）、`tenant_id`、`scope`（`company_api` の1つ）、`iat`、`exp`（5分）、`jti`（乱数）。リフレッシュトークンは出さない。
  - 検証のたびに、テナントとクライアントが登録簿にあり、緊急停止していないことを確かめる。テナントは要求の本文から取らず、トークンから決める。
  - 公開鍵は短い間だけ覚え、知らない `kid` のときだけ引き直す（10秒に1回まで）。
- 呼べる API の範囲：別名の入れ替えと、検証の SET の依頼だけ（`scope` は1つ）。
- 発行済みのトークンの無効化：緊急停止（`suspended`）にして配備し直すと、その時点から、発行済みのトークンも断る。全テナントのトークンを無効にするときは、鍵サービスを起動し直す（`tenant_jwt` の鍵は起動ごとに作る）。

### SET（RP-50、O-32）

- 署名は鍵サービスの `set` の鍵で ES256（`typ` は `secevent+jwt`）。`iss` は company-api、`aud` はテナント ID、`jti` はイベントごとの128ビットの乱数（テナントをまたいだ通番にしない）、`iat` は初めて送る時刻。`exp` は付けない。
- 検証の鍵は `GET /jwks` で配る（ES256 の公開鍵だけ）。
- P0 で送るイベントは、検証のイベント（SSF の `verification`。企業が受け口を確かめるために頼む。`state` は64文字まで）だけ。回復（`recovered_at`）のイベントは M8 で足す。
- 利用者に結び付くイベント（M8）は、テナントごとにランダムに遅らせて送る（テスト12）。検証のイベントは企業が自分で頼むので、遅らせない。
- 送り方は RFC 8935 の push。送るものは `company_api.set_outbox` に置き、署名した SET は置かない（不変条件4。送るときに署名する）。
  - 1件ずつ「借りて」（回数を足し、2分は次に渡さない）、トランザクションを閉じてから sender に渡す。
  - 送れたら消す。送れなければ、1分、5分、30分、2時間、6時間と間を空けて送り直し、6回で諦めて消す（ログには件数だけ）。`jti` と `iat` は送り直しでも同じにする。
  - 緊急停止したテナントと、受け口のないテナントには送らない。受け口のないテナントの依頼は 409。
- company-api は5秒ごとに送信待ちを見る。

### 送信サービスの内部 API（CAP-38、O-33）

- 資格情報は、呼び出し元ごとの `Authorization: Bearer <relay|company-api>.<32バイトの base64url>`（鍵サービス、relay の内部配送 API と同じ形）。形が違う、知らない呼び出し元、長さが違うときも、ダミーと定数時間で比べてから 401 にする。
- 口は3つで、呼び出し元ごとに分ける（`SENDER_ACL`）：`POST /v1/webhook`（company-api）、`POST /v1/mail` と `POST /v1/dns`（relay）。ほかのパスとメソッドは 404。呼び出し元に許していない口は 401。本文は口ごとの上限（16KB、14MB、1KB）までで、余計な項目があれば 400。接続先の IP やヘッダーを指定する口はない。
- 応答は、送れたか、送れなかった理由の種類だけ。URL、宛先、IP を、ログにも応答にも出さない。
- ロールとスキーマ：sender は DB を使わない（ADR 0015 の未定を閉じた）。

### 宛先の検査（plan 2章、CAP-22、RP-51、O-33・34）

- 接続してよいのは、公開のユニキャストのアドレスだけ。IANA の特殊用途のアドレスの登録簿にあるもの、プライベート、ループバック、リンクローカル（IMDS を含む）、CGN、マルチキャスト、文書用、ベンチマーク用、IPv4 を埋め込んだ IPv6（`::ffff:0:0/96`、NAT64、6to4）は拒否する。IPv6 は `2000::/3` の中だけ。
- 名前は、A と AAAA の答えを全部見て、1つでも公開でないアドレスがあれば断る。接続は、確かめたアドレスに直接つなぐ（名前を引き直さない。DNS rebinding 対策）。
  - node:https は、`agent: false` のときに自前のエージェントを作り、`createConnection` を使わずにホスト名を名前解決する。そこで、接続を作る関数を差し替えたエージェントを要求ごとに作り、`lookup` も確かめたアドレスだけを返すものにした。
- Webhook：URL は https、ポートは 443 だけ、ホストは名前（IP の直書き、localhost、1つのラベルの名前は不可）、利用者情報とフラグメントなし。TLS の SNI と証明書の検査はホスト名で行う。リダイレクトに従わない（3xx は失敗）。全体の時間切れは10秒、応答は16KB まで読んで捨てる。つながらなかったときだけ、次のアドレスを試す（2つまで）。
- メール：宛先のドメインの MX を引く（5つまで、優先度の順）。MX がなければ（ENODATA）ドメインそのものに送る（RFC 5321）。null MX（RFC 7505）なら送らない。MX のホストのアドレスが1つでも公開でなければ、そのホストには送らない。STARTTLS は相手が対応していれば使い、証明書は検査しない（MTA-STS と DANE は P1。O-34）。5xx で断られたら、ほかの MX にも送らない。再試行はしない（呼び出し元が決める）。
- 名前解決：relay の返信の DMARC の判定に使う TXT、MX、A、AAAA だけ。名前の形が違うもの（localhost、1つのラベル、IP の形）は問い合わせない。答えは64件、32KB まで。どこにもつながない。
- 名前解決の実体：本番は OS の設定のリゾルバ（node:dns/promises の Resolver。時間切れ2秒、2回）。テストは模擬のリゾルバと、確かめた後の最後の接続（TLS と TCP のソケット）だけを差し替える。宛先の検査は差し替えられない。

### relay の接続（ADR 0021、O-35）

- `SenderOutbound`：relay の Outbound の実装で、署名と封印を付けたメッセージを sender の `/v1/mail` に渡す。断られたら、理由の種類だけを持つ例外にする（relay のログには理由の種類だけが残る）。
- `senderResolver`：mailauth に渡すリゾルバで、sender の `/v1/dns` を通す。TXT、MX、A、AAAA のほか（PTR など）は、問い合わせずに ENOTFOUND にする。
- 実配送を始める前に、受け取ったメールの永続化と、後の処理と配送の再試行を作る（ADR 0021 の O-19）。それまでは、この出口を使うのは開発とテストだけにする。

### 封じ込めと入れ替え（plan 2章、RP-74、O-38・39）

- 緊急停止は、運用の手順として、静的な設定を直して配備し直す（管理 API も、不変条件8の新しい例外も作らない）。
  - API と SET：company-api の登録で `suspended: true` にする。トークンを出さず、発行済みのトークンも断り、SET を送らない（送信待ちは残す）。
  - 送信（企業から利用者へのメール）：relay の登録から、そのテナントを外す（relay のドメインあては 550 になる）。
  - ログイン：idp の登録簿から、そのテナントのクライアントを外す。CIBA の停止は M7。
- テナントの資格情報の入れ替え：新しい公開鍵を jwks に足して配備し（4つまで）、企業が新しい鍵に切り替えた後に、古い鍵を外して配備し直す。DKIM の鍵は、relay の登録のセレクタと公開鍵を新しいものにして配備し直す。別名の再発行は、入れ替えの後に行う。定期的な入れ替えの周期は P1。
- `alias_lookup` の鍵の入れ替え（全世代の索引の作り直し）は、本番の運用の手順として P1 で決める（ADR 0013 の「手順は M5」を移した）。アプリのロールには、世代の UPDATE を与えていないため。

### レート制限（CAP-34、O-36）

| 名前 | キー | 上限 |
|---|---|---|
| tokenByIp | 送信元の IP（クライアントを確かめる前） | 60回／分 |
| tokenByClient | client_id（確かめた後） | 30回／分 |
| apiByTenant | テナント（すべての API） | 600回／分 |
| rotateByTenant | テナント（別名の入れ替え） | 60回／分 |
| verificationByTenant | テナント（検証の SET の依頼） | 10回／時 |

- 上限を超えたら 429 `rate_limited`。窓の数え方は、idp と同じ（プロセスのメモリの固定窓）。

### ロゴ（RP-72、O-40）

- P0 では、ロゴを受け付けない。承認画面は登録簿の企業名だけを出す（DESIGN.md 原則2）。ロゴの渡し方、受け付ける形式と検査は、承認画面を作る M6・M7 か P1 で決める。

### 依存と lint

- `jose` 6.2.12（company-api）、`nodemailer` 10.1.7（sender）、`fastify` 5.12.7（company-api）を足した。どれも package-lock.json にすでにある版で、取り込む版は増えない。
- lint（`biome.json`）で、`jose` の `createRemoteJWKSet`、`customFetch`、`jwksCache`（鍵を外から取りに行くもの）の import を禁じた。禁じる範囲を狭める変更はない。

## 採らなかった案

- **テナントの登録を DB に置く**：書き込む経路として、管理 API か、不変条件8の新しい例外が要る。参加の状態を企業向けのルートから書き換えられないことも、列単位の GRANT に頼ることになる。
- **company-api に `pairwise_sub` の MAC を与える**：sub から利用者は逆に導けないので、索引はどのみち要る。sub を導ける能力を idp の外に広げる理由がない。
- **アクセストークンを、DB に置く不透明なトークンにする**：RP-73 は JWT を求めている。DB にトークンを置くと、不変条件4の平文の対象になる。
- **送信待ちに、署名した SET を置く**：不変条件4（SET を平文で残さない）に反する。
- **Webhook のポートを自由にする**：内部のサービスのポートに向けさせる余地を減らすため、443 だけにした。
- **名前の答えのうち、公開のアドレスだけを使う**：公開と内部を混ぜた答えは、それ自体が不審なので、名前ごと断る。
- **SMTP の STARTTLS の証明書を必ず検査する**：MX の証明書は、名前の合わないものが多く、配送が落ちる。MTA-STS と DANE で検査する形を P1 で決める。

## 残るリスク

- **送信の実配送の前提**：受け取ったメールの永続化と再試行がないまま、relay の出口を sender につなぐと、応答の後に落ちたメールは失われる（ADR 0021 の O-19）。
- **MX への配送の盗聴**：STARTTLS の証明書を検査しないので、経路の途中で中継されうる（MTA-STS と DANE は P1）。
- **SET の受け口の DNS**：送るたびに名前を引いて検査するが、企業の DNS を操れる者は、受け口を外部の別のサーバーに向けられる（SET は企業の鍵ではなく割符の鍵で署名しているので、受け取った者が偽造はできない）。
- **テナントの JWT の有効期間**：緊急停止は配備し直すまで効かない。それまでの間（と、停止の前に発行した5分のトークン）は、侵害された資格情報で呼べる。
- **レート制限はプロセスごと**：複数のプロセスで動かすと、上限はプロセスの数だけ大きくなる（本番の構成は P1）。
- **同じ IP の送信元**：トークンの要求の上限は IP ごとなので、同じ送信元の IP を使う別の企業の要求も数える。
- **sub の索引**：idp が接続の同意のときに置くので、M5 より前に接続した利用者には索引がない（PoC なので移し替えは作らない）。

## 結果

- テスト（`test/leak/`）：
  - `t04-alias-rotation`：入れ替えの後、前の別名あてのメールは届かず、新しい別名あてだけが届くこと。ID トークンの sub で入れ替えると、次の ID トークンの別名が新しい世代になること。照合用の MAC の一意制約で前の値が戻らないこと（UPDATE と DELETE もできない）。企業に渡る値の一覧。
  - `x-company-api-tenant`：A社のトークンでB社の sub を入れ替えられないこと。トークンの書き換え（テナントの差し替え、自分の鍵、none、HS256、期限切れ）と、client assertion の誤り（他社の client_id、aud、aud の配列、期限、iat、ES384、HS256、再送、知らない client_id）が、同じ 401 になること。緊急停止。レート制限。境界の外で行が見えず、参加の状態の列がないこと。
  - `x-company-api-routes`：ルート一覧（5つ。GET の HEAD を含む）。企業のトークンで参加の状態や確かめた入り口を変える口がないこと。知らないパスと違う Host の固定の本文。
  - `x-company-api-set`：SET の署名、aud、jti、events。送り直しで jti と iat が同じで、6回で諦めること。ログに URL と SET が出ないこと。送信待ちの表に SET の列がないこと。
  - `t11-sender-ssrf`：アドレスの検査、URL の形、内部を指す名前、DNS rebinding、リダイレクト、証明書の名前、内部を指す MX と null MX、ログ。
  - `x-sender-internal-api`：資格情報、呼び出し元ごとの口、パスとメソッド、本文の形、名前解決の口、ソケットの権限。
  - `x-relay-sender`：relay から sender を通った配送、内部を指す MX への配送を止めること、名前解決の口。
- `packages/company-api/test/config.test.ts`：参加の状態、移行中の期限、確かめた入り口（M9 までは full・期限なし・空だけ）、jwks の鍵、受け口の URL、重複、issuer の検査。
- `packages/relay/test/sender-lock.test.ts`：企業の DKIM の公開鍵の種類の検査。
- 鍵サービス：`tenant_jwt` と `set`（ES256）の鍵と、company-api の `sign`・`public_keys`。t08-keysvc-acl、t08-key-client-surface、keysvc の acl.test の期待の表を直した。
- マイグレーション 0006：`aliases.subject` と `company_api.set_outbox`。x-rls-fixed の一覧を直した。
- idp：接続の同意のときに sub の索引を置く。レート制限の窓は warifu-core のものを使う。
- CLAUDE.md の不変条件7の注記を、この ADR に合わせて直した。

## オーナーの確認

2026-10-28 に、オーナーが O-28〜O-40 を、すべて既定の案のまま受け入れた。とりあえずの決定（仮）なので、見直すときは、その行と、関係する plan・仕様書・コード・テストを同じ PR で直す。O-36 のレート制限の値は、根拠のない仮置きのまま。

| ID | 判断すること | 決めたこと（既定の案のまま） |
|---|---|---|
| O-28 | テナントの登録の置き場所 | 配備のときの静的な設定（DB に置かない）。参加の状態、移行中の期限、確かめた入り口を持たせ、M9 までは full・期限なし・空だけを受け付ける（ADR 0010） |
| O-29 | sub の扱い | idp が接続の同意のときに sub の索引を置き、company-api は読むだけ。sub は平文で置く |
| O-30 | テナントの JWT | ES256 の JWT、5分、scope は1つ、リフレッシュトークンなし。緊急停止で発行済みも断る（配備し直した時点から） |
| O-31 | client assertion | aud はトークンのエンドポイントの URL だけ。iat から5分、exp は5分先まで、jti は1回だけ |
| O-32 | SET | P0 は検証のイベントだけ。aud はテナント ID。6回（1分〜6時間）送り直して諦める。検証のイベントは遅らせない |
| O-33 | Webhook の宛先 | https、443 だけ、名前だけ。答えがすべて公開のアドレスのときだけ、確かめたアドレスに直接つなぐ。リダイレクトに従わない。10秒、16KB |
| O-34 | メールの配送の TLS | STARTTLS は相手次第で、証明書は検査しない（MTA-STS と DANE は P1） |
| O-35 | relay の出口を sender につなぐ時期 | 経路は作ったが、実配送は O-19（永続化と再試行）の後 |
| O-36 | 企業向け API のレート制限 | 上の表のとおり |
| O-37 | 別名の入れ替え | 企業が sub で1件ずつ頼める。一括はない。入れ替えの SET は送らない |
| O-38 | 緊急停止の手順 | 静的な設定を直して配備し直す（company-api の suspended、relay と idp の登録から外す） |
| O-39 | テナントの資格情報の入れ替え | jwks に新しい鍵を足して切り替えた後、古い鍵を外す。定期の入れ替えは P1 |
| O-40 | ロゴ | P0 では受け付けない（M6・M7 か P1 で決める） |
