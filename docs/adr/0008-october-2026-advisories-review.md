# ADR 0008：2026年10月の注意喚起を受けた、計画と仕様書の見直し

- 状態：採用（2026-10-20 にオーナーが確認した）
- 日付：2026-10-20

## 状況

2026年9〜10月には、国内で大規模な個人情報の漏えいの公表が相次いだ。2026年10月に、次の資料が公表された。オーナーがこれらを共有した。

- JPCERT/CC の注意喚起 JPCERT-AT-2026-0030（10-08 公開、10-09 更新）
- JPCERT/CC Eyes の調査「連続不正アクセス事案の攻撃手法に関する調査」（2026-10）
- 国家サイバー統括室の「不正アクセスによる漏えい等の事案を踏まえた対応について」（10-09）と、各機関の注意喚起をまとめた「お知らせ」（10-14）
- ラックの解説「国内で相次ぐWebシステムからの情報漏えい」（10-15。原文を取得できなかったため、2026-10-22 に standards.md と plan から削った。ADR 0012）

どれも、状態は「抜粋のみ」である。公式のページと報道の、検索結果の抜粋だけによる。原文は、この環境から取得できなかった（イシュー #2、M0）。資料の要点と確認状況は、[docs/standards.md](../standards.md) の「脅威の動向」を正とし、ここには写さない。この ADR は、これらの資料を個別の事案に結び付けない。

計画の主張（plan 1-2）は、漏えいがどの経路で起きたかを問わない。資料が挙げる経路（公開アプリの解析、管理用・内部の API、BI ツール、既知の脆弱性、供給網）は、この主張の前提を変えない。そこで、割符自身の守り、接続要件、残るリスクの書き方に抜けがないかを、資料に照らして点検した。

同じ見直し（2026-10-20）では、文書の点検で見つかった食い違い（ADR 0006 に合わせた sub の書き方、ADR にあった残るリスクの plan 1-2 への追記など）も直した。それらは、この ADR の決定には含めない。

## 決定

2026-10-20 に、計画と仕様書を次のように直した。

1. **主張の範囲**（plan 1-2、01 の 3章）：主張は漏えいの経路を問わないこと、漏えいそのものを防ぐことは主張しないことを書いた。
2. **残るリスク**（plan 1-2、01 の RR-13、03 の 5章）：「企業の側の漏えいそのもの」を足した。割符は、企業のシステムからの漏えいを防がない。紐付けの前から企業が持っている本物の連絡先は、企業が消さない限り残る。原則2の達成範囲も、割符に参加した後に企業へ渡すものに限って書いた（plan 1-1、PRN-02）。
3. **割符の内部の API**（plan 2章、CAP-27、CAP-38、TB-3、TH-39）：keysvc、relay の内部配送 API、sender を、外から届かないようにする。呼べる資格情報と、内部の接続の組を限る。
4. **レート制限**（plan 2章、CAP-34、TH-37）：対象に、CIBA の poll と企業向け API を足した。値を決めるマイルストーンを、機能ごとに書いた。
5. **トークンの期限と無効化**（plan 2章、CAP-39）：用途に要る範囲と期間に限り、漏えいが疑われるときに無効にできるようにする。
6. **配信物は解析される前提**（plan 2章、CAP-37、TH-15）：PWA と承認系の画面に、資格情報、鍵、API キーを含めない。認証と認可の判断は、サーバーで行う。
7. **封じ込め**（plan 2章、02 の 9章、04 の 5章）：P0 では運用の手順として行う。実行の方法は、管理 API も不変条件8の新しい例外も作らない方法から選ぶ。
8. **鍵と資格情報の入れ替え**（plan 2章、CAP-07）：漏えいが疑われるときの失効と入れ替えの手順を持たせる。
9. **運用者のアクセス**（plan 2章、TH-60）：本番の環境と、リポジトリや CI の管理には、フィッシング耐性のある多要素認証で入る。
10. **検知と初動**（plan 2章、04 の 7章）：API の利用と拒否を監視できるようにする。監視に使うログにも、不変条件4を適用する。
11. **企業の API の認可**（plan 3-3、RP-08、TH-44）：要求ごとに、その利用者が対象に触れてよいかをサーバーで確かめる。番号だけで対象を引かない。
12. **管理用・内部の経路と委託先**（plan 3-3、RP-13、RP-29、RP-33）：操作ごとの承認と、sub の書き換えの禁止を、管理用・内部の API、管理画面、バッチの処理にも適用する。委託先にも接続要件を守らせる。
13. **企業の資格情報と判断の置き場所**（plan 3-3、RP-75、RP-76、AS-10、TH-45）：企業が管理するサーバーの中だけに置き、公開アプリと公開のリポジトリに含めない。
14. **紐付けの前からある連絡先**（plan 3-3、RP-35）：保有の必要性を見直して減らすことを推奨する。
15. **企業の側のシステムの管理**（plan 3-3、RP-97、RP-98）：従業員と委託先のフィッシング耐性のある多要素認証と、公開している資産の継続的な点検を推奨する。
16. **サービスの資格情報**（plan 8章、CAP-06）：リポジトリ、コンテナのイメージ、設定ファイル、配信物に平文で置かない。
17. **保存期間**（plan 8章、CAP-19）：保存するものごとに保存期間を決め、過ぎたら消す。
18. **DB につなぐもの**（plan 9章、CAP-18、TH-35）：BI ツール、分析基盤、SQL を自由に書ける管理ツールは、割符の DB につながない。そのためのログインロールも作らない。
19. **依存の更新**（plan 9章、TH-66）：版の完全な固定、`npm ci --ignore-scripts`、アクションの SHA 固定、Dependabot（M1 で設定した）。既知の脆弱性の修正は、週ごとの更新を待たずに取り込む。
20. **外注先**（plan 10章、spec/README.md、ATK-09、TH-66）：外注先（再委託先を含む）にも、不変条件と仕様書の要件を適用する。
21. **P1 の範囲**（plan 10章）：「本番の運用の手順」に、検知と監視、初動、運用者のアクセス、既知の脆弱性の修正の取り込み、外注先の管理、定期的な脆弱性診断と公開している資産の点検、集計の扱いを入れた。
22. **ルート一覧のテスト**（plan 11章 テスト6、04 の 9章）：連絡先・認証器・回復協力者・回復の設定を変えるルートは、利用者自身が plan 4章の手順で行う idp のルートだけにする。管理用のルートにも、企業向けのルートにも置かない。
23. **人が行うこと**（plan 12章）：脆弱性診断を定期的に受ける。本番で公開する資産の一覧を、ルート一覧のテストと突き合わせる。公開した後に、main のブランチ保護（Code Owners のレビューを必須にする）と、GitHub の Dependabot の security updates、secret scanning と push protection を有効にする。
24. **脅威モデル**（03）：ATK-02 の持ち物に、アプリの解析で特定した API のエンドポイントやキーと、AI を使ったスキャンを足した。ATK-09（供給網を通じた侵害）を足した。

## 採らなかった案

- **アクセス元の地域の制限**（JPCERT-AT-2026-0030 の推奨の1つ）：
  - 利用者がどの地域からつないでいるか（IP アドレスから推した地域など）を、割符が扱うことになる。割符は、利用者の属性をできるだけ集めない設計にしている（P0 では電話番号も集めない）。
  - 地域は肯定リスト（不変条件1）にないので、もともと本人確認の根拠にはならない。拒否の方向にだけ使うとしても、そのために位置を集めることになる。
  - 割符は、地域を限ったサービスとしては設計していない。
  - レート制限のキーには送信元の IP を使うが、それは回数を数えるためで、地域を推して判断に使うものではない。
  - 企業が自社のシステムに地域の制限をかけるかは、接続要件では扱わない。
- **緊急停止のための管理 API や、運用者が DB を直接書き換える方法**：P0 では管理 API を作らない（不変条件2）。DB の境界の例外も増やさない（不変条件8）。
- **集計のために、割符の DB に BI ツールなどをつなぐロールを作る案**：不変条件8の例外にない。運用で集計が要るときの扱いは、P1 で決める。
- **検知と監視の仕組み、既知の脆弱性の修正の取り込み方を M10 で決める案**：M10 の範囲は、横断テストと仕様書の確定である。どちらも本番の環境と運用に結び付くので、P1 の「本番の運用の手順」で決める。依存の更新の PR は、M1 から Dependabot で週に1回出している。
- **紐付けの前からある連絡先を消すことを、いま必須にする案**：既存会員の紐付けの手順と合わせて決める必要がある。いまは推奨（RP-35）にとどめ、必須にするかは M9 で決める。
- **企業の側のシステムの管理（RP-97、RP-98）を必須にする案**：割符の対策の範囲の外にあり、守られていなくても割符の側では検出できない。推奨にとどめる。

## 結果

この PR では、次のことを決めていない。

- レート制限の値：M3（ログイン、宛先確認の送信）、M5（企業向け API）、M7（窓口コード、CIBA の要求と poll）、M8（回復の開始、協力者への依頼）。SMTP の受信に上限をかけるかは M4。
- トークンの期限：ID トークンとセッションの有効期間、リフレッシュトークン、パスキーを削除・一時停止したときのセッションの扱いは M3。テナントの JWT の有効期間と範囲、緊急停止のときの無効化は M5。操作ごとの承認の有効期間は M7。
- 緊急停止の実行の方法：M5。
- 鍵と資格情報の入れ替えの手順と周期：保存用の鍵、照合用の HMAC 鍵、署名の鍵とサービスの資格情報は M2、sub の導出に使う鍵は M3、DKIM と ARC の鍵は M4、テナントの資格情報は M5、別名の導出鍵は P1（ADR 0005）。
- 内部の接続の認証：keysvc は M2、relay の内部配送 API は M4、sender は M5。本番のネットワークの設定は P1（AWS アダプタ）。
- サービスの資格情報の渡し方：ローカルは M2、本番は P1（AWS アダプタ）。
- 保存期間：保存物ごとに、それを作るマイルストーンで決める。`x=` がない場合のリプレイの判定の記録は M4、失効した窓口コードの記録は M7、別名の照合用の HMAC の残し方は M3。退会の流れは P1 で扱う（2026-10-20 にオーナーが確認した）。
- 企業のモバイルアプリから、企業のサーバーを通して割符のログインを使う方法：M3。
- 管理用・内部の経路を適合テストで確かめる方法と、紐付けの前からある連絡先を消すことを必須にするか：M9。
- P1 の「本番の運用の手順」：検知の対象と監視の仕組み、初動の手順と点検の頻度、運用者のアクセスの手順、既知の脆弱性の修正を取り込む手順と目安、外注先の管理、定期的な脆弱性診断の頻度、公開している資産の点検の手順、集計の扱い。本番の実行環境の更新の手順は、P1 の AWS アダプタで決める。
- 新しく足した脅威のうち、テストの割り当てがないもの（TH-39 の一部、TH-44、TH-45、TH-66 など）にテストか監査の項目を割り当てるか：M10（03 の 4-9）。
- DESIGN.md の段階2の問い（2章）と固定文 S（3章）は、RP-20 と RP-24 に合わせて、電話のほかにメール、SMS、チャットなども扱うように広げた（2026-10-20 にオーナーが確認した）。
- 資料の原文の照合：M0（イシュー #2）。抜粋と原文が食い違ったら、設計を見直して、この ADR を更新する。
  - 2026-10-22 に、ラックの記事を除いて原文で照合した（ADR 0012）。抜粋になかった推奨（JPCERT-AT-2026-0030 の HTTP メソッドでの制限と、顧客への二次被害の防止の呼びかけ、JPCERT/CC Eyes のリダイレクト後の宛先の検証など）はあったが、この ADR の決定の範囲に入るか、企業の側の対応で、決定は変えない。ラックの記事は、lac.co.jp に接続できず照合できなかったので、引用を削った。この ADR の決定は、どれも JPCERT/CC か国家サイバー統括室の資料（原文で確認済み）の推奨にも当たり、削っても根拠を失わない。
