# ADR 0024：接続する企業の前提条件（必須、望ましい、接続の前に測ること）

- 状態：提案（オーナーのレビュー待ち）
- 日付：2026-10-29

## 状況

接続要件（spec 02 の RP-xx）は、企業が守ることを要件ごとに並べたものである。最初に接続する企業を探すときには、別の見方が要る。その企業がそもそも接続できるのか、接続して効果が出やすいのか、接続の前に何を確かめるべきかである。

2026-10-29 に、最初の企業の候補を検討した。その中で、次のことが分かった。

- いちばん合いそうな企業でも、#30 の初回移行の条件（ADR 0020）では、自分で移れる会員が少ないかもしれない。
  - 移行に使える旧パスキーは、登録・追加・回復の経緯を確認できるものだけである。弱い確認手段で後から付けたパスキーは、古くなっても適格にならない。
  - パスワードと SMS の OTP でログインした後に登録してもらったパスキーは、この「弱い確認手段で付けたもの」に当たりうる。
- 窓口でアプリを使えない人には、一般的な案内とアカウントの一時停止しかできない（ADR 0019、RP-60）。この人が多い企業では、窓口の負担が増える。

オーナーは、対象の業種は文書ではぼかし、そのかわり「何が望ましいか」「何がないと接続できないか」を前提条件として書く、とした。

## 決定

### 業種を書かない（O-56）

前提条件と接続要件は、業種の名前ではなく、企業の状態で書く。最初に想定する業種を、前提条件として書くことはしない。デモの企業（demo-rp）をどんな会社にするかは、見せ方の判断なので、別に決める（plan 10章の M9）。

### ないと接続できない（必須。O-57）

どれも、すでに接続要件にあるものを、企業の側から見た前提にまとめ直したものである。新しい要件は足していない。

| # | 前提 | 対応する接続要件 |
|---|---|---|
| 1 | 自社のアプリかウェブで、利用者が割符のログインと step-up を受けられる。窓口で本人に関わる手続きをするなら、通話中に自社の認証済み画面を開いてもらう運用にできる | RP-04、RP-10、RP-20 |
| 2 | 会員を、割符の企業ごとの ID（`iss` と `sub` の組）だけで識別できる。メールアドレスや別名で会員を探さない | RP-01、RP-03、RP-05、RP-08 |
| 3 | 紐付けた会員については、メールと SMS による再設定と、旧ログインを閉じられる。移行中の参加なら、決まった入り口だけを期限まで残してよい | RP-30〜32、RP-14〜16 |
| 4 | 窓口で、氏名や生年月日などで本人を確かめない運用に変えられる。確かめられない人には、一般的な案内とアカウントの一時停止だけにする | RP-07、RP-27、RP-60、RP-61 |
| 5 | 高リスクの操作（配送先・返金先・支払い手段の変更、解約、高額の取引など）は、その操作に結び付いた承認だけで通す。管理画面や委託先にも例外を作らない | RP-10、RP-12、RP-13 |
| 6 | 割符との接続に使う資格情報と、許可するかどうかの判断を、自社のサーバーの中だけに置く | RP-70、RP-75、RP-76 |
| 7 | 委託先（コールセンター、送信事業者など）にも、同じ要件を守らせられる | RP-29、RP-75 |

### あると望ましい（O-58）

満たさなくても接続はできる。ただ、満たしていないと、効果が出にくいか、移行や窓口の負担が大きくなる。

| # | 前提 | 理由 |
|---|---|---|
| 1 | 会員の多くが、すでにパスキーを使っている | 割符のパスキーへの切り替えの抵抗が小さい |
| 2 | パスキーや FIDO2 を、いつ、どの確認手段で登録・追加・回復したかを記録している | 初回移行の適格性の判断に要る（ADR 0020）。記録がなければ、旧パスキーでは移行できない |
| 3 | JPKI での確認の仕組みを持っているか、持つ予定がある | パスキーをすべてなくした人の回復の本命になり、旧パスキーで移れない会員の移行の道の候補にもなる（P1）。ただし、JPKI だけでは旧会員との対応を証明しない（ADR 0020） |
| 4 | 規制や業界の指針で、フィッシングに強い認証が求められている | 導入の理由がはっきりしていて、パスワードや SMS に戻さない判断をしやすい |
| 5 | 電話や対面でしか手続きできない利用者の割合が小さい | 割符で確かめられない人には、一般的な案内と一時停止しかできない（RP-60） |
| 6 | 配送に電話番号を使わなくて済む。または、受け取り場所の指定を使える | 電話番号は、割符では守れない（不変条件11。RP-96 は P1） |

### 接続の前に測ること（O-59）

接続を決める前に、企業と一緒に次の値を測る。値によっては、移行の方法か、接続の時期を変える。

- **初回移行の対象の割合**：旧パスキーが「適格」「経緯が分からない」「弱い確認手段だけ」のどれに当たるか、会員の割合（ADR 0020）。「適格」が少なければ、JPKI（P1。企業の会員との結び付け方は ADR で決める）を待つか、移行中の参加（ADR 0010。期限の長さは M9 で決める）を使う。
- **窓口でアプリを使えない人の割合**：窓口に来る人のうち、通話中に自社の画面を開けない人がどれだけいるか（ADR 0019）。
- **回復の問い合わせの見込み**：機種変更や紛失の問い合わせの量。P0 では、パスキーをすべてなくし、協力者もいない人は回復できない（ADR 0003）。
- **稼働率と責任の分け方**：割符が止まったときにログインと step-up ができなくなる。求める稼働率と、止まったときの扱い（代わりの手順は RP-60 の範囲だけ）を、接続の前に決める。

## 採らなかった案

- **業種の名前を書く**：オーナーの判断で採らない（O-56）。条件で書けば、同じ条件を満たす別の業種にも使える。
- **望ましいことを必須にする**：たとえば「パスキーの登録の記録」を必須にすると、記録のない企業は接続できなくなる。記録がなくても、JPKI（P1）か移行中の参加で道は残るので、望ましいにとどめる。
- **前提条件を spec 02 の要件として足す**：新しい要件を足すわけではないので、spec 02 には、この ADR への参照だけを置く。

## 残るリスク

- 前提条件を満たしても、測った値しだいで、初回移行の大半が JPKI（P1）待ちになることがある。
- 「望ましい」は、満たしていない企業を断る理由にはならない。営業の判断で、前提を緩めて伝えないようにする（必須の一覧は、接続要件そのものである）。
- 測る値の基準（何割なら移行に進めるか）は、まだ決めていない。最初の企業で測ってから決める。
