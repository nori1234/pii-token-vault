# ADR 0027：回復の細目（回復コード、協力者の指名と承認、新しい端末、待機と取消、成立、回復の後）

- 状態：提案（オーナーのレビュー待ち）。M8 の実装は、この ADR の既定の案で進める
- 日付：2026-11-04

## 状況

M8（plan 10章）では、回復の一式を作る。方式は ADR 0003（回復に連絡先を使わない）で決め、値の考え方は ADR 0012（決定3〜5、7）で決めた。plan 4章、spec 01 の PRN-84〜91、DESIGN.md 2章（回復と協力者の画面）と3章（警告文 C、F、G、H）が、要件を決めている。

実装の前に、次のことを決める必要があった。

- 回復コードの形と保存。DB の境界（不変条件8）は、利用者の範囲（`withWarifuUser`）か、テナントの範囲（`withTenant`）でしか DB に触れさせない。新しい端末には利用者のセッションがないので、コードから利用者を決める方法が要る
- 協力者の指名と、回復の承認で、2人の利用者を結び付ける方法（どちらも、相手の範囲の DB は読めない）
- 新しい端末で、いつパスキーを作り、いつ使えるようにするか。待機（既定72時間）をまたいで、新しい端末をどう覚えておくか
- 取消、成立、回復の後の制限の細目
- 企業への知らせ（`recovered_at` と SET）が、企業をまたいだ突き合わせの材料にならないようにする方法（不変条件5）
- 画面の置き場所（承認系の画面は承認用のオリジン。CAP-36、DESIGN.md 原則8）

## 決定

### 回復コード（O-73）

- 回復コードは、利用者 ID（16バイト）と、80ビットの秘密（10バイト）をつないだ26バイトを、Crockford の base32 で42文字にしたもの。6文字ずつ、ハイフンで区切って出す。入力は、大文字と小文字、ハイフンと空白を区別しない（Crockford の読み替え：O→0、I と L→1）。
  - 利用者 ID を入れるのは、コードから DB の境界（`withWarifuUser`）を決めるため。利用者 ID は乱数の UUID で、パスキーの userHandle としても認証器に入っている。秘密ではないが、それだけでは何も許可しない（不変条件1(c)）。
  - 秘密は ADR 0003 の「64ビット以上」を満たす80ビット。総当たりは、秘密の大きさとレート制限（O-84）で防ぐ。
- 保存するのは、`mac(recovery_code, ラベル‖利用者 ID‖秘密)` だけ（鍵サービスの HMAC-SHA-256。ADR 0012 の決定4）。平文は、作った画面で1回だけ見せ、どこにも残さない（不変条件4）。
- 利用者ごとに有効なコードは1つ。作り直すと前のコードは使えなくなり、全端末（受信箱）と協力者に知らせる（ADR 0012 の決定3）。
- コードを作る・作り直すのは、承認用のオリジンで、承認用のセッションと、その操作に結び付いた UV 付きのパスキーで確かめてから（ADR 0023 と同じ形）。画面は DESIGN.md 2章「回復コードの表示」の必須要素（保管の案内、警告文 G。共有のボタンとメールで送る機能は置かない）。

### 協力者の指名（O-74）

- P0 の協力者は1人（ADR 0003）。協力関係は、`(持ち主の利用者 ID, 協力者の利用者 ID)` の組だけを DB に置く（PRN-91）。協力者が相手を見分ける表示名は、協力者の端末（承認用のオリジンの localStorage）の中だけに置く。
- 招待は、持ち主が承認用のオリジンで作る。使い捨ての招待コード（120ビットの乱数。Crockford の base32 で24文字）と、同じ値の QR を出す（10分、1回だけ）。招待はプロセスのメモリ（MAC を鍵にした保存先。ADR 0018 の O-10）に置き、DB には置かない。2人の利用者を結び付ける間だけ使うので、DB の境界をまたがずに済む。
- 手順（DESIGN.md 2章「協力者の招待」）：
  1. 持ち主が招待を作る。画面に、QR と招待コードと警告文 H を出す。
  2. 協力者が、自分の承認用のオリジンで QR を読む（読めなければコードを入力する）。協力者の端末は、相手の表示名を入力させ、端末の中に覚える。
  3. 持ち主は、協力者の端末に自分の名前が出ていることを、目で確かめる。
  4. 持ち主が、招待に結び付いた UV 付きのパスキーで確定する。DB に協力関係を置き、両者の受信箱に知らせる（PRN-86）。
- 協力関係の ID（乱数の UUID）は、協力者の端末が表示名を引くためにだけ使う。協力者の受信箱の知らせ（回復の依頼など）には、この ID だけを入れ、名前は入れない。
- 協力者を入れ替える、外すのは持ち主だけ（パスキーで確かめ、両者に知らせる）。協力者の側から外れる機能は、P0 では作らない。自分自身を協力者にはできない。

### 回復の始め方と、新しい端末のパスキー（O-75）

- 回復は、承認用のオリジンの `/recover` で始める。入力欄は回復コードだけ（PRN-85。メール、電話、氏名の入力欄と「アカウントを探す」機能は置かない）。
- コードが正しく、協力者がいて、進行中の回復がなく、取消の後の14日（O-78）の中でなければ、回復を始める。どれかが違えば、どの理由でも同じ失敗の応答にする。利用者がいないコードでも、ダミーの MAC を計算してから失敗にし、所要時間をそろえる（不変条件10、テスト10）。
- 始めたら、新しい端末に、その利用者の新しいパスキーを作らせる（承認用のオリジンでの登録。UV 付き）。このパスキーは「回復待ち」（`pending`）で、ログインにも承認にも使えない。
- 回復の記録（`idp.recovery_attempts`。状態 `awaiting_helper`）を DB に置き、持ち主の受信箱（全端末）と協力者の受信箱に知らせる。協力者への依頼と全端末への知らせは、コードを確かめた後に出す（PRN-85）。
- 新しい端末は、セッションを長く持たない。待機の後も含めて、新しい端末は、自分の回復待ちのパスキーのアサーションで、回復の状態を読み直す（`resume`）。72時間の待機をまたいでも、端末の中の資格情報だけで続けられる。

### 協力者の承認（O-76）

- 新しい端末は、協力者に見せる結び付けのコード（120ビットの乱数。24文字）と QR を出す（10分、1回だけ。ADR 0012 の決定5、NIST 4.1.2.2 の112ビット以上）。結び付けは、メモリの保存先に置く（回復の記録、回復待ちのパスキーと組）。期限が切れたら、新しい端末が回復待ちのパスキーで確かめて、出し直す。
- 協力者は、自分の承認用のオリジンで QR を読む（読めなければコードを入力する）。協力者の端末は、協力関係の ID から表示名を引き、警告文 C（〈表示名〉と、使えるようになる時刻）と、承認すると何が起きるかを出す。「承認する」と「入力しない（本人に確かめられない）」は同じ大きさ（DESIGN.md 2章「協力者の承認」）。
- 承認は、協力者の UV 付きのパスキーで、結び付けに結び付いたチャレンジ（`mac(approval_challenge, …)`、ラベル `warifu/recovery-helper/v1`）に答える。
- 次のときは、承認を受け付けない（どれも同じ失敗の応答にする）：
  - 承認した人が、その持ち主の協力者でない
  - 協力者が、直近14日以内に回復した（`recovered_at`）、またはパスキーを足した（ADR 0003、PRN-87）。足した時刻は `idp.users.credential_added_at` に残し、足したパスキーを消しても、足してから14日は承認できない。この列を足す前の利用者の分は、マイグレーション 0009 が監査ログ（`idp.passkey.added`）のいちばん新しい時刻から戻す
  - 結び付けが期限切れか使用済み、回復の記録が `awaiting_helper` でない
- 承認すると、回復の記録を `waiting` にし、待機の終わり（`ready_at`）を決める（O-77）。持ち主の受信箱と協力者の受信箱に知らせる。

### 待機（O-77）

- 待機は、回復コードの確認と協力者の承認がそろった時点（承認の時刻）から数える。既定は72時間。`createIdp` の `recovery.waitSeconds` で変えられる。オリジンが https のとき（本番）は、24時間未満を起動時に断る（ADR 0003、PRN-88）。
- 協力者の承認を待つ間（`awaiting_helper`）は、24時間で期限切れにする（`expired`）。期限切れでは、回復コードは失効させない（持ち主の受信箱には知らせる）。
- 時間の進みは、テストでは注入した時計で進める（plan 11章 テスト3の「ハーネスが ready_at を書き換える」の代わり。DB を直接書き換えない）。
- 待機は、P0 では延ばさない。届いていない知らせを理由に待機を延ばすこと（plan 4章の Web Push の受信確認）は、P1 で扱う（RR-06）。

### 取消（O-78）

- 待機中（`awaiting_helper` と `waiting`）は、持ち主の登録済みの端末から取り消せる。取り消すのは承認用のオリジンで、承認用のセッションと、回復の記録に結び付いた UV 付きのパスキー（有効なもの。回復待ちのパスキーは使えない）で確かめる（DESIGN.md 2章「回復の通知」、警告文 F）。
- 取り消すと、回復コードを失効させ、回復待ちのパスキーを消し、14日間は回復を始められないようにする（`recovery_locked_until`。PRN-89）。持ち主の受信箱と協力者の受信箱に知らせる。

### 成立（O-79）

- 待機が終わった後、新しい端末が回復待ちのパスキーで `resume` すると、回復が成立する。1つのトランザクションで、次をする。
  - 回復の記録を `completed` にする
  - 回復待ちのパスキーを有効にし、ほかの有効なパスキーをすべて一時停止（`suspended`）にする（ADR 0003）
  - `idp.users.recovered_at` を置く
  - 使った回復コードを失効させ、新しい回復コードを作る（平文は、この応答で1回だけ新しい端末に見せる。ADR 0012 の決定3）
  - 持ち主の受信箱に、成立と回復コードの作り直しを知らせる。協力者への同じ知らせは、送信待ち（`idp.helper_notice_outbox`）に置く
  - 接続している企業ごとに、企業への知らせを送信待ち（`idp.recovery_notice_queue`）に置く。回復した日（`recovered_at` を UTC の日にまるめた値）は、ここで成立の時刻から決める
- トランザクションを確定した後、知らせより先に、後始末をする（どれもメモリの操作で、失敗しない）：持ち主のセッションを、OIDC のものも含めてすべて消す（PWA、承認用、oidc-provider の SSO のセッション、その利用者でログインした進行中のインタラクション、発行済みの認可コードとアクセストークン。パスキーの削除と同じ関数）。新しい端末だけを、承認用のオリジンでログインさせる。
- 知らせは、成立と同じトランザクションで送信待ちに置くので、失われない。成立しなかった回復（取消との競合で負けた回復を含む）の知らせは、どこにも残らない。送るのは、どれも利用者の操作によらない（オーナーの再レビュー）。
  - 協力者への知らせ：送信待ちは、持ち主の範囲で書き、協力者の範囲で読む（RLS は、INSERT が持ち主、SELECT と DELETE が協力者。自分あての行だけ）。協力者の端末が受信箱を読むたび（PWA は30秒ごと）に、協力者の範囲の1つのトランザクションで、自分あての行を消して受信箱に置く。送信待ちの ID を受信箱の項目の ID にするので、同じ知らせは1つだけになる。持ち主が何もしなくても、協力者が見るときには届いている。回復の開始、取消、回復コードの作り直し、協力者の指名と削除の知らせも、同じ送信待ちを通す。
  - 企業への知らせ（O-81）：送信待ちは、利用者の範囲で書き、テナントの範囲で読む（RLS は、INSERT が利用者、SELECT・UPDATE・DELETE がテナント）。idp の配送の回（既定30秒ごと。company-api の SET の配送の回と同じ形）が、登録簿のテナントごとに `withTenant` で読み、company-api の内部 API（`/v1/account_recovered`）に渡し、渡せたら消す。渡せなければ、1分、5分、30分、2時間、以後6時間ごとに送り直す（諦めない）。成立の直後にも、その利用者のテナントについて1回渡してみる。送り直しでも、回復した日は送信待ちの値をそのまま渡すので、日付をまたいでも変わらない（オーナーの再レビュー）。
  - company-api に届かない間も、回復は成立する（成立を止めない）。その間、企業には SET が遅れて届くが、ID トークンの `recovered_at` は届く。テナントの範囲で利用者 ID を読むのは idp の配送の回だけで、外から呼べるルートには出さない（不変条件2）。
- 協力者がいないときは、P0 では回復できない（ADR 0003。P1 で JPKI）。

### 回復の後（O-80）

- 回復の後7日間は、次を受け付けない（PRN-90）：協力者の指名・入れ替え・削除、ほかのパスキーの削除、本物のメールの登録と変更（配送先の変更）、高リスクの操作の承認（M6 の承認待ちの型に `highRisk` を足し、その型の承認を `409 {"error":"restricted"}` で断る。拒否は受け付ける。選択肢を出すときと、検証のときの両方で確かめる。P0 には高リスクの型はまだない）。窓口の操作別承認（ADR 0026）は照会と軽い手続きだけなので、断らない。
- 一時停止したパスキーは、ログインにも承認にも使えない。7日を過ぎたら、利用者が削除できる。一時停止を解く機能は、P0 では作らない（回復した端末で新しいパスキーを足せる）。
- パスキーの追加は、回復の後も受け付ける（予備のパスキーを持てるように。追加は全端末に知らせる。ADR 0023）。
- BE/BS フラグの変化をどう使うか（spec 01 の注）は、P0 では記録だけにする（P1 で決める）。

### 企業への知らせ（O-81）

- ID トークンに、独自クレーム `recovered_at` を入れる。値は、回復した日の UTC の0時（秒の UNIX 時刻）にする。正確な時刻は、どの企業にも同じ値になるので、企業をまたいで同じ人を突き合わせる材料になる（不変条件5）。日にまるめて、その日に回復したほかの人と区別できないようにする。
- 回復の SET（`urn:warifu:secevent:account-recovered`。中身は `recovered_at`、宛先はテナントごとの sub）を、接続しているテナントごとに送る。送るのは、成立した回復だけ（O-79）。初めて送る時刻は、company-api が受け取ってから、テナントごとに独立した0〜6時間の乱数だけ遅らせる（同じ回復を複数の企業が受け取るので、送る時刻の近さで突き合わせさせない）。配送の扱いは、窓口の取消の SET（ADR 0026 の O-67、O-72）と同じ（`202` だけを届いたことにし、諦めずに送り直し、保留は同じ経路で解く）。
- 企業は、`recovered_at` から8日の間、高リスクの操作を保留する（RP-53。割符の7日に、日へのまるめの分を足した）。`recovered_at` は制限を強める方向にだけ使う（RP-54）。
- idp から company-api へは、窓口と同じ内部 API（`company-api.sock`）に `/v1/account_recovered`（利用者 ID、テナント、回復の記録の ID、回復した日）を足す。同じ回復の送り直しは、二重に送信待ちに入れない（テナントと回復の記録の ID の一意制約）。
- company-api は、緊急停止中のテナントと、受け口を登録していないテナントの知らせも、送信待ちに入れておく。配送の回は、停止を解いた後（受け口を登録した後）に送る（停止の間は送らない。ADR 0022）。sub は送るときに引く（idp は、接続を記録する前に sub の索引を置くので、接続している利用者には sub がある）。送るときに sub の索引が見つからなければ、送信待ちから消さずに、受け口につながらなかったときと同じ間（1分、5分、30分、2時間、6時間、以後6時間ごと）で送り直し、索引を戻した後に届ける（ADR 0022 の、M5 より前に接続した利用者のように、索引が欠けることはありうる。値はログに出さず、件数だけを出す。オーナーの4回目のレビュー）。登録簿にないテナントが含まれていれば、どのテナントにも入れずに `404` を返し、idp は送信待ちに残して送り直す（設定の食い違いで、知らせを黙って失わない。オーナーの再々レビュー）。

### 画面の置き場所（O-82）

- 回復と協力者の画面は、すべて承認用のオリジンに置く（CAP-36）：回復コードの作成、協力者の招待と受け入れと確定、回復の開始（新しい端末）、協力者の承認、回復の通知と取消。PWA（本来のオリジン）の受信箱からは、承認用のオリジンへのリンクだけを出す。
- QR は、サーバーが `uqr`（MIT、依存なし）で作った白黒の行列を返し、画面が canvas に描く（HTML として描かない。Trusted Types と CSP をそのまま保つ）。QR の読み取りは、ブラウザの BarcodeDetector とカメラが使えるときだけ出し、使えなければコードの入力にする。
- カメラを許すのは、協力者の画面（`/helper`）だけ。その画面の応答だけ `Permissions-Policy` を `camera=(self)` にし、ほかの画面と応答は `camera=()` のままにする。
- 協力者の画面の招待の受け入れには、相手の呼び名を入力する欄を置く（DESIGN.md 2章の注）。呼び名は、承認用のオリジンの `localStorage` にだけ置き、サーバーに送らない。この欄は、DESIGN.md 原則3の氏名の入力欄としては扱わない（オーナーの確認待ち）。
- 回復コードと、招待・結び付けのコードは、3文字ずつ区切って等幅で見せ、読み上げ用に1文字ずつの文を添える（DESIGN.md 6章の CodeDisplay）。サーバーの返す形（6文字ずつのハイフン区切り）とは見せ方が違うが、入力は区切りを問わない。

### 保存期間（O-83）

- 招待と結び付けは、メモリだけ（10分）。
- 回復の記録は、終端（`completed`、`cancelled`、`expired`）から90日で消す（持ち主の範囲で読み書きするときに消す。ADR 0023 の O-47 と同じ考え方）。取消の後の14日の判定は、`idp.users.recovery_locked_until` で行うので、記録を消しても効く。
- 回復コードの照合用の MAC は、作り直すまで置く。失効したコードの MAC は消す。

### レート制限（O-84）

値はどれも、根拠のない仮置き（ADR 0012 の考え方）。

| 機能 | キー | 上限 |
|---|---|---|
| 回復の開始 | IP | 1時間に10 |
| 回復の開始 | コードの利用者 ID | 1時間に5 |
| 招待の作成 | 利用者 | 1時間に5 |
| 招待の受け入れ、結び付けのコードの入力 | 利用者 | 10分に10 |
| 招待の受け入れ、結び付けのコードの入力 | IP | 10分に30 |
| 回復コードの作成 | 利用者 | 1時間に5 |
| `resume`、取消、確定の検証 | IP と userHandle の利用者 | パスキーの検証と同じ（ADR 0018） |

### 監査の事象（O-85）

- idp：`idp.recovery.code_issued`、`idp.recovery.helper_set`、`idp.recovery.helper_removed`、`idp.recovery.started`、`idp.recovery.helper_approved`、`idp.recovery.cancelled`、`idp.recovery.expired`、`idp.recovery.completed`（属性は持ち主の範囲で残す。コード、結び付け、表示名は入れない）。
- company-api：`company_api.recovery.notified`（テナントの範囲。属性なし）。

## 採らなかった案

- **回復コードに、利用者 ID と別の乱数のハンドルを入れる**：ハンドルから利用者を引くには、利用者をまたいで DB を読む必要がある。新しい境界の関数や SECURITY DEFINER 関数を足すことになり、不変条件8に反する。
- **招待と結び付けを DB に置く**：2人の利用者の範囲をまたぐので、どちらかの範囲から相手の行を読む口が要る。10分だけ使う値なので、メモリに置いた。プロセスを立ち直すと消えるが、作り直せば足りる。
- **新しい端末に、待機の間ずっと有効なセッションを持たせる**：72時間以上の長いセッションになる。回復待ちのパスキーでその都度確かめれば、端末の中の資格情報だけで足りる。
- **`recovered_at` を正確な時刻で渡す**：どの企業にも同じ値になり、突き合わせの材料になる。
- **成立の後に企業へ知らせる**：company-api に届かないと、知らせが失われる。先に送信待ちに入れる。
- **QR を HTML や SVG の文字列で返して描く**：Trusted Types で HTML の文字列を使わない方針（ADR 0018）に反する。

## 残るリスク

- **回復コードのフィッシング**（RR-12）：コードを盗んだ攻撃者が、協力者もだまして承認させると、待機に入る。待機中の取消と、警告文 C・F・G で抑える。
- **持ち主がすべての端末を失っている場合**（RR-06）：待機中の知らせは、協力者にしか届かない。協力者が気付かなければ、攻撃者の回復が成立しうる（ADR 0003）。
- **1人で2つの要素がそろう**（RR-07）：身近な人が協力者で、回復コードも手に取れる場合（ADR 0003。強化モードは P1）。
- **回復した日による突き合わせ**（RR-20）：`recovered_at` を日にまるめ、送る時刻を0〜6時間ずらしても、回復した人の少ない日には、複数の企業で同じ日に回復した会員として突き合わせられうる。
- **攻撃者の回復が成立した後の、元の持ち主**（RR-21）：攻撃者の回復が成立すると、元の持ち主のパスキーは一時停止になり、P0 では元に戻す手段がない（P1 の JPKI による回復）。

運用の上の制約：idp を立ち直すと、メモリに置いた招待と結び付けが消える（作り直しが要る。回復の記録と、回復待ちのパスキーは DB にあるので残る）。

## 実装で分かったこと

- 協力者が直近にパスキーを足したかの判定で、最初のパスキー（アカウントと同じトランザクションで作る）を除くために、パスキーとアカウントの作成の時刻を比べる。JS の `Date` はミリ秒までなので、DB の時刻（マイクロ秒）を JS に通して比べると、最初のパスキーを足したものと見なすことがあった。比べるのは DB の中で行う。
- 回復の後の高リスクの承認の制限は、選択肢を出した後に回復が成立した場合に備えて、検証でも確かめる（成立のときに、ほかのセッションはすべて消えるので、多重の守り）。
- 新しい端末のパスキーは、承認用のオリジンで作るが、RP ID が同じなので、回復の後は PWA のオリジンのログインにも使える。
- E2E は、http のオリジンで待機を4秒にして、画面で回復を完了させる（https では起動時に24時間未満を断る）。
- オーナーのレビュー（#50）で、次の3つを直した。
  - 回復の成立で、oidc-provider の SSO のセッションを消していなかった（前の端末が、SSO の窓の間、企業にログインできた）。パスキーの削除と同じ関数で、OIDC のセッション、進行中のインタラクション、認可コード、アクセストークンも消す。
  - 企業への知らせを成立の前に送信待ちに入れていたため、その間に取消が確定すると、成立していない回復が企業に届きえた。
  - 協力者への知らせを、成立のトランザクションの後に別に書き、失敗すると例外になって、セッションの削除と新しい回復コードの返却まで進まなかった。
- 最初の直し（`0a68b2e`）は、企業への知らせを準備と確定の2段にし、送れなかった知らせを持ち主の操作のたびに送り直す形だった。再レビューで、次の2つを指摘された。
  - 持ち主が端末を使わないと、送り直されない（攻撃者の回復の開始を、協力者が知らないままになりうる）。
  - 準備の後に日付をまたいで送り直すと、準備の回復日と、成立した日がずれうる。
- そこで、知らせを成立（と、それぞれの変更）と同じトランザクションで送信待ちに置き、送るのは、協力者の受信箱の読み込み（協力者の範囲）と、idp の配送の回（テナントの範囲）にした。
- 再々レビュー（`a308bf1`）で、company-api が、緊急停止中、登録なし、受け口なし、sub の索引なしのテナントの知らせを入れずに `204` を返し、idp が渡せたものとして消していたことを指摘された。停止中と受け口なしは入れておいて再開の後に送り、登録なしは `404` にして idp に送り直させ、sub の有無は受け付けるときに見ないようにした。新しい境界の関数や SECURITY DEFINER 関数は足していない（不変条件8）。INSERT と SELECT で範囲の違うポリシーは、監査ログ（`audit.events`）と協力関係（`idp.helpers`）と同じ考え方。
- 4回目のレビュー（`b6a1ce1`）で、受け付けるときに sub の索引を見なくなった分、送るときに索引が見つからないと、company-api が送信待ちを消していたことを指摘された（索引を直しても、その知らせは届かない）。回復の SET では消さずに送り直すようにした。窓口の取消の SET は、これまでどおり、正本の行が消えた後（終端から7日を過ぎた後）は送るものがないので消す（ADR 0026）。
- 5回目のレビュー（`247bc21`）で、協力者の14日の判定が、いま残っている有効なパスキーの作成の時刻だけを見ていたことを指摘された。パスキーの削除は行を消すので、足してから消せば、14日を待たずに承認できた（PRN-87 と食い違う）。足した最後の時刻を `idp.users.credential_added_at` に置き（足すのと同じトランザクションで書く。消しても残す）、判定はそれも見るようにした。回復待ちのパスキーは、成立したときに `recovered_at` で判定されるので、この列には書かない。
- 6回目のレビュー（`52ee104`）で、この列を足す前に足して消したパスキーは、既存の利用者では列が NULL で始まるので判定できないことを指摘された。足したことは、追加の機能と同じ M3 から、監査ログの `idp.passkey.added` にすべて残っていて（最初のパスキーは `idp.account.created`）、監査ログは消さない。そこで、マイグレーション 0009 の最後で、利用者ごとのいちばん新しい `idp.passkey.added` の時刻を、この列に戻すようにした。監査ログの本文は FORCE の RLS で、所有者のロールからは0行に見える（戻す処理が黙って何もしない）ので、`RESET ROLE` の後、ブートストラップのロールで読む（マイグレーションは不変条件8の例外。読むのは利用者 ID と時刻だけ）。テストは、0008 まで流した DB に、更新前の書き方で足して消したパスキーと監査ログを置き、0009 を流してから判定する（`t03-recovery-upgrade`）。
