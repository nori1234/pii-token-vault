# ADR 0003：割符の回復に連絡先を使わない

- 状態：採用
- 日付：2026-10-17

## 状況

v2 の計画では、回復に「保存した回復コード」と「本物のメールに送る確認コード」を使っていた。これは、メールの受信箱を本人の証明として使うことになり、ADR 0001 に反する。さらに、回復コードを同じクラウドやメールに保存している人が多く、偽の回復ページで両方とも盗まれうる。

## 決定

1. **予防**：パスキーを2つ以上登録してもらい、うち1つは端末固定のものを推奨する。WebAuthn の BE/BS フラグを記録し、同期パスキーかどうかの変化をリスクの信号として扱う。
2. **回復の始め方**：回復コードだけで始める。コードには、アカウントを指す乱数のハンドルと、64ビット以上の秘密を含める。回復の画面には、メール・電話・氏名の入力欄を置かない。協力者への依頼と、登録済み端末への通知は、回復コードを確かめた後に出す。
3. **回復協力者**：
   - 対面の QR か、使い捨ての招待コードで指名する。連絡先から協力者を探す機能は作らない。
   - 承認では、回復を求めている人の新しい端末に出た QR を、協力者が対面で読み取る。QR が使えない場合だけ、コードを手で入力する。電話やビデオ通話で伝えられたコードは使わない（DESIGN.md の警告文 C）。
   - 直近14日以内に回復した協力者や、パスキーを追加した協力者の承認は無効にする（14日という値の根拠は未確認）。
   - P0 では協力者は1人。P1 で k-of-n にする。
   - 協力関係は、内部 ID の組だけでサーバーに持つ。協力者が相手を見分ける表示名は、協力者の端末の中だけに保存する。新しい端末の画面には、協力者を特定できる情報を出さない。
4. **待機と取り消し**：
   - 待機期間は、回復コードの確認と協力者の承認がそろった時点から数える。既定は72時間、本番の下限は24時間で、起動時に強制する（値の根拠は未確認。M0 で確かめる）。
   - 待機中は、登録済み端末の受信箱と協力者に知らせ、端末のパスキーで取り消せるようにする。
   - 取り消したら回復コードを失効させ、14日間は回復を始められないようにする。
5. **回復後の7日間**：協力者の変更、他のパスキーの削除、配送先の変更、高リスクの承認を禁止する。古いパスキーは一時停止にする。企業には `recovered_at` と SET で知らせる。
6. **協力者がいない場合**：P0 では回復できない。P1 で JPKI による回復を加える。基本4情報は持たない。照合のキーの方式（証明書の更新や再発行をまたいで同じ人を照合する方法を含む）は、P1 の ADR で決める。

## 基準との関係

- NIST SP 800-63B-4 の recovery contacts は、指定した人の連絡先にコードを送る方式で、この協力者の方式とは別物である。そのため「NIST の AAL2 に準拠」とは書かない。AAL2 相当と言えるかは、M0 で原文を確かめたうえで検討する。
- FIDO と DS-511／DS-512 の「回復は元の認証と同等以上の強さ」を、P0 の回復が満たすかは評価していない。回復コードはフィッシングで盗まれうるので、満たすとは書かない。

## 残るリスク

- 端末をすべて失うと、待機中の知らせが本人に届かない。
- 身近な人が協力者で、しかも回復コードを手に取れる場合は、1人で2つの要素がそろってしまう。強化モード（P1）で、協力者を2人以上必須にできるようにする。
- 同期パスキーの安全性は、Apple や Google のアカウント回復の強さに左右される。
