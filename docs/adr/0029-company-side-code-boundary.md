# ADR 0029：企業の側のコード（rp-kit と demo-rp）の通信と暗号の境界

- 状態：決定（オーナー確認済み。2026-11-15。O-111 は、オーナーの補強の2点を入れて確認済み）
- 日付：2026-11-15

## 状況

M9（plan 10章）では、企業が自社のサーバーに組み込む rp-kit（SDK と適合テストキット）と、企業の参照実装の demo-rp を作る。どちらも、割符のエンドポイント（PAR、トークン、company-api の企業向けの API）を呼び、PKCE（RFC 7636）の値を作る必要がある。

これまでの文書と lint は、次のようになっていた。

- 不変条件7は「外向きの通信は送信サービスだけが行う」とだけ書いており、`packages/` の中にある demo-rp も禁止の対象に読める。lint は、`packages/sender` 以外で `fetch` などのグローバルと通信のモジュールを禁じている。
- 不変条件9の許可リストに、PKCE の S256 が使う SHA-256 はない（あるのは HMAC-SHA-256）。lint は、`packages/warifu-core`・`packages/keysvc`・`spikes/` 以外での `node:crypto` の import を禁じている。
- spec 04 の3章は、rp-kit と demo-rp が割符のエンドポイントを呼ぶ方法と、不変条件7・lint の規則との関係を「未定（M9 で決める）」としていた。

## 決定

### 適用範囲（O-107）

- 不変条件7（外向きの通信を sender に集める）は、割符のサービス（idp、relay、company-api、keysvc、sender、warifu-core）に適用する。割符の内部のサービスの扱いは変えない。
- 企業の側のコード（rp-kit と demo-rp）は、割符の一部ではない。企業のサーバーで動く。ただし、このリポジトリで作るので、不変条件の残り（肯定リスト、平文を残さない、暗号の許可リストなど）は、これまでどおり適用する（plan 1-1 の (a) は、rp-kit と demo-rp にも例外なく適用する）。

### rp-kit の SDK（O-108）

- SDK は、自分ではどこにもつながない。企業は、通信の接続部分だけ（1つの要求を送って、1つの応答を返す関数）を渡す。
- 要求の組み立て（client assertion、PAR、トークンの要求、企業向けの API の要求）、応答の検証（ID トークン、操作ごとの承認、紐付けの承認、SET）、エラーの扱いは、SDK が受け持つ。企業が自分で書く部分を、通信の接続だけにして、導入の手間と、検証の書き漏らしを減らすためである。
- SDK が要求を送る先は、企業が設定で与えた割符のオリジン（idp と company-api）だけにする。応答の中の URL（リダイレクトの先など）に、自動で進まない。鍵は、企業が設定で与えた jwks か、割符の公開鍵の URL を設定のオリジンの下で SDK が組み立てて取る（応答の中の `jwks_uri` に従わない）。
- 署名と検証は `jose` の ES256 だけを使う。鍵を外から取りに行く `createRemoteJWKSet` などは使わない（lint で止めている）。

### demo-rp（O-109）

- demo-rp は、企業の側の参照実装として、設定した割符のオリジン（idp と company-api）と模擬 OP への通信を許す。
- 通信するのは、demo-rp の中の1つのファイル（`packages/demo-rp/src/transport.ts`）だけにする。lint の制限（`fetch` などのグローバル）は、このファイルだけ外す。demo-rp のほかのファイルの制限は外さない。
- そのファイルは、設定のオリジンの完全一致でだけ送り、利用者や企業の画面から渡された任意の URL には接続しない。リダイレクトには自動で従わない（`redirect: 'manual'` で、3xx は失敗として扱う）。

### PKCE の S256（O-110）

- 不変条件9の「プロトコルで決まる例外」に、PKCE（RFC 7636）の S256（SHA-256）を足す。認可コードの横取りを防ぐために、割符の idp が S256 だけを受け付けるので、企業の側で要る。
- 用途は、rp-kit が PKCE のチャレンジを作るときだけに限る。`node:crypto` の import は、rp-kit の1つのファイル（`packages/rp-kit/src/pkce.ts`）だけに許し、使うのは `randomBytes` と `createHash('sha256')` だけにする（lint とテストで固定する）。

### 適合テストキットのフックとルートの申告（O-111）

spec 02 の 15-1 で「M9 で決める」としていた、RP 側のテスト用フックの形と、「API がないこと」の確かめ方を、次のようにした。キットは、企業が自社で点検するためのもので、割符が企業全体の安全性を保証するものではない（オーナー、2026-11-15）。

- **模擬 OP**：キットの中で、企業の手元だけで動かす（`packages/rp-kit/src/kit/mock-op.ts`）。SDK に渡す通信の関数として答え、ネットワークを使わない。固定の2人（`alpha` と `beta`）は、sub が違い、別名（email クレーム）が同じ。値は固定で、入力によって変えない。
- **フック**（`RpTestHooks`）：企業が自分のテスト環境で実装する関数の集まり。
  - `signIn`：模擬 OP の固定の利用者で、RP のふだんのログインを1回通し、RP の内部のアカウントの参照（不透明な文字列）を返す。ログインを断ったら空文字。
  - `legacyLogin`、`legacyReset`：初回紐付けを済ませた会員で、旧ログイン（ENT-02）と、メールや SMS による再設定（ENT-01）を試し、`accepted`、`refused`、`absent` を返す。
  - `linkAttack`：漏れたメールで旧アカウントを奪い、攻撃者の sub を紐付けようとした結果（`linked` か `refused`）。
  - `routes`：RP のルート（公開、管理、内部、バッチの入口）を、性質の印（`sub_rewrite`、`account_merge`、`guest_lookup`、`other`）と一緒に申告する。
- **「API がないこと」**：企業の申告したルートで確かめる。印が `sub_rewrite`・`account_merge`・`guest_lookup` のルートがあれば不合格（`fail`）にする。印がなく、パスの名前（`rebind`、`merge`、`subject`、`guest`、`by-email` など）だけが似ているルートは、要確認（`review`）にする。名前だけでは違反と断定しない（`guest` や `subject` という名前の、無害な機能もありうる。オーナー、2026-11-15）。要確認は合否を変えず、企業が自分で確かめる。申告そのものが正しいかは、キットでは確かめられない（自己申告。残るリスク）。
- **フックの応答の検査**：フックの戻り値は、型だけに頼らず、実行時にも形を確かめる。未実装、例外、想定外の値（`undefined`、知らない語、形の違うルート、印のないルート）は、検査できなかった（`unverified`）として、合格にしない（オーナー、2026-11-15）。
- **判定**（`judge`）：観測から合否を決める純粋な関数。移行中の企業では、閉じたと報告していない入り口に対応する検査だけを `relaxed`（不合格にしない）にする。同じ別名で sub の違う2人と、sub の書き換えは、移行中も緩めない。報告の結果（`outcome`）は、不合格があれば `fail`、検査できなかった項目があれば `incomplete`、要確認だけなら `review`、どれもなければ `pass` にする。合格（`passed`）は、`pass` と `review` だけ。
- キットは、結果を外へ送らない。結果は企業の報告の一部で、割符が確かめたことにはならない（spec 02 の14章）。

## 理由

- 案A（demo-rp に通信を許す）と案B（demo-rp も通信の関数を外から受け取る）を比べた。案B は不変条件7の文を変えずに済むが、demo-rp を読んでも、企業が実際に組み込むときの形（どこに、どうつなぐか）が分からない。オーナーは案A を選んだ（2026-11-15）。企業が組み込む形を demo-rp で示せるからである。
- 通信を許す範囲を1ファイルに限ると、demo-rp のほかのコードが、うっかり外へつながることを lint で止め続けられる。宛先を設定のオリジンの完全一致に限り、リダイレクトに従わないことで、demo-rp が SSRF の入り口にならないようにする。
- PKCE の値を企業に作らせる案（不変条件9を変えない）は、企業の手間と、作り方を誤る余地が残るので採らなかった。

## 残るリスク

- 企業が本番で使う通信の部品（企業が SDK に渡す関数）の作りは、割符からは確かめられない（企業の責任。plan 3-3 の資格情報と判断の置き場所）。
- demo-rp は参照実装で、本番の企業のサーバーではない。通信の守り（宛先の固定、リダイレクトに従わない）を、そのまま本番の要件とはしない。
