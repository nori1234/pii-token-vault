# ADR 0010：移行中の参加と、企業ごとの「切り替わったもの」「残っている入り口」の表示

この ADR は、2026-10-20 に書いた案（「ADR 0008（提案）：移行中の参加と『残っている入り口』の表示」）をもとにしている。案は、名前が「金庫」だったときに書いた。0008 は別の ADR（2026年10月の注意喚起を受けた見直し）が使っているので、0010 にした。名前は「割符」に置き換えた（ADR 0009）。案から変えたところは、下の「案からの変更」にまとめた。

## 状況

いまの接続要件では、企業は割符に参加した時点で、次のすべてを済ませなければならない（plan 3-3、[02](../spec/02-rp-requirements.md)）。

- ログインを割符のパスキーだけにする（RP-04）
- 未紐付けの会員も含めて、メールや SMS による再設定を止める（RP-31、RP-32）
- ゲスト照会の画面と API をなくす（RP-40）

これは原則のとおりで、旧経路が1本でも残れば、「漏れた連絡先や属性を知っている・受け取れるだけでは、本人確認は突破できない」という主張は成り立たない。

一方で、企業にとっては、会員の移行、窓口の業務、サポートの体制を一度に変えることになり、導入の壁が大きい。企業が ID 管理の製品を選ぶときには、導入の速さが重視されやすく、割符はこの点で不利である。参加する企業が増えなければ、別名と pairwise sub による「持たせない」「つなげさせない」も広がらない。

## 決定

### 1. 参加を2つの状態に分ける

| 状態 | 意味 | 主張（plan 1-2） |
|---|---|---|
| 完全な参加 | いまの接続要件をすべて守る | 言ってよい |
| 移行中の参加 | 下の「入り口の一覧」にある経路だけを、期限まで残してよい。それ以外の接続要件は、すべてそのまま守る | 言ってはならない。この企業は「接続要件を守る企業」に含めない |

- 残してよい経路は、次の固定の一覧（入り口の一覧）にあるものだけにする。一覧にない経路を残すことは認めない。
- 経路を残すことは、その経路が使う値（パスワード、メールや SMS に届くリンクやコード、予約番号や電話番号など）を根拠にすることと同じである。そこで、入り口の一覧の経路の中に限って、識別と肯定リストの要件（RP-02・RP-03 と、ENT-02 のログインでの識別についての RP-01）と、ENT-03 の画面と API の中での RP-08 について、例外を期限まで認める。経路の外（窓口、高リスクの操作、アカウントの統合、紐付けと sub の扱い）では、これらをそのまま守る。住所や生年月日などの属性による照合（RP-07）は、ENT-03 の画面と API でも認めない。ENT-03 で照合に使ってよいのは、RP-40 に挙げた値（予約番号、電話、メール、氏名。別名は除く）だけにする。警告文 I の補足で利用者に挙げる値と、合わせるためである。どの経路でも、別名を、再設定の宛先にも、アカウントを探す値にも使わせない（RP-05 は緩めない）。
- 高リスクの操作は、移行中でも、操作ごとの承認だけを根拠にする（RP-10、RP-13 は緩めない）。入り口の一覧の経路から、高リスクの操作をさせない。ENT-01 の再設定の宛先（企業が持つメールや電話番号）の変更も、高リスクの操作と同じく、操作ごとの承認だけを根拠にする。入り口の一覧の経路（ENT-03 の変更を含む）から変えさせない（RP-18）。
- 移行中の参加には期限を付ける。原則6か月。企業が残りの作業と見込みを報告し、運営者が内容を確認したうえで、必要な期間を延長する。回数は固定しない。延長は、企業が残りの作業、完了の見込み、希望の期限を申請し、運営者が事項がそろっていることを確かめて、原則として希望どおりの期限で認める（2026-11-14）。期限を過ぎ、延長の申請もないときは、企業に督促し、表示に出す。期限切れだけでは、新しい接続、移行の申請、既存の接続を自動では止めない（2026-11-13。ADR 0028 の O-93）。
- 完全な参加から移行中の参加に戻すことは認める。戻すときは、警告文 I を出し、その企業に知らせる。利用者への案内は企業が行い、割符は利用者に再同意を求めない（2026-11-12 に変えた。ADR 0028 の O-97・O-98）。
- rp-kit の SDK と demo-rp の参照実装は、完全な参加だけを実装し、入り口の一覧の経路を作る機能や設定を入れない。入り口の一覧の経路は、テストの中を含めて、どこにも作らない（「悪い RP」のモードは作らない。下の「M9 の前の判断」）。適合テストキットが不合格にすることと、検査の分け方は、キットに作り物の観測を与えて示す。キットに合格する移行中の企業の設定を、demo-rp の画面や手引きで見本として示さない。適合テストキットは、移行中の参加の検査の分け方（02 の 15-1）を持つ。
- CLAUDE.md の不変条件は変えない。CLAUDE.md は、不変条件を「コード、ライブラリの設定、テスト用の補助、スクリプトのすべてに適用する」としている。割符のコードは、移行中の参加の企業についても、連絡先や属性を、本人確認・承認・識別の根拠にしない。適合テストキットが持つのは、企業の側の検査を緩めるかどうかの分け方だけである。テストの補助も同じで、適合テストキットのテストに与える作り物の観測は、メール、sub、別名などの値を見て変えない（下の「M9 の前の判断」）。一方、[ADR 0001](0001-affirmative-list.md) は (a) を「接続要件と適合テストで課す」としている。そのため、この ADR は、ADR 0001 の (a) の接続要件での課し方を、移行中の参加の企業について変える。
- 割符の側の守り（sub と別名をテナントごとに独立させること、CIBA の hint、送信元ロックなど）は、移行中の企業についても変えない。

### 2. 入り口の一覧

| ID | 入り口（利用者に出す文言） | 緩める要件 | 企業の側の検査（適合テストキット。[02 の 15-1](../spec/02-rp-requirements.md#15-1-適合テストキットp0m9テスト9)） |
|---|---|---|---|
| ENT-01 | メールや SMS に届くリンクやコードでの、パスワードなどの再設定 | RP-31（再設定）、RP-32、RP-02・RP-03（この経路の中だけ） | 旧経路、紐付けの攻撃 |
| ENT-02 | この企業独自のパスワードでのログイン | RP-04、RP-31（旧ログイン）、RP-01（この経路のログインでの識別）、RP-02・RP-03（この経路の中だけ） | 旧経路 |
| ENT-03 | 予約番号や電話番号などでの、予約や注文の確認・変更・取り消し | RP-40、RP-08、RP-02・RP-03（どれも画面と API の中だけ。高リスクの操作は除く。RP-10） | ゲスト照会 |

- 一覧に載せるのは、企業が閉じたことを自分で確かめて報告できる経路だけにする。割符は、閉じたことを確かめない（2026-11-12 に変えた。イシュー #60、ADR 0028 の O-94）。
- 窓口で氏名や生年月日を聞いて本人確認すること（RP-07、RP-27）は、監査でしか確かめられないので、一覧に載せない。この経路は移行中でも残してはならない。
- 各項目の文言は1つにし、下の2つの一覧のどちらに出すときも、同じ文言を使う。

### 3. 利用者の画面に「切り替わったもの」と「まだ残っている入り口」を出す

移行中の企業については、入り口の一覧の各項目を、「割符で確かめる方法に切り替わったもの」と「まだ残っている入り口」に分けて、利用者の画面に出す。目的は、利用者が、その企業でどこまで割符が使われ、どこが使われていないかを知ったうえで、接続を選べるようにすることと、企業が早く入り口を閉じる動機をつくること。

**表示の規則**：

1. **2つの一覧を出す**：「割符で確かめる方法に切り替わったもの」（一覧1）と「まだ残っている入り口」（一覧2）を、同じ大きさ、同じ見た目で並べる。（2026-11-12 に、一覧1の見出しを「この企業が、閉じたと報告している入り口（割符は確かめていません）」に変える案にした。ADR 0028 の O-105。分けて出す方針は決めた。文言の細部は未決）
   - 一覧1の項目に、✓などの「済み」を示す印、緑の色、目立つ強調を付けない。緑の✓が並ぶと、「この企業は安全」と読まれるためである（DESIGN.md 4章の、断定を使わない規則）。ブラウザの鍵マークが「安全なサイト」と誤解されたのと同じ問題を避ける。
   - 「安全」「対策済み」「認定」などの言葉を使わない。事実だけを、中立の文言で書く。
   - 一覧1が空のときは、一覧1の見出しも出さない。
2. **既定は「残っている」**：項目を一覧1に移すのは、企業が、割符の企業向けの報告画面（テナントが指名した報告者だけが、自社の情報だけを変えられる）で、閉じたと報告したときだけにする（運営者が `entryOverrides` に載せた入り口は、報告によらず一覧2）。企業は、状況が変わるたびに報告でき、回数は制限しない。一覧1の見出しで、企業の報告に基づくことと、割符が確かめていないことを示す。報告のない項目は、一覧2に出す（2026-11-12 に変えた。前は「割符が自ら確かめたときだけ。企業の自己申告では移さない」。ADR 0028 の O-94・O-105）。
3. **文言は固定**：見出し、一覧の見出し、各項目、補足の文、日付、規則6の文は、割符が定めた固定の文言だけにする（DESIGN.md の原則2・5）。企業は文言を足したり変えたりできない。企業名は登録簿の値を使う。
4. **確かめた日を出す**：一覧1の各項目に、企業が確かめた日を付ける。切り替えの期限と、企業の直近の報告の日も出す。直近の報告から半年を過ぎたら、「半年以内の報告がありません」と添える（2026-11-12 に変えた。前は「割符が確かめた日。確かめ直しの間隔を過ぎたら一覧2に戻す」。ADR 0028 の O-96）。
5. **出す場所を限る**：出すのは、その企業との接続を始めるときの同意の画面と、別名の一覧の企業ごとの詳細だけにする。承認、窓口コード、回復の画面と、ロック画面やプッシュ通知には出さない。承認の判断に要らない情報で、画面を重くしないためである。完全な参加の企業には出さない（2026-11-13 に変えた：参加の状態によらず、残っていると報告された入り口、運営者が `entryOverrides` に載せた入り口、半年を過ぎた報告があれば、完全な参加の企業にも出す。ADR 0028 の O-105）。
6. **残っている入り口がないときも「安全」とは書かない**：一覧2の項目と補足の代わりに、「この企業は、ここに挙げた入り口をすべて閉じたと報告しています。割符は、閉じたことを確かめていません。」とだけ出す（2026-11-12 に変えた）。

### 4. 主張の範囲と、残るリスク

- 「接続要件を守る企業」は、完全な参加の企業を指す。移行中の企業は含めない（plan 1-2、01 の 3章）。
- 残るリスクに「移行中の企業に残っている入り口」を足す（plan 1-2、RR-14）。漏れた連絡先や属性で、入り口の一覧の経路から本人確認を突破されうる。この企業独自のパスワードでのログイン（ENT-02）が残る間は、漏れたパスワードでも突破されうる。ENT-01 が残る間は、未紐付けの会員の旧アカウントを奪って、攻撃者の sub を紐付ける場面（紐付けの攻撃）も成り立ちうる。移行中に攻撃者の sub が紐付いたアカウントでは、攻撃者が自分の端末で操作ごとの承認を出せるので、高リスクの操作の守りも働かない。このアカウントは、完全な参加に移った後も残る。P0 には、付け替えの手段がない（RP-34。P1）。

### 5. 実装の時期

- **文書**：この変更で、plan、仕様書（01〜04、README）、DESIGN.md、test/leak/README.md、リポジトリの README.md、ADR 0001、principle-review の SKILL.md に反映する。
- **M5（company-api）**：テナントの登録に、参加の状態（完全・移行中）、移行中の期限、割符が確かめた項目と確かめた日を保存する（M9 で、報告者の指名と `entryOverrides` を足し、企業の報告は DB の `company_api.participation_reports` に置く。割符が確かめた項目は、空のままにする。ADR 0028 の O-95・O-105）。テナントの登録の形を決めるのが M5 なので、後から登録の形を変えずに済むように、ここで持たせる。確かめた項目は、登録の時点では空（すべて「残っている」）にする。これらの列は、企業向けのルート（company-api と、CIBA の結果で呼べるもの）から書き換えられないようにする（テスト6）。M9 で表示ができるまでは、移行中の状態のテナントを登録することも、登録済みのテナントを移行中の状態に変えることもできないようにする。
  - → M5 で、テナントの登録を配備のときの静的な設定にした（DB に置かない。どのルートからも書き換えられない）。参加の状態、移行中の期限、確かめた入り口を持たせ、M9 までは full・期限なし・空だけを受け付ける（ADR 0022）。
- **M9（rp-kit、適合テスト）**：
  - 接続の同意の画面と、別名の一覧の企業ごとの詳細に、警告文 I を出す。
  - 割符の側から入り口が閉じたことを確かめる方法と、その結果を記録する経路を、適合テストキットと合わせて決める。
    - → 割符の側からは確かめない。企業が確かめ、企業向けの報告画面で報告する（2026-11-13。ADR 0028 の O-94・O-95・O-105）。
  - 適合テストキットを、移行中の参加に合わせて広げる。緩めるのは、一覧2にある（企業が閉じたと報告していない）入り口に対応する検査だけにする。一覧1に移った入り口に対応する検査と、入り口の一覧で緩めていない検査（email でアカウントをまとめる、sub の書き換えなど）は、移行中でも不合格にする。
  - テスト9を広げる（plan 11章）。
  - 不合格になることと、検査の分け方は、作り物の観測で示す（下の「M9 の前の判断」）。
- 表示を作る M9 までは、移行中の参加の企業を接続しない。いまは、接続している企業はない（ADR 0009）。
- 法務の確認は、イシュー #15 で行う。

## 理由

- 段階的な参加を認めないままだと、参加する企業が増えず、原則2・3も広がらない。
- 段階を認めても、主張を言える範囲を「完全な参加」に限れば、主張そのものは弱めずに済む。主張は、もともと「接続要件を守る企業」に限っている。
- 入り口の一覧を利用者に見せれば、緩めた分のリスクを隠さずに済む。企業にとっては、項目を「切り替わったもの」に移すことが、入り口を閉じる動機になる。
- 切り替わったものも出すのは、その企業で何が割符に切り替わり、何が残っているかを利用者に分かるようにすることを、オーナーが求めたためである。✓を付けない一覧の形にすること、既定を「残っている」にすること、割符が確かめたものだけを移すこと、確かめ直しの間隔を過ぎたら戻すことで、表示が誤って安心を与える方向に壊れないようにする（2026-11-12 に、確かめ方を企業の報告に変えた。かわりに、一覧1の見出しで報告に基づくことを示し、報告が古いことも出す。下の「M9 の判断」）。

## 案からの変更

1. **番号と名前**：0008 を 0010 にし、「金庫」を「割符」に置き換えた。
2. **規則1**：案は「残っているものだけを出す」だった。オーナーの判断で、「割符で確かめる方法に切り替わったもの」と「まだ残っている入り口」の両方を出すことにした。案の守り（✓を付けない、緑の「安全」の表示にしない、既定は「残っている」、割符が確かめたときだけ移す、確かめた日を出す、間隔を過ぎたら戻す、固定の文言だけ、出す場所を限る）は、そのまま残した。
3. **規則4**：一覧が2つになり、項目ごとに確かめた日が違いうるので、日付を一覧1の各項目に付けることにした。
4. **規則6**：案の「決めていないこと」にあった「残っている入り口がないときに、何も出さないか、規則6の文を出すか」は、規則6の文を出すことに決めた（オーナーの判断）。
5. **ENT-02 で緩める要件**：案では、ENT-01 は RP-31 と RP-32 を、ENT-02 は RP-04 だけを緩めていた。RP-31 は、紐付けの完了と同時に、旧ログインと再設定の両方を廃止することを求める。表示を見るのは、これから接続する（紐付ける）利用者である。表示を、その利用者のアカウントに紐付けの後も残る入り口と合わせるため、ENT-02 でも RP-31（旧ログイン）を緩めることを明記した。
6. **肯定リストと高リスクの操作**：案の「それ以外の接続要件は、すべてそのまま守る」とだけ書くと、入り口の一覧の経路そのものが、RP-01〜03（ENT-02 のログインでの識別を含む）や、RP-08（ENT-03 での番号や電話番号による照合）と食い違う。そこで、例外を入り口の一覧の経路の中に限ることと、緩める要件を明記した。RP-07（属性による本人確認。ENT-03 の画面と API の中でも）と、RP-05（別名を再設定の宛先やアカウントを探す値に使わないこと）は緩めない。ENT-03 からは、高リスクの操作を除いた（RP-10 は緩めない）。
7. **テスト9**：「項目が切り替わったものに移るのは、割符が確かめた後だけ」を足した。
8. **実装の時期**：M5 と M9 の分担を足した（オーナーから任された判断）。

## 点検による変更（2026-10-22）

公開のリポジトリに入れる前に、principle-review で点検した。

1. **再設定の宛先の変更**（オーナーの判断）：ENT-03 が残っていると、予約番号と電話番号を知っているだけの人が、再設定の宛先を自分のものに書き換えて、ENT-01 で再設定し、自分の sub を紐付けられる。紐付けた後は、高リスクの操作の操作ごとの承認も、攻撃者の端末で通る。そこで、移行中の企業では、ENT-01 の再設定の宛先の変更を、高リスクの操作と同じに扱うことにした（RP-18）。
2. **完全な参加から移行中の参加に戻すこと**（オーナーの判断）：認める。戻すときは、警告文 I を出し、その企業と接続済みの利用者に知らせる。条件と手順は M9 で決める。M9 までは、登録済みのテナントを移行中の状態に変えることもできないようにする。
3. **ENT-03 の文言**：ゲスト照会の禁止（RP-40）の例外は、照会・変更・取り消しのすべてに及ぶ。表示が、残している範囲より狭く見えないように、文言に「取り消し」を足した。
4. **文書どうしの食い違い**：「悪い RP」のモードと CLAUDE.md の関係が未定であることを、plan、02、principle-review の SKILL.md にも書いた。RR-04 と plan 7章に、移行中の例外を書いた。紐付けの攻撃で攻撃者の sub が紐付いたアカウントでは操作ごとの承認も守りにならないこと、移行中から完全な参加に移った後もそのアカウントが残ること、割符の確かめは確かめた時点の試験用のアカウントについての結果であることを、残るリスク（RR-14、TH-09）に書いた。RP-01 を緩めるのは、ENT-02 のログインでの識別だけであることを、はっきりさせた。

## M9 の前の判断（2026-11-06）

M9 の前にオーナーが決めることにしていた、demo-rp の「悪い RP」のモードと CLAUDE.md の不変条件の関係を、オーナーが決めた。

- **「悪い RP」のコードを作らない**：demo-rp の「悪い RP」のモードは作らない。入り口の一覧の経路も、メールなどでアカウントをまとめる振る舞いも、rp-kit、demo-rp、テスト、スクリプトのどこにも置かない。CLAUDE.md の不変条件1は「テスト用の補助」にも適用する。このモードを作ると、テストの中だけでも、メールで本人を特定するコードを書くことになり、不変条件とぶつかる。CLAUDE.md は変えない。
- **キットが不合格にすることの確かめ方**：適合テストキットを、観測を集める部分（模擬 OP、RP 側のテスト用フックや経路への問い合わせ）と、観測から合否を決める部分に分ける。不合格になることは、合否を決める部分に作り物の観測を与えて確かめる。例：同じ email で sub の違う2人が、同じ内部のアカウントになった。紐付けの後に、旧ログインや再設定が通った。観測を集める部分は、固定の応答を返す模擬を相手にして、応答を観測に正しく写すことを確かめる。作り物の観測と模擬の応答は、入力によらない固定の値にし、メール、sub、別名、パスワードなどの値を見て変えない。
- **移行中の参加の検査の分け方**：キットに移行中の設定（一覧1と一覧2）と作り物の観測を与えて示す。一覧2の入り口に対応する検査だけが緩み、一覧1に移った入り口に対応する検査と、緩めていない検査は不合格になることを確かめる。「決めていないこと」の、どこで確かめるか、への答えでもある。
- **失うもの**：悪い振る舞いをする実際の RP にキットを端から端まで当てて、不合格になるところは示さない。デモでも、悪い振る舞いを動かして見せない。確かめられるのは、キットの合否の判定と、応答から観測への写し方までである。完全な参加の企業の振る舞い（demo-rp）にキットを当てて合格することは、端から端まで確かめる。
- 直した文書：plan（1-1、3-3、10章の M9、11章のテスト9）、[01](../spec/01-principles.md)、[02](../spec/02-rp-requirements.md) の 14章と 15-1、[03](../spec/03-threat-model.md) の TH-44、principle-review の SKILL.md の観点1。

## M9 の判断（2026-11-12）

イシュー #60 で、オーナーは、割符と企業の責務の分け方を示した（割符は橋渡し役で、古い会員情報や仕組みの管理と削減は企業の責務）。それを受けて、ADR 0028 で M9 の細目を決め、この ADR の次の点を変えた。

- **割符は、入り口が閉じたことを確かめない**：企業が自分で確かめ、結果と日を、企業向けの報告画面で報告する（2026-11-13 に決めた。O-105）。試験用のアカウントと外からの検査は作らない（O-94・O-95）。
- **表示**（O-105。分けて出し、割符は確かめていないと明記し、変わるたびに更新する方針は決めた。文言の細部は未決で、下の見出しは案）：2つの一覧の形は保つ。一覧1の見出しを「この企業が、閉じたと報告している入り口（割符は確かめていません）」に変え、企業が確かめた日、切り替えの期限、直近の報告の日を出す。✓や緑の色を付けないこと、「安全」「対策済み」「認定」と書かないこと、企業が書いた文言を出さないことは変えない（O-105）。今の文言は DESIGN.md 3章を正とする。
- **棚卸し**：企業が半年に1回、棚卸しをして報告する。報告がなければ、企業に知らせ、画面に「半年以内の報告がありません」と出す。止めない（O-96）。
- **知らせ**：参加の状態が変わったときは、割符から企業へ知らせる。利用者への案内は企業が行い、割符は利用者に再同意を求めない（O-97）。
- **期限**：原則6か月。企業が残りの作業と見込みを報告し、運営者が内容を確認したうえで、必要な期間を延長する。回数は固定しない。延長の手順は、2026-11-14 に決めた（企業が残りの作業、完了の見込み、希望の期限を申請し、運営者は事項がそろっていることを確かめて、原則として希望どおりの期限で延長する。旧経路は検査しない。ADR 0028 の O-93）。期限を過ぎ、延長の申請もないときは、企業に督促し、表示に出す。期限切れだけでは、新しい接続、移行の申請、既存の接続を自動では止めない（2026-11-13。ADR 0028 の O-93）。
- **旧経路の廃止**：企業の古い仕組みの管理と削減は企業の責任とし、廃止は必須にせず、強く推奨する。すべて閉じたと報告した企業を完全な参加とし、主張はその企業に限る（O-106）。
- **主張の範囲**は変えない。「接続要件を守る企業」は完全な参加の企業を指す。企業の報告が誤っていても、割符には分からない（残るリスク。RR-14）。

## 却下した案

- **段階を認めない（いまのまま）**：原則には最も忠実だが、導入の壁が下がらない。
- **残っているものだけを出す（案の規則1）**：オーナーは、その企業で何が適用され、何が適用されていないかが、利用者に分かることを求めた。残っているものだけでは、切り替わったものが分からない。「安全」と読まれることは、✓を付けない一覧の形と、上の規則2〜6で防ぐ。
- **✓付きのチェックリスト**：閉じた項目に✓を付けると、全部そろったときに「安全な企業」と読まれる。
- **企業の自己申告で表示を変える**：テナント由来の値を信用することになる（DESIGN.md の原則2）。
  - → 2026-11-12 に、イシュー #60 の方針で、企業の報告で一覧1に移すことにした。報告は、テナントが指名した報告者が、割符の企業向けの報告画面で、自社の入り口の報告だけを変える（参加の状態と期限は変えられない。2026-11-13。O-105）。一覧1の見出しで「企業の報告で、割符は確かめていない」ことを示す。企業が書いた文言は、これまでどおり出さない（ADR 0028 の O-94・O-105）。
- **適合した企業に認定のバッジを出す**：✓と同じく、断定として読まれる。
- **CLAUDE.md に注記を足して、demo-rp に「悪い RP」のモードを置く**（2026-11-06）：テストの中でだけ有効にしても、メールで本人を特定するコードを書くことになる。不変条件に例外を作らないことを選んだ。
