# ADR 0010：移行中の参加と、企業ごとの「切り替わったもの」「残っている入り口」の表示

> **現行仕様への注記（ADR 0019・0020の文書PR案）**：CIBAを前提とする画面・クライアントの記述はADR 0019案のstep-upへ読み替える。移行中の参加自体とENT-01〜03の例外は維持し、会員別の旧経路閉鎖の追加は確認待ち。 この文書の過去の決定・試験結果は履歴として残す。

- 状態：採用（2026-10-21 にオーナーが確認した。2026-10-22 に、公開のリポジトリでの点検を受けて変えた。下の「点検による変更」。細部は「決めていないこと」）
- 日付：2026-10-21

この ADR は、2026-10-20 に書いた案（「ADR 0008（提案）：移行中の参加と『残っている入り口』の表示」）をもとにしている。案は、名前が「金庫」だったときに書いた。0008 は別の ADR（2026年10月の注意喚起を受けた見直し）が使っているので、0010 にした。名前は「割符」に置き換えた（ADR 0009）。案から変えたところは、下の「案からの変更」にまとめた。

この ADR は、非公開のリポジトリで書いて、オーナーが確認した。公開のリポジトリには最初のコミットの後に入れた（ADR 0011。イシュー #20）。

## 状況

いまの接続要件では、企業は割符に参加した時点で、次のすべてを済ませなければならない（plan 3-3、[02](../spec/02-rp-requirements.md)）。

- ログインを割符のパスキーだけにする（RP-04）
- 未紐付けの会員も含めて、メールや SMS による再設定を止める（RP-31、RP-32）
- ゲスト照会の画面と API をなくす（RP-40）

これは原則のとおりで、旧経路が1本でも残れば、「漏れた連絡先や属性を知っている・受け取れるだけでは、本人確認は突破できない」という主張は成り立たない。

一方で、企業にとっては、会員の移行、窓口の業務、サポートの体制を一度に変えることになり、導入の壁が大きい。企業が ID 管理の製品を選ぶときには、導入の速さが重視されやすく、割符はこの点で不利である。参加する企業が増えなければ、別名と pairwise sub による「持たせない」「つなげさせない」も広がらない。

## 決定

### 1. 参加を2つの状態に分ける

| 状態 | 意味 | 主張（plan 1-2） |
|---|---|---|
| 完全な参加 | いまの接続要件をすべて守る | 言ってよい |
| 移行中の参加 | 下の「入り口の一覧」にある経路だけを、期限まで残してよい。それ以外の接続要件は、すべてそのまま守る | 言ってはならない。この企業は「接続要件を守る企業」に含めない |

- 残してよい経路は、次の固定の一覧（入り口の一覧）にあるものだけにする。一覧にない経路を残すことは認めない。
- 経路を残すことは、その経路が使う値（パスワード、メールや SMS に届くリンクやコード、予約番号や電話番号など）を根拠にすることと同じである。そこで、入り口の一覧の経路の中に限って、識別と肯定リストの要件（RP-02・RP-03 と、ENT-02 のログインでの識別についての RP-01）と、ENT-03 の画面と API の中での RP-08 について、例外を期限まで認める。経路の外（窓口、高リスクの操作、アカウントの統合、紐付けと sub の扱い）では、これらをそのまま守る。住所や生年月日などの属性による照合（RP-07）は、ENT-03 の画面と API でも認めない。ENT-03 で照合に使ってよいのは、RP-40 に挙げた値（予約番号、電話、メール、氏名。別名は除く）だけにする。警告文 I の補足で利用者に挙げる値と、合わせるためである。どの経路でも、別名を、再設定の宛先にも、アカウントを探す値にも使わせない（RP-05 は緩めない）。
- 高リスクの操作は、移行中でも、操作ごとの承認だけを根拠にする（RP-10、RP-13 は緩めない）。入り口の一覧の経路から、高リスクの操作をさせない。ENT-01 の再設定の宛先（企業が持つメールや電話番号）の変更も、高リスクの操作と同じく、操作ごとの承認だけを根拠にする。入り口の一覧の経路（ENT-03 の変更を含む）から変えさせない（RP-18）。
- 移行中の参加には期限を付ける。期限の長さと、期限を過ぎたときの扱い（新しい接続の受け付けを止める、など）は、まだ決めていない（下の「決めていないこと」）。
- 完全な参加から移行中の参加に戻すことは認める。戻すときは、警告文 I を出し、その企業と接続済みの利用者に知らせる。条件と手順は、M9 で決める。
- rp-kit の SDK と demo-rp の参照実装は、完全な参加だけを実装し、入り口の一覧の経路を作る機能や設定を入れない。入り口の一覧の経路は、demo-rp の「悪い RP」のモード（テスト9）の中にだけ置き、適合テストキットが不合格にすることを示すためだけに使う。検査の分け方は、このモードを移行中の設定にしたうえで、一覧1に移った入り口に対応する検査と、緩めていない検査が不合格になることで示す。このモードは、テストの中でだけ有効にし、既定では無効にする。キットに合格する移行中の企業の設定を、demo-rp の画面や手引きで見本として示さない。適合テストキットは、移行中の参加の検査の分け方（02 の 15-1）を持つ。
- CLAUDE.md の不変条件は変えない。CLAUDE.md は、不変条件を「コード、ライブラリの設定、テスト用の補助、スクリプトのすべてに適用する」としている。割符のコードは、移行中の参加の企業についても、連絡先や属性を、本人確認・承認・識別の根拠にしない。適合テストキットが持つのは、企業の側の検査を緩めるかどうかの分け方だけである。demo-rp の「悪い RP」のモードは、適合テストキットが不合格にすることを示すための模擬で、参照実装には含めない。このモードと、CLAUDE.md の「テスト用の補助」との関係は、まだ決めていない（下の「決めていないこと」）。一方、[ADR 0001](0001-affirmative-list.md) は (a) を「接続要件と適合テストで課す」としている。そのため、この ADR は、ADR 0001 の (a) の接続要件での課し方を、移行中の参加の企業について変える。
- 割符の側の守り（sub と別名をテナントごとに独立させること、CIBA の hint、送信元ロックなど）は、移行中の企業についても変えない。

### 2. 入り口の一覧

| ID | 入り口（利用者に出す文言） | 緩める要件 | 企業の側の検査（適合テストキット。[02 の 15-1](../spec/02-rp-requirements.md#15-1-適合テストキットp0m9テスト9)） |
|---|---|---|---|
| ENT-01 | メールや SMS に届くリンクやコードでの、パスワードなどの再設定 | RP-31（再設定）、RP-32、RP-02・RP-03（この経路の中だけ） | 旧経路、紐付けの攻撃 |
| ENT-02 | この企業独自のパスワードでのログイン | RP-04、RP-31（旧ログイン）、RP-01（この経路のログインでの識別）、RP-02・RP-03（この経路の中だけ） | 旧経路 |
| ENT-03 | 予約番号や電話番号などでの、予約や注文の確認・変更・取り消し | RP-40、RP-08、RP-02・RP-03（どれも画面と API の中だけ。高リスクの操作は除く。RP-10） | ゲスト照会 |

- 一覧に載せるのは、割符が閉じたことを確かめられる経路だけにする。M9 で確かめ方が決まらない項目は、一覧から外す（その経路は、移行中でも残せない）。
- 窓口で氏名や生年月日を聞いて本人確認すること（RP-07、RP-27）は、監査でしか確かめられないので、一覧に載せない。この経路は移行中でも残してはならない。
- 各項目の文言は1つにし、下の2つの一覧のどちらに出すときも、同じ文言を使う。

### 3. 利用者の画面に「切り替わったもの」と「まだ残っている入り口」を出す

移行中の企業については、入り口の一覧の各項目を、「割符で確かめる方法に切り替わったもの」と「まだ残っている入り口」に分けて、利用者の画面に出す。目的は、利用者が、その企業でどこまで割符が使われ、どこが使われていないかを知ったうえで、接続を選べるようにすることと、企業が早く入り口を閉じる動機をつくること。

**表示の規則**：

1. **2つの一覧を出す**：「割符で確かめる方法に切り替わったもの」（一覧1）と「まだ残っている入り口」（一覧2）を、同じ大きさ、同じ見た目で並べる。
   - 一覧1の項目に、✓などの「済み」を示す印、緑の色、目立つ強調を付けない。緑の✓が並ぶと、「この企業は安全」と読まれるためである（DESIGN.md 4章の、断定を使わない規則）。ブラウザの鍵マークが「安全なサイト」と誤解されたのと同じ問題を避ける。
   - 「安全」「対策済み」「認定」などの言葉を使わない。事実だけを、中立の文言で書く。
   - 一覧1が空のときは、一覧1の見出しも出さない。
2. **既定は「残っている」**：項目を一覧1に移すのは、割符が自ら閉じたことを確かめたときだけにする。企業の自己申告では移さない。確かめていない項目は、一覧2に出す。
3. **文言は固定**：見出し、一覧の見出し、各項目、補足の文、日付、規則6の文は、割符が定めた固定の文言だけにする（DESIGN.md の原則2・5）。企業は文言を足したり変えたりできない。企業名は登録簿の値を使う。
4. **確かめた日を出す**：一覧1の各項目に、割符が確かめた日を付ける。確かめ直しの間隔を過ぎた項目は、一覧2に戻す。
5. **出す場所を限る**：出すのは、その企業との接続を始めるときの同意の画面と、別名の一覧の企業ごとの詳細だけにする。承認、窓口コード、回復の画面と、ロック画面やプッシュ通知には出さない。承認の判断に要らない情報で、画面を重くしないためである。完全な参加の企業には出さない。
6. **残っている入り口がないときも「安全」とは書かない**：一覧2の項目と補足の代わりに、「割符が確かめた範囲では、まだ残っている入り口は見つかっていません。割符が確かめているのは、上に挙げた入り口だけです。」とだけ出す。

**固定の文言**（DESIGN.md 3章に、警告文 I として足す）：

```
I（移行中の企業）
見出し：〈企業名〉は、割符への切り替えの途中です
一覧1の見出し：割符で確かめる方法に切り替わったもの
一覧1の項目：入り口の一覧（ENT-01〜03）の文言のうち、割符が閉じたことを確かめたもの
日付（一覧1の各項目の後に付ける。〈日付〉は年を含める）：（割符が確かめた日：〈日付〉）
一覧2の見出し：まだ残っている入り口
一覧2の項目：入り口の一覧（ENT-01〜03）の文言のうち、一覧1にないものすべて
補足：ここに挙げた入り口は、割符が、閉じたことをまだ確かめていないものです。これらは、あなたの氏名、メールアドレス、電話番号、予約番号、パスワードなどを知っている人にも使われるおそれがあります。
規則6の文（一覧2が空のとき、一覧2の項目と補足の代わりに出す）：割符が確かめた範囲では、まだ残っている入り口は見つかっていません。割符が確かめているのは、上に挙げた入り口だけです。
```

### 4. 主張の範囲と、残るリスク

- 「接続要件を守る企業」は、完全な参加の企業を指す。移行中の企業は含めない（plan 1-2、01 の 3章）。
- 残るリスクに「移行中の企業に残っている入り口」を足す（plan 1-2、RR-14）。漏れた連絡先や属性で、入り口の一覧の経路から本人確認を突破されうる。この企業独自のパスワードでのログイン（ENT-02）が残る間は、漏れたパスワードでも突破されうる。ENT-01 が残る間は、未紐付けの会員の旧アカウントを奪って、攻撃者の sub を紐付ける場面（紐付けの攻撃）も成り立ちうる。移行中に攻撃者の sub が紐付いたアカウントでは、攻撃者が自分の端末で操作ごとの承認を出せるので、高リスクの操作の守りも働かない。このアカウントは、完全な参加に移った後も残る。P0 には、付け替えの手段がない（RP-34。P1）。

### 5. 実装の時期

- **文書**：この変更で、plan、仕様書（01〜04、README）、DESIGN.md、test/leak/README.md、リポジトリの README.md、ADR 0001、principle-review の SKILL.md に反映する。
- **M5（company-api）**：テナントの登録に、参加の状態（完全・移行中）、移行中の期限、割符が確かめた項目と確かめた日を保存する。テナントの登録の形を決めるのが M5 なので、後から登録の形を変えずに済むように、ここで持たせる。確かめた項目は、登録の時点では空（すべて「残っている」）にする。これらの列は、企業向けのルート（company-api と、CIBA の結果で呼べるもの）から書き換えられないようにする（テスト6）。M9 で表示ができるまでは、移行中の状態のテナントを登録することも、登録済みのテナントを移行中の状態に変えることもできないようにする。
- **M9（rp-kit、適合テスト）**：
  - 接続の同意の画面と、別名の一覧の企業ごとの詳細に、警告文 I を出す。
  - 割符の側から入り口が閉じたことを確かめる方法と、その結果を記録する経路を、適合テストキットと合わせて決める。
  - 適合テストキットを、移行中の参加に合わせて広げる。緩めるのは、一覧2にある（割符が閉じたことを確かめていない）入り口に対応する検査だけにする。一覧1に移った入り口に対応する検査と、入り口の一覧で緩めていない検査（email でアカウントをまとめる、sub の書き換えなど）は、移行中でも不合格にする。
  - テスト9を広げる（plan 11章）。
- 表示を作る M9 までは、移行中の参加の企業を接続しない。いまは、接続している企業はない（ADR 0009）。
- 法務の確認は、イシュー #15 で行う。

## 理由

- 段階的な参加を認めないままだと、参加する企業が増えず、原則2・3も広がらない。
- 段階を認めても、主張を言える範囲を「完全な参加」に限れば、主張そのものは弱めずに済む。主張は、もともと「接続要件を守る企業」に限っている。
- 入り口の一覧を利用者に見せれば、緩めた分のリスクを隠さずに済む。企業にとっては、項目を「切り替わったもの」に移すことが、入り口を閉じる動機になる。
- 切り替わったものも出すのは、その企業で何が割符に切り替わり、何が残っているかを利用者に分かるようにすることを、オーナーが求めたためである。✓を付けない一覧の形にすること、既定を「残っている」にすること、割符が確かめたものだけを移すこと、確かめ直しの間隔を過ぎたら戻すことで、表示が誤って安心を与える方向に壊れないようにする。

## 案からの変更

1. **番号と名前**：0008 を 0010 にし、「金庫」を「割符」に置き換えた。
2. **規則1**：案は「残っているものだけを出す」だった。オーナーの判断で、「割符で確かめる方法に切り替わったもの」と「まだ残っている入り口」の両方を出すことにした。案の守り（✓を付けない、緑の「安全」の表示にしない、既定は「残っている」、割符が確かめたときだけ移す、確かめた日を出す、間隔を過ぎたら戻す、固定の文言だけ、出す場所を限る）は、そのまま残した。
3. **規則4**：一覧が2つになり、項目ごとに確かめた日が違いうるので、日付を一覧1の各項目に付けることにした。
4. **規則6**：案の「決めていないこと」にあった「残っている入り口がないときに、何も出さないか、規則6の文を出すか」は、規則6の文を出すことに決めた（オーナーの判断）。
5. **ENT-02 で緩める要件**：案では、ENT-01 は RP-31 と RP-32 を、ENT-02 は RP-04 だけを緩めていた。RP-31 は、紐付けの完了と同時に、旧ログインと再設定の両方を廃止することを求める。表示を見るのは、これから接続する（紐付ける）利用者である。表示を、その利用者のアカウントに紐付けの後も残る入り口と合わせるため、ENT-02 でも RP-31（旧ログイン）を緩めることを明記した。
6. **肯定リストと高リスクの操作**：案の「それ以外の接続要件は、すべてそのまま守る」とだけ書くと、入り口の一覧の経路そのものが、RP-01〜03（ENT-02 のログインでの識別を含む）や、RP-08（ENT-03 での番号や電話番号による照合）と食い違う。そこで、例外を入り口の一覧の経路の中に限ることと、緩める要件を明記した。RP-07（属性による本人確認。ENT-03 の画面と API の中でも）と、RP-05（別名を再設定の宛先やアカウントを探す値に使わないこと）は緩めない。ENT-03 からは、高リスクの操作を除いた（RP-10 は緩めない）。
7. **テスト9**：「項目が切り替わったものに移るのは、割符が確かめた後だけ」を足した。
8. **実装の時期**：M5 と M9 の分担を足した（オーナーから任された判断）。

## 点検による変更（2026-10-22）

公開のリポジトリに入れる前に、principle-review で点検した。

1. **再設定の宛先の変更**（オーナーの判断）：ENT-03 が残っていると、予約番号と電話番号を知っているだけの人が、再設定の宛先を自分のものに書き換えて、ENT-01 で再設定し、自分の sub を紐付けられる。紐付けた後は、高リスクの操作の操作ごとの承認も、攻撃者の端末で通る。そこで、移行中の企業では、ENT-01 の再設定の宛先の変更を、高リスクの操作と同じに扱うことにした（RP-18）。
2. **完全な参加から移行中の参加に戻すこと**（オーナーの判断）：認める。戻すときは、警告文 I を出し、その企業と接続済みの利用者に知らせる。条件と手順は M9 で決める。M9 までは、登録済みのテナントを移行中の状態に変えることもできないようにする。
3. **ENT-03 の文言**：ゲスト照会の禁止（RP-40）の例外は、照会・変更・取り消しのすべてに及ぶ。表示が、残している範囲より狭く見えないように、文言に「取り消し」を足した。
4. **文書どうしの食い違い**：「悪い RP」のモードと CLAUDE.md の関係が未定であることを、plan、02、principle-review の SKILL.md にも書いた。RR-04 と plan 7章に、移行中の例外を書いた。紐付けの攻撃で攻撃者の sub が紐付いたアカウントでは操作ごとの承認も守りにならないこと、移行中から完全な参加に移った後もそのアカウントが残ること、割符の確かめは確かめた時点の試験用のアカウントについての結果であることを、残るリスク（RR-14、TH-09）に書いた。RP-01 を緩めるのは、ENT-02 のログインでの識別だけであることを、はっきりさせた。

## 却下した案

- **段階を認めない（いまのまま）**：原則には最も忠実だが、導入の壁が下がらない。
- **残っているものだけを出す（案の規則1）**：オーナーは、その企業で何が適用され、何が適用されていないかが、利用者に分かることを求めた。残っているものだけでは、切り替わったものが分からない。「安全」と読まれることは、✓を付けない一覧の形と、上の規則2〜6で防ぐ。
- **✓付きのチェックリスト**：閉じた項目に✓を付けると、全部そろったときに「安全な企業」と読まれる。
- **企業の自己申告で表示を変える**：テナント由来の値を信用することになる（DESIGN.md の原則2）。
- **適合した企業に認定のバッジを出す**：✓と同じく、断定として読まれる。

## 決めていないこと

- 移行中の参加の期限の長さと、期限を過ぎたときの扱い（M9 で決める）。
- 割符が入り口を「閉じた」と確かめる方法（M9 で決める）。rp-kit の適合テストは企業の側で動くので、その結果をそのまま使うと自己申告と変わらない。割符の側から確かめる方法（送信サービスを通した外からの検査、監査人の立ち会いなど）を決める必要がある。外からの検査で外へつなぐときは、送信サービスを通す（不変条件7）。決まるまでは、規則2により、すべての項目を一覧2に出す。確かめる方法では、利用者の本物の連絡先も別名も使わず、割符が用意した試験用のアカウントだけを使う（不変条件2・4）。検査で受け取った再設定のリンクやコードも、平文で残さない（不変条件4）。試験用のアカウントで確かめた結果は、確かめた時点の、そのアカウントについてのもので、企業が利用者の一部にだけ入り口を残すことは見抜けない（RR-14）。外からの検査に企業が同意することも、接続の契約に入れる（RP-17 と合わせる）。
- 確かめた結果を記録する経路と、idp が表示のために参加の状態を読む方法（M9 で決める）。管理 API も、不変条件8の新しい例外も作らない方法から選ぶ。記録と、その書き換えは、監査ログに残す。
- 確かめ直しの間隔（M9 で決める）。
- 一覧1の項目が一覧2に戻ったときに、その企業と接続済みの利用者に知らせるか（M9 で決める）。
- 一覧2の入り口に対応する検査を緩めることを、どこで確かめるか（rp-kit の単体検査の模擬で足りるか。M9 で決める）。キットに合格する移行中の企業の設定は、demo-rp には置かない。
- demo-rp の「悪い RP」のモードと、CLAUDE.md の不変条件（「テスト用の補助」にも適用する）との関係。このモードは、不合格を示すための模擬として plan 10章の M9 に元からある。CLAUDE.md に注記を足すかを、オーナーが M9 の前に決める。
