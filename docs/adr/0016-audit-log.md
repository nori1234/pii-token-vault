# ADR 0016：監査ログ：2つの表と HMAC のチェーン

- 状態：提案（オーナーの確認待ち。下の「オーナーの確認」の既定の案で実装した）
- 日付：2026-10-23

## 状況

CAP-17 は、監査ログをチェーンにして検証できるようにし、追記を `pg_advisory_xact_lock` で直列にすることを求めている（テスト8）。一方で、監査ログにもテナントの境界（plan 2章「BOLA を防ぐ」）と、平文を残さないこと（不変条件4）が適用される。チェーンを全体で1本にすると、全テナントの行が必要になり、境界と衝突する。

## 決定

- **全体のチェーン** `audit.chain(seq, content_mac, prev_mac, mac)`：テナントも利用者も持たない。境界の中なら、どのアプリのロールも全行の MAC を読める（追記のときに先頭を知るため）。分かるのは件数だけ。
- **本文** `audit.events(seq, scope_seq, occurred_at, service, event_type, tenant_id, user_id, attrs)`：範囲（テナントか利用者のどちらか1つ）を RLS で限る。境界の中からは、自分の範囲の行しか見えず、自分の範囲と、自分のサービスの名前でしか書けない。範囲ごとの通番 `scope_seq` を持つ。
- MAC は鍵サービスの `mac(audit_chain)`（ADR 0013）。DB だけを持つ攻撃者は、MAC を計算し直せない。ハッシュではなく HMAC にするのは、不変条件9（「ハッシュ」も HMAC-SHA-256）と、改ざんした者に計算し直させないため。

```
scope         = ('tenant', tenant_id) または ('user', user_id)
content_mac_i = HMAC(k, lp('warifu/audit/content/v1', scope の種類, scope の ID, scope_seq, occurred_at のミリ秒,
                           service, event_type, canonicalJson(attrs)))
mac_i         = HMAC(k, lp('warifu/audit/link/v1', seq, prev_mac_i, content_mac_i))
prev_mac_1    = 32バイトの0
```

- **追記**（`appendAudit`）：属性を検査し、`pg_advisory_xact_lock` で全体で1つの鍵を取り、全体の先頭と範囲の先頭を読み、MAC を計算して2つの表に INSERT する。ロックはコミットまで持つので、追記はトランザクションの最後の文にする。範囲は境界から決まり、呼び出し側は渡せない。
- **追記だけ**：UPDATE、DELETE、TRUNCATE はどのロールにも GRANT せず、所有者でもトリガーで拒否する（マイグレーションの誤りへの備え）。スーパーユーザーはトリガーも外せるので、改ざんの検出は HMAC のチェーンに頼る。
- **属性に入れてよいもの**：UUID、整数、真偽値、定義した列挙の文字列だけ（`defineAuditEvent`）。自由な文字列（連絡先、トークン、名前など）は入れられない。M2 では本番の事象を定義しない（M3 以降で、使うマイルストーンが定義する）。
- **検証**（`verifyAuditChain`、`verifyAuditRows`）：全体のチェーンが1から連続していること（gap）、`prev_mac` が前の `mac` と一致すること（link）、`mac` を計算し直して一致すること（mac）、範囲の本文が1から連続していること（scope_gap）、`content_mac` を計算し直して同じ seq のチェーンの行と一致すること（content）を確かめる。
- **保存期間**：P0 では消さない（本物の利用者のデータを持たない）。本番の期間と消し方（チェーンの区切りと先頭の記録、消すロール。新しいロールは不変条件8の例外になりうる）は P1 で決める。

## 採らなかった案

- **監査ログを1つの表にし、境界があれば全行を読ませる**：別のテナントの記録（時刻、操作、主体）が、relay と company-api から読める。plan 9章の「relay がテナントを横断して使えるのは関数だけ」と、テスト6の趣旨に反する。
- **範囲ごとに独立したチェーン**：範囲の中の削除と入れ替えは `scope_seq` と `content_mac` で見つかるので、二重のチェーンは要らない。全体の順序も残したいので、全体のチェーンを1本にした。
- **SHA-256 のハッシュのチェーン**：許可リストにない。DB を書き換えられる者が計算し直せる。

## 残る弱点

- 全体の末尾を切り詰めること、範囲の最後の本文の行だけを消すことは、境界の中の検証では見つからない。外に先頭を記録する仕組み（定期的にチェーンの先頭の MAC を別の場所に残すなど）と、全範囲の検証は P1（本番の運用の手順）で決める。全範囲を読むロールは不変条件8の新しい例外になるので、P0 では作らない。
- 追記のとき、鍵サービスの呼び出し（2回、各2秒まで）の間もロックを持つ。lock_timeout は3秒なので、鍵サービスが遅いと追記が詰まる。

## 結果

- テスト8：t08-audit-chain（3つのサービス、2つのテナント、2人の利用者での検証、同時の追記、書き換えと削除の拒否、別の範囲・別のサービス・境界の外として書けないこと、別のテナントの記録を読めないこと、鍵なしの偽の行、DB を書き換えられる運用者による改ざんの検出）と、単体テスト。

## オーナーの確認

- O-4：監査ログの保存期間。既定の案：P0 では消さない。本番の期間と手順は P1。
- O-7：全体のチェーン（seq と MAC だけ）を、境界の中のすべてのアプリのロールが全行読める。既定の案：読めてよい。テナントも利用者も持たないので、plan 9章の「relay がテナントを横断して使えるのは関数だけ」には当たらないと整理する。分かるのは件数だけ。
