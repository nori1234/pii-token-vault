# ADR 0002：TypeScript と oidc-provider、本番は AWS 東京

- 状態：採用
- 日付：2026-10-17

## 状況

オーナーの方針は「要件に合うもの」を選ぶこと。必要な要件は次のとおり。

- 企業ごとの pairwise sub
- email クレームに企業ごとの別名を載せること
- CIBA
- パスキー
- 復号の権限を relay だけに持たせる権限分離
- メールの送受信
- 鍵の管理

## 決定

- 全体を TypeScript（Node 22、ESM）で書く。
- OIDC は `oidc-provider` 9.x を使う。OpenID の認定を受けており、`pairwiseIdentifier` と CIBA（`features.ciba`）を実装していることをパッケージのソースで確認した。
- パスキーは `@simplewebauthn` 14 を使う。
- メールは `smtp-server`、`mailauth` 7（SPF、DKIM、DMARC、ARC。DNS を差し替えられる）、`nodemailer` を使う。
- 本番は AWS の東京リージョンにする。KMS（エンベロープ暗号と HMAC 鍵）、SES（受信は2023年に東京へ拡大。エンドポイントでの最終確認は要る）、RDS、ECS を使う。PoC はローカルで動かし、鍵とメールは差し替えられるアダプタにする。

## 採らなかった案

- **Keycloak**：管理画面などはそろっている。しかし、企業ごとの別名をクレームに載せるには Java の拡張が要り、relay との権限分離も組みにくい。
- **GCP**：Cloud KMS はあるが、メールを受信するマネージドサービスがなく、SMTP サーバーを自前で運用することになる。

## 結果

- oidc-provider が担うのはプロトコルの部分だけ。CIBA の窓口コード、承認画面、端末承認は自作になる（見込みは 800〜1,200 行）。
  - ADR 0006 で、この見込みを見直した。サーバー側の CIBA の部分だけなら 800〜1,200 行、承認画面と窓口コードの発行画面、受信箱の CIBA の分、事後通知と取り消しまで含めると 1,500〜2,500 行（テストを除く）と見る。どちらも根拠の弱い見積もりで、M6 と M7 の実績で見直す。
- Playwright は 1.56.1 に固定する（環境の Chromium が revision 1194 のため）。
