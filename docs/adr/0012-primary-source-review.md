## 照合で分かったこと

### 1. NIST SP 800-63B-4

- **KBA**：3.1.1.2 が禁じているのは、パスワードを選ぶときに KBA や秘密の質問を促すことである。「KBA を認証として認めない」という文はない。KBA は、2章で AAL ごとに許す認証器の種類に入っていない。standards.md の書き方を、原文に合わせて直した。
- **AAL2 での回復（4.2.2.2）**：次のどれかを求めている（SHALL）。
  1. 方法の違う2つの回復コード（保存型・発行型・recovery contacts の中から）
  2. 回復コード1つと、アカウントに結び付いた単要素の認証器での認証
  3. 身元確認のやり直し
- **recovery contacts（4.2.1.3）**：信頼する人の「アドレス」に発行型の回復コードを送る方式である。割符の協力者は、自分のパスキーで認証したうえで、回復する人の新しい端末に出た QR を読み取って承認する。コードを受け取る方式ではないので、recovery contacts には当たらない。
- **独自の方式（4.2.1）**：4つの方式のほかに、リスク分析に基づいて文書化した独自の方式を「MAY」で認めている。ただし、4.2.2.2 の組み合わせには入っていない。したがって、割符の回復（保存型の回復コード＋協力者の承認＋待機）は、4.2.2.2 の文言どおりの組み合わせではない。
- **保存型の回復コード（4.2.1.1）**：
  - 64ビット以上の乱数（割符の設計と一致）。
  - 3.1.1.2 のとおり、承認された一方向関数でハッシュにして保存する（SHALL）。3.1.1.2 はソルトとコストのあるパスワードハッシュを求めている。割符は、不変条件9により、鍵サービスの HMAC-SHA-256（鍵付き）で照合用の値を作る予定（M2）で、パスワードハッシュは許可リストにない。秘密が64ビット以上の乱数で、鍵が DB の外にあるので、DB が漏れても総当たりは成り立たない。ただし、文言どおりではない。
  - 使ったら失効させ、新しいコードを発行する（SHALL）。割符の計画には、回復が成立した後に新しいコードを発行する手順がなかった。
  - コードの再発行は、回復の知らせ（4.6）の対象になる（SHALL）。
- **回復の知らせ（4.2.3、4.6）**：回復は、必ず本人か本人が指名した人に知らせる。知らせの宛先は、プッシュ通知サービスでの参照でもよい。宛先は2つ以上持てるようにする（SHALL）。割符の「端末の受信箱」と協力者への知らせは、この方向に合う。端末をすべて失った場合に届かないことは、すでに残るリスクにある（ADR 0003）。
- **待機期間**：4.2 は、回復が「長い待ち時間を伴いうる」と書くだけで、数値はない。
- **同期パスキー（3.1.7.4、付録 B）**：付録 B は規範（normative）。同期すると鍵が取り出せるので、AAL3 の取り出せないことの要件に反し、AAL2 までとしている。UV フラグを確かめなければ単要素として扱う（SHALL）。BS フラグで、一般向けのサービスの受け入れを決めることは推奨しない（SHOULD NOT）。割符は BE/BS をリスクの信号として記録するだけで、BS で拒否はしない（plan 4章）。この方向と合う。
- **別の端末での認証器の追加（4.1.2.2）**：結び付けのコードは、利用者 ID と組なら40ビット以上、そうでなければ112ビット以上。1回限り、10分以内。手入力か QR で渡し、メールのような安全でない経路で渡してはならない。協力者の承認の QR は、認証器の追加ではないが、同じ形の受け渡しなので、M8 で値を決めるときの参考にする。

### 2. デジタル庁 DS-511／DS-512

- **当人認証の保証レベル（DS-511 3.2 4) 表3-10）**：レベル2は、多要素認証であること、フィッシング耐性のある手法を希望する利用者が選べること、公開鍵認証なら暗号鍵の不正な取り出し・複製への耐性があること。レベル3は、うち一要素が公開鍵認証で、全員がフィッシング耐性のある手法を使うこと。standards.md の「AAL2 以上ではパスキーかマイナンバーカード」は、DS-511 の文言ではない。DS-512 4.4 1) の「2026年2月時点では、フィッシング耐性のある手法が限られるので、レベル2以上では、マイナンバーカードかパスキーの採用が実質的に必須になると想定される」を縮めたものだった。書き分けた。
- **回復（DS-511 3.2 5) ウ）**：「アカウント回復の手段は、採用している当人認証手法と同等以上の強度の手法を選択すること」。表3-11 の例は、身元確認のやり直し、予備の認証器、回復コードの事前発行、回復コードの必要時発行（連絡先に送る）。協力者による承認は例にない。
- **回復コードとフィッシング（DS-512 3.2 3) ウ）**：「リカバリーコード入力はフィッシングには脆弱」と明記している。
- **待機（DS-512 3.2 3) イ）**：認証器の追加や変更では、登録済みの連絡先に知らせ、変更が有効になるまで一定の時間を置くことで、正規の利用者が気付いて連絡する猶予ができる、としている。数値はない。
- **同期パスキー（DS-512 別紙2 1.1 3)）**：同期に使うアカウントを奪われた場合の耐性はない、と明記している。

### 3. CRYPTREC

- **版**：電子政府推奨暗号リストは、LS-0001-2022R2（最終更新 2026-03-30）に改定されていた。R1 には「最終更新 令和6年5月16日」があった。どちらでも、署名に ECDSA、EdDSA、RSASSA-PKCS1-v1_5 が載っている。WebAuthn の RS256（RSASSA-PKCS1-v1_5）は掲載されている。R2 では、RSA 系の注（SHA-1 と RSA1024 の移行指針）が外れ、耐量子計算機暗号（PQC）のリスト（署名は該当なし）が加わった。
- **GCM**：「初期化ベクトル長は96ビットを推奨する」（R2 の注7、R1 の注4）。一致。
- **EdDSA**：電子政府推奨暗号リストに載っている。受け取ったメールの ed25519-sha256 の検証は、プロトコルの例外として扱ってきたが、掲載もされている。
- **SHA-1**：運用監視暗号リスト（互換性の維持のためだけ）。rsa-sha1 の DKIM を不合格にする方針と合う。
- **鍵長（LS-0003-2022R1、2022年3月）**：リストに載った方式でも、設定基準に合わない鍵長なら、推奨暗号を使っているとは見なされない。エンティティ認証（表9）では、112ビットの強度（RSA 2048 ビット）は、2030年までの「移行完遂期間」（既存のシステムとの互換性の維持などに限る）で、2031年からは「利用不可」。128ビット（P-256 の ECDSA、RSA 3072 ビット）は2040年まで「利用可」。WebAuthn の RS256 の資格情報は、RSA 2048 ビットの鍵が多い（`-257` は鍵長を決めていない）。
- 割符は電子政府のシステムではないので、この基準に拘束はされない。ただし、不変条件9の許可リストは CRYPTREC への掲載を根拠にしている（plan 8章）。

### 4. 2026年10月の注意喚起

- **JPCERT-AT-2026-0030**：以前の抜粋で確かめられなかったレート制限の例（ログイン、パスワードリセット、SMS の送信、検索処理）は、原文にあった。ほかに、ケースB の手口（認証トークンの形式を変えて応答の違いを見る、NoSQL インジェクション、他のシステムで盗んだ API キーの使用）、アクセス制御で HTTP メソッドも限ること、漏えいに備えて平時から顧客に二次被害の防止（多要素認証など）を呼びかけること、が書かれていた。どれも ADR 0008 の決定（4、5、6、11 など）の範囲に入るか、企業の側の対応で、決定を変えない。
- **JPCERT/CC Eyes**（2026-10-15）：SSRF の対策として「リダイレクト後の宛先も検証」を推奨している。割符の送信サービスはリダイレクトに従わない（plan 2章、CAP-22）ので、より厳しい側にある。
- **国家サイバー統括室**（10-09 と 10-14）：抜粋と一致。10-14 のお知らせは、個人情報保護委員会の注意喚起の題名を「大規模な漏えい等事案を踏まえた対応について（注意喚起）」としていて、委員会のページの題名と一致した。
- **個人情報保護委員会の注意喚起**（10-07）：法22条（不要になった個人データの消去の努力義務）と、ガイドラインの技術的安全管理措置の見直しの先取りを示している。ADR 0008 の17（保存期間）の方向と合う。

### 5. 残りの行（同じ日に追加で照合）

- **W3C WebAuthn Level 3**：2026-08-25 に W3C 勧告になっていた。BE/BS フラグは抜粋と一致。5.4 は、「幅広い認証器に対応したい RP は、pubKeyCredParams に少なくとも EdDSA（-8）、ES256（-7）、RS256（-257）を含めるべき（SHOULD）」としている。照合した時点の不変条件9は、WebAuthn で ES256 と RS256 だけを受け付けていた（決定10で EdDSA を足した）。CRYPTREC の推奨暗号リストにも EdDSA は載っている（上の3）。
- **DMARC**：RFC 7489 は、2026-05 に RFC 9989（標準化過程）と、報告の RFC 9990、9991 に置き換えられていた。整合（relaxed と strict）の考え方は変わらない。組織ドメインは、Public Suffix List ではなく DNS Tree Walk で決める（4.10）。pct タグは廃止された。relay は `mailauth` で DMARC を判定する（ADR 0002）。
- **RFC 6376（DKIM）**：`x=` は推奨で、「リプレイの防止を意図したものではない」と注記している。割符は、`x=` を、リプレイの判定の記録を持つ期限として使うだけで、判定そのものは記録との照合で行う（plan 3-2、RP-84）。注記と矛盾しない。RFC 8301 は、rsa-sha1 を署名にも検証にも使わないとしており、不変条件9と一致する。
- **Google の転送のガイド**：現在の版は ARC に触れていない。ARC を付けるのは、この製品の選択（RFC 8617。Experimental）である。
- **日本証券業協会のガイドライン**：「SMS やメールの OTP では、リアルタイムのフィッシングを防げない」という文はなかった。standards.md から削った。この文を根拠にした設計はない。
- **金融庁の監督指針**：standards.md のリンク先は、パブリックコメントの回答（別紙1）か公表のページだった。条文（新旧対照表）で「フィッシングに耐性のある多要素認証の実装及び必須化（デフォルトとして設定）」を確かめ、リンクを足した。
- **NICT の報道発表**：A2B攻撃の命名と、3種の対策は一致。「BOLA、SSRF、RCE、SQL インジェクション」という列挙は、報道発表にも総務省のページにもなかった（詳細の CYNEX の資料には接続できない）。plan の冒頭の書き方を、総務省の原文の表現（認証・認可の不備や、不正なデータベース操作などを可能にする脆弱性）に直した。BOLA と SSRF への備え（plan 2章）は、この製品の判断で、JPCERT/CC の資料（原文で確認済み）とも合う。
- **FIDO の回復のベストプラクティス**：「弱くてはならない」ではなく、「弱い回復手段は推奨しない（not recommended）」だった。仮名のアカウントでは、信頼できる事業者に回復トークンを預ける方式も挙げている。決定2（「同等以上」を満たすとは書かない）は変えない。
- **Apple のエスクロー**：キーチェーンの回復の手順（Apple アカウントとパスワード、SMS、iCloud セキュリティコード）は書いてあるが、パスキーには触れていない。「同期パスキーの安全性が回復手段に左右される」は、この製品の推論として書き分けた。
- **RFC 8417（SET）**：`aud` は必須ではなく推奨。RFC は署名を必須にしていない。割符が署名して `aud` を付けるのは、製品の選択として書き分けた。
- **OpenID の認定**：oidc-provider（8.5.0 以上）は OP の認定を受けているが、CIBA（FAPI-CIBA）の認定の一覧には載っていない。ADR 0002 の「認定を受けている」は、OIDC の部分についての記述として読む。
- **個人情報保護法の令和8年改正**：法律の本文で、2条8項（連絡可能個人関連情報。3号が電子メールアドレス）と、31条の2（不適正な利用と不正な取得の禁止）を確かめた。plan 7章と仕様（01 の 3章）の扱いと一致する。
- そのほか（NIST SP 800-63A-4、OpenID Connect Core、CIBA、FAPI-CIBA、RFC 9470・9396、RISC と SSF、OWASP ASVS、RFC 8617・8058・8463・8291、Google の送信者のガイドライン、総務省、警察庁、経済産業省の Q&A、古物営業法、個人情報保護委員会の通則編、CRYPTREC の TLS のガイドライン）は、抜粋と一致した。版と節番号を standards.md に書いた。

### 6. 2026-10-23 に照合した行

- **NICT CYNEX**（2026-10-13、LETTICE）：HTML の「脆弱性の点検」に「APIの認可不備（IDOR/BOLA）、SSRF、RCE、SQLインジェクションなど」とある。PDF の図「主に狙われている脆弱性」は、SSRF、RCE、SQL インジェクション、IDOR の4種類。上の5で「原文になかった」とした NICT の脆弱性の列挙は、報道発表ではなく CYNEX の資料にあった。plan の冒頭は、元の列挙に戻した（決定15）。
- **AWS SES**：2023-09-08 の発表で、受信を追加した7リージョンに Asia Pacific (Tokyo) を含む。ADR 0002 と一致する。
- **ヤマト運輸 EC自宅外受け取り API**：受け取り場所（営業所、PUDO、コンビニ）は購入時に選ぶ。購入後の変更と転送はできない。実装できるのは自社で構築したアプリケーションだけで、EC モールやカートのサイトには実装できない。plan 5章の第1段階と矛盾しないが、モールやカートのサイトを使う企業には使えない。
- **ヤマト運輸 FAQ 678**：「配送連携API フリマ・オークション事業者向け」の分類で、匿名配送を「お受取人様・ご依頼主様が、それぞれお互いの情報を知ることなく、お荷物を輸配送することが可能なサービス」と説明している。standards.md に書いていた「EC から購入者への発送には使えない」は原文になく、分類からの推論だった（決定13）。
- **日本郵便 郵便番号・デジタルアドレス API**（2025-05-26）：デジタルアドレスをキーに、住所の全文（郵便番号、都道府県から町域、建物の情報まで）を返す。使うには、ゆうID、郵便番号・デジタルアドレス for Biz のアカウント、法人か個人事業主としての組織の登録が要る（無料）。プレスリリースは、用途として「複数サービスに横断する住所の名寄せ」と、e転居の反映による「転居後住所の取得」を挙げている。抜粋（事業者は住所を取得できる）と一致し、さらに、企業をまたいだ突き合わせのキーになることを、提供者自身が用途として挙げていた（決定14）。
- **クレジットカード・セキュリティガイドライン 6.0 の本文**：`www.j-credit.or.jp` には接続できるようになったが、2026-10-23 はサイト全体がメンテナンスのページに転送され、本文を取得できなかった。不正対策の「配送先情報」は照合していない。plan 5章の「配送先の不正照合 API」は P1 なので、P1 の設計の前に照合する。

## 決定

1. **回復と NIST の関係**：割符の回復は、NIST SP 800-63B-4 の 4.2.2.2 の組み合わせのどれにも当たらない。4.2.1 の独自の方式に近いが、4.2.2.2 は独自の方式を挙げていない。さらに、回復コードの保存のしかたも 3.1.1.2 の文言どおりではない。したがって、「NIST の AAL2 に準拠する」とも「AAL2 相当」とも書かない（ADR 0003 の扱いを続ける）。説明が要るときは、「保存型の回復コード（4.2.1.1）に、協力者の対面の承認と、取り消せる待機期間を組み合わせた独自の方式」と書く。
2. **回復と DS-511／FIDO の「同等以上」**：満たすとは書かない。理由は次のとおり。
   - 割符の通常の認証（UV 付きのパスキー）は、フィッシングに耐性がある。
   - 回復コードは、フィッシングで盗まれうる（DS-512 も明記している）。
   - 協力者の承認は「対面で QR を読む」ことを求めているが、対面であることを技術で確かめてはいない。写真で送られた QR を読ませる手口は残る。
   - 待機と取り消しは、DS-512 も挙げる補償の手段だが、端末をすべて失った人には効かない。
   - 「同等以上」に近づける手段は、P1 の JPKI による回復（DS-512 が挙げる、マイナンバーカードでの身元確認のやり直し）と、強化モード（協力者2人以上）である。どちらも P1 のまま。
3. **回復の後に、回復コードを入れ替える**：回復が成立したら、使った回復コードを失効させ、新しい回復コードを発行して表示する（NIST 4.2.1.1）。回復コードの再発行は、回復の知らせと同じく、全端末と協力者に知らせる。plan 4章と PRN-89 に足す（M8）。
   - オーナーが承認した（2026-10-23）。あわせて、回復のためにも、重要なデータはできる限り持たない、という方針を確かめた。新しい回復コードも、持つのは照合用の HMAC だけにし、平文は表示した後に残さない（決定4）。協力関係は、内部 ID の組だけで持つ（PRN-91）。M8 の ADR で、回復のために割符が持つものを一覧にし、この方針に照らして確かめる。
4. **回復コードの保存**：鍵サービスの HMAC-SHA-256（鍵付き）で照合用の値を作り、平文を置かない方針を続ける。パスワードハッシュを許可リストに足すことはしない。秘密を64ビット以上の乱数にすることと、鍵を DB の外に置くことで、DB だけが漏れても総当たりが成り立たないようにする。NIST の文言との違いは、この ADR に記録したとおり。
5. **協力者の承認の QR**：値は M8 で決める。NIST 4.1.2.2 の結び付けのコード（112ビット以上、1回限り、10分以内）を下限の目安にする。
6. **RS256 の期限**：CRYPTREC の設定基準では、RSA 2048 ビットでのエンティティ認証は2030年までの移行の期間に限られる。そこで次のようにする。
   - P0 では、WebAuthn の RS256 を受け付け続ける（RSA の鍵しか作れない認証器の利用者を締め出さないため）。
   - M3 で、登録のときに RSA の鍵長を確かめて記録する。2048 ビット未満は拒否する。
   - 2030年中に、3072 ビット未満の RSA の資格情報を、新しい登録でも認証でも受け付けない設定に移る。前もって、該当する利用者に、別のパスキーの追加を案内する。手順は P1 で決める。
   - ES256（P-256）は、2040年まで見直さない。
   - オーナーが承認した（2026-10-23）。
7. **待機などの値の根拠**：一次資料には、どの値の根拠もなかった。NIST と DS-512 が示すのは、「待ち時間を置いてよい」「変更が有効になるまで一定の時間を置くと、正規の利用者が気付く猶予になる」という考え方だけである。そこで、値はこの製品の判断として、次の考え方で置く。運用の実績と、P1 で Web Push の受信確認が入った後に見直す。
   - **待機の既定72時間**：知らせを受けた本人か協力者が、その間に一度は端末を見る見込みが高い長さにする。土日に祝日が続く3連休でも、平日が1日は入る。
   - **本番の下限24時間**：1日1回しか端末を見ない人でも、1回は知らせを見る機会があるようにする。
   - **協力者の承認を無効にする14日**：協力者のアカウント自体が回復で奪われた場合に備える。協力者の回復の待機（既定72時間）と、回復後の制限（7日）を足すと約10日になる。それより長くして、元の持ち主が気付いて取り消す猶予を残す。
   - **取り消しの後に回復を始められない14日**：同じ人への回復の試みを繰り返して、知らせへの慣れ（NIST 3.1.3 の「authentication fatigue」と同じ形）を起こさせない。協力者の無効化の14日と同じ長さにそろえる。
   - **窓口での変更を取り消せる24時間**：回復の待機の下限と同じ考え方（1日に1回は端末を見る機会がある）で置く。
   - オーナーは、これらの値を、根拠のない仮置きとして承認した（2026-10-23）。値を変えるときは、この ADR を更新する。
8. **standards.md の書き方**：原文と違っていた書き方を直し、状態を更新した。製品の解釈（たとえば「別名と sub だけなら、企業にとって個人関連情報」）は、原文の文言と分けて書く。
9. **ラックの記事を削る**：原文を照合できなかったので、standards.md の行と、plan の冒頭の引用を削る。記事が挙げていた対策（ID の不正利用への備え、IDOR/BOLA のサーバー側での確認、アプリは解析される前提、API キーの入れ替え、公開している資産の点検）は、JPCERT-AT-2026-0030、JPCERT/CC Eyes、国家サイバー統括室の資料（原文で確認済み）にもあるので、ADR 0008 の決定は根拠を失わない。
10. **WebAuthn に EdDSA を足す**：オーナーが決めた（2026-10-23）。WebAuthn で受け付けるアルゴリズムを、ES256（-7）、EdDSA（-8。曲線は Ed25519 だけ）、RS256（-257）にする。理由は、WebAuthn Level 3 の 5.4 が、幅広い認証器に対応するために EdDSA を含めることを勧めていること（SHOULD）と、EdDSA が CRYPTREC の電子政府推奨暗号リストに載っていること（上の3）。
    - 同じ変更で、不変条件9（CLAUDE.md）、plan 8章、仕様（04 の暗号の表）、ADR 0007 の決定2、principle-review の観点9、standards.md を直した。
    - 登録の選択肢（pubKeyCredParams）の順は、ES256、EdDSA、RS256 にする。RS256 は、決定6の期限があるので最後に置く。
    - M3 の登録の検査（選択肢と検証の両方に同じ値を渡す。ADR 0007 の決定2）に -8 を足し、Ed25519 以外の曲線の鍵を拒否することをテストで確かめる。
    - 捨てスパイク（`spikes/passkey`）は、足す前の許可リスト（ES256 と RS256）で検査したまま残す。許可リストの一部だけを受け付けるので、不変条件には反しない（M3 で本実装に置き換えて、スパイクは消した。ADR 0018）。
11. **DMARC の参照先を RFC 9989 にする**：standards.md の行を置き換えた。M4 で、`mailauth` が RFC 9989 の DNS Tree Walk で組織ドメインを決めているかを確かめる。決めていなければ、返信の中継（plan 3-2）の整合の判定に与える影響を、M4 の ADR に書く。DNS Tree Walk の問い合わせも、注入したリゾルバを通す（不変条件7）。
12. **原文になかった文言を削り、書き分ける**：日本証券業協会の OTP の文を削った。NICT の脆弱性の列挙を、plan の冒頭から外した。FIDO、Apple、SET、Google、oidc-provider の認定は、原文の文言と製品の選択・推論を分けて書いた。
13. **ヤマト運輸の匿名配送**：standards.md の行を、原文の文言（フリマ・オークション事業者向けの分類と、匿名配送の説明）に直す。「EC から購入者への発送には使えない」とは書かない。plan と仕様は、この文を根拠にしていない（plan 5章の第2段階は、割符が匿名の送り状を出す形で、ヤマト運輸の匿名配送に頼らない）。EC の発送に使えるかは、運送会社との交渉（イシュー #16）で確かめる。
14. **デジタルアドレスは使わない（理由を足す）**：plan 5章の「使えないもの」に、提供者が「複数サービスに横断する住所の名寄せ」を用途に挙げていることを足す。企業に渡せば、企業をまたいで突き合わせられる値になる（不変条件5）。転居後の住所も引けるので、利用者が引っ越しても突き合わせが切れない。
15. **NICT の脆弱性の列挙を plan の冒頭に戻す**：オーナーが決めた（2026-10-23）。CYNEX の資料（2026-10-13）の「APIの認可不備（IDOR/BOLA）、SSRF、RCE、SQLインジェクションなどの脆弱性や設定不備を重点的に点検してください」を原文で確かめたので、plan の冒頭を、決定12で直す前の列挙（BOLA、SSRF、RCE、SQL インジェクション）に戻し、出典を CYNEX の資料と書く。決定12のうち、NICT の列挙を外した部分は、これで置き換える。

## 採らなかった案

- **「AAL2 相当」と書く**：通常の認証は AAL2 で許される種類（多要素の暗号認証器）だが、回復が 4.2.2.2 に当たらない。認証の強さは、回復で決まる。
- **協力者を NIST の recovery contacts に合わせる（協力者の連絡先にコードを送る）**：連絡先を集めることになり、ADR 0001 と ADR 0003 に反する。
- **回復コードの保存に PBKDF2 などのパスワードハッシュを足す**：不変条件9の許可リストを広げることになる。64ビット以上の乱数と、DB の外の鍵で、守りたい性質（DB だけが漏れても総当たりが成り立たない）は得られる。
- **いま RS256 をやめる**：RSA の鍵しか作れない認証器の利用者を、P0 から締め出すことになる。CRYPTREC の基準でも、2030年までは移行の期間として扱える。
- **待機などの値を、資料が見つかるまで決めない**：一次資料には数値がない。決めないままでは M8 の実装とテストができない。考え方を書いて置き、見直しの条件を決めておく。
- **EdDSA を足さない（ES256 と RS256 だけのまま）**：WebAuthn の SHOULD は「幅広い認証器に対応したい RP は」という条件付きで、ES256 と RS256 だけでも仕様に反しない。ただし、EdDSA の鍵しか作れない認証器の利用者を締め出す。RS256 には期限がある（決定6）ので、ES256 を使えない認証器の行き先が、期限のある RS256 だけになる。オーナーの判断で足した（決定10）。
