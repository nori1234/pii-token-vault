# ADR 0001：本人確認の根拠を肯定リストで定める

- 状態：採用（接続要件での課し方を、ADR 0010 で一部変えた）
- 日付：2026-10-17

## 状況

2026年9〜10月、国内で大規模な個人情報の漏えいが相次いだ。NICT は、公開アプリを解析して接続先のサーバーを狙う攻撃を「A2B攻撃」と名付けて注意を促しており、相次ぐ漏えいの原因の一つとされる（出典は `docs/standards.md`）。漏えいは防ぎきれない。被害が広がる大きな理由の一つは、漏れた連絡先や属性が、どこかで本人確認として通用してしまうことにある。

当初の計画は「企業に連絡先を持たせない」ことに重心があった。そのため「本人確認に使わせない」ことが抜けており、割符自身の回復にも本物のメールを使っていた。

## 決定

本人確認・回復・承認・識別の根拠にしてよいものを、肯定リストで定める。立場ごとに2つに分ける。

**(a) 企業（RP）の側**：次だけを根拠にしてよい。接続要件と適合テストで課す。

1. 割符が発行した ID トークンの `iss`・`sub`・`acr`・`auth_time`
2. CIBA の結果。照会と軽い手続きにだけ使う
3. 操作に結び付いた step-up の結果。配送先・返金先・支払い手段の変更、解約、高額の取引、住所の法定開示への同意は、これだけを根拠にする

アカウントの付け替えは、割符が署名したイベントだけで行う。

**(b) 割符の内部**：次だけを根拠にしてよい。

1. 登録済みのパスキー（UV 付き）のアサーション
2. 回復コード、回復協力者の承認、待機期間の満了の3つがそろったとき（ADR 0003）
3. P1 では JPKI も加える

**(a)(b) のどちらにも入らないもの**：メール、電話、住所、氏名、生年月日、注文や予約の番号、決済情報、別名、ID トークンの email クレーム、中継した返信や着信。配送のための照合（relay での別名の解決、送信元ロックの検査）は許すが、その結果を許可の判断に流さない。

## 理由

- 根拠にしてはならないものを列挙する否定リストは、必ず漏れが出る。点検の段階で、本物の電話番号、決済情報、注文番号などの漏れが実際に見つかった。
- 方向が一致する基準として、次のものがある：NIST SP 800-63B-4（KBA を認めない、メールを OOB 認証に使ってはならない）、OIDC Core §5.7（email を識別子にしてはならない）、FIDO（回復手段は、取り戻す認証情報より弱くてはならない）、デジタル庁 DS-511／DS-512。
- ただし、P0 の回復が FIDO や DS-512 の「同等以上の強さ」を満たすかは、まだ評価していない（ADR 0003）。
- NIST は、メールや SMS で回復コードを送ることを条件付きで認めている。この決定は、それより厳しい、この製品の方針である。

## 結果

- 割符の回復は、本物のメールを使わない方式にする（ADR 0003）。
- 窓口の本人確認は CIBA で行い、高リスクの操作には端末での step-up を求める。
- 接続要件で、既存会員の紐付け、ゲスト照会、sub の書き換えを規制する。
- 運送会社、カード会社、携帯キャリアのように、割符の外で行われる本人確認は、この決定では変えられない。残るリスクとして仕様に明記する。

## 追記（2026-10-21）

- 接続要件で課す (a) に、移行中の参加の企業についての、入り口の一覧の経路に限った期限付きの例外を設けた（[ADR 0010](0010-staged-participation.md)）。割符のサービス、rp-kit の SDK、demo-rp の参照実装と、完全な参加の企業には、例外を設けない。別名と email クレームは、この例外に含めない。
