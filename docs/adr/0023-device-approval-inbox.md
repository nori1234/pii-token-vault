# ADR 0023：端末承認の共通基盤（受信箱、要求に結び付いたチャレンジ、承認と拒否、承認用のオリジン）

- 状態：提案（オーナーの確認待ち。下の「オーナーの確認」の既定の案で実装した）
- 日付：2026-10-28
- 2026-10-28：#39 のレビュー（窓口での承認の画面の必須要素、上限の同時作成、後処理の失敗）を受けて、O-42 を直し、O-49 を足した。

## 状況

M6（plan 10章、イシュー #8）で、端末承認の共通基盤を作る。M7（CIBA と窓口、操作に結び付けた承認）と M8（回復の知らせと取り消し）が、この上に載る。plan、DESIGN.md、ADR には、次のことが「M6 で決める」として残っていた。

- サーバー側の「端末の受信箱」の形と、受け取り方（plan 4章「通知」。ポーリングか SSE）
- 承認要求ごとのチャレンジを、要求の内容に結び付ける方法（イシュー #8）
- 承認と拒否の記録と、状態の変え方（ADR 0006 の「承認と拒否の競合」）
- 受信箱の保存期間と消し方（plan 8章）
- 承認用の別オリジン（DESIGN.md 原則8、ADR 0018 の O-17）
- パスキーの追加と削除の、全端末への知らせ（ADR 0018 の「M6 で足す」）

M6 の時点では、承認待ちを作る製品の機能はまだない（M7 で作る）。#30（窓口の操作別承認と初回移行。2026-10-28 にオーナーが推奨案を仮に受け入れた。まだマージしていない）が入ると、窓口の承認は CIBA から操作に結び付いた step-up に変わる。どちらになっても使えるように、M6 は、承認待ちを作る入り口（CIBA か OIDC のインタラクションか）に依らない形にする。

## 決定

### 受信箱（O-41）

- idp のスキーマに `idp.inbox` を置く（マイグレーション 0007）。利用者の範囲（`withWarifuUser`）でだけ読み書きし、RLS の ENABLE と FORCE、列単位の GRANT を付ける。作った後に変えられるのは、状態とその時刻だけ（中身、型、期限は書き換えられない）。
- 項目は2種類。
  - **承認待ち**（approval）：承認か拒否を受け付ける。期限がある。状態は pending、approved、denied。
  - **知らせ**（notice）：読むだけ。状態は unread、read。
- 中身（`content`）は、割符のコードの型が検査した、平らなオブジェクトだけにする。キーは小文字の英数字、値は200文字までの文字列（制御文字と書式文字を除く）、整数、真偽値。16項目、2 KiB まで。型の外の自由文、連絡先、トークンは入れない（不変条件4）。企業名は登録簿から引くので、テナント ID だけを置く。
- PWA は、受信箱を30秒ごとに読み直す（ポーリング）。SSE は使わない。接続を張り続ける仕組みを増やさず、受け取る側の正しさを、サーバーの受信箱だけで決めるため。Web Push は P1（plan 4章）。

### 承認待ちの型（O-42）

- 承認待ちの型（`ApprovalType`）は、割符のコードで定義する。企業の設定からは作らない。型は次のものを持つ。
  - 名前、承認の種類（M6 は端末での承認だけ。DESIGN.md 2章）、操作の種類の語（割符が決めた語）
  - 中身を検査して置く形にする関数（型に合わなければ、承認待ちを作らずに断る。DESIGN.md 1章）
  - 画面に出す項目（ラベル付き）を作る関数
- M6 では製品の型はまだない。型は `createIdp` の `approvalTypes` で渡し、テストは自分の型を渡す。
- **窓口での承認は、M6 では受け付けない**。DESIGN.md 2章の「窓口での承認」の必須要素（窓口コードの発行時刻と窓口の種類、窓口でできることの範囲、変更の通知と取り消しの期限、割符が生成した binding_message、「心当たりがない」）は、窓口コードと CIBA（#30 が入れば、操作に結び付いた承認）がないと作れない。そこで、`ApprovalTypes` は、窓口での承認の型を起動時に断る。窓口の型は、必須要素とともに M7 で足す。
- **確定の後の後処理は、M6 では持たない**。企業への引き渡しに失敗しても利用者に成功と返し、再試行もできない形は作らない。M7 で、製品の型と一緒に、次のことを決める。`ApprovalTypes` は、後処理を持つ型を起動時に断る。
  - 引き渡しの状態（確定、引き渡し待ち、引き渡し済み、引き渡せなかった）。確定と同じトランザクションで「引き渡し待ち」を残す。#30 の「承認済み（作成の知らせ待ち）」も、この状態の1つになる。
  - 再試行（引き渡し待ちを、何回、どの間隔で送り直すか。送り直しても二重にならないこと）。
  - 利用者への表示（引き渡せなかったときの文言と、利用者にできること）。
- 承認待ちを作るのは、HTTP のルートではなく idp の中の関数（`requestApproval`）だけにする。
  - 有効期間は1〜15分の範囲で、型ごとに決める。
  - 1人の利用者が同時に持てる承認待ちは20まで。企業に受信箱を埋めさせないため。
  - 件数の確認と挿入は、利用者ごとに直列にする。トランザクションの初めに `pg_advisory_xact_lock(2023, hashtext(user_id))` を取り、トランザクションの終わりに外す。同時に作っても、上限をすり抜けない。鍵は2つの int の形で、監査ログ（1つの bigint の鍵）とは鍵の空間が重ならない。`hashtext` が重なる別の利用者とは待ち合うだけで、正しさは変わらない。
- 作ったときと確定したときは、監査ログに、承認の種類、テナント ID、決定だけを残す（中身は残さない）。

### チャレンジを要求の内容に結び付ける（O-43）

- 承認と拒否の WebAuthn の challenge は、乱数ではなく、鍵サービスの `mac(approval_challenge, …)` の値にする。MAC にかける材料は次のもので、長さ付きでつなぐ。
  - 要求の内容：項目の ID、型、企業、中身の正規形、作った時刻、期限
  - 決定（承認か拒否か）
  - 利用者、承認用のセッションの参照
  - 使い捨ての乱数
- 検証のときは、DB の要求から材料を作り直し、儀式に覚えた値と一致したときだけ、アサーションを検証する。こうすると、パスキーの署名は、この内容のこの決定にだけ結び付く。別の要求のアサーションも、逆の決定のアサーションも通らない。
- MAC の用途 `approval_challenge` は、idp だけが持つ（鍵サービスの能力の表。ADR 0013）。idp のプロセスは HMAC の鍵を持たない。

### 承認と拒否（O-44）

- 承認も拒否も、承認用のオリジンで、UV 付きのパスキーで確かめる（ADR 0006 の「UV 付きパスキーでの承認と拒否」）。拒否も同じ強さにすると、盗んだセッションだけでは、正規の要求を拒否して邪魔することもできない。
- 状態の変更は1つの文で行う（`UPDATE … SET state = $2 WHERE item_id = $1 AND state = 'pending' AND expires_at > now RETURNING …`）。同じ要求への承認と拒否は、両方は通らない（ADR 0006）。監査ログは同じトランザクションに残す。
- 確定できなかった場合は、理由を区別しない。ほかの利用者のもの、ない、期限切れ、決まった後のどれでも同じ失敗にする。

### 承認用のオリジン（O-45）

- `createIdp` の `approvalOrigin` を必須にする。本来のオリジンと違うオリジンで、ホスト名は RP ID か、その下の名前にする。
- Host で振り分け、ルートはどちらか一方のオリジンにだけ登録する（Fastify の host の制約）。
  - 承認用のオリジン：承認待ちの画面と、承認と拒否の API（`/api/approvals/*`）。
  - 本来のオリジン：PWA、インタラクション、OIDC。承認用のオリジンに OIDC は置かない。
- WebAuthn の `expectedOrigin` は、目的ごとに固定する。承認用のログインと、承認と拒否は、承認用のオリジンだけで通す。PWA の画面（本来のオリジン）で動くスクリプトが、同じ RP ID のパスキーでアサーションを作らせても、承認には使えない。
- 承認用のオリジンには、別のセッションを置く。クッキーは `warifu_idp_approval` で、そのオリジンでのパスキーのログインだけで作る。最後の操作から10分、作ってから最長1時間で切れる。パスキーを消したら、PWA のセッションと一緒に消す。
- ローカルでは、ポートが違ってもクッキーは共有される（CLAUDE.md「環境の注意」）。そこで、サーバーが、オリジンごとに読むクッキーの名前を分ける。
- ローカルの開発とテストでは、承認用のオリジンを別のポートで待ち受ける（`listenApproval`。同じアプリの処理に渡し、Host で選ぶ）。本番は、前段で Host を振り分ける。
- 承認待ちの画面（DESIGN.md 2章「端末での承認」）：
  - 出すもの：企業名、操作の種類、型が決めた項目、要求の時刻と端末（O-49）、期限（絶対時刻と分単位の相対時刻）、警告文 A-2、同じ大きさの承認と拒否。
  - サーバーは警告文の ID だけを渡し、文言は画面の定数（DESIGN.md 3章のまま）を使う。窓口での承認の A-1 は、M7 で足す。
  - 初期フォーカスは企業名に置き、どのボタンにも置かない。

### 要求の端末（O-49）

- DESIGN.md 1章の④「要求の時刻と端末」の端末は、要求を出したブラウザの User-Agent から決めた、OS の大まかな種類だけにする（iPhone、iPad、Android の端末、Windows のパソコン、Chromebook、Mac、Linux のパソコン、そのほかの端末）。
- `requestApproval` の呼び出し側（M7 の OIDC のインタラクションなど）が、`deviceKindOf(userAgent)` で決めて渡す。DB には種類の名前だけを置き、版、機種名、User-Agent の文字列は置かない。知らない種類は、承認待ちを作らずに断る。
- 画面に出すのは、割符が決めた語だけ。チャレンジの材料にも入れる。
- User-Agent は、要求を出す側が自由に書ける。だから、これは利用者が「今使っている端末からの要求か」を見比べる手がかりにすぎず、承認の根拠にはしない（不変条件1）。iPadOS の Safari は Mac と名乗るので、Mac と出ることがある。
- 窓口での承認（M7）の「端末」は、窓口の種類（DESIGN.md 2章）で表す。M7 で決める。

### 知らせを出すもの（O-46）

M6 では、次の変更を、その変更と同じトランザクションで、受信箱の知らせにする（plan 4章「全端末に知らせる」、TH-26・TH-27）。

- パスキーの追加（同期パスキーか端末固定か）
- パスキーの削除
- 本物のメールの登録と変更（旧アドレスへの知らせ（relay）とは別に）

回復の開始、窓口での変更、協力者の変更は、M7・M8 で足す。知らせの見出しは型が決めた一般的な文言だけで、企業名も操作の内容も差し込まない。

### 保存期間と消し方（plan 8章。O-47）

- 承認待ちは、期限の30日後に消す。知らせは、作ってから90日後に消す。
- 消すのは、その利用者の受信箱を読むときと、項目を入れるときに限る（`withWarifuUser` の中）。利用者をまたいで消す経路は作らない。作るには、保守用のロールか、利用者をまたいで読めるポリシーが要り、不変条件8の新しい例外になるため。

### レート制限（O-48）

| 機能 | キー | 上限 |
|---|---|---|
| 受信箱と承認待ちの一覧、既読（`inboxByUser`） | 利用者 | 1分に60 |
| 承認と拒否の選択肢（`approvalByUser`） | 利用者 | 1分に20 |
| 承認用のログインと、承認と拒否の検証 | IP と userHandle の利用者 | パスキーの検証と同じ（ADR 0018） |

値に一次資料の根拠はない（ADR 0012 の考え方で、根拠のない仮置き）。

## 採らなかった案

- **SSE（サーバーから送り続ける）**：接続を張り続けるため、上限、再接続、プロキシの扱いを決める必要がある。P0 では、30秒のポーリングで足りる。
- **乱数のチャレンジと、サーバーの記録だけでの結び付け**：儀式に要求の ID を覚えれば、流用は止められる。ただし、署名そのものは内容に結び付かない。内容の MAC をチャレンジにすれば、記録の取り違えのような誤りがあっても、別の内容への承認は検証を通らない。
- **拒否はセッションだけで受け付ける**：盗んだセッションで、正規の要求を拒否できてしまう。ADR 0006 の「UV 付きパスキーでの承認と拒否」とも合わない。
- **承認の画面を、本来のオリジンに置く**：DESIGN.md 原則8に反する。PWA の画面で動くスクリプト（テナント由来の文字列の扱いを誤ったとき）が、承認の画面を操れる。
- **承認待ちを作る HTTP のルート**：企業が直接、利用者の受信箱に項目を作れる口になる。作るのは M7 の CIBA などの、割符の中の処理だけにする。
- **期限の過ぎた行を、利用者をまたいで定期的に消す**：不変条件8の新しい例外（保守用のロール、または利用者をまたいで読めるポリシー）が要る。
- **知らせの見出しに、企業名や操作の内容を入れる**：受信箱は画面の中だけだが、DESIGN.md 原則6（ロック画面とプッシュ通知には詳細を出さない）を P1 の Web Push にそのまま写せるよう、見出しは一般的な文言にした。

## 残るリスク

- **戻ってこない利用者の受信箱の行は、保存期間を過ぎても残る**：消すのは、その利用者が受信箱を読むときと、項目を入れるときだけだから。中身は型が決めた項目（連絡先やトークンは入らない）と時刻だけ。利用者をまたいで消す方法は、P1 で、DB の永続化と保守の手順（不変条件8の例外の要否）と合わせて決める。
- **ローカルでは、クッキーがオリジンごとに分かれない**：サーバーが、オリジンごとに読むクッキーの名前を分けているだけ。ブラウザによるクッキーの分離は、本番の別のホスト名でしか確かめられない（CLAUDE.md「環境の注意」）。
- **承認用のオリジンでも、パスキーは同じ RP ID**：だまされた利用者が、承認用のオリジンで自分から承認すれば通る。照会と軽い手続きに限ることと、固定の警告文（M6 は A-2。窓口の A-1 は M7）で抑える（RR-01、TH-10）。
- **受信箱はポーリングなので、利用者がアプリを開くまで届かない**：Web Push（起こすだけ）は P1。回復の待機を延ばす条件（plan 4章）は M8 で決める。
- **PWA の受信箱（本来のオリジン）にも、承認待ちの企業名と操作の種類が出る**：承認と拒否はできない。本来のオリジンで動くスクリプトは、これを読める。
- **要求の端末は、要求を出した側の申告**：User-Agent は偽れる。攻撃者が利用者の端末の種類に合わせれば、画面の端末の表示は手がかりにならない。正とするのは、要求に結び付いたチャレンジ、警告文 A-2、承認用のオリジンでの UV 付きのパスキーである。
- **M6 だけでは、確定した結果を企業に引き渡せない**：窓口での承認と、確定の後の引き渡し（状態、再試行、表示）は M7 で足す。それまで、M6 の基盤に製品の型は載せない。

## 変えたもの

- マイグレーション 0007：`idp.inbox`（要求の端末の列 `request_device` を含む）。x-rls-fixed の一覧を直した。
- 鍵サービス：MAC の用途 `approval_challenge`（idp だけ）。t08-keysvc-acl、t08-key-client-surface、keysvc の acl.test の期待の表を直した。
- idp：
  - `inbox.ts`：受信箱、承認待ちの型、チャレンジの材料。
  - `webauthn.ts`：目的ごとの `expectedOrigin`、承認と拒否の儀式。
  - `sessions.ts`：承認用のセッション。
  - `app.ts`：2つのオリジン、受信箱と承認の API、知らせ。
  - `repo.ts`：パスキーとメールの変更の知らせ。
  - `public/`：受信箱、承認待ちの画面、ApprovalCard、FixedWarning、ExpiryText。
- テスト（`test/leak/`）：
  - `x-device-approval`：チャレンジの結び付け（別の要求、逆の決定、再送）、承認用のオリジンの固定、UV、同時の承認と拒否、期限、型の検査（知らない端末の種類を含む）、画面の中身（要求の時刻と端末）、承認待ちの上限と同時の作成、オリジンの分け方。
  - `x-inbox-bola`：テスト6（利用者 U1 は U2 のものに触れない）。承認待ちと知らせ。
  - `x-inbox-notices`：全端末への知らせ、既読、保存期間。
  - `x-idp-routes`：ルート一覧。
  - `x-idp-browser.e2e`：受信箱から承認待ちの画面を開き、要求の時刻と端末を確かめ、パスキーで承認する。
- 単体テスト（`packages/idp/test/inbox.test.ts`）：中身の形、チャレンジの材料（要求の端末を含む）、型の検査（窓口での承認の型と、後処理を持つ型を断る）、要求の端末の決め方、警告文 A-2 が DESIGN.md の文言のまま画面に入っていること。
