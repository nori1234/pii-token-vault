# ADR 0020：既存会員の初回紐付け

- 状態：決定（仮、オーナー確認済み。2026-11-12 に、移行中の企業への追加の条件を推奨に変えた。下の「オーナーの決定（仮）」。細目は ADR 0028）
- 日付：2026-10-27

## 背景と決定

既存会員の初回移行に限り、登録・追加・回復の経緯を確認できる旧パスキーまたはFIDO2資格情報の検証と、同じ申請に結び付いた割符の操作別承認を使う。不変条件1(a)へ限定追加する。旧パスワード・メール・SMS・既存セッションだけで紐付けない。検証結果は移行専用とし、通常ログイン、窓口、回復、高リスク業務の権限に使わない。

旧資格情報自体の盗難、企業の虚偽証跡、同期パスキー側の回復は残存リスク。強い旧資格情報またはその履歴を確認できない会員は本案で自己移行できず、旧残高や契約の履行方法は別途必要となる。JPKIだけでは旧会員との対応を証明しない。

証跡は連絡先・会員属性・注文・認証器の生データを含めず、割符には検証結果と必要な状態・用途別HMACの索引を残す。証跡原文は永続保存しない。初回移行待機24時間・親申請72時間・短命証跡5分は根拠のない仮置き。

初回紐付けの取消配送もM5の検証イベント専用SETと同一ではない。ADR 0019に記した未完了記録の保持、結果確認と再発行を、M9までに対象のイベントについて設計・検査する。

## 経路・保存と監査の設計案

初回移行には、企業からの適格な旧資格情報の証跡提出・再提出、利用者本人の割符での承認・取消、待機後の双方の再確認と最終承認、割符から企業への取消配送、企業側の確定・取消結果の報告をそれぞれ別の経路で用意する。待機は本人承認の内部結果と旧証跡がそろって初めて開始する。経路名・認証・状態・期待ステータスは[仕様案の§3.4.1](../proposals/desk-and-initial-binding-v0.7.md)に列挙する。企業APIはテナントJWTと用途限定scope、利用者APIは本人セッション・CSRF対策・新しいUV付きパスキーを要求する。旧セッションや連絡先だけで待機・通知・確定を行わない。利用者向けの承認ルートと企業向けの最終承認ルートは、ADR 0028（O-86）で PAR と RAR に置き換えた。移行が始まったら、企業から旧会員の側へ知らせることを必須にした（ADR 0028 の O-103。2026-11-12 のオーナーの判断）。

割符は仮申請の受付時に内部乱数レコードIDからテナント・用途・鍵版を結び付けた `mac(initial_link_public_id)` で移行専用IDを導出し、認証済み企業へ返す。企業は自社申請と対応付け、取消配送・結果報告と再送はこのIDを使う。割符は別用途のHMAC索引と内部ID・鍵版から再導出し、外向きIDや企業の申請IDを平文保存しない。再送中の鍵版を保持し、他テナント・別申請への流用を拒否する。ID・用途のACLと企業側の保護・再提示はM9の実装前に定める。relay以外に復号権限を追加しない。

申請状態の正本はcompany-apiのwithTenant境界、本人の承認・受信箱はidpのwithWarifuUser境界に置く案とする。両者は認証済み内部経路と冪等な状態で連携し、両DBが同一トランザクションだと仮定しない。用途別MAC・署名とサービス別ACLは能力表に追加する設計案であり、現行ACLで使用可能とは扱わない。relay以外への復号権限・新しいテナント横断DB例外は足さない。

ADR 0016の削除しない監査チェーンへ、申請ID・旧会員参照・証跡・トークンなどの原値や連絡先・属性・業務本文を入れない。固定事象コードと必要最小限の検証結果だけを記録する案とし、活動履歴としての残存と保存期間を別途定める。

## オーナーの決定（仮）

ADR 0010は移行中の参加を認め、ENT-01・02の例外を許す。移行中の企業にも、本案で紐付けた会員の旧経路を閉じ、企業が移行中へ戻っても再開しない追加条件を課す。企業の参加自体と個別会員の移行条件は区別する。

2026-11-12 のオーナーの判断（イシュー #60、ADR 0028 の O-104）：移行中の企業では、本案で紐付けた会員の旧経路を閉じることを、強く推奨するにとどめる。上の追加条件は取り下げる。完全な参加は、旧経路をすべて閉じたと企業が報告した状態なので、紐付けた会員の旧経路も閉じている（RP-31・RP-32。ADR 0028 の O-106）。移行中の企業で紐付けた会員は、紐付けの後も、まだ残っている入り口から入られうる（残るリスク。RR-14）。紐付けの根拠（適格な旧資格情報と割符の操作別承認。旧パスワード・メール・SMS・既存セッションだけでは紐付けない）は変えない。

## 検査

plan 11章テスト9として、漏えいした旧パスワードと攻撃者自身の割符による紐付け、履歴不明・弱い回復後のパスキー、証跡の差し替え、待機・取消と確定の競合、旧経路の閉鎖（完全な参加の企業）、企業の参加状態の変化を検査する。

詳細な手順・保存物・受け入れテストの候補は[仕様案 v0.7](../proposals/desk-and-initial-binding-v0.7.md)を参照する。
