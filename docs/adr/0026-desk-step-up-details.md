# ADR 0026：窓口の操作別承認の細目（申請の受け取り、承認の画面、操作ごとの承認、作成の正本、知らせと取消）

- 状態：提案（オーナーのレビュー待ち）。M7 の実装は、この ADR の既定の案で進める
- 日付：2026-10-29

## 状況

M7（plan 10章）では、用途 `desk` の操作別承認、窓口での変更の知らせと取消を作る。方式と範囲は、ADR 0019（窓口を操作別 step-up に一本化する、P0 の窓口の書き込みは一般問い合わせの作成と利用者自身の取消だけ）と、ADR 0025（操作の内容を付けた認可要求は PAR で受け取る）で決めた。仕様案 v0.7 は、手順、保存物、受け入れテストの候補を示した。

実装の前に、次のことを決める必要があった。

- 企業の申請を、割符がどこで受け取り、どう照合するか（ADR 0025 の O-52 で「M7 の ADR で決める」とした）
- 承認の画面をどこに置くか（DESIGN.md 原則8は、承認系の画面を承認用のオリジンに置くとする。OIDC のインタラクションは本来のオリジンにある）
- 割符が署名する「操作ごとの承認」の形と、企業への渡し方（plan 8章で「操作ごとの承認の鍵は M7 で足す」とした）
- 作成の承認、作成の知らせ、取消、結果の報告の正本と、idp と company-api の分担（ADR 0019 は、正本を company-api のテナントの範囲に置き、idp は本人の承認と受信箱を扱うとした）
- 取消の SET の配送（ADR 0019 は、M5 の SET の配送をそのまま使えないとした）
- 保存期間、レート制限、監査の事象

## 決定

### 申請は PAR で受け取る（O-60）

- 企業のサーバーは、申請を固定した後、PAR の受け口（`/oidc/request`。ADR 0025）に、次の `authorization_details` を1件だけ送る。これを、割符への申請の登録とする。仕様案 v0.7 の `POST /v1/desk/approval-requests` は作らない。

  ```json
  [
    {
      "type": "warifu_desk",
      "actions": ["desk.case.create"],
      "identifier": "<申請ID。128ビット以上の乱数の base64url>",
      "subject": "<申請を作った会員の sub>",
      "choices": { "category": "general", "language": "ja" }
    }
  ]
  ```

- 型の検査（oidc-provider の RAR の `validate`）で、次をすべて確かめる。1つでも外れれば、PAR の受け口で `invalid_authorization_details` にする。通常のログインに縮退させない。
  - 配列は1件だけ。`type` は `warifu_desk`。`actions` は1件だけで、DESIGN.md 3章の3つ（`desk.case.status.read`、`desk.order.status.read`、`desk.case.create`）のどれか。
  - `identifier` は base64url の22〜128文字。`subject` は sub の形（base64url の43文字）。
  - `choices` は `desk.case.create` のときだけ必須で、`category`（`general`、`order`、`account`、`other`）と `language`（`ja`、`en`）だけ。ほかの操作では付けない。
  - 上のほかの項目（自由文、受付番号、注文番号、`locations` など）は拒否する。
- 操作は、登録簿のクライアントごとに許す（`deskActions`）。許していない操作と、許していないクライアントの `warifu_desk` は拒否する（oidc-provider の `authorization_details_types` と、型の検査の両方）。企業は、適合確認を受けた操作を減らせるが、増やせない。
- 受付番号は、割符に送らない（不変条件6）。割符は、受付番号を受け取る口を持たない。
- `subject` は、申請を作った会員を指す。割符は、ログインした利用者の sub がこれと一致するかを確かめるだけに使う（O-61）。利用者を探す、知らせを送る、承認待ちを作る、のどれにも使わない。PAR の受け口は、`subject` の利用者がいるかどうかで応答を変えない（仕様案 v0.7 の D-30）。
- 申請の期限は、割符の側では、インタラクションを始めてから5分にする（ADR 0019 の仮置き）。PAR の `request_uri` の60秒（ADR 0025）とは別である。
- **resource**：oidc-provider 9.12.2 では、RAR は `resourceIndicators` を有効にしないと使えず、RAR の要求には `resource` が要る（`checkDependantFeatures` と `check_resource`。実装で分かった）。そこで、窓口のための仮のリソース `urn:warifu:desk` だけを置き、`authorization_details` のある要求にだけ既定で付ける。企業は `resource` を送らない（認可の入口では拒否する引数に入れた。PAR でも、ほかの値は `invalid_target`）。アクセストークンは不透明で、受け付ける口はない（userinfo と introspection は無効のまま。ADR 0018）。リソースサーバーを足すわけではない。

### 承認の画面と流れ（O-61）

- 認可の入口に `request_uri` で来た要求に `warifu_desk` があれば、本来のオリジンのインタラクションは、承認用のオリジンの `/desk` に引き継ぐ（`303`。インタラクションの uid は URL のフラグメントで渡し、サーバーには送らない）。本来のオリジンでは、パスキーのログインを求めない。
- 引き継ぎ（`DeskHandoff`）は、インタラクションごとに1つ、プロセスのメモリ（MAC を鍵にした保存先。ADR 0018 の O-10）に置く。中身は、テナント、クライアント、操作、申請ID、`subject`、`choices`、要求の端末（`deviceKindOf`。ADR 0023 の O-49）、作った時刻、期限（5分）、状態（`pending`、`approved`、`declined`）、失敗の回数。
- 承認用のオリジンの画面は、DESIGN.md 2章「窓口での承認（step-up）」の必須要素を、この順に出す：登録済みの企業名、固定の操作ラベル（3章）、`choices` のラベル（作成のとき）、要求の時刻と端末、用途と権限の範囲（割符の固定文）、変更の知らせと取消の説明、相手からの電話かを尋ねる問い、警告文 A-1、「承認する」「承認しない」「心当たりがない」（同じ大きさ、既定の選択なし、初期フォーカスは企業名）。受付番号と、企業の自由文は出さない。
- **相手からの電話かを尋ねる問い**：「はい、相手からかかってきました」と答えたら、承認を中止し（申請を `declined` にする）、公式窓口へ自分から連絡し直すよう案内する。サーバーは、「いいえ、自分から公式窓口に連絡しました」と答えた要求にだけ、承認の選択肢を出す（D-38）。
- **承認**：発見可能な資格情報で、UV 付きのパスキーを求める（承認用のオリジンだけで通る。ADR 0023 の O-45）。WebAuthn の challenge は、引き継ぎの中身（テナント、クライアント、操作、申請ID、`subject`、`choices`、時刻、期限、要求の端末）と、決定（承認）と、uid と、使い捨ての乱数を、鍵サービスの `mac(approval_challenge, …)` にかけた値にする（ADR 0023 の O-43 と同じ考え方。ラベルは `warifu/desk/v1`）。
  - アサーションの利用者の sub（テナント単位の pairwise）が `subject` と一致し、その企業に接続済みのときだけ承認する。違えば、ほかの失敗と同じ応答にし、失敗を数える。3回失敗した引き継ぎは使えなくする（ADR 0025 の O-53。漏れた `request_uri` を別の利用者が開いても承認できない）。
  - 承認の前に、利用者が誰かは分からない。そのため、M6 の承認用のセッション（承認用のログイン）は求めない。正とするのは、内容に結び付いた UV 付きのアサーションである。
  - 同じ引き継ぎの承認と拒否は、プロセスの中で直列にする。承認は、アサーションを検証した後に引き継ぎを読み直し、まだ開いているときだけ進める。承認と拒否の両方が通ることはない（ADR 0023 の O-44 と同じ考え方）。
- **承認しない、心当たりがない、相手からの電話**：申請を `declined` にして、認可の応答を `access_denied` で返す。パスキーは求めない（利用者がまだ分からず、受信箱にも何も書かないので、盗んだセッションで邪魔される心配がない。ADR 0023 の O-44 は、受信箱の承認待ちについての決定）。理由（`denied`、`unrecognized`、`incoming_call`）は監査にだけ残し、企業には区別して返さない。「心当たりがない」では、企業の公式窓口に自分から連絡して不正の疑いを申告するよう案内する。
- **インタラクションの完了**：承認用のオリジンは、決まった後に、本来のオリジンの `GET /interaction/:uid/desk/finish` に移らせる。本来のオリジンは、インタラクションのクッキーで同じ uid を確かめ、引き継ぎが `approved` なら、承認した利用者でログインし（`acr` はパスキー、`auth_time` は承認の時刻）、`authorization_details` を付けた Grant で同意を返す。`declined`、期限切れ、ないときは `access_denied` にする。引き継ぎは、取り出した時点で消す。
  - oidc-provider が Grant から `authorization_details` を引き継ぐとき（`authorizationDetailsForGrantSource`）に、Grant の中身が要求の申請と同じで、操作ごとの承認が入っていることを確かめる。違えば `access_denied` にする。窓口の要求が、承認なしの通常のログインと同意で完了する経路を残さない（本来のオリジンのログイン、登録、同意の画面は、窓口の要求では使えない）。
- M6 の `ApprovalTypes` は、窓口の型を断ったままにする。窓口の承認は、受信箱の承認待ち（`requestApproval`）を使わない。

### 操作ごとの承認（O-62）

- 承認すると、idp が、操作ごとの承認の JWT を作る。鍵は、鍵サービスの新しい署名の鍵 `op_approval`（ES256。idp だけが署名と公開鍵の取得をできる）。ID トークンの鍵（`id_token`）とは分ける。
  - ヘッダー：`alg` は `ES256`、`typ` は `warifu-op-approval+jwt`、`kid`。
  - クレーム：`iss`（idp の issuer）、`aud`（クライアントの `client_id`）、`sub`（pairwise）、`purpose`（`desk`）、`action`、`request_id`（申請ID）、`change_id`（作成のときだけ。O-64）、`acr`、`auth_time`、`iat`、`exp`（`iat` から5分。ADR 0019 の仮置き）、`jti`（128ビットの乱数）。
- 企業には、トークンの応答の `authorization_details` の要素に、`approval` として入れて渡す（RFC 9396 の応答の形。ほかの項目は PAR で送ったもののまま）。ID トークンには入れない。
- 公開鍵は、本来のオリジンの `GET /op-approval/jwks` で配り、OIDC の discovery に `warifu_op_approval_jwks_uri` として載せる。
- 企業は、署名、`typ`、`iss`、`aud`、`purpose`、`action`、`exp`、`sub` が会員のものか、`request_id` が自社で固定した申請か、`jti` を一度しか使っていないか、を確かめる。通常の ID トークン、パスキーの成功、申請ID の所持だけでは、担当者に権限を渡さない（RP-12、RP-13）。この検査の参照実装は、M9 で rp-kit に入れる。M7 のテストは、テストの中の企業の側で同じ検査をする。
- JWT は、割符の DB にもログにも置かない（不変条件4）。PAR、引き継ぎ、Grant、認可コードとアクセストークン（メモリ。ADR 0018）の中にだけある。

### 作成の正本と、idp と company-api の分担（O-63）

- 照会（`desk.case.status.read`、`desk.order.status.read`）は、割符に状態を残さない。承認と操作ごとの承認の JWT だけで終わる（監査の事象は残す）。
- 作成（`desk.case.create`）は、承認の時点で、割符が変更を1件、払い出す。
  - 正本は、company-api の `company_api.desk_changes`（テナントの範囲。`withTenant`、RLS の ENABLE と FORCE、列単位の GRANT）。
  - idp には、利用者の範囲の索引 `idp.desk_items`（`withWarifuUser`）を置く。受信箱に出す項目と、取消の入り口のため。idp は company-api の表を読まない。
- idp から company-api へは、内部 API（Unix ドメインソケット `company-api.sock`。呼べるのは idp だけ。資格情報は relay の内部配送 API と同じ形。ADR 0021）で頼む。逆向き（company-api から idp）は作らない。
  - `/v1/desk_approve`：承認した作成を記録し、変更ID を返す。同じ内部のレコード ID の再送は、同じ変更ID を返す。同じ申請ID を別の承認で使おうとすると `409`。テナントが緊急停止していれば断る。
  - `/v1/desk_status`：利用者の項目の状態と取消期限を返す。company-api は、行の利用者が頼んだ利用者と同じかも確かめる。
  - `/v1/desk_cancel`：取消を受理する（O-66）。
- 承認の順番（仕様案 v0.7 の「承認時の受信箱」）：
  1. idp が、`idp.desk_items` に `approving` の行を置く（内部のレコード ID は乱数）。
  2. company-api の `/v1/desk_approve` で、正本に `awaiting_notice` の行を置き、変更ID を受け取る。
  3. idp が、行を `approved`（受信箱では「承認済み（作成の知らせ待ち）」）にする。
  4. ここまで済んでから、操作ごとの承認を作り、インタラクションを完了させる。どこかで失敗すれば、企業に承認を返さない。
- 2 が済んだのに idp が応答を受け取れなかった場合、正本には行が残り、企業には承認が届かない。企業は、届かなかった申請を未作成として報告できる（O-65 の `execution-results`）。利用者は、受信箱の項目から取り消せる（受信箱を読むときに、正本に行のある `approving` の項目を `approved` にする）。`approving` のまま company-api に行がない項目は、2分を過ぎたら、受信箱を読むときに消す。

### 外に出す ID（O-64）

- 申請ID は企業が作る。割符は、`mac(desk_lookup, テナント‖"request"‖申請ID)` だけを正本に置く（照合用）。原値は、PAR、引き継ぎ、内部 API の要求の本文（メモリ）にだけある。
- 変更ID と取消要求ID は割符が払い出す。正本には内部のレコード ID（乱数の UUID）だけを置き、外に出す値は `mac(desk_id, テナント‖"change"‖レコード ID)` と `mac(desk_id, テナント‖"cancel"‖レコード ID)` からその都度導く（仕様案 v0.7 の 2.7）。企業が提示した変更ID は、`mac(desk_lookup, テナント‖"change"‖変更ID)` の索引で引く。
- `desk_id` と `desk_lookup` は、company-api だけが持つ MAC の用途として足す（鍵サービスの能力の表。ADR 0013）。テナントを材料に入れるので、別のテナントでは同じ値にならない（不変条件5）。

### 企業向けのルートと scope（O-65）

- company-api に4つのルートを足す。どれも、テナントの JWT（RP-73）で認証する。テナントは JWT から決め、本文からは取らない。
  - `POST /v1/desk/change-notices`：`request_id` と `change_id`。作成を記録し、取消期限を返す（O-66）。
  - `POST /v1/desk/execution-results`：`request_id` と `result`（`not_created` だけ）。承認を受けたのに作らなかったことを報告する。
  - `POST /v1/desk/cancellation-results`：`change_id`、`cancellation_id`、`result`（`applied` か `already_applied`）。取消を適用したことを報告する。
  - `POST /v1/desk/cancellation-status`：`change_id`。取消の受付の状態を、割符の時計で確かめる（O-66）。
- テナントの JWT の scope を足す。これまでの `company_api`（別名の入れ替えと検証の SET）に加えて、`desk`（上の4つ）を新設する。トークンの要求の `scope` で1つを選び、登録簿のクライアントごとに許す scope を決める（既定は `company_api` だけ）。違う scope のトークンは `403`。
- 応答：認証の失敗は `401`、scope の違いは `403`、知らない ID と別テナントの ID は区別しない `404`、既知の記録と食い違う要求は `409`、形の違いは `400`。正常は、状態を返すものが `200`、返さないもの（`execution-results`、`cancellation-results`）が `204`。同じ要求の再送は、同じ結果を返す。エラーの本文は固定で、受け取った値を返さない。

### 状態の遷移と取消期限（O-66）

- 正本の状態は、`awaiting_notice`（作成の知らせ待ち）、`created`（作成済み。取消期限まで取り消せる）、`cancel_requested`（取消を受理した。企業の結果待ち）、`cancelled`、`not_created`、`closed`（取消なしで受付を終えた）。後ろの3つは終端。
- 状態の変更は、行を1つの文で書き換えるか、行のロックの中で判定する。取消の受理と、受付の終了（`cancellation-status`）は、同じ行の状態で原子的に決まる。
- 作成の知らせ（`change-notices`）：`awaiting_notice` なら `created` にし、知らせを記録した時刻から24時間（ADR 0012 の決定7の仮置き）を取消期限にする。期限は割符の時計で決め（正本の列は `cancel_closes_at`）、応答の `cancel_deadline` で企業に伝える。受信箱の項目は承認の時点からあり、状態は正本から読むので、知らせの記録と同時に、利用者のどの端末の受信箱にも出る。先に取消を受理していれば（`cancel_requested`）、知らせの時刻だけを記録し、状態は戻さない。
- 取消（idp → `/v1/desk_cancel`）：`awaiting_notice` と、期限内の `created` で受理する。受理した時刻は割符の時計で記録し、取消要求の内部のレコード ID を払い出し、同じトランザクションで取消の SET を送信待ちに入れる。期限内に受理した取消は、企業への配送が期限を過ぎても有効である。すでに `cancel_requested` か `cancelled` なら、同じ結果を返す。期限を過ぎた `created` と、`closed`、`not_created` では断る。
- 受付の状態（`cancellation-status`）：期限を過ぎた `created` は、その場で `closed` にして `closed_without_cancellation` を返す。期限内の `created` と `awaiting_notice` は `window_open`、`cancel_requested` は `cancellation_pending`、`cancelled` は `cancelled`。`not_created` は `409`。企業は、`closed_without_cancellation` か取消の適用が済むまで、取消を妨げる後の処理を保留する（RP の要件。仕様案 v0.7 の 2.4）。
- 未作成の報告（`execution-results`）：`awaiting_notice` と、知らせの前の `cancel_requested` を `not_created` にする（後者は「作成されず取消完了」）。`created` などとは食い違うので `409`。
- 取消の結果（`cancellation-results`）：`cancel_requested` で、`cancellation_id` が受理した取消のものと一致するときだけ `cancelled` にする。

### 取消の SET の配送（O-67）

- 取消を受理すると、company-api が、そのテナントの受け口に SET を送る（RFC 8417、RFC 8935 の push。M5 の送信待ち `company_api.set_outbox` に、種類 `desk_cancellation` を足す）。
  - イベント：`urn:warifu:secevent:desk-cancellation`。中身は `change_id`、`cancellation_id`、`accepted`（`within_window`）。正確な受理時刻は入れない（企業をまたいだ照合の材料にしない）。
  - `iss` は company-api、`aud` はテナント ID、`jti` は送るたびの乱数、`iat` は署名した時刻。`exp` は付けない。
  - 初めて送る時刻は、受理の時点で0〜60秒の乱数だけ遅らせる（送るたびに独立。不変条件5、テスト12）。
- 配送の結果ごとの扱い。取消の送信待ちは、検証の SET（ADR 0022 の6回で諦める）と違い、諦めて消すことはしない。
  - `202`：配送できた。送信待ちを消す。業務の取消の完了は、企業の `cancellation-results` で決める。
  - `400` で、本文が `{"err":"invalid_request", …, "warifu_reason":"set_too_old"}`：同じ取消（変更ID と取消要求ID）を、5秒あけてから、新しい `jti` と `iat` で送り直す（同じ回の配送で送り直すと、企業の時計の狂いを確かめる間がないため）。続けて3回これになったら保留にする。
  - `400` で `warifu_reason` が `iat_in_future`、そのほかの `400`、`401`、`403`、`404`、リダイレクト、`202` 以外の `2xx`：保留にする（時計、鍵、登録の確認が要る。自動では送らない）。
  - `429`、`5xx`、つながらない、時間切れ：1分、5分、30分、2時間、6時間、以後6時間ごとに、0〜20%揺らして送り直す。
- 送り直しで長く待った SET は、送る直前に、署名から240秒を過ぎていれば、新しい `jti` と `iat` で署名し直す（企業の受け口の `set_too_old` を、こちらの待ちで起こさない）。
- sender は、応答のステータスと、`400` の JSON の本文の `err` と `warifu_reason` が決まった値かどうかだけを読んで返す（`description` は読まない。本文をログに残さない）。外へ送るのは、これまでどおり sender だけ。
- 保留した送信待ちを動かす管理の口は、P0 では作らない（不変条件2）。保留を解く経路は O-72 に書く。

### 保留した取消の SET を送り直す（O-72）

オーナーのレビュー（2026-10-29）で、保留を解く経路がないことが分かった。「運用で設定を直して配備し直す」としていたが、保留の印は DB に残るので、配備し直しても送られなかった。管理 API は作らずに（不変条件2）、次の2つの経路だけで解く。

- **割符の側で直したとき**：テナントの登録に、SET の受け口の設定の版 `setDeliveryRevision`（0 以上の整数。既定は 0）を置く。保留にするときに、その時の版を送信待ちに覚える（`held_revision`）。原因（登録、時計、鍵）を直したら、版を変えて配備し直す。配送の各回の初めに、覚えた版が今の版と違う保留を解く。同じ版のまま配備し直しても解かない（直していない設定で送り続けない）。
- **企業の側で直したとき**：企業が受け口を直して、検証の SET（`POST /v1/events/verification`。ADR 0022）を頼む。それが `202` で届いたら、そのテナントの保留をすべて解く。検証の SET は、取消の SET と同じ受け口に、同じ鍵と同じ時刻の規則で届くので、受け取れるようになったことの確かめになる。`202` 以外の `2xx` では解かない（`202` だけを配送できたことにする規則と同じ）。
- 解いた送信待ちは、回数と送り直しの回数を0に戻し、0〜60秒の乱数の後に、新しい `jti` と `iat` で送る（解いた時刻で企業をまたいで突き合わせさせない。不変条件5）。また失敗すれば、上の規則のとおり、また保留になる。
- 解いた数だけを、ログ（`company_api.set_resumed`）に残す。

### 受信箱と取消（O-68）

- 受信箱（PWA の本来のオリジンと、承認用のオリジン）に、作成の項目を出す。状態は company-api の正本から読む。出すもの（DESIGN.md 2章「窓口の承認済み・作成の知らせ待ち」「窓口での変更の通知」）：企業名、固定の操作型、状態（「承認済み（作成の知らせ待ち）」「作成されました」「取消を受け付けました（企業の確認待ち）」「取り消しました」「作成されませんでした」「受付を終えました」）、取消期限、「取り消す」「心当たりがない」、警告文 E。
- 取り消すのは、承認用のオリジンだけ。承認用のセッションと、項目と「取消」と承認用のセッションと乱数を `mac(approval_challenge, …)` にかけたチャレンジの、UV 付きのパスキーで確かめる（ADR 0023 と同じ）。「心当たりがない」も、同じ取消に、不正の申告の案内を添えたもの。
- ほかの利用者の項目と、ない項目は、同じ失敗にする（D-41）。

### 保存期間（O-69）

- PAR と引き継ぎ、操作ごとの承認の JWT は、メモリだけ（PAR は60秒、引き継ぎは5分）。
- 正本の行は、終端（`cancelled`、`not_created`、`closed`）になってから7日（ADR 0019 の仮置き）を過ぎたら消す。消すのは、そのテナントの窓口のルートか内部 API で行を書き換えるとき（テナントをまたいで消す経路は作らない。ADR 0023 の O-47 と同じ考え方）。終端でない行は、期限が過ぎても消さない（仕様案 v0.7 の 2.5、D-45）。
- `idp.desk_items` は、受信箱を読むときに、正本が終端なら7日後に消す予定を付け、過ぎたら消す。終端でない項目は消さない。M6 の受信箱の30日・90日の決まり（`idp.inbox`）は、この表には当てはめない。
- 送信待ちの取消の SET は、`202` で消す。保留したものは消さない。

### レート制限（O-70）

値はどれも、根拠のない仮置き（ADR 0012 の考え方）。

| 機能 | キー | 上限 |
|---|---|---|
| PAR の受け口（入口） | IP | 1分に120 |
| PAR の受け口（受け付けた後） | クライアント | 1分に60（超えたら、作った `request_uri` を消して `429`） |
| 窓口の引き継ぎを作る | クライアント | 1分に60 |
| 窓口の承認の選択肢、取消の選択肢 | IP | WebAuthn の選択肢と同じ（ADR 0018） |
| 窓口の承認の検証 | IP と userHandle の利用者 | パスキーの検証と同じ（ADR 0018） |
| 窓口の項目の一覧 | 利用者 | 受信箱の一覧と同じ（ADR 0023） |
| 窓口の項目の取消の選択肢 | 利用者 | 1分に10 |
| 窓口の項目の取消の検証 | IP と userHandle の利用者 | パスキーの検証と同じ（ADR 0018） |
| 企業向けの窓口のルート | テナント | 1分に300（`apiByTenant` とは別に） |

受付番号の試行の上限は、企業の側の要件（RP の要件。M9 の demo-rp と rp-kit で作る）。割符は受付番号を受け取らない。

### 監査の事象（O-71）

- idp：`idp.desk.approved`（テナント、操作）、`idp.desk.declined`（テナント、理由）、`idp.desk.cancel_requested`（テナント）。
- company-api：`company_api.desk.change_recorded`、`company_api.desk.notice_recorded`、`company_api.desk.cancel_accepted`、`company_api.desk.cancel_applied`、`company_api.desk.not_created`、`company_api.desk.closed`（どれも属性なし。テナントの範囲で残す）。
- 申請ID、変更ID、取消要求ID、受付番号、`request_uri`、JWT は入れない（不変条件4、ADR 0016、ADR 0019 の「監査の保持」）。

## 採らなかった案

- **`POST /v1/desk/approval-requests` で先に登録する（仕様案 v0.7）**：PAR も、企業のサーバーからの、クライアント認証の付いた要求である。同じ企業が同じ鍵で2回登録しても、守りは増えない。企業が、利用者の操作の前に割符の状態を作れる口が増える。
- **本来のオリジンのインタラクションで承認する**：DESIGN.md 原則8に反する。本来のオリジンで動くスクリプトが、承認の画面を操れる。
- **承認用のログインの後に承認する（パスキーを2回）**：承認のアサーションが内容と結び付いていれば、ログインは守りを増やさない。手順が長いと、利用者が画面を読まずに進めやすくなる。
- **ID トークンに承認を入れる**：ID トークンはログインの結果で、企業はログインの検証にも使う。取り違えを防ぐため、鍵と `typ` を分けた別の JWT にした（仕様案 v0.7 の D-22）。
- **idp と company-api で表を共有する**：分散の整合は簡単になるが、idp がほかのサービスの表を読む形になる（仕様案 v0.7 の 2.5.1）。
- **company-api から idp に知らせを書き込む**：内部 API が双方向になる。受信箱の項目は承認の時点で idp が作り、状態は正本から読めば足りる。
- **変更ID を乱数で作って保存する**：不変条件4（変更ID を平文で残さない）に反する。HMAC の索引だけを置くと、取消の SET を送るときに元の値を作れない。

## 残るリスク

- **中継の詐欺**：攻撃者が、自分で得た受付番号を、相手からの電話で利用者に入力させ、利用者が問いに「いいえ」と答えて承認すれば、通る。警告文 A-1 と、照会と一般問い合わせの作成だけに限ること、作成の取消で被害を抑える（ADR 0019、RR-01）。
- **企業の偽り**（RR-19 として plan 1-2 に足した）：企業が、作成していないのに作成の知らせを送る、適用していないのに取消の結果を報告する、といったことは、署名やクライアント認証では見抜けない（仕様案 v0.7）。適合テストと監査で扱う。
- **保留した取消の SET**：時計の狂いや、企業の受け口の設定の誤りで保留になると、割符が版を変えて配備し直すか、企業が検証の SET を `202` で受け取るまで、送られない（O-72）。取消そのものは受理済みで、正本の状態は `cancel_requested` のまま残り、企業の `cancellation-status` にも `cancellation_pending` と返す。企業は、`cancellation-status` で受理済みの取消を確かめられる。
- **知らせの届かない利用者**：受信箱はポーリングで、利用者がアプリを開くまで気付かない（ADR 0023）。Web Push は P1。
- **メモリの保存先**：idp を再起動すると、PAR と引き継ぎが消える。承認の途中の申請は、やり直しになる。承認済みの作成は、正本と `idp.desk_items` に残る。
- **未作成の報告に頼る行**：企業が承認を受け取れなかったのに未作成を報告しないと、正本の行は `awaiting_notice` のまま残る。利用者は受信箱から取り消せる。
