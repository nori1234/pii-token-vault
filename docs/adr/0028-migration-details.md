## 状況

M9 は、既存会員の移行と移行中の参加の設計を先に ADR で決め、rp-kit・適合テスト・demo-rp の実装は、その後に合わせて進める（2026-11-06 にオーナーが決めた。plan 10章）。企業が割符を導入しやすくなるかどうかは、この2つで大きく変わる。

すでに決まっていることは、次のとおり。

- **移行中の参加**（ADR 0010）：入り口の一覧（ENT-01〜03）の経路だけを、期限まで残せる。利用者には、接続の同意の画面と、別名の一覧の企業ごとの詳細に、警告文 I で「切り替わったもの」（一覧1）と「まだ残っている入り口」（一覧2）を出す。項目を一覧1に移すのは、割符が閉じたことを確かめたときだけにする（イシュー #60 の方針で、ここが変わる。下の「#60 の方針との照合」と O-105）。「悪い RP」のモードは作らない（ADR 0010 の「M9 の前の判断」）。
- **既存会員の初回紐付け**（ADR 0020、CLAUDE.md の不変条件1(a)）：登録・回復の経緯を確認できる旧パスキーか FIDO2 の資格情報の検証と、同じ申請に結び付けた割符の操作別承認だけで紐付ける。旧パスワード、メール、SMS、旧セッションだけでは紐付けない。手順、状態、ルートの案、保存の最小化は、仕様案 v0.7 の3章にある。
- **移行中の企業で紐付ける会員**（ADR 0020 のオーナーの決定（仮））：その会員の旧経路は、紐付けと同時に閉じる。企業が移行中に戻っても、再開しない（2026-11-12 のオーナーの判断で、移行中の企業では推奨に変える。O-104）。
- **窓口の操作別承認**（ADR 0026）：PAR と RAR で申請を受け、承認用のオリジンでパスキーで承認し、company-api に正本を置き、取消を SET で届ける。初回紐付けも、この形に合わせられる。
- **接続の前に測ること**（ADR 0024 の O-59）：初回移行の対象の割合。

**変わらないこと**

- CLAUDE.md の不変条件は変えない。割符のコード（idp、relay、company-api、sender、rp-kit、demo-rp）は、移行中の企業についても、連絡先や属性を根拠にしない。
- 主張（plan 1-2）は、接続要件を守る企業（完全な参加の企業）に限る。移行中の企業と、旧経路の残る会員には及ばない。#60 の方針は、この限り方をはっきりさせるもので、主張を広げるものではない。
- 初回紐付けの根拠（ADR 0020、不変条件1(a)）は、適格な旧資格情報の検証と、割符の操作別承認である。旧パスワード、メール、SMS、旧セッションだけでは紐付けない。

**変わること（割符がしなくなること）**

- 割符は、企業の旧経路を確かめない。試験用のアカウントも、外からの検査も持たない。
- 割符は、企業の参加の状態が変わったことを理由に、利用者に再同意を求めない。
- 旧経路に問題があったときに、企業の全体を自動では止めない（O-100）。
- 移行中の企業に、初回紐付けをした会員の旧経路を閉じることを求めない（推奨にする。O-104）。旧会員の側への待機の知らせも、推奨にする（O-103）。

**残るリスクの書き方に足すこと**（RR-14）

- 企業の報告は、企業が自分で確かめた結果である。割符は確かめていない。報告が誤っていても、割符には分からない。
- 完全な参加かどうかも、企業の報告と、接続の契約に基づく。

## 決定（案）

### 初回紐付けの流れ（O-86）

窓口の操作別承認（ADR 0026）と同じ形にする。仕様案 v0.7 の 3.4 の手順1〜8を、次のように割符のルートに当てる。

1. **接続**：利用者は、ふだんのログインと同意で、その企業に接続する（移行中の企業なら、同意の画面に警告文 I が出る）。企業は、ID トークンの `sub` を受け取る。旧会員の権限は、まだ付けない。
2. **仮申請**（企業のサーバー → company-api）：`POST /v1/initial-link/prepare`。企業は自社の申請 ID と、試行限定の会員参照（O-88）を渡し、割符は移行専用 ID を返す（O-87）。この時点では、待機も通知も始めない。
3. **旧会員の側の確かめ**（企業のサーバー → company-api）：企業は、自社の RP ID とオリジンで、適格な旧パスキーを UV 付きで新しいチャレンジで検証し、移行証跡（O-88）を `POST /v1/initial-link/proofs` で出す。
4. **本人の承認**（利用者 → idp）：企業のサーバーは、PAR の受け口（`/oidc/request`）に `authorization_details` を1件だけ送る。

   ```json
   [
     {
       "type": "warifu_initial_link",
       "actions": ["initial_link.approve"],
       "identifier": "<移行専用 ID>",
       "subject": "<手順1で受け取った sub>"
     }
   ]
   ```

   承認用のオリジンの `/initial-link` で、利用者が UV 付きのパスキーで承認する。画面は、DESIGN.md 2章に新しく足す「初回紐付けの承認」の行に従う（企業名、固定の説明「この企業で確認された旧会員を、この割符のアカウントに結び付けます」完全な参加の企業では「結び付けた後は、この企業の旧ログインと、メールや SMS による再設定は使えなくなります」。移行中の企業では、この文を出さず、かわりに「この企業には、割符を通らない入り口がまだ残っています。結び付けた後も、この企業が閉じるまで残ります。」を出す（O-104。DESIGN.md 2章）「P0 では、結び付けた後に付け替えることはできません」、待機と取消の説明、「承認する」「承認しない」「心当たりがない」）。企業が書いた文言、旧会員の氏名やメールは出さない。sub の一致、接続済みであること、失敗の数え方、承認と拒否の直列化は、ADR 0026 の O-61 と同じにする。
5. **待機の始まり**（idp → company-api の内部 API）：順番は、旧会員の側の証跡が先、本人の承認が後に固定する（初回の証跡を受理していない申請の承認は断る）。idp は、受信箱の項目を先に記録してから、承認を company-api に記録させる。待機の時間は、本人の承認を company-api が記録した時刻から進める。旧会員の側への知らせは、企業の推奨にとどめる。細目は O-103。
6. **最終の確かめ**：待機が満ちても、自動では確定しない。企業は、申請で固定した同じ旧会員について、新しいチャレンジで旧パスキーをもう一度検証して、2つ目の証跡を出す（同じ旧会員であることの確かめ方は O-88）。利用者は、PAR で `initial_link.finalize` を送られ、承認用のオリジンでもう一度パスキーで承認する。
7. **紐付けの承認**（idp）：最終の承認のとき、idp は、自分の側に受信箱の項目の行があることと、最初の承認と同じ利用者であることを確かめたうえで、company-api の内部 API で、親申請の期限、待機の満了、2つ目の証跡（会員参照と認証世代が初回と同じこと。O-88）、状態の版（O-90）を確かめさせ、通ったときだけ、一度しか使えない紐付けの承認の JWT を作る。鍵は、鍵サービスの新しい署名の鍵 `initial_link`（ES256。idp だけが署名と公開鍵の取得をできる）にし、窓口の `op_approval` とは分ける。`typ` は `warifu-initial-link-approval+jwt`、クレームは `iss`、`aud`（`client_id`）、`sub`、`purpose`（`initial_link`）、`initial_link_id`（移行専用 ID）、`acr`、`auth_time`、`iat`、`exp`（5分）、`jti`。企業には、トークンの応答の `authorization_details` の `approval` で渡す（ADR 0026 の O-62 と同じ）。
8. **企業の確定**：企業は、承認の JWT を検証し、紐付けと `auth_epoch` の更新を、1つの認証状態の切り替えとして適用し（その会員の旧経路と旧セッションの閉鎖は、完全な参加の企業では必須で、同じ切り替えに含める。移行中の企業では推奨。O-104）、結果を `POST /v1/initial-link/results` で報告する（O-91）。

- 企業向けのルートは company-api に置き、テナントの JWT（scope `initial_link`。O-89）で認証する。応答のステータスは ADR 0026 の O-65 と同じ規則にする（`401`、`403`、区別しない `404`、`409`、`400`、`200`、`204`）。
- 利用者の承認と取消は、承認用のオリジンだけで受ける。仕様案 v0.7 の `POST /v1/me/initial-link/approve` と `POST /v1/initial-link/final-approval` は作らず、PAR に置き換える（窓口と同じ理由。ADR 0026 の O-60）。
- 申請の正本は company-api の `company_api.initial_links`（テナントの範囲。`withTenant`、RLS の ENABLE と FORCE、列単位の GRANT）、利用者の索引は idp の `idp.initial_link_items`（`withWarifuUser`）に置く。idp から company-api へは、窓口と同じ内部 API（Unix ドメインソケット）で頼む。逆向きは作らない。2つの DB を1つのトランザクションとは仮定しない（仕様案 v0.7 の 3.4.1）。
- 回復の後7日の制限（ADR 0027 の O-80）の間は、初回紐付けの承認を出さない。

### 移行専用 ID と企業の申請（O-87）

- 移行専用 ID は割符が払い出す。正本には内部のレコード ID（乱数）だけを置き、外に出す値は `mac(initial_link_public_id, テナント‖レコード ID)` からその都度導く。企業の申請 ID は `mac(initial_link_lookup, テナント‖"request"‖申請 ID)` の索引だけを置く。企業が提示した移行専用 ID は、`mac(initial_link_lookup, テナント‖"link"‖移行専用 ID)` で引く（窓口の `desk_id` と `desk_lookup` と同じ考え方。ADR 0026 の O-64）。2つの MAC の用途は、company-api だけが持つ。
- 同じテナントの同じ申請 ID の `prepare` の再送には、同じ移行専用 ID を返す。別テナントでは同じ値にならない（不変条件5）。
- **鍵の版**（ADR 0020 の「再送中の鍵版を保持する」の具体化）：鍵を入れ替えても、開いている申請の移行専用 ID が変わらず、再送と取消の照合が続けられるようにする。企業の側に仕組みは足さない。
  - 鍵サービスの `initial_link_public_id` と `initial_link_lookup` は、版を持つ鍵にする（保存用の鍵と同じく、版の一覧を持つ。ADR 0013）。`mac` の要求は、この2つの用途に限って版の指定を受け付け、指定がなければ最新の版を使い、使った版を応答で返す。
  - 正本の行に、移行専用 ID を導いた版（`public_id_key_version`）を置く。索引の MAC（申請 ID、移行専用 ID、会員参照、証跡）には、それぞれ作ったときの版を一緒に置く。
  - 移行専用 ID を導き直すとき（`prepare` の再送への応答、待機と取消の SET の送信と送り直し、結果の報告の照合）は、いつも行に置いた版を使う。開いている申請の ID を、新しい版で導き直すことはしない。新しい版は、入れ替えの後に作る申請から使う。
  - 企業が提示した ID を引くときは、鍵サービスが持つすべての版で索引の MAC を作って引く（当たったかどうかで作る回数を変えない）。持つ版の数は3つまで（仮置き）にする。
  - 古い版は、P0 では消さない。保留した SET の送信待ち（諦めて消さない。O-91）と、続く記録の証跡の MAC（O-92）が、古い版を参照し続けうるためである。消す条件と手順は、ADR 0013 の入れ替えの手順と合わせて P1 で決める。
  - company-api は、起動のときに、登録簿のテナントごとに（`withTenant`）、行と送信待ちが参照する版が鍵サービスにあるかを確かめ、なければ起動しない（別の版で導いた ID を黙って出さない）。
- 企業は、申請 ID と移行専用 ID の対応を自社のサーバーに置き、ログ、URL、画面に出さない（不変条件4 と同じ扱いを、接続要件として求める）。demo-rp と rp-kit は、これをそのまま実装する。
- 1つの割符の利用者（テナントの範囲）につき、同時に開いている申請は1件、紐付け済みの記録は1件だけにする（一意制約）。旧会員の側の一意（1人の旧会員に1つの `sub`）は、企業の側で守る（仕様案 v0.7 の 3.6）。

### 移行証跡の形（O-88）

- 企業のサーバーが、クライアントの登録済みの鍵（`jwks`）で署名した JWS（ES256）にする。`typ` は `warifu-initial-link-proof+jwt`、`aud` は company-api の初回紐付けのルートにする。client assertion とは `typ` と `aud` で区別し、お互いの検証で断る。
- クレームは許可リストにする：`iss`（`client_id`）、`aud`、`iat`、`exp`（`iat` から5分まで）、`jti`、`initial_link_id`、`member_ref`（下の会員参照）、`stage`（`initial` か `final`）、`eligibility`（`eligible` だけ。それ以外の判定の会員には、企業が証跡を出さない）、`credential_kind`（`passkey` か `fido2`）、`profile_version`（O-89）、`auth_epoch`（企業の側の認証世代。整数）。ほかのクレーム（連絡先、属性、旧会員番号、注文、生のアサーション、資格情報 ID、自由文）があれば断る。
- 割符は、証跡の原文を保存しない。検証の結果と、`mac(initial_link_lookup, テナント‖"proof"‖JWS)` だけを、紐付けの記録に残す。争いになったときに、企業が持っている原文が、そのとき割符が受け取ったものと同じかを確かめるためである。`jti` は、5分の間、使い済みとして覚える。MAC の鍵の版も一緒に残す（鍵を入れ替えた後も突き合わせられるように）。
- **同じ旧会員の再確認**：待機の前と後の2つの証跡が、同じ旧会員についてのものであることを、割符の側でも確かめる。
  - 会員参照 `member_ref` は、企業が申請ごとに作る、128ビット以上の乱数である（仕様案 v0.7 の 3.4 の「試行限定の会員参照」）。恒久の会員番号や、連絡先や属性から作った値にしない。企業は、自社のサーバーで、申請と旧会員の対応を固定し、`prepare` でこの値を渡す。割符は、`mac(initial_link_lookup, テナント‖"member"‖member_ref)` だけを置く。
  - 初回と最終の証跡の `member_ref` が、`prepare` のものと同じでなければ断る。
  - 初回の証跡の `auth_epoch` を正本に置き、最終の証跡の `auth_epoch` が違えば、申請を `expired` にする（待機中に、旧会員の側で認証器の追加や削除、回復、権限の変更があった。時間がたっても、疑いは消えない。仕様案 v0.7 の 3.6）。企業は、待機中の旧会員の側の重要な変更を、保留するか、起きた時点で `cancel-requests` で申請を終わらせる。
  - 割符の側の利用者も、最初の承認と最終の承認で同じでなければならない（受信箱の項目の行の持ち主で確かめる）。
  - これで見つけられるのは、企業が別の会員の証跡を取り違えて出すことと、待機中の旧会員の側の変化までである。企業が偽の証跡を出すことは防げない（残るリスク）。

### 移行プロファイルと scope（O-89）

- 移行プロファイルは、企業が「どの旧資格情報を適格とするか」を決めた手順書である。登録の根拠、追加と回復の経緯の確かめ方、`auth_epoch` を更新する事象、適格でない会員の扱いを書く。割符の運営者が、接続の契約の中で読んで認め、版を付ける。
- テナントの登録（配備のときの静的な設定。ADR 0022）に、`initialLink: { profileVersion, approvedOn }` を置く。これがないテナントでは、scope `initial_link` のトークンを出さず、PAR の `warifu_initial_link` も断る。
- テナントの JWT に scope `initial_link` を足す（plan 2章の「初回移行用の限定 scope」）。初回紐付けの4つの企業向けのルート（`prepare`、`proofs`、`cancel-requests`、`results`）だけを呼べる。クライアントごとに許す（既定は許さない）。
- 証跡の `profile_version` が登録の版と違えば断る。待機中に版が変われば、申請は失効させる（仕様案 v0.7 の 3.3）。

### 状態、待機と期限、取消（O-90）

- 正本の状態：`prepared`、`pending_link`（本人の承認済みで、待機中。O-103）、`awaiting_final`（待機が満ちた。まだ権限なし）、`approved`（紐付けの承認を出した。企業の結果待ち）、`linked`、`cancel_requested`、`cancelled`、`expired`、`not_linked`（企業が確定しなかったと報告した）。終端は、`linked`、`cancelled`、`expired`、`not_linked` の4つ。
- 申請には、参加の状態の版（O-95 の `participationRevision`）と移行プロファイルの版を結び付ける。待機中か最終の確かめの前に、どちらかが変われば、`expired` にする。
- 値は、どれも根拠のない仮置き（仕様案 v0.7 の 0.2）：待機24時間、親申請の期限は `pending_link` になってから72時間（送り直しで延ばさない）、証跡と承認は5分、移行専用 ID は128ビット以上の乱数から導く。
- 利用者の取消：受信箱の項目から、承認用のオリジンでパスキーで取り消す（ADR 0026 の O-68 と同じ）。`pending_link` と `awaiting_final` で受理し、`approved` では受理しない（`prepared` には、まだ受信箱の項目がない。企業の側の取消だけを受ける）。企業は、紐付けの承認の JWT がなければ確定できず、割符は取消を受理した申請に JWT を出さないので、取消と確定の競合は、割符の正本の状態で決まる（仕様案 v0.7 の 3.5 では、企業の側で原子的に判定するとしていた。ここを変える）。企業の側の取消（旧会員の側の新しい証跡を添えた `POST /v1/initial-link/cancel-requests`）は、`prepared` と、利用者の取消と同じ状態で受理する。
- 受信箱の項目は、本人の承認の時点で置き（O-103）、状態（待機中と確定できるようになる時刻、待機の満了、取消の受理、紐付けの完了、期限切れ）は、正本から読んで出す（窓口と同じ。ADR 0026 の O-68）。通知の文言は、DESIGN.md の原則6の2種類だけにする。

### 待機の始まりと知らせ（O-103）

待機は、本人と旧会員の持ち主が、申請に気付いて取り消せるようにするための時間である。idp と company-api は別の DB で、1つのトランザクションにできない（不変条件8）ので、順番と条件で守る。

オーナーの判断（2026-11-12）：旧会員の側への知らせは、企業の推奨にとどめる。待機の起点は、本人の承認を company-api が記録した時刻にする。割符は、旧会員の側の知らせが出たかどうかで、待機を止めたり遅らせたりしない。

- **利用者の側の知らせ（受信箱の項目）を、先に記録する**（ADR 0026 の O-63 と同じ形）：
  1. idp が、`idp.initial_link_items` に `approving` の行を置く（利用者の範囲。内部のレコード ID は乱数）。これが、受信箱の項目の記録である。
  2. idp が、company-api の内部 API `/v1/initial_link_approve` を、項目のレコード ID を添えて呼ぶ。company-api は、1つのトランザクションで、承認を記録し、状態を `pending_link` にし、その時刻を待機の起点として固定し（割符の時計。送り直しでずらさない）、待機の知らせの SET を送信待ちに入れる。
  3. idp が、行を進める。
  - 1 が済まなければ、2 を呼ばない。受信箱の項目の記録がない申請は、待機に入れない。company-api から idp へ書き込む経路は作らない（窓口と同じ）。
  - 2 が済んだのに idp が応答を受け取れなかったときは、同じレコード ID で送り直す（同じ結果を返し、待機の起点は動かさない）。受信箱を読むときにも、正本に行のある `approving` の項目を進める。正本に行のない `approving` の項目は、2分を過ぎたら、受信箱を読むときに消す。
  - 企業には、最初の承認のトークンの応答で、状態（`pending_link`）と、確定できるようになる時刻だけを返す。紐付けの承認の JWT は出さない。
- **待機の知らせの SET**：
  - company-api が、そのテナントの受け口に、SET（イベント `urn:warifu:secevent:initial-link-waiting`。中身は `initial_link_id`）を送る。企業がトークンの応答を受け取れなくても（利用者がブラウザを閉じた、など）、この SET で待機に入ったことを知れる。送信待ちは DB に置き、取消の SET と同じく送り直す（ADR 0026 の O-67 と O-72）。取消や期限切れで申請が終わったら、まだ届いていないこの SET は、送信待ちから消す。企業に新しいルートは足さない（初回紐付けの取消の SET のために、どのみち要る受け口を使う）。
  - この SET が届いたかどうかは、待機の起点にも、待機の満了にも使わない。
- **旧会員の側の知らせ（推奨）**：企業は、待機の SET か、最初の承認のトークンの応答を受けたら、旧会員の側に知らせを出すことが望ましい（接続要件では推奨にする）。出す先は、旧会員として認証済みの画面（アプリの中のお知らせなど）と、以前から登録されている信頼できる通知の経路である。メールや SMS で知らせるときは、知らせだけにし、リンクやコードで承認や取消をさせない（仕様案 v0.7 の 3.4 の6）。知らせを見た旧会員の持ち主は、旧会員の側のパスキーで確かめたうえで、取り消せる（`cancel-requests`）。
  - 推奨にとどめる理由：企業の導入の負担を軽くする（イシュー #60 の、企業の責任とベストエフォートの方針）。
  - 推奨にとどめることで残るもの：旧パスキーを盗んだ人が、自分の割符のアカウントに紐付けようとするとき、割符の受信箱はその人のものである。旧会員の本当の持ち主が待機中に気付けるかどうかは、企業が知らせを出すかどうかしだいになる（残るリスク）。
- 割符は、企業が旧会員の側に知らせを出したかどうかは確かめない。
- **実効性の見立て**：旧会員の側の知らせが効くのは、旧会員の本当の持ち主が、待機の間に企業のアプリや画面を開くか、以前から登録している通知を受け取るときである。待機の24時間は、根拠のない仮置きである。

### 取消の SET と結果の報告（O-91）

- 利用者の取消を受理したら、company-api が、そのテナントの受け口に SET を送る（イベント `urn:warifu:secevent:initial-link-cancellation`。中身は `initial_link_id` と `cancellation_id`）。送り方、送り直し、保留と保留の解き方は、窓口の取消の SET と同じにする（ADR 0026 の O-67 と O-72）。待機の知らせの SET（O-103）も、同じ送信待ちで送る。SET に入れる `initial_link_id` は、送るたびに、行に置いた鍵の版で導く（O-87）。
- 企業は、`POST /v1/initial-link/results` で、`linked`、`not_linked`、`cancelled`（取消を適用した）のどれかを報告する。同じ報告の再送は `204`。`approved` の前の `linked` と、取消を受理した後の `linked` は `409` にする。後者は、企業の側で紐付けが先に決まったことを意味するので、割符は利用者に「取消済み」と出さず、防御の停止と調査に進む（仕様案 v0.7 の 3.5）。

### 割符に残すもの（O-92）

- `company_api.initial_links` の行は、終端になってから7日（仮置き）で消す。終端でない行は、期限が過ぎても消さない（窓口と同じ。ADR 0026 の O-69）。
- 紐付けが済んだら、続く記録として、テナント、利用者、方式（`credential_kind`）、プロファイルの版、紐付けた日、証跡の MAC だけを残す（`company_api.initial_link_records`）。再度の紐付けを防ぎ、移行中に紐付けたかどうかを区別するために使う。接続の終わりとアカウントの削除のときの扱いは、M10 の保存物の一覧と合わせて決める。
- 申請 ID、移行専用 ID、証跡の原文、承認の JWT は、DB、ログ、監査に置かない（不変条件4）。

### 移行中の参加の期限（O-93）

- 期限は、移行中として登録したときに決める。原則6か月にする（イシュー #60）。
- 企業の申請による延長を認める（イシュー #60）。オーナーの判断（2026-11-12）で、次のようにする。
  - 延長は1回で、6か月までとする（移行中の期間は、通しで最長12か月）。延長の後にさらに延ばすことはしない。この読み方が違っていれば直す。
  - 申請には、直近の棚卸しの報告（O-96）と、残っている入り口を閉じる予定を添える。
  - 延長した後の期限を、利用者の画面に出す（O-105）。
- 期限を過ぎたとき（延長の後の期限を含む）は、新しい接続（同意）と、初回紐付けの新しい申請だけを断る。接続済みの利用者のログイン、step-up、窓口、回復の知らせは続ける（利用者を締め出さない）。企業に知らせる（O-97）。期限の後の扱い（契約の終わりなど）は、接続の契約で決める。
- 完全な参加から移行中へ戻したとき（O-98）は、新しい期限（原則6か月）と、新しい延長1回を付ける。

### 入り口を閉じたことの確かめと報告（O-94）

- 確かめるのは、企業自身である。割符の運営者は、企業ごとに試験用のアカウントを用意せず、企業の旧経路を確かめない（イシュー #60）。送信サービスを通した外からの検査も作らない。
- 企業は、入り口の一覧の項目ごとに、閉じたことを自分で確かめ、結果と確かめた日時を記録し、割符に報告する。確かめ方は企業が決める（適合テストキットの旧経路の検査を使える）。
- 報告は、接続の契約で決めた連絡の経路で受け、運営者がテナントの登録（配備のときの静的な設定）に写す（O-95）。企業向けの API から参加の状態を書き換える経路は作らない（ADR 0010 とテスト6のまま）。管理 API も作らない（不変条件2）。
- 報告は、割符が確かめた結果ではない。記録でも表示でも、「企業が報告した」ことと「割符が確かめた」ことを混ぜない。P0 では、割符が確かめた項目はない。
- 利用者の画面への出し方は、O-105 で決めた。

### 記録の経路と、idp の読み方（O-95）

- 参加の状態、期限、企業の報告は、これまでどおりテナントの登録（配備のときの静的な設定）に置く。管理 API も、DB の新しい列も、不変条件8の新しい例外も作らない。書き換えは、設定を直して配備し直すことだけにする。
  - 形：`participation`（`full` か `migrating`）、`migrationDeadline`（日付）、`reportedEntries`（`{ entry: "ENT-01", state: "closed", checkedOn: "2026-11-06" }` の配列。企業が報告した結果（`closed` か `remaining`）と、企業が確かめた日）、`lastInventoryOn`（直近の棚卸しの報告の日。O-96）、`participationRevision`（0 以上の整数。参加にかかわる項目を変えたら、必ず上げる）。
  - いまある `verifiedEntries`（割符が確かめた入り口。ADR 0022）は、空だけを受け付けるままにする。割符が確かめる仕組みは、P0 にはない。企業の報告を、この項目に入れない。
  - M9 の実装で、company-api の設定の検査（いまは `full` だけを受け付ける）を広げる。
- idp も、同じ元から作った設定で、同じ項目を読む（idp の登録簿。ADR 0018）。表示の判定は、idp が表示のたびに割符の時計で行う。
- 起動のとき、company-api は、テナントごとに `participationRevision` が、監査ログに最後に残した版と違えば、監査の事象 `company_api.participation.changed`（テナント、版、参加の状態、報告のあった入り口の ID と結果と日）を足す。配備し直しての書き換えも、監査ログに残る。

### 棚卸しの間隔（O-96）

- 企業は、半年に1回、旧経路の棚卸しをして、結果を報告する（イシュー #60）。入り口の一覧にない経路が残っていないことも、棚卸しに含める（RP-15）。
- 完全な参加の企業も行う、と読んだ（閉じた経路が、また開いていないことを確かめるため）。イシュー #60 は、対象を移行中の企業に限っていない。違っていれば直す。
- 直近の報告の日を、記録に置く（O-95）。半年を過ぎても報告がないときは、企業に知らせて報告を求める（O-97）。利用者の画面には、古い日付がそのまま見えるようにし、「半年以内の報告がありません」と添える（O-105）。接続は止めない（オーナーの判断、2026-11-12）。

### 状況が変わったときの知らせ（O-97）

- 割符から企業へ知らせる（イシュー #60）。知らせる場面は、期限の30日前（仮置き）、期限切れ、棚卸しの報告の期限、参加の状態や表示の変更である。経路は、接続の契約で決めた連絡の経路にする。割符の側の記録は、`participationRevision` と監査ログである。
- 利用者への案内は、企業の責任とする。割符は、利用者に再同意を求めず、ログインを止めない。接続済みの利用者の受信箱に、一斉に書き込むこともしない（イシュー #60）。
- 割符の画面（接続の同意の画面と、別名の一覧の企業ごとの詳細）は、開いたときの、今の状態を出す。これは、いつもの表示で、知らせではない。
- ADR 0010 の「完全な参加から移行中に戻すときは、接続済みの利用者に知らせる」（2026-10-22 のオーナーの判断）と RP-14 は、この方針で、「企業に知らせ、利用者への案内は企業が行う」に変わる。
- 前の版の、`idp.connections` に同意したときの版を覚えて、次のログインで同意を取り直す案は、取り下げた。

### 移行中から完全な参加へ、完全な参加から移行中へ（O-98）

- **完全な参加へ**：企業が、入り口の一覧のすべての項目を閉じたと報告し（O-94）、適合テストキットを自社で通し、接続の契約の確認が済んだら、運営者が `participation` を `full` にして配備し直す。割符は、閉じたことを確かめない。完全な参加は、「企業が、接続要件をすべて守ると報告し、契約で約束している状態」である。
  - 移行中に紐付けた会員は、そのままにする。続く記録（O-92）に、移行中に紐付けたことと方式を残す。完全な参加になったことで、強い証明を満たしたとは見なさない（仕様案 v0.7 の 3.3）。完全な参加では、RP-31・RP-32 がすべての会員に及ぶので、移行中に紐付けた会員の旧経路も、閉じていなければならない（O-104）。
- **完全な参加から移行中へ**：認める（ADR 0010）。新しい期限を付け、企業の報告を出し直してもらう。利用者への案内は、企業が行う（O-97）。回数の上限は置かない（オーナーの判断、2026-11-12）。戻すたびに、新しい期限と報告を求める（O-93）。前の版の「1回まで」は、取り下げた。

### 紐付けの前から企業が持っている本物の連絡先（O-99）

- P0 では、推奨（RP-35）のままにし、必須にしない。理由：
  - 割符の側からは確かめられず、監査でしか見られない。
  - 法令で保存が求められるものや、配送に電話番号を使うもの（不変条件11。RP-96 は P1）があり、一律に消すことを求めると、接続できない企業が増える。
- かわりに、接続の前に測ること（ADR 0024 の O-59）に、「持っている連絡先の種類と、消せる時期」を足す。
- 持っている連絡先を本人確認の根拠に使わないこと（RP-02〜05）は、参加の状態で分けて書く。
  - 完全な参加の企業：どの経路でも、根拠に使わない。これまでどおり必須である。
  - 移行中の参加の企業：入り口の一覧（ENT-01〜03）の経路の中に限り、期限まで、その経路が使う値（企業が持つメールや電話番号を含む）を根拠にすることを認める（ADR 0010 の例外。RP-02・RP-03）。経路の外（窓口、高リスクの操作、アカウントの統合、紐付けと sub の扱い）では認めない。別名と email クレームは、この例外に含めない（RP-05）。
  - 移行中は、ENT-01 の再設定の宛先に使う連絡先を消せない。連絡先を消すことの推奨は、その入り口を閉じた後に効く。再設定の宛先の変更は、操作ごとの承認だけを根拠にする（RP-18）。
  - ADR 0020 で紐付けた会員についても、この例外は、企業がその会員の経路を閉じるまで続く（O-104。閉じることは推奨）。期限が来たら、例外は全体で終わる。
- 残るリスク RR-13（企業の側の漏えいそのもの）は、そのまま書く。

### 旧経路の問題が見つかったとき（O-100）

- 見つかるのは、企業の棚卸し、利用者の申告、監査からである。割符は旧経路を確かめないので（O-94）、割符が自分で見つけることは、ふつうない。
- 割符がすること：企業に知らせ（O-97）、報告の訂正を求める。閉じたと報告していた項目は、運営者が記録を `remaining` に直す（O-95。利用者の画面も変わる）。
- 企業がすること：経路を閉じるか直すこと、利用者への案内。責任は企業にある（イシュー #60）。
- 旧経路の問題を理由に、自動では止めない（オーナーの判断、2026-11-12）。直さないときや、誤った報告が繰り返されるときの扱いは、接続の契約で決める。緊急停止（ADR 0022）は、割符との接続そのものが危ういとき（資格情報の漏えいなど）の手段として、これまでどおり残す。
- 前の版の「見つかったら、緊急停止にする」は、取り下げた。

### 初回紐付けをした会員の旧経路（O-104）

ADR 0020 のオーナーの決定（仮）は、移行中の企業でも、初回紐付けをした会員の旧経路（旧ログイン、再設定、ゲスト照会）を、紐付けと同時に閉じ、再開しないことを条件にしていた。

オーナーの判断（2026-11-12）：移行中の企業では、推奨にとどめる（案 B。イシュー #60 の、旧経路の管理は企業の責任でベストエフォート、という方針に合わせる）。

| 参加の状態 | 初回紐付けをした会員の旧経路 |
|---|---|
| 完全な参加 | これまでどおり、閉じていなければならない（RP-31・RP-32） |
| 移行中の参加 | 紐付けと同時に閉じることを推奨する。求めない。閉じるのは企業で、割符は閉じられず、確かめもしない（O-94） |

これに伴って、次のようにする。

- 主張（plan 1-2）は、移行中の企業の会員には、紐付けの後も及ばない。会員が割符のパスキーに移った後も、まだ残っている入り口（漏れたパスワード、メールや SMS の再設定など）から、割符を通らずに、同じ会員として入られうる（残るリスク。RR-14 と TH-09 を書き直す）。
- 待機と旧会員の側の知らせ（O-103）は、紐付けの前の乗っ取りへの守りである。紐付けの後に残る旧経路には、効かない。
- 利用者に見えるようにする：初回紐付けの承認の画面（O-86 の手順4）と、警告文 I に、結び付けた後も、まだ残っている入り口から入られうることを書く（文言は DESIGN.md を直すときに決める）。
- ADR 0020 のオーナーの決定（仮）のうち、移行中の企業に追加の条件を課す部分を取り下げる。旧パスワード、メール、SMS、旧セッションだけでは紐付けないこと（紐付けの根拠）は、変えない。
- 企業が完全な参加に移るとき（O-98）は、移行中に紐付けた会員の旧経路も、閉じていなければならない。

### 企業の自己申告の表示（O-105）

- 守ること（イシュー #60）：企業の自己申告を、割符が確かめたものとして出さない。ADR 0010 の表示の規則のうち、✓や緑の色などの「済み」を示す印を出さないこと、「安全」「対策済み」「認定」と書かないこと、企業が書いた説明を出さないことは、変えない。
- オーナーの判断（2026-11-12）：2つの一覧の形は保ち、一覧1の見出しを、報告に基づくことが分かる文言に変える。たとえば「この企業が、閉じたと報告している入り口（割符は確かめていません）」とし、項目ごとに「企業が確かめた日」を出す。直近の棚卸しの報告の日と、移行中の期限（延長したときは、延長した後の期限）も出す。半年以内の報告がないときは、「半年以内の報告がありません」と添える（O-96）。
- 一覧1に移すのは、企業の報告（`reportedEntries` の `closed`）を運営者が設定に写したときである。割符が確かめたことを意味しない。
- 警告文 I の文言は、DESIGN.md 3章を正とする（この ADR と同じ PR で直した）。M9 の実装で表示ができるまでは、移行中の企業を接続しない（ADR 0010 のまま）。

### レート制限（O-101）

値はどれも、根拠のない仮置き。

| 機能 | キー | 上限 |
|---|---|---|
| 企業向けの初回紐付けのルート | テナント | 1分に300（`apiByTenant` とは別に） |
| `prepare` | テナント | 1時間に1,000 |

| 初回紐付けの項目の取消 | 利用者 | 窓口の取消と同じ（ADR 0026 の O-70） |

### 監査の事象（O-102）

- idp：`idp.initial_link.approved`（テナント、段階）、`idp.initial_link.declined`（テナント、理由）、`idp.initial_link.cancel_requested`（テナント）。
- company-api：`company_api.initial_link.prepared`、`company_api.initial_link.proof_accepted`（段階）、`company_api.initial_link.waiting`（本人の承認を記録し、待機に入った）、`company_api.initial_link.approved`、`company_api.initial_link.linked`、`company_api.initial_link.cancel_accepted`、`company_api.initial_link.cancelled`、`company_api.initial_link.expired`、`company_api.initial_link.not_linked`、`company_api.participation.changed`（O-95）。

## 企業にとっての導入の壁（まとめ）

この ADR の決め方で、何が下がり、何が残るかを書く。数字の基準は、最初の企業で測ってから決める（ADR 0024）。

- 下がるもの：
  - 入り口を一度に全部閉じなくても、期限（原則6か月）まで残して参加できる。延長も申請できる（ADR 0010、O-93）。
  - 適格な旧パスキーを持つ会員は、自分で割符へ移れる（O-86）。企業の側の仕事は、移行プロファイル、4つのルートと PAR、SET の受け口である。旧会員の側に知らせを出すことは推奨にとどめる（O-103）。知らせの届け直しと、鍵の入れ替えをまたいだ ID の保持は、割符の側で持つ（O-103、O-87）。
  - 既存の連絡先を消すことは必須にしない（O-99）。
  - 割符の運営者による確かめがない。企業は、試験用のアカウントを置かず、旧経路を自分で確かめて報告する（O-94）。
  - 参加の状態が変わっても、割符は利用者に再同意を求めない（O-97）。旧経路の問題で、自動では止めない（O-100）。
  - 移行中の企業では、初回紐付けをした会員ごとに旧経路を閉じる仕組みを、求めない（推奨。O-104）。
- 残るもの、増えるもの：
  - 適格な旧資格情報のない会員は、P0 では自分で移れない。救済の経路は作らない（ADR 0020）。旧会員の残高や契約の引き継ぎ方は、企業の側で別に要る。JPKI での道は P1 で、JPKI だけでは旧会員との対応を証明しない。
  - 半年に1回の棚卸しと報告（O-96）。利用者への案内は、企業の責任になる（O-97）。
  - 移行中の企業には、警告文 I が出る。企業に不利な表示の契約と法務の確認は、イシュー #15 で行う。
  - 完全な参加に移るときは、移行中に紐付けた会員を含めて、旧経路をすべて閉じていなければならない（O-98、O-104）。

## オーナーの判断（2026-11-12）

#60 で決まっていなかった項目を、オーナーが次のように決めた。

| ID | 判断 |
|---|---|
| O-104 | 移行中の企業では、初回紐付けをした会員の旧経路を閉じることを、推奨にとどめる（案 B）。完全な参加では必須のまま |
| O-105 | 2つの一覧を保ち、一覧1を「この企業が、閉じたと報告している入り口（割符は確かめていません）」に改める |
| O-103 | 旧会員の側への知らせは、推奨にとどめる。待機の起点は、本人の承認を記録した時刻にする（`pending_notice` をなくす） |
| O-93 | 延長は1回、6か月まで。期限が切れたら、新しい接続と新しい申請だけを断る |
| O-96 | 半年以内の報告がなければ、企業に知らせ、画面に出す。接続は止めない |
| O-98 | 完全な参加から移行中に戻す回数に、上限を置かない |
| O-100 | 旧経路の問題では、自動では止めない。契約で決める |

O-93 の「延長は1回6か月まで」は、延長を1回だけ認め、その長さを6か月までとする、と読んだ。延長を何回でも認め、1回ごとに6か月まで、の意味であれば直す。

## レビューによる変更（2026-11-11）

`5c0e557` へのレビューの5点を受けて直した。

1. **待機の始まりの知らせを、障害があっても残す**：待機を始めてから受信箱に項目を出す順番だと、間の障害で、本人が知らせを見ないまま待機が進みうる。受信箱の項目を先に記録し、項目の記録がない申請は待機に入れない順番にした（O-103）。
2. **鍵を入れ替えたときの再送**：移行専用 ID を導いた鍵の版を行に置き、いつもその版で導く。古い版は P0 では消さず、起動のときに版があることを確かめる（O-87）。
3. **旧会員の側への知らせ**：仕様案 v0.7 の 3.4 の6にあったのに、この ADR から落ちていた。割符の送信待ちから SET で届け、企業が旧会員の側に知らせを出す。待機の起点は、その SET が届いた時刻にした（O-103）。その後、2026-11-12 のオーナーの判断で、旧会員の側の知らせは推奨にし、待機の起点は本人の承認を記録した時刻に戻した（`pending_notice` はなくした）。
4. **同じ旧会員の再確認**：仕様案 v0.7 の「試行限定の会員参照」が落ちていた。2つの証跡の会員参照と認証世代が同じことを、割符の側でも確かめる（O-88）。
5. **移行中の連絡先の例外**：O-99 に「どの経路でも根拠に使わないことは必須」と書いていたが、移行中の企業には、入り口の一覧の経路の中だけの例外がある（ADR 0010）。参加の状態で分けて書き直した。

1 と 2 は、企業の側に仕組みを足さず、割符の側の順番、送信待ち、鍵の版で受ける。3 で企業に足すのは、SET を受けて旧会員の側に知らせを出すことだけだったが、これも推奨になった。

窓口の `desk_id` と `desk_lookup`（ADR 0026 の O-64）も、鍵の版を持たない1つの鍵で導いている。保留した取消の SET は消さないので、同じ問題がありうる。この ADR では直さず、M9 の実装の PR で、同じ形を当てるかを決める。

## 採らなかった案

- **初回紐付けの承認を、利用者向けの専用ルート（`POST /v1/me/initial-link/approve`）と企業向けの最終承認のルートで受ける**（仕様案 v0.7 の 3.4.1）：窓口で PAR と RAR に置き換えたのと同じ理由で採らない（ADR 0026 の O-60）。承認の画面、失敗の数え方、承認と拒否の直列化を、窓口と同じ部品で作れる。
- **移行証跡を、署名のない JSON の本文にする**：認証済みの経路なので受け取るときの確かさは同じだが、争いになったときに、企業の原文と割符が受け取ったものを突き合わせられない。署名した JWS と、その MAC を残す形にした（O-88）。
- **移行証跡に、クライアントの認証とは別の鍵を求める**：鍵の管理が増えて、企業の負担が上がる。`typ` と `aud` で用途を分ければ、取り違えは断れる。
- **待機を始めてから、company-api が idp に受信箱の項目を書かせる**（送信待ちで送り直す）：company-api から idp へ書き込む経路が要る（窓口では作らなかった。ADR 0026 の O-63）。項目を先に記録してから待機に入る順番にすれば、送り直しの仕組みなしで、「項目の記録がないのに待機が進む」ことをなくせる（O-103）。
- **旧会員の側に知らせたことを、企業に新しいルートで報告させる**：企業の側の仕組みが増える。
- **旧会員の側の知らせを必須にし、待機の SET が届いた時刻を待機の起点にする**（前の版の O-103。状態 `pending_notice`）：オーナーの判断（2026-11-12）で採らない。企業の負担を軽くし、知らせは推奨にとどめる。
- **移行中の企業にも、初回紐付けをした会員の旧経路を、紐付けと同時に閉じることを求める**（O-104 の案 A。ADR 0020 のオーナーの決定（仮））：オーナーの判断（2026-11-12）で採らない。移行中の企業では推奨にとどめる。
- **移行中の企業の自己申告を、すべて一覧2に残して注記を付ける**（O-105 の対案）：オーナーの判断（2026-11-12）で採らない。
- **鍵を入れ替えたら、開いている申請の移行専用 ID を新しい版で導き直す**：企業が持っている ID と合わなくなり、再送と取消の照合ができなくなる。行に置いた版で導き続ける（O-87）。
- **期限を過ぎたら、テナントを止める**：接続済みの利用者がログインできなくなる。既定の案は、新しい接続と申請だけを断る（O-93）。
- **割符の運営者が、試験用のアカウントで企業の旧経路を確かめる**（前の版の O-94）と、**送信サービスを通した自動の外からの検査**：イシュー #60 の方針で取り下げた。確かめるのは企業自身にする。
- **参加の状態が変わったら、次のログインで利用者に同意を取り直す**（前の版の O-97）と、**接続済みの利用者全員の受信箱に書き込む**：イシュー #60 の方針で取り下げた。割符は企業に知らせ、利用者への案内は企業が行う。
- **旧経路の問題が見つかったら、緊急停止にする**（前の版の O-100）：イシュー #60 の方針で取り下げた。自動では止めない（O-100）。
- **企業の報告を、企業向けの API で受けて、参加の状態を書き換える**：企業の資格情報で、利用者に出す表示を書き換えられるようになる（ADR 0010、テスト6）。契約の連絡の経路で受け、運営者が設定に写す（O-94）。
- **紐付けの前からの連絡先を消すことを、完全な参加の条件にする**（O-99 の対案）：原則2には近いが、割符から確かめられず、接続できない企業が増える。オーナーの判断で、こちらにすることもできる。

## 残るリスク

- 旧資格情報そのものの盗難、企業の虚偽の証跡、同期パスキーの提供者の側の回復（ADR 0020）。
- 移行中の企業に残っている入り口（RR-14）。その経路による被害を、割符は防げない（イシュー #60）。
- 企業の報告は、企業が自分で確かめた結果で、割符は確かめていない。報告が誤っていても、割符には分からない。完全な参加かどうかも、企業の報告と契約に基づく（O-94、O-98）。
- 利用者への案内を企業が行わなければ、接続済みの利用者は、割符の画面を開くまで、参加の状態が変わったことを知らない（O-97）。
- 旧会員の側の知らせは推奨で、企業が出したかどうかを、割符は確かめない（O-103）。出さない企業では、旧パスキーを盗まれた会員が、待機中に気付けない。
- 会員参照と認証世代の一致は、企業が出した値どうしの比較である。企業が偽の値を出すことは防げない（O-88）。
- 期限を過ぎても、延長しても、接続済みの利用者の接続は続く。その間、入り口は残りうる（O-93）。
- 移行中の企業で初回紐付けをした会員は、紐付けの後も、まだ残っている入り口から、割符を通らずに同じ会員として入られうる（O-104。閉じることは推奨）。旧経路が残っているか、開け直されたかを、割符は知らない（O-100）。
