## 状況

M9 は、既存会員の移行と移行中の参加の設計を先に ADR で決め、rp-kit・適合テスト・demo-rp の実装は、その後に合わせて進める（2026-11-06 にオーナーが決めた。plan 10章）。企業が割符を導入しやすくなるかどうかは、この2つで大きく変わる。

すでに決まっていることは、次のとおり。

- **移行中の参加**（ADR 0010）：入り口の一覧（ENT-01〜03）の経路だけを、期限まで残せる。利用者には、接続の同意の画面と、別名の一覧の企業ごとの詳細に、警告文 I で「切り替わったもの」（一覧1）と「まだ残っている入り口」（一覧2）を出す。項目を一覧1に移すのは、割符が閉じたことを確かめたときだけにする（イシュー #60 の方針で、ここが変わる。下の「#60 の方針との照合」と O-105）。「悪い RP」のモードは作らない（ADR 0010 の「M9 の前の判断」）。
- **既存会員の初回紐付け**（ADR 0020、CLAUDE.md の不変条件1(a)）：登録・回復の経緯を確認できる旧パスキーか FIDO2 の資格情報の検証と、同じ申請に結び付けた割符の操作別承認だけで紐付ける。旧パスワード、メール、SMS、旧セッションだけでは紐付けない。手順、状態、ルートの案、保存の最小化は、仕様案 v0.7 の3章にある。
- **移行中の企業で紐付ける会員**（ADR 0020 のオーナーの決定（仮））：その会員の旧経路は、紐付けと同時に閉じる。企業が移行中に戻っても、再開しない（2026-11-12 のオーナーの判断で、移行中の企業では推奨に変える。O-104）。
- **窓口の操作別承認**（ADR 0026）：PAR と RAR で申請を受け、承認用のオリジンでパスキーで承認し、company-api に正本を置き、取消を SET で届ける。初回紐付けも、この形に合わせられる。
- **接続の前に測ること**（ADR 0024 の O-59）：初回移行の対象の割合。

## #60 の方針との照合（2026-11-12）

**変わらないこと**

- CLAUDE.md の不変条件は変えない。割符のコード（idp、relay、company-api、sender、rp-kit、demo-rp）は、移行中の企業についても、連絡先や属性を根拠にしない。
- 主張（plan 1-2）は、接続要件を守る企業（完全な参加の企業）に限る。移行中の企業と、旧経路の残る会員には及ばない。#60 の方針は、この限り方をはっきりさせるもので、主張を広げるものではない。
- 初回紐付けの根拠（ADR 0020、不変条件1(a)）は、適格な旧資格情報の検証と、割符の操作別承認である。旧パスワード、メール、SMS、旧セッションだけでは紐付けない。

**変わること（割符がしなくなること）**

- 割符は、企業の旧経路を確かめない。試験用のアカウントも、外からの検査も持たない。
- 割符は、企業の参加の状態が変わったことを理由に、利用者に再同意を求めない。
- 旧経路に問題があったときに、企業の全体を自動では止めない（O-100）。
- 移行中の企業に、初回紐付けをした会員の旧経路を閉じることを求めない（強く推奨にする。O-104）。

- 企業の旧経路（旧ログイン、メールや SMS による再設定、ゲスト照会）を廃止することは、接続を続ける条件にしない。強く推奨する。すべて閉じたと企業が報告した状態を「完全な参加」とし、主張はその企業に限る（O-106）。

**まだ決まっていないこと**

- 企業の報告の表示の文言の細部（O-105）。延長の手順（O-93）は、2026-11-14 に決めた。

**残るリスクの書き方に足すこと**（RR-14）

- 企業の報告は、企業が自分で確かめた結果である。割符は確かめていない。報告が誤っていても、割符には分からない。
- 完全な参加かどうかも、企業の報告と、接続の契約に基づく。

## 決定（案）

### 初回紐付けの流れ（O-86）

窓口の操作別承認（ADR 0026）と同じ形にする。仕様案 v0.7 の 3.4 の手順1〜8を、次のように割符のルートに当てる。

1. **接続**：利用者は、ふだんのログインと同意で、その企業に接続する（移行中の企業なら、同意の画面に警告文 I が出る）。企業は、ID トークンの `sub` を受け取る。旧会員の権限は、まだ付けない。
2. **仮申請**（企業のサーバー → company-api）：`POST /v1/initial-link/prepare`。企業は自社の申請 ID と、試行限定の会員参照（O-88）を渡し、割符は移行専用 ID を返す（O-87）。この時点では、待機も通知も始めない。
3. **旧会員の側の確かめ**（企業のサーバー → company-api）：企業は、自社の RP ID とオリジンで、適格な旧パスキーを UV 付きで新しいチャレンジで検証し、移行証跡（O-88）を `POST /v1/initial-link/proofs` で出す。
4. **本人の承認**（利用者 → idp）：企業のサーバーは、PAR の受け口（`/oidc/request`）に `authorization_details` を1件だけ送る。

   ```json
   [
     {
       "type": "warifu_initial_link",
       "actions": ["initial_link.approve"],
       "identifier": "<移行専用 ID>",
       "subject": "<手順1で受け取った sub>"
     }
   ]
   ```

   承認用のオリジンの `/initial-link` で、利用者が UV 付きのパスキーで承認する。画面は、DESIGN.md 2章に新しく足す「初回紐付けの承認」の行に従う（企業名、固定の説明「この企業で確認された旧会員を、この割符のアカウントに結び付けます」完全な参加の企業では「この企業は、結び付けた後、この企業の旧ログインと、メールや SMS による再設定を使えなくすると報告しています。割符は、実際に使えなくなったかを確かめていません。」。移行中の企業では、この文を出さず、かわりに「この企業には、割符を通らない入り口がまだ残っています。結び付けた後も、この企業が閉じるまで残ります。」を出す（O-104。DESIGN.md 2章）「P0 では、結び付けた後に付け替えることはできません」、待機と取消の説明、「承認する」「承認しない」「心当たりがない」）。企業が書いた文言、旧会員の氏名やメールは出さない。sub の一致、接続済みであること、失敗の数え方、承認と拒否の直列化は、ADR 0026 の O-61 と同じにする。
5. **待機の始まり**（idp → company-api の内部 API）：順番は、旧会員の側の証跡が先、本人の承認が後に固定する（初回の証跡を受理していない申請の承認は断る）。idp は、受信箱の項目を先に記録してから、承認を company-api に記録させる。企業は、待機の知らせの SET を受けたら、旧会員の側に知らせを出さなければならない。待機の時間は、その SET が届いてから進める。細目は O-103。
6. **最終の確かめ**：待機が満ちても、自動では確定しない。企業は、申請で固定した同じ旧会員について、新しいチャレンジで旧パスキーをもう一度検証して、2つ目の証跡を出す（同じ旧会員であることの確かめ方は O-88）。利用者は、PAR で `initial_link.finalize` を送られ、承認用のオリジンでもう一度パスキーで承認する。
7. **紐付けの承認**（idp）：最終の承認のとき、idp は、自分の側に受信箱の項目の行があることと、最初の承認と同じ利用者であることを確かめたうえで、company-api の内部 API で、親申請の期限、待機の満了（旧会員の側の知らせの SET が届いた後の24時間。O-103）、2つ目の証跡（会員参照と認証世代が初回と同じこと。O-88）、状態の版（O-90）を確かめさせ、通ったときだけ、一度しか使えない紐付けの承認の JWT を作る。鍵は、鍵サービスの新しい署名の鍵 `initial_link`（ES256。idp だけが署名と公開鍵の取得をできる）にし、窓口の `op_approval` とは分ける。`typ` は `warifu-initial-link-approval+jwt`、クレームは `iss`、`aud`（`client_id`）、`sub`、`purpose`（`initial_link`）、`initial_link_id`（移行専用 ID）、`acr`、`auth_time`、`iat`、`exp`（5分）、`jti`。企業には、トークンの応答の `authorization_details` の `approval` で渡す（ADR 0026 の O-62 と同じ）。
8. **企業の確定**：企業は、承認の JWT を検証し、紐付けと `auth_epoch` の更新を、1つの認証状態の切り替えとして適用し（その会員の旧経路と旧セッションの閉鎖は、完全な参加の企業では必須で、同じ切り替えに含める。移行中の企業では推奨。O-104）、結果を `POST /v1/initial-link/results` で報告する（O-91）。

- 企業向けのルートは company-api に置き、テナントの JWT（scope `initial_link`。O-89）で認証する。応答のステータスは ADR 0026 の O-65 と同じ規則にする（`401`、`403`、区別しない `404`、`409`、`400`、`200`、`204`）。
- 利用者の承認と取消は、承認用のオリジンだけで受ける。仕様案 v0.7 の `POST /v1/me/initial-link/approve` と `POST /v1/initial-link/final-approval` は作らず、PAR に置き換える（窓口と同じ理由。ADR 0026 の O-60）。
- 申請の正本は company-api の `company_api.initial_links`（テナントの範囲。`withTenant`、RLS の ENABLE と FORCE、列単位の GRANT）、利用者の索引は idp の `idp.initial_link_items`（`withWarifuUser`）に置く。idp から company-api へは、窓口と同じ内部 API（Unix ドメインソケット）で頼む。逆向きは作らない。2つの DB を1つのトランザクションとは仮定しない（仕様案 v0.7 の 3.4.1）。
- 回復の後7日の制限（ADR 0027 の O-80）の間は、初回紐付けの承認を出さない。

### 移行専用 ID と企業の申請（O-87）

- 移行専用 ID は割符が払い出す。正本には内部のレコード ID（乱数）だけを置き、外に出す値は `mac(initial_link_public_id, テナント‖レコード ID)` からその都度導く。企業の申請 ID は `mac(initial_link_lookup, テナント‖"request"‖申請 ID)` の索引だけを置く。企業が提示した移行専用 ID は、`mac(initial_link_lookup, テナント‖"link"‖移行専用 ID)` で引く（窓口の `desk_id` と `desk_lookup` と同じ考え方。ADR 0026 の O-64）。2つの MAC の用途は、company-api だけが持つ。
- 同じテナントの同じ申請 ID の `prepare` の再送には、同じ移行専用 ID を返す。別テナントでは同じ値にならない（不変条件5）。
- **鍵の版**（ADR 0020 の「再送中の鍵版を保持する」の具体化）：鍵を入れ替えても、開いている申請の移行専用 ID が変わらず、再送と取消の照合が続けられるようにする。企業の側に仕組みは足さない。
  - 鍵サービスの `initial_link_public_id` と `initial_link_lookup` は、版を持つ鍵にする（保存用の鍵と同じく、版の一覧を持つ。ADR 0013）。`mac` の要求は、この2つの用途に限って版の指定を受け付け、指定がなければ最新の版を使い、使った版を応答で返す。
  - 正本の行に、移行専用 ID を導いた版（`public_id_key_version`）を置く。索引の MAC（申請 ID、移行専用 ID、会員参照、証跡）には、それぞれ作ったときの版を一緒に置く。
  - 移行専用 ID を導き直すとき（`prepare` の再送への応答、待機と取消の SET の送信と送り直し、結果の報告の照合）は、いつも行に置いた版を使う。開いている申請の ID を、新しい版で導き直すことはしない。新しい版は、入れ替えの後に作る申請から使う。
  - 企業が提示した ID を引くときは、鍵サービスが持つすべての版で索引の MAC を作って引く（当たったかどうかで作る回数を変えない）。持つ版の数は3つまで（仮置き）にする。
  - 古い版は、P0 では消さない。保留した SET の送信待ち（諦めて消さない。O-91）と、続く記録の証跡の MAC（O-92）が、古い版を参照し続けうるためである。消す条件と手順は、ADR 0013 の入れ替えの手順と合わせて P1 で決める。
  - company-api は、起動のときに、登録簿のテナントごとに（`withTenant`）、行と送信待ちが参照する版が鍵サービスにあるかを確かめ、なければ起動しない（別の版で導いた ID を黙って出さない）。
- 企業は、申請 ID と移行専用 ID の対応を自社のサーバーに置き、ログ、URL、画面に出さない（不変条件4 と同じ扱いを、接続要件として求める）。demo-rp と rp-kit は、これをそのまま実装する。
- 1つの割符の利用者（テナントの範囲）につき、同時に開いている申請は1件、紐付け済みの記録は1件だけにする（一意制約）。旧会員の側の一意（1人の旧会員に1つの `sub`）は、企業の側で守る（仕様案 v0.7 の 3.6）。

### 移行証跡の形（O-88）

- 企業のサーバーが、クライアントの登録済みの鍵（`jwks`）で署名した JWS（ES256）にする。`typ` は `warifu-initial-link-proof+jwt`、`aud` は company-api の初回紐付けのルートにする。client assertion とは `typ` と `aud` で区別し、お互いの検証で断る。
- クレームは許可リストにする：`iss`（`client_id`）、`aud`、`iat`、`exp`（`iat` から5分まで）、`jti`、`initial_link_id`、`member_ref`（下の会員参照）、`stage`（`initial` か `final`）、`eligibility`（`eligible` だけ。それ以外の判定の会員には、企業が証跡を出さない）、`credential_kind`（`passkey` か `fido2`）、`profile_version`（O-89）、`auth_epoch`（企業の側の認証世代。整数）。ほかのクレーム（連絡先、属性、旧会員番号、注文、生のアサーション、資格情報 ID、自由文）があれば断る。
- 割符は、証跡の原文を保存しない。検証の結果と、`mac(initial_link_lookup, テナント‖"proof"‖JWS)` だけを、紐付けの記録に残す。争いになったときに、企業が持っている原文が、そのとき割符が受け取ったものと同じかを確かめるためである。`jti` は、5分の間、使い済みとして覚える。MAC の鍵の版も一緒に残す（鍵を入れ替えた後も突き合わせられるように）。
- **同じ旧会員の再確認**：待機の前と後の2つの証跡が、同じ旧会員についてのものであることを、割符の側でも確かめる。
  - 会員参照 `member_ref` は、企業が申請ごとに作る、128ビット以上の乱数である（仕様案 v0.7 の 3.4 の「試行限定の会員参照」）。恒久の会員番号や、連絡先や属性から作った値にしない。企業は、自社のサーバーで、申請と旧会員の対応を固定し、`prepare` でこの値を渡す。割符は、`mac(initial_link_lookup, テナント‖"member"‖member_ref)` だけを置く。
  - 初回と最終の証跡の `member_ref` が、`prepare` のものと同じでなければ断る。
  - 初回の証跡の `auth_epoch` を正本に置き、最終の証跡の `auth_epoch` が違えば、申請を `expired` にする（待機中に、旧会員の側で認証器の追加や削除、回復、権限の変更があった。時間がたっても、疑いは消えない。仕様案 v0.7 の 3.6）。企業は、待機中の旧会員の側の重要な変更を、保留するか、起きた時点で `cancel-requests` で申請を終わらせる。
  - 割符の側の利用者も、最初の承認と最終の承認で同じでなければならない（受信箱の項目の行の持ち主で確かめる）。
  - これで見つけられるのは、企業が別の会員の証跡を取り違えて出すことと、待機中の旧会員の側の変化までである。企業が偽の証跡を出すことは防げない（残るリスク）。

### 移行プロファイルと scope（O-89）

- 移行プロファイルは、企業が「どの旧資格情報を適格とするか」を決めた手順書である。登録の根拠、追加と回復の経緯の確かめ方、`auth_epoch` を更新する事象、適格でない会員の扱いを書く。割符の運営者が、接続の契約の中で読んで認め、版を付ける。
- テナントの登録（配備のときの静的な設定。ADR 0022）に、`initialLink: { profileVersion, approvedOn }` を置く。これがないテナントでは、scope `initial_link` のトークンを出さず、PAR の `warifu_initial_link` も断る。
- テナントの JWT に scope `initial_link` を足す（plan 2章の「初回移行用の限定 scope」）。初回紐付けの4つの企業向けのルート（`prepare`、`proofs`、`cancel-requests`、`results`）だけを呼べる。クライアントごとに許す（既定は許さない）。
- 証跡の `profile_version` が登録の版と違えば断る。待機中に版が変われば、申請は失効させる（仕様案 v0.7 の 3.3）。

### 状態、待機と期限、取消（O-90）

- 正本の状態：`prepared`、`pending_notice`（本人の承認済みで、旧会員の側の知らせの SET が届くのを待つ。待機の時間は進まない。O-103）、`pending_link`（待機中）、`awaiting_final`（待機が満ちた。まだ権限なし）、`approved`（紐付けの承認を出した。企業の結果待ち）、`linked`、`cancel_requested`、`cancelled`、`expired`、`not_linked`（企業が確定しなかったと報告した）。終端は、`linked`、`cancelled`、`expired`、`not_linked` の4つ。
- 申請には、参加の状態の版（O-95 の `participationRevision`）と移行プロファイルの版を結び付ける。待機中か最終の確かめの前に、どちらかが変われば、`expired` にする。
- 値は、どれも根拠のない仮置き（仕様案 v0.7 の 0.2）：待機24時間、`pending_notice` でいられるのは24時間まで（過ぎたら `expired`）、親申請の期限は `pending_link` になってから72時間（送り直しで延ばさない）、証跡と承認は5分、移行専用 ID は128ビット以上の乱数から導く。
- 利用者の取消：受信箱の項目から、承認用のオリジンでパスキーで取り消す（ADR 0026 の O-68 と同じ）。`pending_notice`、`pending_link`、`awaiting_final` で受理し、`approved` では受理しない（`prepared` には、まだ受信箱の項目がない。企業の側の取消だけを受ける）。企業は、紐付けの承認の JWT がなければ確定できず、割符は取消を受理した申請に JWT を出さないので、取消と確定の競合は、割符の正本の状態で決まる（仕様案 v0.7 の 3.5 では、企業の側で原子的に判定するとしていた。ここを変える）。企業の側の取消（旧会員の側の新しい証跡を添えた `POST /v1/initial-link/cancel-requests`）は、`prepared` と、利用者の取消と同じ状態で受理する。
- 受信箱の項目は、本人の承認の時点で置き（O-103）、状態（待機中と確定できるようになる時刻、待機の満了、取消の受理、紐付けの完了、期限切れ）は、正本から読んで出す（窓口と同じ。ADR 0026 の O-68）。通知の文言は、DESIGN.md の原則6の2種類だけにする。

### 待機の始まりと知らせ（O-103）

待機は、本人と旧会員の持ち主が、申請に気付いて取り消せるようにするための時間である。idp と company-api は別の DB で、1つのトランザクションにできない（不変条件8）ので、順番と条件で守る。

オーナーの判断（2026-11-12）：移行が始まったら、企業から元の会員（旧会員の側）へ知らせることを、必須にする。

- **利用者の側の知らせ（受信箱の項目）を、先に記録する**（ADR 0026 の O-63 と同じ形）：
  1. idp が、`idp.initial_link_items` に `approving` の行を置く（利用者の範囲。内部のレコード ID は乱数）。これが、受信箱の項目の記録である。
  2. idp が、company-api の内部 API `/v1/initial_link_approve` を、項目のレコード ID を添えて呼ぶ。company-api は、1つのトランザクションで、承認を記録し、状態を `pending_notice` にし、待機の知らせの SET を送信待ちに入れる。
  3. idp が、行を進める。
  - 1 が済まなければ、2 を呼ばない。受信箱の項目の記録がない申請は、待機に入れない。company-api から idp へ書き込む経路は作らない（窓口と同じ）。
  - 2 が済んだのに idp が応答を受け取れなかったときは、同じレコード ID で送り直す（同じ結果を返す）。受信箱を読むときにも、正本に行のある `approving` の項目を進める。正本に行のない `approving` の項目は、2分を過ぎたら、受信箱を読むときに消す。
  - 企業には、最初の承認のトークンの応答で、状態（`pending_notice`）だけを返す。紐付けの承認の JWT は出さない。
- **待機の知らせの SET**：company-api が、そのテナントの受け口に、SET（イベント `urn:warifu:secevent:initial-link-waiting`。中身は `initial_link_id`）を送る。企業がトークンの応答を受け取れなくても（利用者がブラウザを閉じた、など）、この SET で知れる。送信待ちは DB に置き、取消の SET と同じく、届くまで送り直し、申請が開いている間は諦めて消さない（ADR 0026 の O-67 と O-72）。取消や期限切れで申請が終わったら、まだ届いていないこの SET は、送信待ちから消す。企業に新しいルートは足さない（初回紐付けの取消の SET のために、どのみち要る受け口を使う）。
- **旧会員の側の知らせ（必須）**：企業は、この SET を受けたら、旧会員の側に知らせを出さなければならない（接続要件）。出す先は、旧会員として認証済みの画面（アプリの中のお知らせなど）と、以前から登録されている信頼できる通知の経路である。メールや SMS で知らせるときは、知らせだけにし、リンクやコードで承認や取消をさせない（仕様案 v0.7 の 3.4 の6）。知らせを見た旧会員の持ち主は、旧会員の側のパスキーで確かめたうえで、取り消せる（`cancel-requests`）。
  - 必須にする理由：旧パスキーを盗んだ人が、自分の割符のアカウントに紐付けようとするとき、割符の受信箱はその人のものである。旧会員の本当の持ち主に届くのは、旧会員の側の知らせだけである。
- **待機の起点**：SET に `202` が返ったことを記録した時点で、状態を `pending_link` にし、その時刻を待機の起点として固定する（割符の時計。送り直しでずらさない）。それまで（`pending_notice`）は、待機の時間は進まない。`pending_notice` のまま24時間（仮置き）を過ぎたら、`expired` にする。
- 割符が確かめられるのは、SET が届いたこと（`202`）までである。`202` は企業が受け取った記録で、元の会員に実際に知らせが届いたことも、見たことも意味しない。割符の画面（受信箱の項目、承認の画面）に「元の会員に知らせました」とは出さず、出すとしても「企業に、元の会員への知らせを依頼しました」の範囲にとどめる。保証もその範囲にとどめる。企業が実際に知らせを出したかは、適合テストキット（待機の SET の後に、旧会員の側の知らせがあること。RP 側のテスト用フックで確かめる）と、監査で見る（残るリスク）。
- **実効性の見立て**：旧会員の側の知らせが効くのは、旧会員の本当の持ち主が、待機の間に企業のアプリや画面を開くか、以前から登録している通知を受け取るときである。待機の24時間は、根拠のない仮置きである。
- **企業の導入負担**：旧会員の側の画面か、以前から登録されている通知の経路に、知らせを出す実装が要る。SET の受け口が止まると、申請が待機に入らない（`pending_notice` のまま期限切れになる）。

### 取消の SET と結果の報告（O-91）

- 利用者の取消を受理したら、company-api が、そのテナントの受け口に SET を送る（イベント `urn:warifu:secevent:initial-link-cancellation`。中身は `initial_link_id` と `cancellation_id`）。送り方、送り直し、保留と保留の解き方は、窓口の取消の SET と同じにする（ADR 0026 の O-67 と O-72）。待機の知らせの SET（O-103）も、同じ送信待ちで送る。SET に入れる `initial_link_id` は、送るたびに、行に置いた鍵の版で導く（O-87）。
- 企業は、`POST /v1/initial-link/results` で、`linked`、`not_linked`、`cancelled`（取消を適用した）のどれかを報告する。同じ報告の再送は `204`。`approved` の前の `linked` と、取消を受理した後の `linked` は `409` にする。後者は、企業の側で紐付けが先に決まったことを意味するので、割符は利用者に「取消済み」と出さず、防御の停止と調査に進む（仕様案 v0.7 の 3.5）。

### 割符に残すもの（O-92）

- `company_api.initial_links` の行は、終端になってから7日（仮置き）で消す。終端でない行は、期限が過ぎても消さない（窓口と同じ。ADR 0026 の O-69）。
- 紐付けが済んだら、続く記録として、テナント、利用者、方式（`credential_kind`）、プロファイルの版、紐付けた日、証跡の MAC だけを残す（`company_api.initial_link_records`）。再度の紐付けを防ぎ、移行中に紐付けたかどうかを区別するために使う。接続の終わりとアカウントの削除のときの扱いは、M10 の保存物の一覧と合わせて決める。
- 申請 ID、移行専用 ID、証跡の原文、承認の JWT は、DB、ログ、監査に置かない（不変条件4）。

### 移行中の参加の期限（O-93）

- 期限は、移行中として登録したときに決める。原則6か月にする（イシュー #60）。
- オーナーの判断（2026-11-12。イシュー #60）：企業は、残りの作業（まだ残っている入り口と、それぞれを閉じる作業）と、閉じる見込みを報告する。運営者は、内容を確認したうえで、必要な期間を延長する。延長の回数は、最初から固定しない。
  - **延長の手順**（オーナーの判断、2026-11-14。イシュー #60）：
    1. 企業が、残っている作業、完了の見込み、希望する延長の期限を申請する。
    2. 運営者は、必要な事項（この3つ）がそろっていることを確かめ、原則として、希望どおりの期限で延長する。企業の旧経路を実地で検査しない（O-94）。
    3. 延長の記録を残し、表示する期限を更新する。延長の回数に上限は置かない。
  - 申請は、接続の契約で決めた連絡の経路で受ける。運営者は `migrationDeadline` を直して配備し直す（O-95）。延長の記録は、静的な設定の変更と監査ログに残る。新しい申請の仕組み（画面や API）は作らない。
  - 延長した後の期限を、利用者の画面に出す（O-105）。
  - 回数を固定しないので、移行中の参加が長く続きうる。その間、残っている入り口は残り、主張は及ばない（残るリスク）。
- **期限を過ぎ、延長の申請もないとき**（オーナーの判断、2026-11-13。イシュー #60）：
  - 割符は、企業に督促する（O-97 の経路）。利用者が状況を見る画面に、期限を過ぎていて延長の申請がないことを出す（O-105）。
  - 期限切れだけでは、新しい接続、初回紐付けの新しい申請、既存の接続を、どれも自動では止めない。
  - 移行と、旧アカウントの削除や管理は、企業の責任である。
  - 期限切れが続くときの扱い（契約の終わりなど）は、接続の契約で決める。

### 入り口を閉じたことの確かめと報告（O-94）

- 確かめるのは、企業自身である。割符の運営者は、企業ごとに試験用のアカウントを用意せず、企業の旧経路を確かめない（イシュー #60）。送信サービスを通した外からの検査も作らない。
- 企業は、入り口の一覧の項目ごとに、閉じたことを自分で確かめ、結果と確かめた日を、企業向けの報告画面（O-105）で報告する。確かめ方は企業が決める（適合テストキットの旧経路の検査を使える）。
- 企業は、半年ごとの棚卸し（O-96）のほか、入り口の状況が変わるたびに報告する。報告の回数は制限しない（イシュー #60）。
- 報告で変えられるのは、自社の入り口ごとの報告（閉じた・残っている、確かめた日）と、棚卸しの報告だけである。参加の状態（完全・移行中）、期限、割符が確かめた入り口（`verifiedEntries`）は、報告画面からも、企業向けの API からも変えられない（ADR 0010 とテスト6。O-95）。
- 報告は、割符が確かめた結果ではない。記録でも表示でも、「企業が報告した」ことと「割符が確かめた」ことを混ぜない。P0 では、割符が確かめた項目はない。

### 記録の経路と、idp の読み方（O-95）

記録を2つに分ける。

| 項目 | 置き場所 | 変える人と方法 |
|---|---|---|
| `participation`（`full` か `migrating`）、`migrationDeadline`、`verifiedEntries`（空だけ）、報告者の登録（`participationReporters`。O-105）、運営者が一覧2に戻す入り口（`entryOverrides`。O-100） | テナントの登録（配備のときの静的な設定。ADR 0022） | 運営者が、接続の契約の経路で受けた内容を確かめ、設定を直して配備し直す。`participationRevision` を上げる |
| 入り口ごとの報告（閉じた・残っている、企業が確かめた日）、棚卸しの報告の日、報告者、報告の時刻 | DB の `company_api.participation_reports`（テナントの範囲。`withTenant`、RLS の ENABLE と FORCE、列単位の GRANT。追記だけで、行を書き換えない） | 企業の報告者が、企業向けの報告画面（O-105）から |

- 管理 API は作らない（不変条件2）。報告画面は、運営者のためのものではなく、テナントの報告者が自社の情報だけを変える、企業向けの経路である（O-105）。
- 不変条件8の新しい例外は作らない。報告画面は idp の承認用のオリジンに置き、idp は、company-api の内部 API（Unix ドメインソケット。ADR 0026 と同じ向き）で、報告を書かせる。company-api は、`withTenant` の中で行を足す。idp が company-api の表を直接読むことも、company-api から idp へ書くこともしない。
- 利用者の画面（警告文 I）を出すとき、idp は、company-api の内部 API で、そのテナントの最新の報告を読む。表示の判定（期限切れ、半年以内の報告がないこと）は、idp が表示のたびに割符の時計で行う。
- `verifiedEntries` は、空だけを受け付けるままにする。企業の報告を、この項目に入れない。
- 起動のとき、company-api は、テナントごとに `participationRevision` が、監査ログに最後に残した版と違えば、監査の事象 `company_api.participation.changed`（テナント、版、参加の状態、期限）を足す。報告画面からの報告は、そのたびに監査の事象 `company_api.participation.reported`（テナント、報告の版、入り口ごとの結果と日）を足す。
- M9 の実装で、company-api の設定の検査（いまは `full` だけを受け付ける）を広げる。

### 棚卸しの間隔（O-96）

- 企業は、半年に1回、旧経路の棚卸しをして、結果を報告する（イシュー #60）。入り口の一覧にない経路が残っていないことも、棚卸しに含める（RP-15）。
- 完全な参加の企業も行う、と読んだ（閉じた経路が、また開いていないことを確かめるため）。イシュー #60 は、対象を移行中の企業に限っていない。違っていれば直す。
- 棚卸しは、企業向けの報告画面（O-105）で、すべての入り口について報告し直すことで行う。直近の棚卸しの日を、記録に置く（O-95）。半年を過ぎても報告がないときは、企業に知らせて報告を求める（O-97）。利用者の画面には、古い日付がそのまま見えるようにし、「半年以内の報告がありません」と添える（O-105）。接続は止めない（オーナーの判断、2026-11-12）。

### 状況が変わったときの知らせ（O-97）

- 割符から企業へ知らせる（イシュー #60）。知らせる場面は、期限の30日前（仮置き）、期限切れ、棚卸しの報告の期限、参加の状態や表示の変更である。経路は、接続の契約で決めた連絡の経路にする。割符の側の記録は、`participationRevision` と監査ログである。
- 利用者への案内は、企業の責任とする。割符は、利用者に再同意を求めず、ログインを止めない。接続済みの利用者の受信箱に、一斉に書き込むこともしない（イシュー #60）。
- 割符の画面（接続の同意の画面と、別名の一覧の企業ごとの詳細）は、開いたときの、今の状態を出す。これは、いつもの表示で、知らせではない。
- ADR 0010 の「完全な参加から移行中に戻すときは、接続済みの利用者に知らせる」（2026-10-22 のオーナーの判断）と RP-14 は、この方針で、「企業に知らせ、利用者への案内は企業が行う」に変わる。
- 前の版の、`idp.connections` に同意したときの版を覚えて、次のログインで同意を取り直す案は、取り下げた。

### 移行中から完全な参加へ、完全な参加から移行中へ（O-98）

- **完全な参加へ**：企業が、入り口の一覧のすべての項目を閉じたと報告し（O-94）、適合テストキットを自社で通し、接続の契約の確認が済んだら、運営者が `participation` を `full` にして配備し直す。割符は、閉じたことを確かめない。完全な参加は、「企業が、接続要件をすべて守ると報告し、契約で約束している状態」である。
  - 移行中に紐付けた会員は、そのままにする。続く記録（O-92）に、移行中に紐付けたことと方式を残す。完全な参加になったことで、強い証明を満たしたとは見なさない（仕様案 v0.7 の 3.3）。
  - 入り口を廃止することは、接続を続ける条件ではない（O-106）。すべて閉じたと報告しない企業は、移行中の参加のまま、延長を申請して接続を続けられる（O-93）。
- **完全な参加から移行中へ**：認める（ADR 0010）。新しい期限を付け、企業の報告を出し直してもらう。利用者への案内は、企業が行う（O-97）。回数の上限は置かない（オーナーの判断、2026-11-12）。戻すたびに、新しい期限と報告を求める（O-93）。前の版の「1回まで」は、取り下げた。

### 紐付けの前から企業が持っている本物の連絡先（O-99）

- P0 では、推奨（RP-35）のままにし、必須にしない。理由：
  - 割符の側からは確かめられず、監査でしか見られない。
  - 法令で保存が求められるものや、配送に電話番号を使うもの（不変条件11。RP-96 は P1）があり、一律に消すことを求めると、接続できない企業が増える。
- かわりに、接続の前に測ること（ADR 0024 の O-59）に、「持っている連絡先の種類と、消せる時期」を足す。
- 持っている連絡先を本人確認の根拠に使わないこと（RP-02〜05）は、参加の状態で分けて書く。
  - 完全な参加の企業：どの経路でも、根拠に使わない。これまでどおり必須である。
  - 移行中の参加の企業：入り口の一覧（ENT-01〜03）の経路の中に限り、期限まで、その経路が使う値（企業が持つメールや電話番号を含む）を根拠にすることを認める（ADR 0010 の例外。RP-02・RP-03）。経路の外（窓口、高リスクの操作、アカウントの統合、紐付けと sub の扱い）では認めない。別名と email クレームは、この例外に含めない（RP-05）。
  - 移行中は、ENT-01 の再設定の宛先に使う連絡先を消せない。連絡先を消すことの推奨は、その入り口を閉じた後に効く。再設定の宛先の変更は、操作ごとの承認だけを根拠にする（RP-18）。
  - ADR 0020 で紐付けた会員についても、この例外は、企業がその会員の経路を閉じるまで続く（O-104。閉じることは推奨）。期限が来たら、例外は全体で終わる。
- 残るリスク RR-13（企業の側の漏えいそのもの）は、そのまま書く。

### 旧経路の問題が見つかったとき（O-100）

- 見つかるのは、企業の棚卸し、利用者の申告、監査からである。割符は旧経路を確かめないので（O-94）、割符が自分で見つけることは、ふつうない。
- 割符がすること：企業に知らせ（O-97）、報告画面での報告し直しを求める（O-105）。企業が直さないうちは、運営者が、テナントの登録の `entryOverrides`（入り口の ID の一覧。静的な設定）に載せて配備し直す。載せた入り口は、企業の報告によらず一覧2に出す（誤表示を防ぐ。運営者が企業の報告を書き換えることはしない。報告の記録は残る）。
- 企業がすること：経路を閉じるか直すこと、利用者への案内。責任は企業にある（イシュー #60）。
- 旧経路の問題を理由に、自動では止めない（オーナーの判断、2026-11-12）。直さないときや、誤った報告が繰り返されるときの扱いは、接続の契約で決める。緊急停止（ADR 0022）は、割符との接続そのものが危ういとき（資格情報の漏えいなど）の手段として、これまでどおり残す。
- 前の版の「見つかったら、緊急停止にする」は、取り下げた。

### 初回紐付けをした会員の旧経路（O-104）

ADR 0020 のオーナーの決定（仮）は、移行中の企業でも、初回紐付けをした会員の旧経路（旧ログイン、再設定、ゲスト照会）を、紐付けと同時に閉じ、再開しないことを条件にしていた。

オーナーの判断（2026-11-12）：移行中の企業では、強く推奨するにとどめ、求めない（案 B。イシュー #60 と O-106 の、古い仕組みの廃止は必須にせず強く推奨する、という方針に合わせる）。

| 参加の状態 | 初回紐付けをした会員の旧経路 |
|---|---|
| 完全な参加 | 完全な参加は、旧経路をすべて閉じたと企業が報告した状態なので、紐付けた会員の旧経路も閉じている（RP-31・RP-32。O-106） |
| 移行中の参加 | 紐付けと同時に閉じることを強く推奨する。求めない。閉じるのは企業で、割符は閉じられず、確かめもしない（O-94） |

これに伴って、次のようにする。

- 主張（plan 1-2）は、移行中の企業の会員には、紐付けの後も及ばない。会員が割符のパスキーに移った後も、まだ残っている入り口（漏れたパスワード、メールや SMS の再設定など）から、割符を通らずに、同じ会員として入られうる（残るリスク。RR-14 と TH-09 を書き直す）。
- 待機と旧会員の側の知らせ（O-103）は、紐付けの前の乗っ取りへの守りである。紐付けの後に残る旧経路には、効かない。
- 利用者に見えるようにする：初回紐付けの承認の画面（O-86 の手順4）と、警告文 I に、結び付けた後も、まだ残っている入り口から入られうることを書く（DESIGN.md 2章・3章）。
- ADR 0020 のオーナーの決定（仮）のうち、移行中の企業に追加の条件を課す部分を取り下げる。旧パスワード、メール、SMS、旧セッションだけでは紐付けないこと（紐付けの根拠）は、変えない。
- 企業が完全な参加に移るとき（O-98）は、移行中に紐付けた会員の旧経路も閉じたと報告する（O-106）。

### 完全な参加と、企業の責務・割符が主張できる範囲（O-106）

イシュー #60 は、「古い会員情報や仕組みを管理し、減らすことは企業の責務で、古い情報や仕組みを持たないことは企業のベストエフォート」とした。一方、これまでの接続要件は、完全な参加の企業に、旧ログインと、メールや SMS による再設定をすべて閉じること（RP-04、RP-31、RP-32）と、ゲスト照会をなくすこと（RP-40）を求め、移行中の企業には期限までに閉じることを求めていた。

オーナーの判断（2026-11-12）：企業の古い仕組みの管理と削減は、企業の責任である。廃止は必須にせず、強く推奨する。残る経路を、割符が守れるとは主張しない。

これを、次のように書く。

- **接続を続ける条件にしない**：旧経路（入り口の一覧の ENT-01〜03）が残っていても、移行中の参加として接続を続けられる。期限は、残りの作業と見込みを報告すれば、必要な期間だけ延ばせる（O-93）。
- **完全な参加の意味**：完全な参加は、旧経路をすべて閉じたと企業が報告し、適合テストキットを自社で通し、接続の契約で確かめた状態である（O-98）。RP-04、RP-31、RP-32、RP-40 は、企業に求めること（強く推奨）と、完全な参加と呼ぶ条件（必須）を分けて書く。企業に完全な参加を強いることはしない。
- **主張の範囲**：主張（plan 1-2、01 の 3章。「接続要件を守る企業」）は、これまでどおり、完全な参加の企業に限る。移行中の企業と、その企業に残っている経路には及ばない。CLAUDE.md の「主張の書き方」は変えない。
- **主張の条件**（レビュー、2026-11-13）：完全な参加は、企業が旧経路をすべて閉じたと報告した状態である。割符は、報告が正しいかを確かめない。主張が成り立つのは、企業が報告どおりに旧経路を閉じ、接続要件を守っている場合だけである。報告が誤っていて旧経路が残っていれば、その経路から、漏れた連絡先や属性で本人確認を突破されうる。企業の報告だけで、すべての経路の安全性が保証されたとは書かない（plan 1-2、01 の 3章、RR-22）。
- **変えないもの**：入り口の一覧にない経路（窓口で氏名や生年月日で本人確認すること、高リスクの操作を操作ごとの承認以外で通すこと、別名でアカウントを探すこと、sub の書き換えなど）は、移行中でも残してはならない（RP-05、RP-07、RP-10、RP-13、RP-27、RP-33。ADR 0010）。「廃止を必須にしない」のは、入り口の一覧の経路だけと読んだ。違っていれば直す。
- 割符のコードは、どの企業についても、連絡先や属性を根拠にしない（不変条件は変えない）。

### 企業の自己申告の表示と、企業向けの報告画面（O-105）

- オーナーの判断（2026-11-12。イシュー #60）：企業が「閉じた」と報告した入り口と、「まだ残っている」と報告した入り口を分けて出し、割符は直接確かめていないことを明記する。企業の状況が変わるたびに、企業が報告して表示を更新する。変更の回数は制限しない。
- 守ること：企業の自己申告を、割符が確かめたものとして出さない。ADR 0010 の表示の規則のうち、✓や緑の色などの「済み」を示す印を出さないこと、「安全」「対策済み」「認定」と書かないこと、企業が書いた説明を出さないことは、変えない。
- 形：2つの一覧（ADR 0010 の一覧1と一覧2）を保つ。一覧1は、企業が閉じたと報告した入り口。一覧2は、それ以外のすべて（まだ残っていると報告した入り口と、報告のない入り口）。既定は一覧2にする。項目ごとに「企業が確かめた日」、直近の報告の日、移行中の期限（延長したときは、延長した後の期限）を出す。半年以内の報告がないとき（O-96）と、期限を過ぎて延長の申請がないとき（O-93）は、そのことを出す。
- **未決**：画面の文言の細部。DESIGN.md 3章の警告文 I には、案の文言を入れてある。M9 の実装で表示ができるまでは、移行中の企業を接続しない（ADR 0010 のまま）。

**企業向けの報告画面**（更新の方法。オーナーの判断、2026-11-13。イシュー #60）

企業が、自社の旧経路の状況を報告すると、利用者向けの表示が更新される、シンプルな企業向けの画面を先に作る。企業のシステムから呼ぶ API は、必要になったら後で検討する。

- **置き場所**：idp の承認用のオリジン（厳しい CSP と Trusted Types。ADR 0023）の `/company/participation`。企業の側に実装は要らない。
- **誰が使えるか**：報告者は、その企業の担当者が持つ割符のアカウントである。担当者は、ふだんの割符の利用者と同じく、UV 付きのパスキーでログインする（不変条件1(b)）。運営者は、接続の契約の経路で企業から受けた報告者の指名を、テナントの登録の `participationReporters`（そのテナントでの担当者の `sub` の一覧）に写して、配備し直す。報告者を足す・外すのも、同じ手順にする。メールや氏名で報告者を探したり指名したりはしない（不変条件1(d)）。
- **自社の情報だけ**：画面を開いた利用者の、そのテナントでの `sub` が、そのテナントの `participationReporters` にあるときだけ、そのテナントの報告を出し、受け付ける。別のテナントの報告者は、そのテナントの報告を読めも書けもしない（テスト6）。報告者でない利用者には、画面があることも、どのテナントがあるかも区別できない応答を返す（`404`）。
- **変えられるもの**：入り口ごと（ENT-01〜03）に、`closed`（閉じた）か `remaining`（まだ残っている）と、企業が確かめた日。棚卸しとして全項目を報告し直す操作。自由文、企業名、説明、リンクは受け付けない。参加の状態、期限、`verifiedEntries`、報告者の一覧は変えられない。
- **誤表示を防ぐ**：
  - 送る前に、利用者に出る警告文 I を、そのままの形で見せ（プレビュー）、確かめてから送る。
  - 送るたびに、新しい UV 付きのパスキーで確かめる（step-up）。
  - 確かめた日は、今日以前で、接続の日より後のものだけを受け付ける。`closed` には確かめた日を必須にする。
  - 開いたときの報告の版を添えて送り、その間に別の報告があれば `409` で断る（後から送った人が、前の報告を知らずに上書きしない）。
  - 報告を受けたら、そのテナントの受け口に SET（`urn:warifu:secevent:participation-reported`。中身は報告の版だけ）を送る。企業が知らない報告（担当者のアカウントの乗っ取りなど）に気付けるようにする。
  - 報告は追記だけにし、前の報告は消さない。誤りは、報告し直して直す。
  - レート制限：報告者ごとに1時間に20回、テナントごとに1日に100回（仮置き）。
- **記録**：報告ごとに、テナント、報告の版、入り口ごとの結果と確かめた日、報告者（そのテナントでの `sub`）、割符の時計での報告の時刻を、`company_api.participation_reports` に残す。監査ログには、報告の版と結果を残す（O-95、O-102）。報告者の `sub` は、そのテナントの中だけの値で、企業をまたいでは使えない（不変条件5）。
- 報告者のアカウントの回復の後7日（ADR 0027 の O-80）の間は、報告を受け付けない。
- 表示は、報告を受けた後の、次の表示から変わる（運営者の転記や配備し直しを待たない）。割符は、報告の内容を確かめない。
- **参加の状態と表示を切り離す**（レビュー、2026-11-13）：参加の状態（静的な設定）は、配備し直すまで変わらない。完全な参加の企業が、入り口を `remaining` と報告し直したとき、運営者が `entryOverrides` に載せたとき、報告が半年を過ぎたときに、配備し直すまで利用者に何も出ないと、残っている経路を知った後も利用者に伝わらない。そこで、警告文 I は、参加の状態によらず、次のどれかに当たる企業について出す：移行中の参加である、企業の最新の報告で閉じたと報告していない入り口がある（`remaining` と、報告のない入り口）、運営者が `entryOverrides` に載せた入り口がある、直近の報告から半年を過ぎている。完全な参加の企業でも、これに当たれば出す。どれにも当たらない完全な参加の企業には出さない（ADR 0028 の O-105）。
  - 完全な参加の企業に出すときの見出しは、移行中の企業とは別の文にする（案：「〈企業名〉の入り口の状況（企業の報告）」。文言の細部は未決）。
  - 完全な参加の企業が入り口を `remaining` と報告したときは、完全な参加の条件（O-106）を満たしていない。割符は企業に知らせ（O-97）、企業が閉じ直すか、接続の契約に沿って運営者が移行中に戻す。その間も、表示は報告どおりに出す。主張は及ばない。接続は自動では止めない。

### レート制限（O-101）

値はどれも、根拠のない仮置き。

| 企業向けの初回紐付けのルート | テナント | 1分に300（`apiByTenant` とは別に） |

### 監査の事象（O-102）

## 企業にとっての導入の壁（まとめ）

この ADR の決め方で、何が下がり、何が残るかを書く。数字の基準は、最初の企業で測ってから決める（ADR 0024）。

- 下がるもの：
  - 入り口を一度に全部閉じなくても、期限（原則6か月）まで残して参加できる。残りの作業と見込みを報告すれば、必要な期間だけ延長できる（O-93）。廃止は必須にせず、強く推奨する（O-106）。
  - 適格な旧パスキーを持つ会員は、自分で割符へ移れる（O-86）。企業の側の仕事は、移行プロファイル、4つのルートと PAR、SET の受け口と、旧会員の側に知らせを出すこと（必須。O-103）である。知らせの届け直しと、鍵の入れ替えをまたいだ ID の保持は、割符の側で持つ（O-103、O-87）。
  - 既存の連絡先を消すことは必須にしない（O-99）。
  - 旧経路の報告は、割符の企業向けの報告画面からできる。企業の側にシステムの実装は要らない（O-105）。
  - 期限切れだけでは、接続も新しい申請も止めない（O-93）。
  - 割符の運営者による確かめがない。企業は、試験用のアカウントを置かず、旧経路を自分で確かめて報告する（O-94）。
  - 参加の状態が変わっても、割符は利用者に再同意を求めない（O-97）。旧経路の問題で、自動では止めない（O-100）。
  - 移行中の企業では、初回紐付けをした会員ごとに旧経路を閉じる仕組みを、求めない（強く推奨。O-104）。
- 残るもの、増えるもの：
  - 適格な旧資格情報のない会員は、P0 では自分で移れない。救済の経路は作らない（ADR 0020）。旧会員の残高や契約の引き継ぎ方は、企業の側で別に要る。JPKI での道は P1 で、JPKI だけでは旧会員との対応を証明しない。
  - 半年に1回の棚卸しと報告（O-96）。利用者への案内は、企業の責任になる（O-97）。
  - 移行中の企業には、警告文 I が出る。企業に不利な表示の契約と法務の確認は、イシュー #15 で行う。
  - 旧会員の側に知らせを出す実装が要る（O-103）。
  - 完全な参加と名乗るには、移行中に紐付けた会員を含めて、旧経路をすべて閉じたと報告する（O-106）。

## レビューによる変更（2026-11-11）

`5c0e557` へのレビューの5点を受けて直した。

1. **待機の始まりの知らせを、障害があっても残す**：待機を始めてから受信箱に項目を出す順番だと、間の障害で、本人が知らせを見ないまま待機が進みうる。受信箱の項目を先に記録し、項目の記録がない申請は待機に入れない順番にした（O-103）。
2. **鍵を入れ替えたときの再送**：移行専用 ID を導いた鍵の版を行に置き、いつもその版で導く。古い版は P0 では消さず、起動のときに版があることを確かめる（O-87）。
3. **旧会員の側への知らせ**：仕様案 v0.7 の 3.4 の6にあったのに、この ADR から落ちていた。割符の送信待ちから SET で届け、企業が旧会員の側に知らせを出す。待機の起点は、その SET が届いた時刻にした（O-103）。その後、2026-11-12 に、必須にするか推奨にするかを未決にし、2つの案を並べた（O-103）。
4. **同じ旧会員の再確認**：仕様案 v0.7 の「試行限定の会員参照」が落ちていた。2つの証跡の会員参照と認証世代が同じことを、割符の側でも確かめる（O-88）。
5. **移行中の連絡先の例外**：O-99 に「どの経路でも根拠に使わないことは必須」と書いていたが、移行中の企業には、入り口の一覧の経路の中だけの例外がある（ADR 0010）。参加の状態で分けて書き直した。

1 と 2 は、企業の側に仕組みを足さず、割符の側の順番、送信待ち、鍵の版で受ける。3 で企業に足すのは、SET を受けて旧会員の側に知らせを出すことだけである（必須にするかは O-103 で決める）。

窓口の `desk_id` と `desk_lookup`（ADR 0026 の O-64）も、鍵の版を持たない1つの鍵で導いている。保留した取消の SET は消さないので、同じ問題がありうる。この ADR では直さず、M9 の実装の PR で、同じ形を当てるかを決める。

## 採らなかった案

- **初回紐付けの承認を、利用者向けの専用ルート（`POST /v1/me/initial-link/approve`）と企業向けの最終承認のルートで受ける**（仕様案 v0.7 の 3.4.1）：窓口で PAR と RAR に置き換えたのと同じ理由で採らない（ADR 0026 の O-60）。承認の画面、失敗の数え方、承認と拒否の直列化を、窓口と同じ部品で作れる。
- **移行証跡を、署名のない JSON の本文にする**：認証済みの経路なので受け取るときの確かさは同じだが、争いになったときに、企業の原文と割符が受け取ったものを突き合わせられない。署名した JWS と、その MAC を残す形にした（O-88）。
- **移行証跡に、クライアントの認証とは別の鍵を求める**：鍵の管理が増えて、企業の負担が上がる。`typ` と `aud` で用途を分ければ、取り違えは断れる。
- **待機を始めてから、company-api が idp に受信箱の項目を書かせる**（送信待ちで送り直す）：company-api から idp へ書き込む経路が要る（窓口では作らなかった。ADR 0026 の O-63）。項目を先に記録してから待機に入る順番にすれば、送り直しの仕組みなしで、「項目の記録がないのに待機が進む」ことをなくせる（O-103）。
- **旧会員の側に知らせたことを、企業に新しいルートで報告させる**：企業の側の仕組みが増える。
- **移行中の企業にも、初回紐付けをした会員の旧経路を、紐付けと同時に閉じることを求める**（O-104 の案 A。ADR 0020 のオーナーの決定（仮））：オーナーの判断（2026-11-12）で採らない。移行中の企業では推奨にとどめる。
- **鍵を入れ替えたら、開いている申請の移行専用 ID を新しい版で導き直す**：企業が持っている ID と合わなくなり、再送と取消の照合ができなくなる。行に置いた版で導き続ける（O-87）。
- **期限を過ぎたら、テナントを止める**：接続済みの利用者がログインできなくなる。期限切れでは止めない（O-93）。
- **旧会員の側の知らせを推奨にとどめ、待機の起点を本人の承認の時刻にする**（O-103 の案 B）：オーナーの判断（2026-11-12）で採らない。旧パスキーを盗んだ人による紐付けに、元の持ち主が気付けるかが、企業しだいになる。
- **延長の回数と1回の長さに上限を置く**（O-93 の前の版の案）：オーナーの判断（2026-11-12）で採らない。企業が残りの作業と見込みを報告すれば、必要な期間だけ延ばせる。
- **完全な参加でなくても、旧経路の廃止を期限付きで必須にする**（O-106 の前の記述）と、**主張を割符自身の振る舞いまでに狭める**（O-106 の案3）：オーナーの判断で、廃止は必須にせず強く推奨し、主張は完全な参加の企業に限ったまま、CLAUDE.md の主張の書き方は変えない形にした。
- **割符の運営者が、試験用のアカウントで企業の旧経路を確かめる**（前の版の O-94）と、**送信サービスを通した自動の外からの検査**：イシュー #60 の方針で取り下げた。確かめるのは企業自身にする。
- **参加の状態が変わったら、次のログインで利用者に同意を取り直す**（前の版の O-97）と、**接続済みの利用者全員の受信箱に書き込む**：イシュー #60 の方針で取り下げた。割符は企業に知らせ、利用者への案内は企業が行う。
- **旧経路の問題が見つかったら、緊急停止にする**（前の版の O-100）：イシュー #60 の方針で取り下げた。自動では止めない（O-100）。
- **企業の報告を、企業のサーバーの資格情報（テナントの JWT）で受ける API を先に作る**：企業のシステムに実装が要る。オーナーの判断で、シンプルな報告画面を先に作り、API 連携は後で考える（O-105）。参加の状態と期限は、どちらの経路からも変えない。
- **報告画面を、割符の運営者が企業に代わって使う管理画面にする**：管理用の経路になり、不変条件2の方針と合わない。報告者は、テナントが指名した担当者だけにする（O-105）。
- **報告者を、メールアドレスや氏名で指名する**：不変条件1(d)。そのテナントでの `sub` で指名する（O-105）。
- **期限切れで、新しい接続や移行の申請を断る**（O-93 の前の案）：オーナーの判断（2026-11-13）で採らない。督促と表示にとどめる。
- **延長を、運営者が見込みの妥当さを審査して認める期間だけにする、または延長の前に旧経路を検査する**：オーナーの判断（2026-11-14）で採らない。運営者は必要な事項がそろっていることだけを確かめ、原則として希望どおりの期限で延長する。旧経路は確かめない（O-94）。
- **延長の申請を受ける画面や API を作る**：オーナーの判断（2026-11-14）の要件ではない。接続の契約の連絡の経路で受け、静的な設定を直す。
- **紐付けの前からの連絡先を消すことを、完全な参加の条件にする**（O-99 の対案）：原則2には近いが、割符から確かめられず、接続できない企業が増える。オーナーの判断で、こちらにすることもできる。

## 残るリスク

- 旧資格情報そのものの盗難、企業の虚偽の証跡、同期パスキーの提供者の側の回復（ADR 0020）。
- 移行中の企業に残っている入り口（RR-14）。その経路による被害を、割符は防げない（イシュー #60）。
- 企業の報告は、企業が自分で確かめた結果で、割符は確かめていない。報告が誤っていても、割符には分からない。完全な参加かどうかも、企業の報告と契約に基づく（O-94、O-98）。
- 利用者への案内を企業が行わなければ、接続済みの利用者は、割符の画面を開くまで、参加の状態が変わったことを知らない（O-97）。
- 企業が旧会員の側に知らせを実際に出したかどうかを、割符は確かめられない（O-103）。出さない企業では、旧パスキーを盗まれた会員が、待機中に気付けない。出さないことは接続要件の違反で、監査で扱う。
- 会員参照と認証世代の一致は、企業が出した値どうしの比較である。企業が偽の値を出すことは防げない（O-88）。
- 延長の回数を固定せず、必要な事項がそろえば原則として希望どおりに延長するので、移行中の参加が長く続きうる。その間、入り口は残り、主張は及ばない（O-93、O-106）。期限を過ぎても、接続済みの利用者の接続は続く。
- 完全な参加の企業が旧経路をすべて閉じていることも、企業の報告と契約に基づく。割符は確かめていない。報告が誤っていれば、残った経路から、漏れた連絡先や属性で本人確認を突破されうる（O-94、O-106。RR-22）。
- 報告者のアカウントが乗っ取られると、偽の報告で表示を変えられうる。報告ごとの step-up、企業への SET、追記だけの記録で、気付いて直せるようにする（O-105）。
- 期限を過ぎても、接続も新しい申請も止めないので、旧経路が残ったまま移行中が続きうる（O-93）。
- 移行中の企業で初回紐付けをした会員は、紐付けの後も、まだ残っている入り口から、割符を通らずに同じ会員として入られうる（O-104。閉じることは推奨）。旧経路が残っているか、開け直されたかを、割符は知らない（O-100）。
