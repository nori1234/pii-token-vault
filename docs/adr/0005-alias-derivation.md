# ADR 0005：別名は保存せず、鍵つき HMAC で導く

- 状態：採用
- 日付：2026-10-17

## 状況

別名（企業ごとのメールアドレス）について、計画には次の3つの要件があった。

- DB に平文で置かない（不変条件4）
- 復号できるのは relay だけ（不変条件3）
- idp は、ログインのたびに ID トークンの email クレームに別名を載せ、PWA は別名の一覧を表示し、company-api は再発行した別名を企業に返す

別名を乱数で作って暗号化して保存すると、idp と company-api は復号できないので、別名を取り出せない。平文で保存すれば、不変条件4に反する。

## 決定

- 別名のローカル部は、鍵サービスの `derive_alias(tenant_id, user_id, generation)` で導く。外に出せない HMAC 鍵（HMAC-SHA-256）による決定的な導出で、出力を base32 にして、十分な長さ（80ビット以上）に切る。鍵を持たない者には、乱数と区別できない。
- DB に置くのは、`(tenant_id, user_id, generation)` と、受信時に照合するための HMAC（照合用の鍵は、導出用とは別にする）だけ。
- 再発行では `generation` を1つ上げる。古い世代は廃番として残し、照合用の HMAC に一意制約をかけて、二度と割り当てない。
- `derive_alias` を呼べるのは idp と company-api だけにする（鍵サービスの ACL で制限する）。relay は、受信した別名を照合用の HMAC で引き、利用者 ID とテナント ID を得る（不変条件8の SECURITY DEFINER 関数）。

## 理由

- 復号の能力を relay 以外に広げずに、idp と company-api が別名を必要なときに得られる。
- DB だけが漏れた場合（鍵サービスや KMS の鍵が漏れていない場合）は、DB から別名も本物の連絡先も平文では出てこない。導出鍵の漏えいは下の「結果と注意」と RR-11、relay の侵害は TH-62 を参照。

## 結果と注意

- 導出用の鍵が漏れると、鍵と ID の組から全員の別名を計算できる。鍵は KMS（本番）か鍵サービス（ローカル）から外に出さない。
- 導出用の鍵を入れ替えると、全員の別名が変わる。入れ替えの手順（旧鍵での照合を一定期間残す、企業に SET で知らせる）は、P1 で決める。
