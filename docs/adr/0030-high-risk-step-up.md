# ADR 0030：高リスクの操作の step-up（出金先の変更）

- 状態：提案（オーナーの確認待ち）。実装は、確認の後に始める
- 日付：2026-11-15

## 状況

plan 3-1 と spec 02 の RP-10〜RP-13 は、高リスクの操作（配送先・返金先・支払い手段の変更、解約、高額の取引、住所の法定開示への同意）を、割符が発行した操作ごとの短命な承認（step-up の結果）だけを根拠にすることを求めている。M7 では窓口の型 `warifu_desk` だけを作り、高リスクの操作の `authorization_details` の型は未定のままだった（spec 02 の2章）。

M9 の demo-rp の A社（デモ証券）は、出金先の変更を、端末での step-up で守る例として見せる（plan 10章）。そのために、高リスクの操作の承認の型が要る。

オーナーの方針（2026-11-15）：通常のログインや、窓口用の承認を流用しない。「この企業の、この変更内容」に結び付いた承認にする。内容の差し替え、期限切れ、使い回しを拒否できる設計を確かめてから実装する。

## 決定（案）

### 型と操作（O-112）

- RAR の新しい型 `warifu_operation` を足す。P0 の操作は `payout_destination.change`（出金先の変更）の1つだけにする。ほかの高リスクの操作（配送先、支払い手段、解約、高額の取引）は、同じ型に操作を足す形で、必要になったときに決める。「高額」の基準は、引き続き未定。
- 企業は、PAR で次の1件だけを送る。

  ```json
  [
    {
      "type": "warifu_operation",
      "actions": ["payout_destination.change"],
      "identifier": "<企業の申請ID>",
      "subject": "<sub>",
      "content": { "bank_code": "0001", "branch_code": "123", "account_last4": "4567" }
    }
  ]
  ```

  - `identifier`：企業が変更の申請ごとに作る乱数（128ビット以上）。企業は、申請ID と変更の内容の全体（口座番号の全桁など）を、自社のサーバーに置く。割符には渡さない。
  - `content`：利用者に見せて確かめてもらう内容。操作ごとに、割符が決めた項目と形だけを受け付ける。出金先の変更では、金融機関コード（数字4桁）、支店コード（数字3桁）、口座番号の末尾4桁（数字4桁）だけ。企業の自由文、口座名義、口座番号の全桁は受け付けない（数字だけにして、承認の画面に企業の文言を出させない。DESIGN.md 原則2）。
- 型は、クライアントごとに許す（登録簿の `operationActions`。既定は空）。許していないクライアントの PAR は断る。

### 承認の画面（O-113）

- 承認用のオリジンの `/operation` に引き継ぐ（窓口と同じ形。ADR 0026 の O-61）。引き継ぎは、プロセスのメモリに5分。
- 画面は、DESIGN.md 2章の「端末での承認（step-up）」の行に従う：登録簿の企業名、操作の種類（固定のラベル「出金先の変更」）、内容（割符の固定の書式：「金融機関コード 0001、支店コード 123、口座番号の末尾 4567」）、要求の時刻と端末、警告文 A-2、「承認する」「承認しない」（同じ大きさ。どれも既定にしない）。
- 承認は、内容に結び付いた UV 付きのパスキーで行う。チャレンジの材料に、引き継ぎの uid、テナント、クライアント、操作、申請ID、sub、`content` の各項目、時刻、端末を、長さ付きでつなぐ（ADR 0026 と同じ考え方）。画面に出した内容と違う内容には、同じアサーションが使えない。
- アサーションの利用者の sub が申請の `subject` と一致し、その企業に接続済みで、回復の後7日の制限の中でないときだけ承認する（ADR 0027 の O-80）。失敗は、引き継ぎごとに3回まで。

### 承認の JWT（O-114）

- 鍵は、鍵サービスの新しい署名の鍵 `operation_approval`（ES256。idp だけが署名と公開鍵の取得をできる）。窓口の `op_approval` と、初回紐付けの `initial_link` とは分ける。公開鍵は `/operation-approval/jwks`。
- `typ` は `warifu-operation-approval+jwt`。クレームは `iss`、`aud`（`client_id`）、`sub`、`purpose`（`operation`）、`action`、`request_id`、`content`（PAR と同じ項目と値）、`acr`、`auth_time`、`iat`、`exp`（5分）、`jti`。
- 企業には、トークンの応答の `authorization_details[0].approval` で渡す（ADR 0026 の O-62 と同じ）。

### 差し替え、期限切れ、使い回しを断る（O-115）

| 攻撃 | 断るところ |
|---|---|
| 承認の後に、変更の内容を差し替える | 企業は、申請ID で自社に置いた内容を引き、JWT の `content` と照らして、同じときだけ変更する（rp-kit の `verifyOperationApproval` が、期待する内容を受け取って比べる） |
| 承認の画面と違う内容に、同じアサーションを使う | チャレンジが内容に結び付いている（O-113） |
| 期限の切れた承認を使う | JWT の `exp`（5分）。引き継ぎも5分、`request_uri` は60秒 |
| 同じ承認を2回使う | rp-kit が `jti` を一度だけにする。企業は、申請ID ごとに変更を一度だけ実行する（申請ID を使い済みにする） |
| 窓口の承認、初回紐付けの承認、通常のログインを流用する | 鍵、`typ`、`purpose` が違う。rp-kit は、鍵、`typ`、`purpose`、`action` をすべて確かめる |
| 別の企業の承認を使う | `aud`（`client_id`）と、企業ごとに違う `sub` |
| 別の利用者の承認を使う | `sub` が、企業のセッションの利用者と同じであること |

- 割符は、申請ID と内容を、DB にもログにも置かない（メモリの引き継ぎ、Grant、認可コードの中だけ）。監査には、テナントと操作の種類だけを残す（`idp.operation.approved`、`idp.operation.declined`）。

### rp-kit と demo-rp（O-116）

- rp-kit に `pushOperation`（PAR）と `verifyOperationApproval`（期待する申請ID と内容を受け取る）を足す。
- demo-rp の A社では、出金先の変更を、申請ID と内容を自社のサーバーに置いて PAR を送り、承認の JWT を確かめてから、置いた内容と照らして変更する。承認がなければ変更の API は動かない（RP-10）。

## 理由

- 窓口の承認を流用しないため、型、鍵、`typ`、`purpose` を分ける（RP-21）。初回紐付けで鍵を分けたのと同じ考え方。
- 内容の全体（口座番号の全桁など）は割符に渡さず、確かめてもらうのに足りる一部と、企業の申請ID だけを渡す。割符が企業の顧客の金融情報を持たずに済み、企業は自社に置いた全体を、申請ID と見せた内容で照らせる。
- 数字だけの決まった項目にすることで、承認の画面に企業の文言を出さない（フィッシングの文言を割符の画面に載せさせない）。

## 残るリスク

- 末尾4桁と金融機関・支店のコードが同じ別の口座への差し替えは、画面の表示だけでは利用者に見分けられない。企業が、申請ID で自社に置いた全体と照らすことで防ぐ（企業の責任）。
- 利用者が、だまされて自分の端末で承認すること（リアルタイムの中継）は、警告文 A-2 で減らすだけで、防ぎきれない（plan 1-2）。

## オーナーに確かめたいこと

1. 型を `warifu_operation` の1つにして、P0 では `payout_destination.change` だけを作ることでよいか。
2. 画面に出す内容を、数字だけの決まった項目（金融機関コード、支店コード、口座番号の末尾4桁）に限ることでよいか。名義や金融機関の名前は出さない。
3. 鍵を、窓口と初回紐付けとは別の `operation_approval` にすることでよいか。
