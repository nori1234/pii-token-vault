# Codex のクラウド環境

この手順は Codex 用。規則の本体は [CLAUDE.md](../CLAUDE.md) を全部読む。
セットアップは、メンテナーが内容を確認したブランチでだけ行う。外部から届いた PR のブランチでは実行しない。

## 環境の設定

Codex のリポジトリ用の環境設定で、次を指定する。

| 項目 | 設定 |
|---|---|
| Node | 22 系、22.18.0 以降 |
| OS | `apt-get` が使え、設定済みの配布元から `postgresql-16` を入れられる環境（例：Ubuntu 24.04） |
| 権限 | root、またはパスワードなしの sudo |
| セットアップスクリプト | リポジトリのルートで `bash scripts/setup-codex.sh` |
| 作業段階のインターネット接続 | 無効 |
| シークレット | このテスト環境のためには登録しない |
| 環境変数 | 通常は不要。配置済みの PostgreSQL 16 を使う場合だけ `PG_BIN` を bin ディレクトリの絶対パスにする |

セットアップ段階には npm レジストリ、Playwright のブラウザ配布元、OS のパッケージ配布元への接続が必要になる。環境から渡されたプロキシと CA の設定を使い、TLS の検証を無効にしない。ネットワーク設定そのものは、このスクリプトでは変更しない。

Node の版、権限、`PG_BIN` は依存の変更前に確認する。Node の別のメジャー版を自動で入れ替えたり、PostgreSQL の配布元を追加したりはしない。

## セットアップで行うこと

[scripts/setup-codex.sh](../scripts/setup-codex.sh) は、次を順に行う。

1. `npm ci --ignore-scripts --no-audit --no-fund` で lockfile の依存を入れる。
2. PostgreSQL 16 がなければ、システムのクラスタ作成とサービスの起動を抑止してバイナリを入れる。
3. `npx --no playwright install --with-deps chromium` で、ローカルの Playwright に対応する Chromium と OS の依存を入れる。

`policy-rc.d` とクラスタ作成を抑止する設定は、一時的なものにする。既存の `policy-rc.d` があれば保存し、成功時も失敗時も元に戻す。HUP・INT・TERM でも後始末する。SIGKILL や環境の強制終了では後始末できないため、途中で強制終了した環境は作り直す。初回と再実行では、同じユーザーを使う。ブラウザのキャッシュは、そのユーザーのものを使う。

セットアップは DB を起動しない。テストは既存の [scripts/pg-up.ts](../scripts/pg-up.ts) を使い、一時ディレクトリのクラスタを Unix ソケットで起動して終了時に消す。

## 初回の動作確認

セットアップログに `セットアップ完了` と PostgreSQL 16 の版が出たら、作業段階で次を実行する。

```sh
npm run lint
npm run typecheck
npm test
npm run e2e
```

4つすべての成功を確認してから、その環境をレビュー後の動作確認や実装に使う。依存だけを更新する場合も、セットアップ段階で同じスクリプトを再実行し、4つの確認をやり直す。セットアップの成功だけでは、テストの成功とはしない。

## 検証状況

2026-10-23 に、Ubuntu 24.04 と Node 22 の Docker コンテナ（root）で、このスクリプトを実行した。PostgreSQL 16 と Chromium の導入、lint、typecheck、test、e2e が成功した。既存の `policy-rc.d` の内容とモードが戻ること、システムのクラスタが作られないこと、一時的なクラスタ抑止設定が残らないことも確認した。

root と sudo の経路について、事前検査8件と、成功・apt の失敗・Chromium の失敗・TERM を含む後始末40件の検証も行った。この検証では外部コマンドを置き換えており、一般ユーザーと sudo による実インストールの確認とはしない。

Codex の環境設定画面への登録と、その環境からの初回起動は未確認。登録後は、上の4つのコマンドを通し、結果を PR に残す。
